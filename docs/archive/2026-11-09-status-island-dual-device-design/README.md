## 1. 本轮讨论范围与结论

本轮围绕一个实际部署变化展开：成熟脚本项目（首先是售后系统）计划从黑苹果迁移到一台 24 小时运行、无常驻显示器的 Mac mini；Codex 仍只在黑苹果使用。

核心方向：

**Mac mini 是售后自动化生产执行端；黑苹果是开发、人工操作与多设备管理端。两台机器各自保留独立的 Status Island 和本地浏览器能力，通过私人网络交换任务请求、运行状态和必要数据。**

这不是把所有功能集中到一台电脑，也不是建设复杂的多节点集群。

### 1.1 双设备角色

**黑苹果（主端 / 人工操作端）**
- Codex / CodexPro 只在黑苹果使用；Mac mini 不安装或运行 Codex。
- 保留 Codex Monitor 原有本地用量统计、5 小时 / 周限额及倒计时。
- 保留完整 Status Island 主界面，能够查看本机状态和 Mac mini 状态。
- 保留现有本地 Chrome 控制入口，用于人工打开店铺、查看工单和处理异常。
- 店铺新增、登录、重新登录和 Session 保存优先在黑苹果完成。
- iPhone 继续通过向日葵等远程软件连接黑苹果；不单独开发手机端。

**Mac mini（子端 / 生产执行端）**
- 独立运行售后业务服务、自动化调度和自动化 Chrome。
- 保留完整 Status Island 桌面界面，便于用户通过向日葵、UU 等远程桌面软件查看实际运行现场。
- 已接收的任务不依赖黑苹果、Codex 或黑苹果上的 Status Island 持续在线。
- 生产服务和任务应在黑苹果断网、关机或 Codex 退出时继续独立运行。

两台机器不是“一个 UI 关闭就会停止另一个节点”的主从进程关系。主端 / 子端是使用和职责定位，不代表运行依赖。

### 1.2 每台机器有自己的本地队列

2026-11-06 讨论中的“唯一权威队列”仍适用于**同一台物理设备上的共享桌面资源**，但不应再解释为跨两台电脑的单一全局队列。

当前双设备方向：
- 黑苹果维护自己的本地任务队列和桌面资源。
- Mac mini 维护自己的本地任务队列和桌面资源。
- 两边可互相发送任务请求并同步状态；消息传递不是任务持续运行的前提。
- 两台机器可以同时工作，因为它们拥有不同的物理桌面。
- 只有真实共享的业务平台、账号或其他资源冲突，才需要跨设备协调；不建立通用多资源锁矩阵。
- 当前不建设多节点集群、分布式调度中心或云端业务中台。

Mac mini 的售后自动化仍由 Mac mini 本地调度队列管理。黑苹果本地人工浏览器操作不应被误当成 Mac mini 本地队列中的普通自动化任务。

### 1.3 网络方向

- 两台机器不在同一个局域网。
- 初步计划使用 Tailscale 建立私人网络连接；尚未安装或配置，仍是待实施的网络方案。
- 当前不购买固定公网 IP、VPS 或独立公网服务器。
- 任务请求、接收确认、状态和少量结果数据允许数分钟延迟；不以低延迟为目标。
- 需要可靠的接收确认、重复请求识别和断网后补传语义，不能仅凭发送端显示“已发送”就认为对端已接收。
- 断网时，已由目标机器接收的任务继续运行；尚未确认送达的请求保留在发送端，恢复后查询或安全重发，避免重复执行。
- Mac mini 的完整桌面仍可通过用户已有的远程桌面软件直接查看；本轮不讨论具体远程控制软件的安装和配置。

## 2. 售后系统的部署与数据归属

### 2.1 一套售后业务服务、一个业务数据源

**用户确认的方向：售后业务服务整体运行在 Mac mini，黑苹果访问同一套售后页面和业务数据。**

- Mac mini 运行售后 server、业务数据文件、自动化调度和自动化 Chrome。
- 黑苹果通过私人网络访问 Mac mini 提供的售后 Web 页面 / API。
- 黑苹果页面显示的工单、推理结果、扫描进度、历史归档、账号配置和状态都来自 Mac mini 的同一业务服务。
- 黑苹果页面上的删除、手动归档、标记等待等纯业务数据操作，直接修改 Mac mini 的数据源；不需要同步第二份数据库。
- Mac mini 自动操作后的结果和异常信息，通过现有页面数据 / SSE 等机制投射到黑苹果页面。
- 不在黑苹果再运行一套完整售后服务或第二份权威业务数据库。

### 2.2 两套浏览器执行环境

业务服务集中，不代表浏览器操作也集中。

**Mac mini Chrome：自动化**
- 定时售后扫描。
- 店铺批次处理。
- 单店铺处理工单。
- 自动采集、推理、已授权的自动处理。
- 重新采集、人工发起但由售后系统执行的业务操作。
- 其他明确由售后自动化服务执行的浏览器任务。

**黑苹果 Chrome：人工操作**
- 人工打开店铺后台。
- 人工查看指定工单。
- 人工处理售后异常工单。
- 人工登录、重新登录和验证登录状态。
- 其他需要用户直接进入平台操作的事项。

保留黑苹果现有可用的本地浏览器控制入口。未来主要改变的是**浏览器操作发往哪台机器执行**，而不是重写已经成熟的账号安全流程或工单业务流程。

黑苹果上托管的售后页面不能误把本地人工浏览器操作转发给 Mac mini Chrome；需要保留一个明确的本地浏览器执行入口 / 桥接能力。具体接口和调用方式待后续讨论。

### 2.3 已统一的功能名称与执行归属

避免继续用内部实现名让用户难以辨认：

| 页面 / 业务名称 | 实际含义 | 未来执行位置 |
|---|---|---|
| 自动扫描 | 按计划切换启用店铺并处理 48 小时工单 | Mac mini |
| 单店铺处理工单 | 店铺管理中单个店铺的“处理工单”按钮，对该店铺执行固定清单 | Mac mini |
| 打开店铺后台 | 人工进入某店铺平台后台 | 黑苹果本地 Chrome |
| 查看工单 | 人工打开指定工单详情 | 黑苹果本地 Chrome |
| 重新采集 / 推理 | 通过售后业务服务重新采集并推理 | Mac mini |
| 执行操作 / 批量执行 | 由售后业务服务执行既有业务门禁允许的动作 | Mac mini |
| 删除 / 手动归档 / 标记等待 | 修改售后业务数据，不直接控制浏览器 | Mac mini 售后服务 |

“自动打开店铺进行业务处理”在本轮讨论中指自动扫描内部逐店铺切换和处理，不等于店铺管理里的“打开店铺后台”按钮。

### 2.4 CLI、启动检查与提醒边界

- 售后 CLI 中直接读取或操作鲸灵 / ERP / CDP 的原始命令保留为本机独立工具，不作为日常业务入口或本轮正常迁移入口。
- 用户说明这些 CLI 命令目前没有单独使用；Codex 的正常售后操作限定走售后系统，不走独立账号注入体系。
- 售后服务启动时的 ERP 登录检查只在服务进程启动 / 重启时执行一次，不是每次定时扫描触发；它属于服务内部启动检查，不作为跨设备人工操作冲突的主要来源。
- remind 是售后项目内部辅助操作，不纳入跨项目提醒冲突调度。
- 本轮没有修改这些现有机制。

## 3. 账号登录与 Session 的已确认方向

### 3.1 双端职责与权威数据

**用户确认：统一售后控制台和账号管理界面运行在 Mac mini；店铺新增、登录、重新登录和完整 Session 保存仍在黑苹果完成。**

- Mac mini 是用户查看和操作售后账号的唯一控制台。
- 黑苹果保留现有原始 `sessions/accounts.json` 与完整 `accountN.json` Session 文件；现有登录业务流程不重写。
- Mac mini 独立维护自己的账号索引和业务字段，包括账号名称、备注、扫描开关及售后状态。
- 黑苹果的原始账号配置不需要把名称、备注、扫描开关等字段持续同步到 Mac mini。
- 黑苹果是登录手机号 `phone` 和完整认证 Session 的来源；手机号发生变化时单独同步给 Mac mini。
- 两台机器不共享 Chrome 用户目录或整个浏览器配置文件。

两端的账号索引可以有不同内容，因为它们承担不同职责；不做整份 `accounts.json` 双向覆盖或冲突合并。

### 3.2 现有登录流程保持不变

黑苹果继续执行现有流程：
1. 使用现有 `sessions/jl.js` 启动独立 Chrome for Testing 登录窗口。
2. 从黑苹果本地 `accounts.json` 读取手机号并按现有逻辑自动填写。
3. 用户手动完成登录、验证码及教程弹窗处理。
4. 用户在 Mac mini 提供的统一售后网页点击“确认保存”或“取消”。
5. 黑苹果本地登录进程按现有逻辑保存完整 Playwright storageState，并更新黑苹果本地账号配置。
6. 保存完成后，黑苹果额外生成一份最小认证信息同步文档并发送给 Mac mini。

登录浏览器、手机号自动填写、完整 Session 保存、首次新增手机号初始化及关闭浏览器等现有业务规则均保留。跨设备改造只增加登录启动 / 确认 / 取消指令的转发，以及保存后的认证信息交付。

### 3.3 Mac mini 接收的最小信息

黑苹果不发送整份原始 `accounts.json`，也不发送完整原始 Session。每个账号只交付：
- 账号编号；
- 四种认证 Cookie：`JSESSIONID`、`ssxmod_itna`、`ssxmod_itna2`、`_us`；
- 五种账号身份 LocalStorage key：`__supplierId__`、`__subBizType__`、`currentSubBizType`、`supplierInfo`、`aifocus-cookie`；
- 登录手机号 `phone`。

设备 / 网络指纹类 Cookie 不复制；目标浏览器保留 Mac mini 本机设备环境并自行生成相应字段。注入时现有的“引导已读”标记继续由 Mac mini 侧既有注入逻辑处理。

Mac mini 收到文档后，通过固定流程校验账号编号、认证字段和文档完整性，将必要信息转换为本机注入逻辑可使用的 Session 文件，并更新自己账号索引中的 `phone`。Mac mini 生成的 `accountN.json` 是自己的最小认证副本，不覆盖或回传黑苹果原始文件。

### 3.4 保存、接收确认与失败处理

- 黑苹果先完成本地完整 Session 保存，保证本地人工 Chrome 使用不受 Mac mini 网络状态影响。
- 随后发送最小认证信息同步文档。
- Mac mini 校验后先写临时文件，验证通过再原子替换本地正式 Session，并返回接收确认。
- 只有 Mac mini 确认接收并完成本地保存后，统一售后网页才显示“保存并同步成功”。
- 若黑苹果本地保存成功但同步失败，保留黑苹果原始 Session 和 Mac mini 原有可用 Session；界面显示“本地保存成功，等待 Mac mini 同步”，待连接恢复后安全重试。
- 传输与接收确认只处理认证信息交付，不要求用户再次登录或再次点击保存。

传输版本、更新时间、校验摘要、敏感文件权限和日志脱敏等协议细节留待后续实现设计；不得在日志中输出 Cookie、LocalStorage 值或完整同步文档。

### 3.5 鲸灵平台资源锁

用户确认登录过程也纳入鲸灵平台资源锁：
1. 用户在 Mac mini 统一售后控制台点击“重新登录”时，先申请鲸灵平台操作许可；资源空闲并取得许可后才通知黑苹果启动登录窗口。
2. 登录窗口存活期间持续持有资源锁，阻止 Mac mini 发起新的鲸灵平台操作。
3. 用户点击“确认保存”或“取消”后，待黑苹果确认本地登录进程已完成保存 / 取消并关闭浏览器，再释放资源锁。
4. Session 文件传输和 Mac mini 本地转换不操作平台浏览器，不需要继续占用鲸灵平台资源锁。
5. 浏览器异常关闭可按现有 `jl.js` 逻辑视为取消；设备离线、进程崩溃等异常恢复与锁状态安全将在后续停止 / 失联 / 恢复阶段讨论。

不采用固定自动释放时间，也不要求用户手动释放锁。

### 3.6 下一步待讨论

本次已确认登录业务保留、最小认证信息同步、两端账号数据归属、Mac mini 接收确认和登录资源锁的正常释放条件。

下一项继续讨论：**Mac mini 统一售后网页如何调用黑苹果本地浏览器入口 / 登录桥接服务**，明确启动、确认、取消指令如何抵达黑苹果，以及黑苹果离线时页面如何反馈。随后再讨论一般跨设备任务请求的接收确认、幂等和断网恢复。

## 4. 跨设备平台操作冲突与限时人工注入许可

### 4.1 只保护真实冲突的资源

用户确认：黑苹果人工操作和 Mac mini 自动化使用不同物理桌面，但鲸灵平台 / 店铺账号操作仍按最保守原则避免并发冲突。

当前主要并发风险是：
- Mac mini 正在进行自动售后扫描或其他鲸灵平台操作；
- 黑苹果同时开始向本地 Chrome 注入账号并打开鲸灵后台。

用户此前实测过同一份必要 Session 在两台电脑间交替使用。这里要保护的是同时操作的时间重叠，而不是禁止两台机器交替使用同一个店铺 Session。

### 4.2 自动申请限时许可，不使用永久人工占用

用户不希望依赖手动点击“释放人工占用”，因为忘记释放可能导致售后任务长期停摆；也不采用“关闭工单页面 / 关闭 Chrome 即自动释放”的推断。

当前方向：
1. 黑苹果发起本地平台注入 / 打开后台请求前，先查询 Mac mini 的售后平台操作状态。
2. 如果 Mac mini 正在执行售后平台操作，黑苹果提示当前占用，不启动本地注入。
3. 如果 Mac mini 售后平台空闲，黑苹果自动获得一次限时许可，再执行本地注入。
4. 许可采用短时自动过期，讨论范围约 5–10 分钟；精确时长、是否可在注入验证成功后提前结束，尚未最终定稿。
5. 不根据浏览器或工单页面关闭事件判断许可结束。
6. 不建立需要用户手动释放的无限期全局人工占用。

### 4.3 资源隔离

- 如果 Mac mini 正在运行其他项目，只要不使用相同鲸灵平台资源，仍允许黑苹果进行注入。
- 许可不暂停其他项目，不清空或改写其他项目队列。
- 许可只保护黑苹果本地注入与 Mac mini 售后平台操作之间的冲突。
- Mac mini 的售后任务队列保留原任务和顺序；不把人工许可变成全局停止。
- 若许可有效期间恰好遇到售后定时扫描触发，具体是拒绝新许可、延迟该次扫描，还是采用其他安全处理，尚未最终讨论。不能擅自假设定时任务可与注入并发。

### 4.4 状态岛展示

状态岛应同时展示：
- 当前正在执行的任务；
- 下一项即将执行的队列任务；
- 该下一项任务距离开始还有多久。

用户不希望把“下一项普通队列任务”和“下一次定时任务”拆成两个区域。定时任务本质上也是未来队列候选项，统一展示即可。

显示规则：
- 如果下一项是定时任务，显示任务名和倒计时，例如“售后扫描 · 58 分钟后”。
- 如果下一项是普通即时排队任务，显示任务名和“即将执行”等即时状态，不需要伪造倒计时。
- 没有固定开始时间的普通排队任务可持续作为下一项显示，直到轮到执行；后续队列项不展示。
- 只显示下一项，不展开整个等待队列。
- 没有待执行任务时显示空闲 / 暂无待执行任务。

定时任务即使尚未真正到点入队，也需要作为下一项候选显示；具体由调度层如何提供这一候选状态，后续实现时确定。

## 8. 2026-11-12 至 2026-11-13 双设备通信架构与登录状态恢复

**决策状态：** 用户已确认采用方案 B：黑苹果主动连接 Mac mini，建立长期双向 WebSocket 通信。本节确认通信架构方向和正常登录恢复原则，不代表所有传输协议、重连参数或异常恢复规则均已定稿。

### 8.1 设备与通信角色

- 黑苹果是本地登录执行端，桥接服务调用现有 `sessions/jl.js`，不重写原有登录业务流程。
- Mac mini 是售后业务服务与通信协调端，维护指令、请求身份、业务状态和认证信息接收结果。
- 售后控制台始终由黑苹果本机浏览器打开；iPhone 只通过远程桌面控制黑苹果，不直接参与设备间业务通信。
- 黑苹果主动向 Mac mini 建立 WebSocket 连接。Mac mini 通过该连接发送登录启动、确认保存、取消等预定义指令；黑苹果通过同一连接回传接收确认、执行状态和最终结果。
- 桥接服务应独立于售后网页标签页的生命周期运行，采用 macOS 用户级 LaunchAgent：用户登录 macOS 后自动启动并常驻；睡眠 / 关机时连接中断，唤醒后自动重连。它不依赖售后控制台页面或登录 Chrome 窗口持续打开。具体 plist、进程健康检查和异常重启策略留待实现设计确认。
- 通信接口只暴露明确授权的业务操作，不开放任意 Shell / 命令执行能力。

### 8.2 连接状态与业务状态分离

- WebSocket 已连接 / 已断开只表示通信链路状态，不代表登录任务是否启动、是否保存、是否取消或是否结束。
- 连接断开不得自动释放鲸灵平台资源锁，也不得将任务直接标记为失败或取消。
- 现有售后前端使用内存态 `reloginConfirm`（`public/app.js` 中的 `Set`）控制「确认保存 / 取消」按钮。关闭独立登录窗口后，`jl.js` 会检测浏览器断开并清理临时 port 文件，但售后控制台的确认按钮仍可能保留，直到用户点击确认 / 取消，或后端明确返回“没有待确认的登录会话”后前端清理状态。**按钮仍显示代表控制台尚有待用户收口的确认状态，不代表登录浏览器或本地登录进程仍然存活。**
- 因此恢复时要分别核对：控制台是否仍处于待用户确认状态、黑苹果本地登录进程 / confirm endpoint 是否仍存在、Session 是否更新。按钮状态是有效的辅助凭证，但不能单独作为登录进程存活证明或资源锁释放依据。
- 为支持跨设备和页面刷新后的恢复，Mac mini 应持久保存同一请求 ID 对应的登录操作状态；控制台按钮应由该状态呈现，黑苹果桥接服务报告本地执行现场。不能把当前浏览器内存中的 `Set` 当作唯一持久真值。
- 每次登录操作需要有唯一请求 ID，并关联目标账号，使指令发送、黑苹果接收、实际执行、最终结果和认证信息同步能够关联到同一请求。
- 指令发送后未收到确认时，结果属于“是否送达 / 是否执行未知”；不得直接生成新的登录请求重放。连接恢复后先查询原请求状态。
- 重连后由 Mac mini 主动查询黑苹果当前登录操作状态及目标账号认证信息版本；先核对现场，再决定后续动作，不因重连自动重新启动登录。

### 8.3 已确认的正常恢复路径

**场景 A：黑苹果已保存 Session，但保存结果反馈丢失**

1. 黑苹果已按原流程保存完整 Session，并持久记录本次请求对应的保存成功事实，同时生成最小认证信息。
2. WebSocket 断开，Mac mini 未收到保存完成反馈。Mac mini 应提示结果尚未确认 / 等待核实，不得声称已保存，也不得释放资源锁。
3. 连接恢复后，Mac mini 查询原请求的持久操作记录及目标账号的当前认证信息状态。
4. 如果操作记录能够确认本次 Session 已保存，且认证信息版本 / 内容摘要与记录相符，Mac mini 获取最新最小认证信息，完成校验和本地原子保存。
5. Mac mini 确认认证信息同步成功后，才将登录任务标记为成功并释放资源锁。
6. 不重新启动登录，不要求用户再次登录或重复点击确认。

**场景 B：登录页面仍在，Session 尚未更新**

1. 黑苹果报告原登录页面 / 执行流程仍然存在，且本次 Session 尚未更新、没有最终确认结果。
2. Mac mini 将其视为原任务仍在进行，恢复观察并继续等待用户确认保存或取消。
3. 不重新启动浏览器，不创建第二个登录请求，不释放资源锁。

**场景 C：用户关闭登录窗口，但尚未在售后控制台点击确认 / 取消**

1. 现有 `jl.js` 会在检测到登录浏览器断开时执行本地取消收尾并删除 `.relogin-port-<num>`；本次不会保存 Session。
2. 但售后前端的 `reloginConfirm` 待确认状态仍然保留，因此控制台继续显示「确认保存 / 取消」。这表示控制台尚未完成用户侧收口，**不代表登录浏览器或本地登录进程仍然存活**。
3. 重连后，Mac mini 查询黑苹果本地执行状态、Session 是否更新，以及本次请求的待确认状态。即使确认登录窗口和本地进程均已结束、Session 未更新，也只记录为“登录窗口已关闭，等待用户取消”，不自动清除确认按钮、不结束业务任务、不释放资源锁。
4. 用户的业务需求会提示其需要处理该店铺登录；按用户明确选择，依靠售后控制台保留的「确认保存 / 取消」状态等待人工收口，不设置自动超时取消，也不因浏览器断开自动终结。
5. 如果用户在窗口关闭后误点「确认保存」，黑苹果返回“没有待确认的登录会话”不能清除 Mac mini 上的待确认业务状态；控制台应提示登录窗口已关闭、无法保存，并继续保留「取消」入口，直到用户明确点击取消。

**场景 D：用户明确点击取消（包括登录窗口此前已关闭）**

1. 控制台进入取消处理中，禁用确认 / 取消按钮，并向黑苹果桥接服务发送原请求的取消指令。
2. 黑苹果确认原登录执行已结束；若窗口此前已关闭，可以返回“没有待确认的登录会话”，同时提供本次登录窗口关闭 / 本地取消的持久记录，并确认 Session 未更新。
3. Mac mini 将“没有本地待确认会话”与“用户本次明确点击取消”结合核验。前者不能代替后者；收到明确取消动作及未保存终态后，才清除控制台待确认状态。
4. Mac mini 收到并记录最终取消确认后，才将任务记为“未保存结束”并释放鲸灵平台资源锁。不重新启动登录，不重试本次请求。

### 8.4 资源锁释放规则

- **保存路径：** Mac mini 必须明确确认本次保存结果，并完成最小认证信息的校验、原子保存和同步确认，才允许释放鲸灵平台资源锁。
- **正常未保存结束路径：** 必须确认登录页面及执行流程均已结束、目标 Session 未更新，并且用户明确点击「取消」、Mac mini 记录该取消动作且黑苹果确认本地未保存终态，才允许按未保存结束释放资源锁。登录窗口关闭、port 文件消失或黑苹果报告本地自动取消，都不能代替用户在控制台明确点击取消（见场景 C、D）。
- **仅连接断开、仅请求超时、仅收到进程 / 页面不确定信息，均不足以释放资源锁。**
- 无法查询、证据冲突或状态未知时，保持资源占用，进入异常处理；不得为了恢复队列而猜测任务已经结束。

### 8.5 待进一步确定的实现证据与异常分支

以下属于后续协议设计，不在本次提前定稿：

- 如何为每次登录操作持久记录请求 ID、目标账号、启动状态、保存 / 取消结果及最终结束状态；黑苹果侧还需保留终止原因，区分用户明确取消、登录窗口关闭触发的本地取消、保存成功和进程异常，不能只凭 port 文件消失推断原因。
- 如何可靠证明 Session 更新属于本次请求：建议结合操作记录与认证信息版本 / 内容摘要；单独依赖文件修改时间不足以证明。
- 最小认证信息的版本、摘要、传输确认、原子替换和重复交付处理。
- 长期离线提醒的实现细节：复用现有快捷指令的调用封装、跨设备离线事件补发与去重持久化（业务决策见 §8.7）；连接尝试超时的具体实现参数。
- 黑苹果桥接服务崩溃、浏览器异常关闭、设备重启、Mac mini 重启、状态查询失败或页面 / 进程 / Session 证据矛盾时的处理。
- 异常情况下资源锁的保持、人工核实和安全释放机制。

### 8.6 WebSocket 心跳与传输在线判定

**初始参数：已按同类项目调研确定**

| 参数 | 初始值 |
|---|---:|
| Ping 发送间隔 | 30 秒 |
| 心跳失效超时 | 60 秒 |
| 无响应判定窗口 | 约 60 秒（从最后一次有效心跳响应 / 接收开始计时） |

**实现方向：**
- 使用 RFC 6455 定义的 WebSocket 控制帧 Ping / Pong，不另造自定义 JSON 心跳消息。Mac mini 作为 WebSocket 服务端，每 30 秒发送 Ping；黑苹果桥接端按协议自动返回对应 Pong。
- 双方分别维护心跳存活时间：Mac mini 连续 60 秒未收到有效 Pong，判定连接失效；黑苹果连续 60 秒未收到服务端 Ping，也判定连接失效。超时按“距离最后一次有效心跳的静默时间”计算，不按“30 秒间隔再额外等待 60 秒”计算，避免把实际检测窗口意外拉长到 90 秒。
- 如果操作系统 / WebSocket 库已明确触发 close 或 error，不必等待心跳超时，立即进入连接中断状态。
- WebSocket 刚建立时先完成设备身份认证和状态核对；只有认证及重连状态核对完成后，才标记为业务可用。TCP / WebSocket 刚连通不等于业务已恢复。
- Pong 只证明 WebSocket 通信路径仍有响应，不代表登录、Session 保存或认证信息同步等业务操作成功；所有业务指令仍须有独立的接收确认和执行结果。
- 心跳超时、连接关闭均不得自动释放业务资源锁，不得清除登录待确认状态。

**参数依据与取舍：**
- RFC 6455 规定 Ping / Pong 的协议行为，但不规定固定发送间隔。
- Node.js `ws` 官方示例采用 30 秒 Ping 检查；LiveKit Agent Worker 源码采用 30 秒 WebSocket heartbeat，并为短暂断线设置 30 秒 reconnect grace period。
- Python `websockets` 官方库默认采用 20 秒 Ping / 20 秒 Pong 等待；Socket.IO 默认采用 25 秒 Ping 间隔 / 20 秒 Pong 超时。它们说明 20–30 秒是成熟实现中的常见心跳频率。
- 本项目采用 30 秒心跳，并将失效超时放宽至 60 秒，是结合只有一条设备连接、业务不要求秒级发现、售后已有独立安全收口规则后的保守选择。60 秒是本项目的容忍策略，不是 WebSocket 标准规定值。

参考：
- [RFC 6455 §5.5.2–5.5.3 Ping / Pong](https://www.rfc-editor.org/rfc/rfc6455.html)
- [Python websockets: Keepalive and latency](https://websockets.readthedocs.io/en/17.3/topics/keepalive.html)
- [Socket.IO server options](https://socket.io/docs/v4/server-options/)
- [LiveKit Agents worker.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/worker.py)

### 8.7 自动重连、长期离线与恢复

**决策状态：** 用户确认采用以下第一版重连策略；HTTP 备用轮询暂不建设。

| 项目 | 第一版规则 |
|---|---|
| 首次重连 | 连接被判定中断后等待 30 秒 |
| 第二次重连 | 上次尝试失败后等待 60 秒 |
| 第三次及以后 | 上次尝试失败后等待 120 秒 |
| 最大重连间隔 | 120 秒 |
| 最大重试次数 | 不设上限，持续重试 |
| 随机抖动 | 第一版不启用（目前只有一个黑苹果 WebSocket 客户端） |
| HTTP 降级通道 | 第一版不建设，恢复只依赖 WebSocket 重连 |

**重连运行规则：**
- 连接明确 close / error 时立即进入离线状态并启动重连计时；心跳静默超过 §8.6 的 60 秒阈值时判定离线。
- 每次失败尝试结束后再计算下一次等待间隔：30 秒 → 60 秒 → 120 秒 → 之后始终 120 秒。不得并行启动多个重连循环。
- 每次连接尝试必须有有限的握手超时；超时后关闭本次 Socket、释放资源，再进入下一轮等待。具体超时值在实现前结合 Tailscale 实测确定。
- 只有完成设备身份认证及业务状态恢复核对，才重置退避计数；仅 TCP / WebSocket 握手成功不能重置。
- 黑苹果桥接服务由用户级 LaunchAgent 管理；如果进程崩溃，由 LaunchAgent 负责重新拉起，应用自身负责网络重连。睡眠期间连接自然中断，唤醒后恢复重连循环。
- 第一版不增加 HTTP 轮询备用链路。两种方式依赖同一 Mac mini 服务及同一网络路径，当前没有足够理由维护第二套指令通道；若后续实测发现 WebSocket 独立故障而 HTTP 仍可用，再单独评估。

**计划下线与服务重启：**
- 正常计划关闭服务时，当前连接仍可用，服务可先发送 `server_going_offline` 状态事件，再正常关闭连接。
- 崩溃、断电或网络突然中断时不要求发送下线通知，由 close / error 或心跳超时检测。
- Mac mini 售后服务每次进程启动生成新的 `server_instance_id`。黑苹果重连后，Mac mini 在握手响应中返回当前实例 ID 和服务就绪状态；由于断线后原 WebSocket 已不存在，Mac mini 不另建反向连接尝试推送通知。
- `server_instance_id` 变化表示 Mac mini 服务进程已重启，触发完整状态核对。即使实例 ID 未变化，任何实际发生的 WebSocket 重连也必须核对未完成指令、运行中任务和事件游标，不能假设断线期间没有状态变化。
- 短暂网络波动若未导致连接关闭，且在 60 秒心跳失效阈值内恢复，则连接保持，不触发离线流程；若 TCP / WebSocket 已明确关闭，则按重连流程处理。

**长期离线与人工提醒：**
- 从连接被确认中断时持久记录 `offline_since` / outage ID；连续离线达到 10 分钟，创建一条「双设备通信异常，需人工检查」提醒事项。
- **提醒事项统一由黑苹果创建**，复用现有 Mac「创建提醒」快捷指令及共享输入文件渠道；Mac mini 不直接创建提醒。
- 同一次连续离线只创建一次提醒，使用 outage / incident ID 去重。若黑苹果在线，它在达到 10 分钟时创建；若黑苹果当时不可用，由 Mac mini 持久保存待创建事件，黑苹果恢复连接后补建。若两端均曾离线，启动 / 重连后根据持久化的最后成功连接时间恢复离线时长，达到阈值仍只补建一次。
- 创建过程遵循工作区 `docs/reminders.md`：黑苹果串行写入共享输入文件并运行「创建提醒」快捷指令；只有从本次输出核验到匹配的 VTODO / UID 才记为已创建。输出缺失、部分成功或结果不确定时不得自动重发，避免重复提醒，转为人工核查。
- 连接恢复后，两边状态岛更新为已恢复并清除持续离线提示；**已创建的提醒事项保持未完成，不自动完成、不删除**，由用户查看状态岛后自行决定是否处理提醒。
- 持续离线期间，状态岛显示对端离线、持续时间及下一次重连倒计时，不反复弹出通知。设备自身完全关机时无法显示，其重新启动后根据当前连接状态更新。

**连接长期不可用时的影响边界：**
- 重连循环只进行低频连接尝试，不会自行执行登录、重复任务或清理业务状态。
- 不依赖对端的本地任务可以按原有规则运行；需要跨设备通信或共享资源锁确认的任务，在无法确认对端状态时不得冒险启动。
- 队列中尚未开始的任务保留，连接恢复并完成状态核对后继续执行。
- 没有排队任务时不需要额外处理。
- 运行中途被中断的任务标记为中断，不自动重放；由人工判断是否创建新的独立任务重新入队。
- 如果连接永远无法恢复，跨设备通信能力会一直不可用，但重试资源消耗有上限；人工可通过既有 UU 远程 CLI 兜底处理。该兜底不替代正常自动重连。

**恢复状态核对：**
- 每次 WebSocket 重新建立后，先认证设备，再核对任务状态，最后恢复业务可用状态。
- **无论 `server_instance_id` 是否变化，每次真实重连都必须检查全部未完成指令、运行中任务和当前队列状态**；不能因为实例 ID 相同就跳过检查。
- 若 `server_instance_id` 改变，说明 Mac mini 服务进程已重启，除上述检查外还要执行完整状态快照核对。
- 若实例 ID 未变，但事件游标 / 状态版本出现缺口、前后状态矛盾或无法确认断线期间的变更，也升级为完整状态快照核对。
- 任何情况下都不因重新连接而重放运行中途被中断的任务；排队但尚未执行的任务则在核对后恢复。

**参数依据：**
- Eclipse Paho MQTT 官方客户端采用指数退避，支持从配置的最小延迟开始每次翻倍，并设置最大延迟 120 秒；成功连接确认后重置退避。这里采用相同机制，但将起始值提高为 30 秒、最大值保持 120 秒。
- EMQX 工程建议推荐指数退避和最大间隔，并指出随机抖动主要用于避免大量客户端同时重连造成连接风暴。当前只有一个客户端，因此第一版不启用抖动。
- Apple 的 launchd 文档说明 LaunchAgent 随用户登录启动，KeepAlive 可用于维持进程运行；网络可用性仍需由应用自行检测和处理。
