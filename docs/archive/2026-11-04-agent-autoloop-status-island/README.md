## 2. 原始资料与源码观察

### 2.1 调度和执行模型

1. **Rule group 是任务并发控制，不是通用多资源锁。**多个 Rule 可以加入同一个 group；同组任务受 group 并发上限约束。按本轮阅读的默认行为，不设置并行容量时同组按单任务执行；若显式设置 parallel，则同组 Rule 需要保持一致的配置。
2. **任务执行不要求调用大模型。**仓库支持 command 类型的执行 Agent，普通脚本可以作为任务执行体。Autoloop 可以只负责何时启动、谁先执行、状态如何恢复，不必让模型参与运行时业务判断。
3. **group 不等于资源集合锁。**它不能直接表达一个任务占用鼠标、Chrome、ERP，另一个任务占用鼠标、微信的任意资源组合；它提供的是同组任务的并发限制。
4. **外部任务展示不等于接管调度。**协议中的 elsewhere 用于把在其他地方运行的任务展示出来，不会因此启动或完整管理那些任务。若现有项目继续绕过调度层自行启动，Autoloop 就无法知道真实占用情况，也不能阻止冲突。
5. **状态持久化和幂等处理是内核的重要部分。**此前阅读看到 SQLite WAL / FULL、事件记录与状态重建、claim/result 幂等处理、重放恢复等机制。仓库还包含故障模拟、进程被杀后的恢复测试和较大步数的状态模拟。它的价值不只是一个定时器，而是有持久任务状态和恢复协议的调度内核。
6. **失败重试是通用默认策略，不等于业务安全策略。**此前阅读到的默认退避策略从约 5 分钟开始，逐步增加，最长可到约 1 小时；连续失败达到阈值后会通知。具体默认值必须在集成时按选定版本复核。
7. **worker 活性判断存在桌面操作需要额外关注的边界。**此前代码阅读发现，worker 对任务心跳/存活状态有判定；任务长时间没有报告时可能进入 unknown，并释放 group 让后续任务继续。这个设计能避免幽灵任务永久占队列，但对鼠标控制任务需要额外验证：旧进程是否可能仍然活着、仍能操作桌面，而调度层已经释放 group。
8. **进程组恢复和停止逻辑已有实现。**worker 会管理 Agent 子进程组，并尝试在重启后恢复或识别运行进程；这降低了孤儿进程风险，但不能替代我们对真实桌面进程互斥的验证。

### 2.2 权限和安全边界

1. askFirst 更接近写入 Agent prompt 的行为要求，不是内核对“退款、删除、停服”等业务动作进行拦截的硬权限门。内核不能仅凭这条 prompt 知道 Agent 是否绕过了要求。
2. 真正的执行权限边界仍依赖 read/edit/full 权限、sandbox、操作系统账户和容器等机制。
3. 因此，Autoloop 的通用 Agent 授权方式不能替代售后项目现有的代码级业务门禁、人工确认、执行 journal、白名单和 fail-closed 规则。
4. 对售后而言，业务动作报错即停、不得自动重试第二次等既有风控边界必须继续由售后项目自己执行。调度层不能根据通用 retry 策略擅自重跑业务动作。

### 2.3 Delivery / Review 流程

1. 仓库把 Review 放进 delivery 生命周期，而不是只提供一个“需要时手动调用”的审查提示。
2. delivery 会在交付阶段安排独立 Review；审查结果与具体代码快照关联。审查期间代码或基线发生变化时，旧审查结果不能继续作为新代码的通过凭证。
3. Reviewer 使用隔离上下文和只读快照，避免继承实现者的大量上下文，也避免 Reviewer 自己修改被审查代码。
4. Reviewer 的任务被限制为寻找可能造成真实结果错误、数据损失、权限或发布事故的问题；不以代码风格、抽象偏好或一般优化建议为目标。
5. finding 使用结构化输出，必须指向具体文件/位置、触发条件和实际后果。没有可行动问题时允许返回空结果。
6. Review 是交付 Gate 的一部分：发现成立的问题后先修复，再对修复后的新快照重新审查。它不是一份可以永久沿用的“这段代码以前审过了”证明。

### 2.4 Skill 与 decisions / declined 文件

- 仓库中的 Skill 更偏向给长期自动执行的 Agent 提供任务手册，例如如何判断完成、如何核验、什么情况下停止。
- decisions.md / declined.md 是项目级 Markdown 约定，不是 Autoloop 内核提供的自动决策记忆数据库。长期内容仍需要人工整理、去重和维护。
- 因此，这两项属于作者工作流选择，不是使用 Autoloop 调度能力的必要条件。

## 3. 用户明确表达与已认可的方向

### 3.1 用户对 AI 自主执行的态度

用户明确说明，与作者相比，自己没有那么忙，也没有那么信任 AI。AI 独立执行后，经常仍需要用户修正方向或返工；用户不认为“完全无人干预、一次成功”是现实目标。

用户认可无人值守的价值，但开发阶段仍需要保留介入能力。用户有时会因为观察到 AI 长时间没有进展而主动插手，判断是否走错方向、是否需要调整。这是用户当前的实际协作方式，不应被误判为不愿自动化。

**用户已明确的运行现状：**

- 用户的整体设计原则是正式运行以确定性脚本为主，不让通用 Agent 自由规划并控制业务流程；AI 主要参与项目制作、排查和修改。
- 这不等于所有项目代码里绝对没有模型调用：例如售后项目存在局部 ai-infer 模块。这里必须区分窄范围的项目内推理 / AI 组件，与“让 Agent 在运行时自主规划并控制鼠标”这两种不同模式；某模块是否进入当前生产链，仍以该项目现役入口和配置为准。
- 用户指出当前农场、群聊分析含有一些 AI 成分；未来群聊分析可能需要模型参与语义分析。其余自动化无需为了 Autoloop 引入运行期 Agent 或新增 Skill。
- 现有 SOP 已经承担项目运行说明和操作边界的作用。卡兹克项目中面向自动化 Agent 的 Skill 不需要复制到所有现有项目。
- 当前不需要新增 decisions.md / declined.md，也不需要为了适配 Autoloop 重构现有 SOP、neat 或规则体系。

### 3.2 共享桌面资源排队是确定需求

用户明确表示只有一台电脑，所有相关自动化最终通过鼠标控制桌面，因此共享资源排队是必须做的事情；当前不需要考虑并行执行。

用户也明确指出，售后系统不一定必须在 cron 的精确分钟启动。延迟 5 分钟或更长时间通常可以接受，排队比人为扩大固定禁用时间段更合理。

由此形成的用户方向：

- 售后、农场、群聊采集及未来其他会控制桌面的自动化，都需要服从同一套串行排队。
- 不需要为每个应用建立多资源锁矩阵，也不需要设计并行调度。
- 原先人工维护的时间冲突区间不应继续充当最终互斥机制；真实运行状态和队列决定任务何时取得桌面。

### 3.3 Review 的真正需求是对抗性审查常规化

用户认为当前工作方式已经包含开发者自检和用户实测：开发过程中助手会检查代码，用户也会观察真实运行结果；真实效果没有问题时，用户通常不会再要求额外 AI Review。

用户不希望增加传统的“每次代码改动后再检查一遍代码”流程。真正想学习的是卡兹克如何把**对抗性审查**变成默认流程，不再需要用户每次单独提出。

用户的方向是：只要涉及无人监管自动化，就应该自动经过一道对抗性审查。触发粒度、例外范围和落地到哪一层规则，仍需在后续流程设计中明确。

### 3.4 Status Island 的产品方向已获用户认可

用户认可将现有 Codex Monitor 改造成一个常显的桌面状态岛，而不是另建完整中台。

用户明确要求：

- 保留现有用量统计功能。
- 保留当前的限额倒计时显示；不能为了显示自动化状态而丢掉它。
- 提供一个可点击的人工占用开关，用户可以手动切换“人工正在使用电脑”与“释放桌面”。
- 能看见当前桌面由谁占用，例如空闲、售后系统运行、农场种植、群聊抓取聊天记录。
- 能看见下一项计划任务及其倒计时，例如“售后 5 分钟后运行”。
- 能看见后续等待任务；人工占用时自动任务应排队，释放后再继续。
- 售后当前独立弹窗中的运行信息可以并入状态岛的展开详情。
- 不需要完整任务管理中台，只需要简单、常显、可操作的状态展示。

“灵动岛”是用户对外观和常显交互形态的比喻，不代表已经决定具体尺寸、位置、材质或最终产品名称。

### 3.5 异常显示和通知的分工已获认可

用户提出：如果农场或其他项目出现异常，状态岛应该一直保留异常，还是只短暂显示几秒；是否应该由各项目决定是否真正通知用户。

随后用户认可了以下分工：

- 状态岛持续显示当前桌面 owner / 当前运行任务，不因旧异常而掩盖正在发生的任务。
- 未处理异常不能只闪现几秒后消失，应留下可见的未处理标记；异常发生时可以短暂强化视觉提示。
- 是否进一步创建 Mac 提醒事项或进行远程打扰，由各项目自己的业务规则决定。
- 售后当前创建提醒事项的机制第一阶段保持不动；状态岛同时展示相关异常即可。
- 农场、群聊等项目可以先只在状态岛留下异常，是否升级通知由各项目自己的规则决定。

## 4. 助手的分析与建议（不是用户原话）

本节保存助手在讨论中提出的设计建议。除非第 3 节标为“用户已认可”，其余细节仍需设计或验证。

### 4.1 调度层

- 首选认真评估直接采用 Agent Autoloop 的 group / claim / queue / recovery 能力，不自己从零造一个共享调度器。
- 建议所有桌面自动化使用同一个 group，例如 desktop-automation，并把并发上限固定为 1。group 名称尚未定稿。
- 售后、农场等项目只把“何时启动 / 等待桌面 / 释放桌面”的控制权交给调度层；各项目内部的业务规则、状态机、SOP、数据结构和安全门禁保持原样。
- 所有可能操作鼠标或键盘的任务必须经过同一调度入口。若售后仍由自己的 cron 绕过调度层启动，Autoloop 就无法防止它与农场冲突。
- 不把 elsewhere 状态展示误当成已经纳入互斥队列。
- group 是本场景需要的粗粒度串行门，不继续扩展成通用多资源锁系统。

### 4.2 重试与进程安全

- Autoloop 的通用失败重试不能替业务决定是否允许重试。
- 售后业务动作失败、页面状态不明、账号异常等必须按售后现有规则停止并生成待办；不能简单返回通用 failed 后让调度器自动重跑。
- 集成时需要区分“可安全重试的基础设施启动失败”和“必须停止并等待人工处理的业务失败”。
- 对桌面控制任务，必须重点验证 worker 将任务标记 unknown 并释放 group 时，原进程是否确实不再可能控制鼠标。必要时保留一层很薄的本机进程存活保护；这不是第二套调度器，而是避免旧进程与新任务同时操作桌面的最后一道保险。
- 用户人工占用应阻止后续自动任务取得桌面；若当前自动任务已经运行，点击人工占用后如何安全交接仍未决定。

### 4.3 Status Island 的职责边界

建议把职责拆成三层：

1. **调度层**：Autoloop 或经验证的调度内核，维护唯一权威的 owner、队列、下一次任务、运行状态和人工占用状态。
2. **项目层**：售后、农场、群聊等项目报告自己的进度和异常，并自行决定异常是否需要提醒用户。
3. **显示层**：Codex Monitor / Status Island 读取调度状态，展示项目进度和用量；人工占用按钮向调度层发出状态切换请求。UI 不自行维护第二份调度真值。

建议状态岛常显区域优先回答两个问题：

- 现在谁在使用电脑？
- 下一件将要发生的任务是什么、还有多久？

展开区域再显示队列、当前项目进度、异常详情和原售后 HUD 的必要信息。

第一版不建议增加 cron 编辑器、Agent 配置、完整日志浏览器、任务管理后台、统计 Dashboard 等中台功能。

### 4.4 人工占用交互

用户已确定需要一个可点击的开关；以下细节仍是助手建议，不能当作已确认规格：

- 空闲时开启人工占用：调度层登记 human owner，后续自动任务排队。
- 人工结束时点击释放：调度层释放人工占用，再按队列顺序启动下一任务。
- 不建议通过鼠标/键盘活动自动判断人工占用，因为自动化本身也会产生输入事件，容易误判。
- 建议人工占用默认不自动超时释放，以免用户仍在操作时自动任务突然抢占；是否采用永久占用直至手动释放，需在设计时确认。
- 当前自动任务运行中点击人工占用，是立即停止、只阻止下一任务，还是请求当前任务到安全点后交接，尚未决定。
- “人工占用”与“紧急停止当前任务”应分开设计，避免一个按钮同时承担两种含义。

### 4.5 异常状态

建议把“当前运行状态”和“未处理异常”分开：

- 当前任务始终作为主状态展示。
- 未处理异常保留 badge / 数量，直到异常恢复或被明确处理。
- 异常发生时可短暂高亮状态岛；高亮结束后 badge 仍保留。
- 如果异常使整个桌面队列无法继续，才把主状态显示为队列阻塞。
- 项目决定通知等级和渠道；共享层只提供展示或提醒传输能力，不替项目决定业务严重程度。
- 不应为了统一而第一阶段重写售后现有 Reminders 机制。

### 4.6 用量统计和现有 HUD

- 现有 Codex Monitor 已有本地 JSONL reader、聚合、项目归因、5 小时 / 周限额、限额倒计时、Tk 浮窗、AppKit 磨砂 backing window、.app、LaunchAgent、单实例和后台刷新。
- 建议保留 reader、聚合、项目归因、额度计算和现有倒计时能力，只扩展显示数据源与交互。
- 售后现有 HUD 不应与状态岛并列存在两套常驻运行窗口；建议把仍有价值的运行进度和停止/查看入口并入状态岛展开详情。具体字段需盘点后决定。
- 自动化状态和用量统计共享一个显示位置，但两者仍是独立数据来源。状态岛不能因为用量达到某个百分比就擅自停止项目，除非该项目自己定义了明确规则。
- 用户偏好异常优先：正常运行不需要每天发日报；用户空闲时可以主动查看，系统只对需要处理的异常进行提醒。

### 4.7 UI 技术选型

- 当前项目是 Tkinter 前景 + 独立 AppKit NSVisualEffectView backing window。它已经能提供常驻胶囊、磨砂背景、展开层和交互，但两套窗口/渲染链路存在原生材质、字体合成和生命周期限制。
- 现有 docs/FUTURE.md 已记录保留 Python 数据层、评估 NSPanel + SwiftUI/AppKit 的长期方向。
- Status Island 增加了状态展示和人工交互，值得在设计阶段重新比较：继续扩展 Tk/AppKit 的成本，和原生 NSPanel / SwiftUI 的开发、打包、常驻、功耗及维护成本。
- 不能因为“灵动岛”外观就默认重写成 SwiftUI；也不能因为已有 Tk 窗口就默认继续堆叠。先做产品交互设计，再按真实需求做技术选择。

### 4.8 与现有项目的职责边界

本次 NEAT 只归档跨项目接入原则，不修改这些项目的业务代码、SOP 或运行配置。根据各项目现役入口文档，后续接入时需要保留以下边界：

- **售后自动化：**现有 lib/server/op-queue.js 已经负责项目内部的浏览器操作串行化，并有自己的紧急停止、恢复标记和扫描 HUD。Autoloop 应位于它外层，负责跨项目桌面占用和定时任务排队；不得替换 op-queue，也不得绕开其内部安全门。售后当前 server.js 的定时扫描启动入口以后若接入共享调度，需要迁移“启动权”，而不是迁移业务处理流程。售后 HUD 当前包含预告倒计时、店铺/工单进度、异常、停止和完成状态；状态岛设计时先盘点哪些字段值得并入展开详情。
- **QQ / 微信农场：**现役架构是 Runner V2。用户与 ChatGPT / Planner 决定种植计划，本地 Runner 按固定窗口、固定坐标和确定性流程执行；视觉只做局部 ROI 验证，DIRTY / UNKNOWN 立即 STOP。定时化当前暂停，稳定后只允许调度层调用 Runner，不让 Agent 在运行期自主研发或逐点击控制。Autoloop 只负责排队和启动 Runner，不改变 Runner 的状态机。
- **群聊分析：**必须区分桌面采集和语义分析。run_capture.py 及 QQ 窗口定位/滚动会控制桌面，应纳入共享串行 group；后续 GPT/Codex 语义分析与发布流程属于另一阶段，不因名称上同属“群聊分析”就默认占用鼠标资源。现有 OPERATING-SOP、规则 owner、work package、review receipt 和发布门禁继续负责项目内流程，不为 Autoloop 重复造一套任务 Skill。
- **提醒事项：**工作区已有统一提醒输入协议和快捷指令；项目负责决定是否发提醒。共享状态岛不把每个异常都自动升级成 Mac Reminders，也不在第一阶段重写售后 createReminder()。

### 4.9 对抗性审查工作流

Reviewer 不需要比主 Agent 更强的模型；独立上下文、没有参与实现的历史包袱、只读权限和严格的 finding 格式，比换一个模型名称更重要。可以评估同一 GPT 模型在全新上下文中审查；其他模型给出的意见不能直接覆盖主 Agent 判断，必须由主 Agent 独立验证。

真实现场验收与对抗性审查互补：现场验收回答“正常真实场景是否做对”，对抗性审查回答“是否存在尚未走到、但现实可达的失败路径”。两者不能互相替代。

### 4.10 推荐验证顺序

助手建议按风险从低到高验证：

1. 先用两个或多个无副作用的 command 假任务，在隔离环境验证同组排队、延迟执行、重复触发、停止、进程崩溃、worker 重启、电脑休眠/唤醒和恢复行为。
2. 确认桌面进程确实不会因 unknown / worker 恢复而重叠后，再接入低风险自动化。
3. 农场可作为后续低风险实测候选；售后最后接入，因为其业务操作和风控后果最高。
4. 售后接入前必须保留原有人工确认、业务 fail-closed 和“行为操作报错即停”的规则。
5. 不应在调度器验证完成前更改现有售后、农场或群聊自动任务的启动入口。

## 5. 当前已收敛的架构结论

以下是本轮可以作为下一阶段设计基线的内容：

1. **共享桌面调度是明确需求。**一台电脑、所有桌面自动化串行执行，不考虑并行。
2. **优先复用 Agent Autoloop 的调度能力。**不自己建设完整中台；具体版本和接口仍需集成前验证。
3. **现有项目业务逻辑不迁移。**调度层只管启动、排队、桌面占用和任务生命周期；项目继续拥有自己的 SOP、状态机、安全门禁和业务结果。
4. **现有 SOP 保持权威。**不为了 Autoloop 批量创建任务 Skill，也不新增 decisions.md / declined.md。
5. **无人监管自动化需要常规化对抗性审查。**不是每次普通代码改动都跑传统 Review；凡涉及无人监管自动化的实现/运行行为，应由流程自动触发独立对抗性审查。精确触发粒度和例外范围仍需制定。
6. **Codex Monitor 是 Status Island 的改造基础。**保留原用量统计、限额数据和限额倒计时，在现有项目上扩展，而不是另起一个常驻桌面工具。
7. **人工占用由用户点击切换。**自动任务在人工占用期间排队；释放后继续。按钮的当前任务交接语义仍待设计。
8. **异常与通知分层。**状态岛保留未处理异常；是否创建提醒由各项目自行决定。售后提醒第一阶段不改。
9. **Status Island 不是调度器。**调度器是真值来源，状态岛负责展示和发出人工占用切换操作。
10. **保留极简产品范围。**当前状态、下一任务倒计时、队列、人工占用、项目进度、异常标记和用量信息是核心；不做完整任务管理后台。

### 6.4 UI 技术和迁移范围

- 对比现有 Tk + AppKit 实现与 NSPanel + SwiftUI/AppKit。
- 保留 Python reader / aggregator / quota 逻辑，不因 UI 选型重写统计核心。
- 评估常驻、开机启动、单实例、窗口层级、磨砂材质、CPU/内存、打包维护成本。
- 确定先做交互原型还是直接在现有界面上扩展；未经比较不预设技术方案。

### 6.5 对抗性审查流程

- 明确“涉及无人监管自动化”的范围和自动触发点。
- 区分首次从实验态进入无人监管运行，与已无人监管系统的后续行为改动。
- 明确纯展示/文案修改是否排除，涉及重试、恢复、队列、账号、写操作和停止逻辑是否必审。
- Reviewer 使用独立上下文、只读快照和无修改权限。
- finding 必须包含具体路径、触发条件、真实后果和证据；拒绝风格建议与无证据猜测。
- 主 Agent 负责验证 finding，确认成立才修；修复后对新快照重新审查。
- 真实现场验收与对抗性审查是两种不同验证，不能互相替代。
