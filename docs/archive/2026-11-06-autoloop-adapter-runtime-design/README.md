## 0. 范围与结论

本轮讨论的是跨项目共享桌面调度的架构边界，重点为：
1. 适配层如何接入现有项目，避免重复队列，同时保留稳定的业务执行逻辑。
2. 统一桌面队列如何排队、合并、人工占用、处理重试、错过定时任务和执行失联。

这不是安装或集成授权，也不是最终接口规格。当前没有修改售后、农场、群聊或 Codex Monitor 的运行代码。

核心结论：

**统一迁移的是桌面任务的排队与调度所有权，不是把各项目的业务执行系统重写一遍。**

Autoloop 负责谁在什么时候获得桌面使用权；项目负责获得使用权之后执行什么、内部如何重试、遇到业务异常如何处理，以及什么时候向调度层报告任务最终结束。

## 1. 第 1 阶段：适配层

### 1.1 队列管理权整体迁移，不保留双队列

**用户确认：**
- 适配层不是在旧项目队列外再套一层长期并存的队列。
- 原来由项目自身维护的待执行队列，其排队管理职责整体迁移给统一调度层。
- 任务先提交给调度层；调度层空闲则安排执行，有其他任务则等待。
- 状态岛读取调度层的权威队列，不再维护第二份队列列表。
- 不能让任务先进入 Autoloop，再进入旧项目待执行队列形成双重排队。

### 1.2 保留现有执行细节，优先做最小改动

**用户确认：**
- 原有项目已经稳定可用的执行逻辑应尽量保留。
- 改造重点是把原有队列管理职责拆出并迁移，而不是顺手重写 executor、业务流程和安全机制。
- 适配层取得调度执行机会后，应尽量调用项目原有执行入口及其执行细节。
- 只有在旧队列管理与执行逻辑耦合程度确实很高、无法安全拆分，且重构范围本身清晰简单时，才考虑较大改造。
- 不为追求架构整齐而重写已经稳定的业务代码。

**设计基线：**
- 调度层：接收任务、维护唯一权威队列、安排执行、管理桌面占用、记录任务最终生命周期。
- 项目适配层：把项目任务请求交给调度层；轮到时调用项目原有执行逻辑；转发进度、内部异常和最终结果。
- 项目执行层：继续负责业务流程、数据写入、业务安全门禁、内部重试、异常分支和项目自身停止机制。

具体执行函数如何从旧队列模块中拆出、是否仍在原 server 进程内执行、Autoloop command runner 如何调用，尚未定为最终代码方案；必须根据实际代码耦合和进程边界逐项讨论。

### 1.3 任务最终状态与内部异常事件分开

**用户确认：**
- 调度层任务状态跟随项目对整个任务的最终反馈。
- 项目内部发生异常，不自动等于整个调度任务失败。
- 内部异常是独立的展示信息：项目可向状态岛报告异常，即使整个任务最后成功。
- 调度层不必理解售后具体哪个店铺或工单出错；业务细节由项目提供给状态岛。
- 如果项目因致命异常停止并清空自己的待执行队列，那么该任务已经终结，最终结果为失败，而不是仍处于运行中。
- 状态岛应同时展示当前任务状态和未处理内部异常；不能把两者合并成一个状态字段。

示例：
- 售后扫描多个店铺，其中部分店铺登录失败，项目创建提醒并继续处理其他店铺，整轮扫描最终完成：调度任务可以成功结束，状态岛仍显示本轮内部异常。
- 售后队列遇到致命异常并停止清空：项目报告任务失败完成，状态岛显示对应异常。
- 任务成功/失败是任务生命周期结果；内部异常是执行过程中产生、需要展示或处理的事件。

### 1.4 项目内部异常分支仍属于原任务

**用户确认：**
- 如果某项目在异常后需要执行恢复脚本 X，X 应是任务 A 的内部流程分支，而不是调度层新插入的独立任务。
- 项目自行判断是否进入异常分支；调度层不理解业务原因，也不决定是否运行 X。
- 例如售后处理店铺 A 失败后，先创建提醒事项，再继续处理店铺 B；提醒事项创建是整轮售后任务的一部分。
- 只要项目完整流程尚未结束，当前调度任务就没有完成，桌面占用权也不应提前释放。

### 1.5 紧急停止仍由项目原有机制执行

**用户确认：**
- 紧急停止继续通过项目现有按钮、API 或其他现有渠道触发，不要求把原停止机制复制到调度层。
- 项目向调度层发出“正在请求停止”的信号。
- 项目继续执行自己的停止逻辑和停止验证。
- 确认停止成功后，项目再通知调度层：该项目当前任务已停止，队列中属于该项目的待执行任务应清除。
- 清理范围只针对发起停止的项目，不影响其他项目的排队任务。
- 停止尚未确认完成前，调度层不得提前释放桌面给下一任务。

具体映射成 Autoloop 的取消 / 终态类型、如何批量清除指定项目任务、暂停与恢复是否持久化，仍待停止安全阶段设计。

## 2. 第 2 阶段：统一桌面调度运行模型

### 2.1 单一桌面资源与严格排队

**用户确认：**
- 当前只建设桌面占用调度，不建设多资源锁矩阵或并行桌面任务系统。
- 所有需要控制共享桌面（鼠标 / 键盘 / 浏览器等）的自动化进入同一桌面调度组。
- 同一时刻只允许一个桌面任务实际执行。
- 任务按调度层接收顺序领取；同一秒内提交的任务不要求进一步区分先后，可任意排序。
- 调度层只负责桌面使用权，不替项目决定业务执行内容。

Autoloop group / parallel / worker capacity 是否能完整保证上述行为，仍须对固定版本源码和运行结果进行验证，不能只凭配置名称推断。

### 2.2 事件合并规则

**用户确认：**
- 允许保留指定项目、指定 subject 的事件合并能力。
- 合并必须显式配置白名单，不能默认对所有事件启用。
- 不在白名单内的项目任务 / subject 每次提交都应形成独立任务，不得意外合并。
- 不同项目的事件不得因为 subject 文本相同而合并。
- 同一项目连续提交的任务，根据其是否命中允许合并的配置决定是否合并。
- 合并范围和键至少应明确项目身份与 subject，避免跨项目碰撞。

待验证：Autoloop 的 subject / lane / event 去重机制是否支持该白名单策略；若不支持，评估最小适配，不先假定需要自建第二套队列。

### 2.3 项目内部重试保留原任务位置

**用户确认：**
- 重试策略由项目自身决定，调度层不负责业务任务失败后的自动重派。
- 项目等待重试时，视为原任务 A 尚未完结。
- A 保留原任务身份和队列位置；等待期间不重新入队，不生成一个排到队尾的新任务。
- B、C 等后续任务不能因为 A 的内部重试而改变彼此顺序。
- Autoloop 通用 failed 自动重派机制应关闭或移除，不能覆盖项目自己的重试、停止和安全策略。

需要区分：
- **项目业务重试**：项目流程的一部分，仍是原任务。
- **调度基础设施恢复**：例如调度服务重启后恢复尚未执行的持久队列；这是调度状态恢复，不是重跑业务失败任务。
- 对已经开始执行、结果不明的任务，不能仅因调度服务恢复就盲目重新执行。

### 2.4 人工占用是排队中的无限期桌面占用任务

**用户确认：**
- 用户点击“我要操作桌面”时，调度层创建一个人工占用任务，放在当时队列的最后。
- 现有队列任务先按顺序完成；轮到人工占用任务后，桌面转为人工占用。
- 人工占用没有自动结束时间；除非用户主动释放，否则后续进入的任务全部排在它后面。
- 用户释放后，人工占用任务结束，队列继续按顺序执行。
- 这不是一个绕过队列的即时全局暂停开关，也不能抢占正在执行的任务。

Autoloop 是否能可靠承载长期运行的人工占用任务、心跳和人工释放机制，待验证。

### 2.5 错过定时任务不补跑

**用户确认：**
- 电脑休眠、服务离线等原因错过的定时触发不自动补跑。
- 恢复后不创建历史积压任务。
- 如果确实需要执行，由用户人工指定新增相关任务。
- 具体时区、各项目定时入口和旧定时器停用方式留到任务入口映射阶段。

### 2.6 调度服务离线与执行任务卡死分开处理

**用户确认：**
- **调度服务离线 / 请求无响应：**项目提交任务请求后没有收到调度层确认，任务不应被视为已创建或已进入队列。请求是否被接收必须有明确响应边界。
- **调度层在线、任务已接收，但执行端无响应：**这才是任务运行异常，需要进行健康检测。
- 健康检测不能只看进程 PID 是否存在，还要判断项目执行服务是否真正可响应。
- 若检测到服务仍存活但没有响应，应报告异常并按安全策略关闭对应执行服务。
- 只有确认旧执行端及其可能继续操作桌面的进程确实失去操作能力，才能释放桌面。
- 状态不明时宁可保持占用、报警并等待人工确认，不能猜测任务已经结束。

**待具体设计：**
- 参考售后当前的异常检测、进程状态判断和服务关闭方式。
- 根据各项目实际运行结构判断健康检查信号，不预设统一超时时间。
- 研究调度服务、项目 server、runner 和可能的子进程之间的存活关系。
- 机器整体死机后重启与“服务仍活着但任务卡死”是不同故障场景，检测与恢复不能混为一谈。
- 不把“进程查不到 / 检查命令失败”直接解释为“旧任务已经安全停止”。

### 2.7 当前群聊分析按整个项目脚本作为一个桌面调度任务

**用户确认：**
- 当前版本先把群聊分析的整个项目脚本放在桌面调度层中执行。
- 即使采集结束后的 GPT 语义分析、整理和输出不需要鼠标，也暂时不拆分；整个脚本完成后才向调度层报告结束。
- 当前状态岛只显示桌面调度，不额外显示后台占用状态。

**未来理想形态（不是当前实施范围）：**
- 群聊流程可拆为桌面阶段“采集 → 释放桌面”和后台阶段“分析 → 输出 → 完成”。
- 桌面调度和后台调度分别管理各自资源。
- 状态岛未来可以同时展示桌面占用和后台处理状态。
- 目前不为这个未来形态提前建设后台调度系统。

## 3. 状态岛与调度层的职责边界

- Autoloop / 经验证的调度内核维护唯一权威桌面任务队列和桌面 owner。
- 项目负责业务执行、进度、内部异常和最终任务结果。
- Status Island / Codex Monitor 读取调度层状态并展示，不维护第二份队列真值。
- 状态岛展示的任务最终状态跟随项目反馈；内部异常作为独立事件显示。
- 项目自行决定是否创建 Reminders 等额外通知；状态岛显示异常不等于自动创建提醒。
- 当前版本不展示后台资源占用；整个群聊脚本仍作为一个桌面调度任务。
- 保留 Codex Monitor 原有本地用量统计、5 小时 / 周限额和限额倒计时，不因自动化状态扩展而删除。

## 4. 改造原则

1. **迁移职责，不重写稳定业务。**先把原队列管理与执行逻辑拆分清楚，再决定最小改动方式。
2. **唯一队列真值。**旧项目不得继续保留第二份权威待执行队列；状态岛也不得自行维护队列副本。
3. **项目拥有业务流程。**调度层不理解项目内部业务异常、不替项目决定重试，也不覆盖项目安全门禁。
4. **任务状态与异常事件分离。**一个任务可以成功完成，同时留下一个或多个内部异常事件。
5. **桌面安全优先。**未确认旧执行端失去操作能力之前，不释放桌面。
6. **当前只做桌面调度。**后台分析等非桌面工作暂时随完整项目脚本一起执行，不提前扩展为多资源调度。
7. **逐项讨论和验证。**每个阶段先解释现状、确认方案，再实施和反查；未获确认不直接改生产入口。

## 5. 尚未决定或必须验证的事项

- 固定采用的 Agent Autoloop 版本、部署方式、运行时隔离和持久化位置。
- Autoloop 是否能保证跨规则严格 FIFO，以及同秒任务的可接受排序语义。
- 指定项目 / subject 合并白名单如何映射到 Autoloop 的 subject、lane 和 event id。
- 如何可靠关闭通用失败自动重派，同时保留队列持久化和调度服务重启恢复。
- 人工占用长任务的心跳、释放和重启恢复行为。
- 调度请求的接收确认、重复提交幂等和“未确认是否入队”的处理。
- 各项目具体任务入口、任务粒度、定时触发和桌面 / 后台分类。
- 项目紧急停止信号、项目级待执行任务清理、任务终态映射和桌面释放时机。
- 执行端健康检测、进程组检查、服务关闭、恢复顺序、持久 desktop lease 和未知状态处理。
- 项目进度、内部异常事件和最终任务结果的具体数据结构。
- 状态岛的收起态 / 展开态、状态优先级、异常详情、人工占用交互和售后 HUD 合并。
- Tk + AppKit 与 NSPanel + SwiftUI / AppKit 的技术比较；不预设重写。
- 每个项目按真实场景制定的验收标准；不使用一张抽象通用表代替项目验收。

## 6. 下一阶段顺序修正

原有 Codex Monitor 待办倾向于下一步直接开展 Status Island 产品界面设计。经过本轮适配层和桌面调度讨论，建议调整顺序：

### 第 3 阶段：任务入口与触发源映射（下一阶段）

先盘点每个项目的真实任务入口和触发来源，至少包括：
- 页面按钮 / HTTP API / 批量操作；
- CLI 与独立命令；
- 登录、重新登录和启动时检查；
- cron / setTimeout 等定时任务；
- 农场 Runner、群聊采集脚本等项目执行入口；
- 哪些步骤实际控制桌面，哪些仅是后台处理。

对每个入口确认：
- 是否进入桌面调度；
- 任务粒度和任务名称；
- 是否属于允许合并的项目 / subject；
- 是否是一个完整项目脚本，还是可安全区分的子任务；
- 请求是否得到调度层接收确认；
- 定时任务的时区、错过触发不补跑、人工补发方式；
- 旧定时器、skipNextScan 等现有行为如何保留或退役。

当前阶段先做映射和讨论，不安装 Autoloop、不修改生产入口。

### 第 4 阶段：停止、失联、恢复与崩溃安全

详细讨论项目停止、项目级队列清理、执行端健康检查、旧进程确认、调度服务 / Worker / 项目 server 重启顺序、桌面占用恢复，以及未知状态下 fail-closed 的具体规则。

### 第 5 阶段：项目状态反馈协议与逐项目验收

根据真实入口和生命周期，确定 progress、internal incident、final result 的最小数据结构；按售后、农场、群聊等项目及其实际操作场景制定验收步骤和通过条件。

### 第 6 阶段：Status Island 产品形态与 UI 技术选型

在任务来源、状态和数据协议明确后，再设计收起态、展开态、队列展示、人工占用交互、异常展示、用量倒计时和售后 HUD 合并；随后比较 Tk + AppKit 与 NSPanel + SwiftUI / AppKit。保留现有统计核心，不预设重写。

后续再制定分阶段实施、低风险试接入、生产迁移和旧入口退役计划。每个阶段均需单独确认与验收。
