# CodexPro 大文件读取修复归档

本文件保存历史问题与验证证据；后续操作以[启动脚本](../../../scripts/start-codexpro-full.sh)、[现役补丁](../../../scripts/lib/ensure-codexpro-paged-read.mjs)和[回归测试](../../../test/workspace/codexpro-paged-read.test.mjs)为准。

## 问题与根因

在 CodexPro 0.28.5 的近期请求中，同一个 71,807 字节文件先后使用 `max_bytes: 50000`、`max_bytes: 30000` 读取，两次均返回文件大小错误。HTTP 状态仍为 200，工具结果通过 `isError: true` 表示失败。

原实现把 `max_bytes` 当作整个源文件的大小门槛，并在按行截取之前检查。GPT 为缩小返回内容而降低参数时，反而降低了文件准入门槛；缩短行号范围也不能解除错误。这两条证据属于同类实际失败，未据此声称已取得用户提到的 registry 原始失败请求。

## 本阶段交付

- 仅为公开 `read` 工具增加分段读取：`max_bytes` 限制本次带行号正文的 UTF-8 字节数，不代表 MCP 总响应大小。
- 一页装不下时只返回完整行，并通过 `nextStartLine` 和正文提示给出续读位置。GPT 继续调用原来的工具即可，行为不依赖会话记忆或额外策略。
- 源文件安全上限为 2,000,000 字节；单行本身超过返回预算时明确报错并提示提高预算或按键提取。未把截断内容伪装成完整文件。
- 内部规则加载、写入校验及路径、敏感文件、二进制保护沿用原实现。
- `start-codexpro-full.sh` 启动时自动检查并应用本地补丁；遇到不匹配的源码结构会停止补丁写入，不猜测修改新版代码。

用户将范围收敛到大文件读取。连接失败未在本轮定因，未修改并发、重试、会话或网络机制，也不把本机另一条 Codex CLI 调用链的报错当作 CodexPro MCP 根因。

- 安装后的两份 JavaScript 语法检查、启动脚本语法检查与 Git 空白检查通过；重复执行补丁没有重复插入。

- 实际服务已返回新版工具说明及续读提示。验证没有另起服务，临时 MCP 会话已显式关闭。
