# 定时任务时间设置与核验

本页是工作区跨项目定时任务的唯一时间规则 owner。项目仍自行维护成熟时间、避让窗口、业务执行顺序和续排条件；这里只负责目标时间表达、工具时区适配和排期落地核验。

## 一句话硬规则

**任何定时任务都必须先把目标保存为完整日期时间和 IANA 时区，再用 Python `datetime` / `zoneinfo` 按实际工具语义转换；创建或修改后必须读回实际下一次触发时刻核对，禁止心算时区、固定减 8 小时或只凭成功回执认定正确。**

## 目标时间

- 目标记录使用 `YYYY-MM-DDTHH:mm:ss` 加 IANA 时区，例如 `2026-11-13T14:02:00 + Asia/Shanghai`。用户明确指定的时区优先；未指定时按当前客户端默认 `Asia/Shanghai`。这只是目标时区，不代表所有工具都用同一时区格式或固定偏移。
- 转换使用 Python 标准库 `datetime` 和 `zoneinfo`；不做字符串改小时或模型心算。目标已过去时拒绝新建，不自动补跑或改期。
- 其它时区遇到夏令时不存在或重复的本地时刻时，必须停止并要求明确时刻；不得自行选择 fold。
- 一次性任务明确目标日期、时区、`COUNT=1`（工具支持时）及有效执行窗口/截止时间。错过窗口就报告跳过，不补跑、不自动顺延。

## 工具语义适配

### Codex 本机 cron（按农场现役经验）

- 当前本机调度器的 `RRULE` 时间字段按 UTC 解释。农场第一次晚 8 小时，是把本地时刻直接写入 UTC 规则；后来已改为 `datetime/zoneinfo` 转 UTC，并读回 `next_run_at` 回转本地核验。当前农场数据库的 `BYHOUR=6` 对应北京时间 14 点，`BYHOUR=14` 对应北京时间 22 点。
- 群聊事故中的 `BYHOUR=1` 实际在 UTC 01:00 触发，即北京时间 09:00。该次只读回规则、未核验 `next_run_at`，因此没有及时发现偏移。
- 该 heartbeat 已删除，原始调度记录不存在；这里只能确认本次触发行为与 UTC 解释一致，不把它扩展成所有 heartbeat 接口的无条件契约。群聊一次性任务 `11-13-01-00` 绝不恢复。
- 目标先按 IANA 时区转换为 UTC，再按官方工具 schema 生成规则。现有 `FREQ=YEARLY;BYMONTH;BYMONTHDAY;BYHOUR...` 规则本身不含年份；完整目标日期和 IANA 时区必须保留在项目 CURRENT 或 job 记录中。ACTIVE 的实际 `next_run_at` 才能核实年份。
- 所有定时任务必须通过正式、可持久化的调度入口创建；创建 cron 时若工具 schema 支持 `durable: true`，必须显式设为 `true`。若工具没有该字段，不猜参数、不改底层配置，按其正式持久化契约执行并读回核验；无法确认持久化状态时不得报告已可靠安排。
- 创建、更新、暂停、删除只调用官方 automation 工具。禁止直接写 `automation.toml` 或 SQLite。

### Mac 提醒事项

- Mac 提醒事项不在本页重复定义时间和创建流程，统一沿用现有 [docs/reminders.md](reminders.md)；其中已明确输入时间按 Mac 本地时间解释，并规定了快捷指令发送与结果读回。

## 排期落地核验

- **Codex 本机 ACTIVE**：只读读取 `file:/Users/chat/.codex/sqlite/codex.db?mode=ro` 中指定任务的 `status`、`rrule`、`next_run_at`。当前 `next_run_at` 为 Unix 毫秒时间戳；必须用 `datetime.fromtimestamp(next_run_at / 1000, timezone.utc)` 转换到目标 IANA 时区，与目标精确一致。ACTIVE 缺少 `next_run_at`、时间不符或 schema 变化均视为未验证并停止判断。
- **Codex 本机 PAUSED**：若没有 `next_run_at`，只能核对候选规则；不得声称已进入执行队列或已验证实际触发。由于规则不含年份，PAUSED 也不能仅凭 RRULE 声称目标年份已验证。
- SQLite 只读读取遇到数据库不存在、表/字段变化或查询失败时，明确报告失败，不猜 schema、不改库。查询只针对已知任务 ID，不枚举个人无关任务。
- 新建/修改任务经核验不匹配时，必须通过官方工具暂停该任务并报告；本次只读盘点的既有任务只报告，不擅自暂停或重排。
- 工具返回“创建成功”只证明配置请求被接受，不证明排期正确；任务配置读回也不等于业务已经执行。

## 业务执行边界

任务真正开始时，仍须核对当前真实时间、有效执行窗口和必要互斥条件。提示词写明“北京时间”不能替代调度器排期核验；开工时的时间保护也不能替代创建后的排期读回。

本次不新增调度器、daemon、任务创建器或独立辅助脚本。现有官方工具、Python 标准库和只读证据已足够；离线测试使用临时 fixture，不创建会触发真实业务的测试任务。
