## 结论

Claude 的 7 项计划需要按用户原话进一步收紧。核心不是“补 fruit 数据”，而是纠正任务边界：

> 任务只代表世界图鉴里的课题任务。任务来源只能是 `课题进度` sheet，且要排除 `异色` 行。`果实进度`、`多形态进度`、`pets.json.forms` 都不能反向生成任务，只能在已有任务上补充达成方式。

用户口径里 `fruit` 不是一类泛化收集物，说人话就是“精灵果实课题任务”，即“捕捉 20 只获得果实”。游戏里每个家族可能有果实，但不是每只精灵、每个形态、每个进化阶段都有果实课题任务。

## 逐条审计

### 1. 删除 256 条错误 fruit 任务：方向正确，但删除依据要改

不要把删除条件写成“凡是 `desc !== "捕捉20只精灵"` 都删”这种纯文案判断。更安全的口径是：

1. 从 Excel `课题进度` sheet 建立任务白名单：排除 `异色`，其余任务逐行对应。
2. `tasks.json` 中不在白名单里的任务删除。
3. 当前多出来的 256 条已实证都是 `type="fruit" && desc="获得果实"`，可以作为本轮删除对象。

原因：用户强调“是否有果实任务以课题进度里的任务列表为准”。所以判断任务存在与否必须回到 `课题进度`，不能用 `果实进度`、`pets.fruit`、进化链终点或描述字符串推导。

删除后应满足：

- `tasks.json` 总任务数 = 1848
- 精灵果实课题任务 = 96
- `type="fruit" && desc="获得果实"` = 0
- `pet_239`、`pet_240` 不是最终形态，当前没有 fruit 任务是正确的

### 2. 合并首领/多形态获取方式到任务 obtainMethods：只能补现有任务，不能生成任务

这个计划原方向可以保留，但必须加约束：

- `obtainMethods` 是任务达成方式，不是任务来源。
- `果实进度` / `多形态进度` / `forms.*.obtainMethods` 只能给已经存在于 `课题进度` 的任务补说明。
- 不允许因为某个 form 或某个 fruit 存在，就新增任务。

#### 2a. `leader_evolve`

- 当前 27 个 `leader_evolve` 任务已经都有 `obtainMethods`。
- 可以和 `pets.json.forms.leader.obtainMethods` 做去重合并，但只写回对应的 `leader_evolve` 任务。
- 不要在前端保留独立“首领形态获取方式区”。用户要求获取方式只显示在对应任务后面。

#### 2b. `confirm_forms`

- 当前 51 条 `confirm_forms` 与 `课题进度` 的 51 行“形态”一致。
- 可以把 `多形态进度` E 列捕捉方式展开进 `confirm_forms.obtainMethods`，但必须带形态名，例如：`夏天的样子：果实放入眠枭庇护所后可捕捉...`。
- 展开范围必须受 `课题进度` G/I 列约束。像鸭吉吉这种任务只确认 2 种样子，即使表里还有其他样子，也不能让用户误以为全部都算任务进度。
- 不要把 `forms.leader` 合入 `confirm_forms`。首领对应的是 `leader_evolve` 任务。

#### 2c. 精灵果实课题任务的获取方式

- `pet_241` 龙鱼已有正确 fruit 任务，但当前缺 `obtainMethods`，应补为 `捕捉20只龙鱼`。
- 这里可以参考 `果实进度`，但只能用于“已有 fruit 任务的达成方式补充”，不能用于给 `pet_239`、`pet_240` 或其他家族成员新增 fruit 任务。

### 3. 补 3 只 boss 标签：正确

缺失项：

- `pet_4` 魔力猫
- `pet_107` 罗隐
- `pet_233` 高脚鹬

补完后 `tags.boss` 数量应从 24 变为 27，与 `forms.leader` 数量闭合。首领标签是稀有度/状态标签，不是独立形态展示区。

### 4. 前端任务分类重构为 3 类：正确

用户明确要求只分 3 类：

- 捕捉
- 奖牌：仅 `destined_hero`
- 技能：仅 `skill`

归类规则：

- 捕捉：`capture`、`capture_gifted`、`capture_chromatic`、`fruit`、`confirm_forms`、`evolve`、`leader_evolve`、`affection`
- 奖牌：`destined_hero`
- 技能：`skill`

这里的“捕捉”是页面展示分类，不是严格数据语义。用户要的是减少前端认知负担，不再展示“进化 / 形态 / 果实”等额外大类。

### 5. 任务行展示 obtainMethods：正确

当前 `index.html` 的 `renderSpriteCard()` 只展示任务描述，没有展示 `t.obtainMethods`。

要求：

- 获取方式显示在对应任务行后面。
- 必须 HTML 转义。
- 不要新建独立“获取方式区”。
- 对用户展示时建议写“达成方式”，不要直接暴露 `obtainMethods` 这种字段名。

### 6. 移除形态独立展示区：正确，并同步处理 header

当前 `renderSpriteCard()` 会遍历 `pet.forms` 输出 `.form-label`，这与用户要求冲突，应移除。

同时卡片 header 中的 `${formCount}形态 · ${totalDone}/${tasks.length}` 也应改掉。用户说“精灵下面不需要单独显示基础形态/首领形态/多形态等”，前端不应继续强调形态数量。建议只显示任务进度：`${totalDone}/${tasks.length}`。

保留进化链展示可以接受，因为进化链不是“形态区”；但不要把首领/多形态获取方式放在那里。

### 7. 首领标签位置优化：作为 UI 细节处理

用户目标是：魔力猫等首领标签要和系别、异色、炫彩标签同组展示，不要在形态区里单独展示。

因此关键是：

1. 补齐 `tags.boss`。
2. 移除独立 forms 展示区。
3. 保证前端 tags 渲染把 `首领 / 异色 / 炫彩` 放在同一标签组。

`span` 是否从元素标签中移出不是硬性数据要求，只要视觉上同组展示且不再依赖形态区即可。

## 必须同步修正的文档口径

`lkwj/SKILL.md` 里的“精灵果实（fruit 任务）354 只”是错误口径，会继续误导后续 agent。
