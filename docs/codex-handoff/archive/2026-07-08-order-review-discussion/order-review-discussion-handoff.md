## 一句话结论

这个项目本质上是一个新的「审单系统」，最终目标可以是审单自动化；但当前阶段不是自动执行、不是批量处理、不是置信系统设计，而是先把第一部分做出来：在 ERP 待审核订单里，只读获取当前订单信息，分析订单结构，显示判断信息和建议操作，并尽可能给出能帮助用户筛选同类订单的筛选条件。

当前不要设计自动审核、自动合单、自动拆单，也不要预设自动化释放门槛。后续是否加入「手动点击后脚本执行」或「自动系统 / 置信系统」，要等第一部分实际做出来、看清 ERP 页面结构和审单信息后再讨论。

## 用户修正后的真实目标

用户确认：项目本质上仍然需要「自动审单」。此前之所以看起来不适合直接自动化，不是因为用户不需要自动审单，而是因为订单审核情况过于复杂，用户暂时无法建立一套机械、可重复、可复用、可提前完整描述的规则。

因此，项目路线应参考售后系统：

1. 初期不自动处理。
2. 先只输出判断、分析信息和建议操作。
3. 用户人工判断是否应该处理，并手动在 ERP 中操作。
4. 在系统稳定、信息读取足够清楚、用户实际使用一段时间后，再讨论是否加入「点击后脚本自动操作」。
5. 更后面才考虑自动审单系统和置信系统。

这意味着当前阶段的任务不是设计完整自动化，而是建设审单系统的第一部分能力。

## 当前阶段范围：第一部分

第一部分只做「单订单 / 当前订单」维度的只读分析和信息展示。

这里的「单订单」不是说项目最终只能处理单订单，而是指当前阶段以用户正在查看或选中的订单作为分析入口。后续是否扩展到批量订单，要等第一部分实际落地后再判断。

第一部分包含以下能力：

### 1. 当前订单读取

从 ERP「订单处理 / 待审核订单」中读取用户当前关注的订单信息。优先只读，不点击任何会改变业务状态的按钮。

需要研究和读取的信息包括但不限于：

- 订单行基础信息
- 订单号 / 平台交易号等可见标识
- 店铺
- 仓库
- 商品简称
- SKUID
- 商品数量
- 是否存在赠品 / 满赠表现
- 付款时间
- 承诺发货时间
- 剩余小时
- 收货信息摘要
- 买家留言 / 卖家备注 / 异常提示
- 商品明细入口能否稳定展开

当前不要假设所有字段都一定能读到。Codex 应先研究页面结构，以实际 DOM 为准。

### 2. 当前订单结构化分析

把 ERP 页面中分散、难读的信息整理成适合人工快速判断的订单结构。

目标不是替用户最终决策，而是降低用户审单时的脑力负担。

示例输出方向：

- 当前订单包含哪些商品
- 每个商品的 SKU / 简称 / 数量
- 是否存在赠品
- 赠品和主品的数量关系
- 是否可能是活动组合
- 是否存在数量异常
- 是否存在备注 / 留言 / 时间 / 仓库等需要人工注意的信息
- 是否可能需要合单、拆单或保持当前状态

### 3. 审核建议展示

系统可以给出建议，但建议必须是「显示给用户参考」，不是自动执行。

建议类型可以先保持开放，不要过早固化为完整规则引擎。初期可以包括：

- 倾向直接审核
- 倾向保持当前子订单原样
- 可能需要合单
- 可能需要拆单
- 需要人工确认
- 信息不足，无法判断
- 存在异常，建议不要自动处理

当前阶段不要把这些建议绑定到真实点击动作。

### 4. 同类订单筛选条件展示

这是本次方向修正后新增的关键能力。

当用户查看一个订单时，系统不仅要分析这一单，还应尽可能展示：如果用户想在 ERP 中找到同类订单，可能应该使用哪些筛选条件。

可展示的筛选条件方向包括：

- 仓库
- 店铺
- 商品简称
- SKUID
- 时间范围
- 当前活动相关商品集合
- 是否包含赠品
- 数量特征
- 是否排除未知 SKU / 异常备注 / 异常留言

这里的目标不是让系统立即批量处理，而是帮助用户从当前单反推出「如何筛出同类订单」。这可以为后续批量审单能力提供基础，但当前阶段只做显示，不做批量执行。

### 5. 用户人工判断与反馈

第一部分做出来后，用户仍然人工完成审单操作。

系统可以在后续记录用户对建议的反馈，例如：

- 建议是否正确
- 用户最终是否审核
- 用户最终是否合单
- 用户最终是否拆单
- 用户是否认为该组合以后可以复用

但反馈记录和经验沉淀也不应一开始设计得过重。先以第一部分的信息展示和分析准确性为核心。

## 当前明确不做

当前阶段明确不做以下内容：

- 不做自动审核
- 不做自动合单
- 不做自动拆单
- 不做提交、确认、保存等会改变订单状态的操作
- 不做批量处理设计
- 不做自动化释放门槛设计
- 不做置信系统设计
- 不做完整规则引擎
- 不要求用户提前描述完整审单规则
- 不设计动作落地路径
- 不假设 ERP 能还原平台主订单

原因：当前获取到的 ERP 审单信息仍不完整。在第一部分只读分析和显示信息做出来之前，提前设计动作落地路径、自动化释放顺序或批量处理方案都不可靠。

## ERP 业务背景

用户主要在快麦 ERP 的「订单处理 / 待审核订单」标签页进行审单。

活动期间，一个活动可能涉及几十个 SKU。审单不是固定流程，而是根据当时活动组合、仓库、商品简称、SKUID、时间、数量、赠品等条件不断筛选和判断。

常见筛选条件包括：

- 仓库
- 商品简称
- SKUID
- 时间
- 当前活动组合相关的商品集合

审单判断的核心不是单纯审核按钮，而是：

- 是否需要合单
- 是否需要拆单
- 是否保持 ERP 当前子订单原样发货
- 数量是否合理
- 满赠赠品是否应该和购买商品合并发货
- 某些组合是否受箱规影响，需要拆成多个包裹

## 已知关键约束

### ERP 视角只有子订单

平台里一个客户看到的是一个主订单，但 ERP 里每个不同 SKU 对应一个独立子订单。

ERP 中没有稳定字段能把多个子订单关联回同一个平台主订单。也就是说，当前不要假设系统可以在 ERP 内可靠判断：

- 哪几个子订单属于同一个平台主订单
- 哪个购买子订单对应哪个满赠子订单
- 主订单和子订单之间的完整关系

实际审单中，用户通常也不会核对子订单和平台主订单的对应关系。

### 满赠在 ERP 中表现为独立子订单

如果客户购买商品触发满赠，ERP 中通常表现为：

- 一个子订单是客户购买的商品
- 另一个子订单是满赠赠品

用户需要根据实际商品和数量判断：

- 合并订单发货
- 拆分订单发货
- 保持子订单原样发货

### 合单 / 拆单能力暂不进入当前设计

原交接文件记录过：ERP 中可用的合单方式主要包括人工指定订单合单，以及批量核单按姓名、手机号、收件地址完全一致合并。

但当前阶段不设计合单 / 拆单动作落地路径。原因是：在只读读取和分析能力完成前，现有 ERP 审单信息不足以可靠设计后续动作。

后续如果进入「点击后脚本操作」或「自动处理」阶段，再重新研究 ERP 的真实操作入口。

## 已检查到的 ERP 页面事实

当前浏览器中存在 ERP 标签页：

- 标题：`快麦ERP--待审核订单`
- URL hash：`#/trade/toaudit/`
- 所属标签：订单处理 / 待审核订单

页面结构初步观察：

- 订单行不是标准 `el-table` 表格，而是 `.module-trade-list-item`
- 当前可见约 9 条待审核订单行
- 每行包含复选框、订单号链接、商品种类链接、快递模板、运单号区域、备注、留言、`审核`动作、收货信息、金额、付款时间、承诺发货时间、剩余小时
- 筛选区包含仓库/店铺/订单号/平台交易号/时间/快递单号/SKUID/达人信息/每页数量等控件
- 下拉框不是所有都能通过标准 `.el-select-dropdown__item` 直接读取，后续若做页面助手需要单独适配

安全边界：

- 目前只允许只读 DOM 检查
- 不点击 `审核`
- 不提交、合单、拆单或修改任何订单

## 给 Codex 的当前研究任务

如果现在重启项目，不要先写完整项目，也不要先设计自动化流程。先研究第一部分。

建议 Codex 先做只读研究：

1. 打开或定位当前 ERP「待审核订单」页面。
2. 研究订单行 DOM 结构，确认 `.module-trade-list-item` 下可稳定读取哪些字段。
3. 研究商品明细入口是否能稳定展开。
4. 研究展开后能否读到商品简称、SKU、数量、赠品标识。
5. 研究当前订单信息能否整理成结构化 JSON。
6. 研究如何根据当前订单信息生成「同类订单筛选条件展示」。
7. 只输出读取结构、字段、限制和建议的数据形态，不做任何真实订单操作。

当前产物目标不是自动审单，而是为第一阶段 UI / 面板提供可靠数据基础。
