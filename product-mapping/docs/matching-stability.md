# 商品匹配稳定性手册

这份文档解决一个问题：自动匹配重复运行时，怎样区分“应该立即修的安全缺陷”和“可以先观察的 ERP 页面变化”，并在中断后安全恢复。

## 1. 第一性原理

商品匹配不是一串互不相关的点击，而是一个有状态的写入流程。判断成功不能看“点击函数是否返回”，只能看 ERP 是否进入了预期状态，并在最终 `check` 中与已确认识图结果完全一致。

单个套件 SKU 的最小状态机：

```text
未处理
  → 已精确定位目标货号和 platformCode
  → 已清除其他 SKU 勾选
  → 已标记套件（出现“复制为套件”）
  → 选择商品弹窗内部选择数已归零
  → 本次子品全部加入
  → ERP 确认成功并生成 erpCode
  → check 回读档案
  → 识图明细与 ERP 明细完全一致
```

任何中断都要从 ERP 当前可观察状态继续，不能假设上一次要么全成功、要么完全没发生。

## 2. 故障优先级

| 优先级 | 判断标准 | 处置 |
|---|---|---|
| P0：立即停止并修 | 可能选错 SKU、带入旧子品、重复写入，或脚本把未验证的点击当成功 | 停止整批；修复后先用 1 个 SKU 实测，再续批量 |
| P1：本轮修复 | 不会写错商品，但会阻塞批量、污染后置核查或让进程长期占锁 | 修复并做局部回归；确认锁和页面状态恢复 |
| P2：记录观察 | ERP 文案、选择器或特殊提示发生变化，但 stop-on-error 已阻止写入 | 记录复现条件；出现第二次或影响常规路径时升为 P1 |

### P0 典型信号

- 本轮品牌缺失，或报告、sku-records、命令指定品牌不一致；
- 自动流程试图修正、换绑或覆盖已有匹配异常；该操作必须由用户在平台人工完成；
- 目标行勾选数不是 `1`；
- “已选择商品”不是 `0` 就开始添加本次子品；
- 精确商品名不存在或存在多个无法消歧的候选；
- 中断后重复执行“标记套件”，没有识别已有“复制为套件”；
- ERP 已确认，但没有生成 `erpCode`；
- 最终 `comparisonMismatch > 0` 或 `comparisonPending > 0`。

### P1 典型信号

- `match` 被无关的鲸灵标签页缺失阻塞；
- ERP 锁未在 `finally` 中释放；
- 后置 `check` 重复下载平台商品，或复用范围与原范围不一致仍继续；
- 只读对应表继承旧筛选/旧页码，导致少读、漏读或重复读。

### P2 典型信号

- ERP 新增仅在特殊订单状态下出现的确认弹窗；
- Element UI 类名或按钮文案变化，但定位失败后没有执行确认；
- 某个历史品牌特例未在当前活动触发。

## 3. 已固化的防护

### 3.1 依赖按实际动作拆分

- `match` 只依赖 ERP，用 `getErpTargetId()`，不要求鲸灵标签页存在。
- `check --reuse-active --skip-download` 只依赖 ERP；它会用上一份报告与当前
  `sku-records.json` 精确核对 `productCode + platformCode` 商品链接集合。
- 新活动首次 `check` 才需要鲸灵当前店铺页面。

人话：已经确认过的活动范围不会因为一个无关标签页没开而无法继续，也不会偷偷换成另一批 SKU。

### 3.2 品牌必须显式且贯穿整轮

首次运行使用 `check --shop <店铺> --brand <品牌>`。品牌写入报告和每条 SKU 记录；
preview、match、匹配前/后的 check 自动继承。品牌缺失、未知、混入多个品牌或前后不一致时，
必须在 ERP 写入前停止，禁止默认猜成 kgos 或 hee。

### 3.3 商品链接必须按货号与规格编码联合识别

ERP 中不同活动链接可能复用同一个 `platformCode`，例如折扣/免费入口或秒杀/常规入口。
因此运行态记录、活动范围和断点日志的唯一键必须是：

```text
productCode + platformCode
```

图片按 `data/imgs/{productCode}__{platformCode}.jpg` 保存，让每个商品链接拥有独立图片证据；
每个链接还必须独立保存识图结论、读取对应表绑定状态并参与最终比较。只按 platformCode 去重会
把多个活动链接覆盖掉，造成漏匹配或错误地提前判定完成。

重复 platformCode 还是一组主动交叉校验信号：

- 两张链接图一致且 ERP 明细一致：两个链接都可通过；
- 两张链接图不一致但 ERP 明细相同：至少一个链接复用了错误的 SKU 编码；
- 两张链接图一致但 ERP 明细不同：至少一个链接的 ERP 对应关系错误；
- 两张链接图与各自 ERP 明细分别一致：两个链接独立通过，即使 platformCode 相同也不能合并。

因此重复编码不能被当作待清洗的重复数据；必须保留两条链接证据，才能发现已经存在的错误绑定。

### 3.4 对应表按货号搜索

当前 ERP 实测中，`.el-input-popup-editor input` 输入 `productCode`（货号）能定位产品行，
输入 `platformCode` 返回 0 行。展开后再用子行 `tds[5]` 精确匹配 platformCode。

这条与 2026-05-27 的历史观察相反，说明 ERP 搜索维度发生过变化。代码和文档必须以当前
页面实测为准；再次出现 0 行时，应先做同页 A/B 探针，不要直接沿用旧结论。

### 3.5 下拉菜单必须绑定到当前触发按钮

“套件处理”由 Element UI 动态生成菜单，后台标签页的展开动画可能停在 `height=0`：

1. 找到当前可见的“套件处理”按钮并触发；
2. 读取按钮的 `aria-controls`；
3. 用该 ID 精确定位所属菜单并点击“标记套件”，不扫描其他隐藏菜单；
4. 点击后等待目标 SKU 行出现“复制为套件”。

只有第 4 步成立才算标记成功。

### 3.6 选择状态必须同时清 DOM 和 Vue

“选择商品”弹窗使用 `v-show`，关闭后组件没有销毁。当前 DOM 只显示一个勾选项时，
`TableItem.multipleSelection` 仍可能保留上一 SKU 的隐藏选择。

正确顺序：

1. 等第一个子品搜索结果和初始化 watcher 稳定；
2. 调用 `TableItem.clearSelection()`；
3. 调用 `TableItem.updateCheckRows([])`；
4. 验证界面显示“已选择商品：0”；
5. 再选择本次商品。

只点当前页面已勾选的 checkbox 不足以清理内部状态；清得过早也会被 watcher 灌回旧值。

### 3.7 重试必须识别中间状态

若 SKU 已出现“复制为套件”，说明“标记套件”已经成功。重试应直接继续配置子品，
不能再次标记。每次标记前还必须先清除展开区全部已勾选项，再精确勾选目标行，并验证
`selectedCount === 1`。

### 3.8 只读核查也要重置页面

读取对应表前：

1. 重置筛选下拉；
2. 等输入框异步重建后重新查询 DOM；
3. 再次清空输入框并触发搜索；
4. 强制回到第 1 页；
5. 用 ERP 实时总条数和 pageSize 计算总页数；
6. 每次翻页验证 active 页码。

禁止依赖 `btn-next.disabled` 判断最后一页。

### 3.9 进程退出必须释放 ERP 锁

所有持锁入口都要在 `finally` 调用 `releaseErpLock()`。无论成功、异常还是 stop-on-error，
都不能让售后项目继续保持暂停状态。

### 3.10 保存确认必须等待业务状态

“选择商品”点确定后，ERP 关闭弹窗的时间会随负载变化。不能固定等待 2 秒后只检查一次：

1. 最多轮询 10 秒；
2. “选择商品”弹窗关闭，表示新套件保存已被接收；
3. “换对应商品”弹窗出现，表示 ERP 找到同比例套件并进入换绑选择；
4. 两种状态都未出现才判为超时。

这样可以避免 ERP 已保存、脚本却误报失败并诱发重复写入。

### 3.11 档案回读必须精确命中查询编码

商品档案 V2 返回多行时不能默认取第一行。主商家编码必须精确匹配 `outerId`；规格商家编码
回退必须在返回对象中找到查询编码。子品弹窗第一次返回空明细时关闭后重试一次，避免把页面
瞬态未加载误判为真实空套件。

## 4. 中断后的恢复顺序

1. 确认没有另一个 product-mapping Node 进程正在操作同一 ERP 标签页。
2. 查看失败 SKU 当前 ERP 行：
   - 已有 `erpCode`：不要自动换绑或覆盖；报告差异并等待用户人工修正，完成后只回读；
   - 无 `erpCode`、已有“复制为套件”：从配置子品继续；
   - 两者都没有：从标记套件开始。
3. 关闭或刷新残留弹窗，保证只存在本轮目标弹窗。
4. 用单个失败 SKU 验证修复。
5. 再运行整批 `match`。
6. 最后运行：

```bash
node cli.js check --shop <店铺> --reuse-active --skip-download
```

7. 只有以下关系同时成立才完成：

```text
recognitionDone = SKU总数
comparisonMatch = SKU总数
comparisonMismatch = 0
comparisonPending = 0
pendingVisualReview = 0
```

如果自动核对无法得到这组结果，才需要人工重新核对。

## 5. 下次修改时的回归用例

任何触及套件流程、弹窗选择或对应表读取的修改，至少覆盖：

- 连续处理两个组合装，第二个不能带入第一个的隐藏选择；
- 第一个 SKU 在“已标记、未确认”时中断，重跑能从中间状态恢复；
- 当前页面已有其他 checkbox 勾选时，最终只能选中目标 SKU；
- 对应表停在非第 1 页且有筛选残留时，纯读取仍返回准确总数；
- 两个不同 productCode 复用同一 platformCode 时，sku-records、后置 check 和 match 日志仍保留两条独立记录；
- 无鲸灵标签页时 `match` 和后置 `check` 仍可运行；
- 任一异常退出后 ERP 锁恢复。

## 6. 仍值得继续改进

### P1：统一套件实现

`lib/auto-match2.js`、`lib/mark-suite.js`、`lib/ops/create-suite.js` 仍有相似页面操作。
同一规则分散在多处，会出现“修了主流程、旧入口仍保留旧行为”。下一次再修改套件流程时，
应先把搜索、标记、中间态识别、弹窗清理和结果验证收口到单一实现；在没有新改动前不为抽象而抽象。

### P1：补齐尚未覆盖的浏览器状态回归

现有快速测试主要覆盖纯逻辑。2026-07-28 百浩/悦希实战已覆盖连续套件、同比例套件换绑、
单品重映射和最终全量核对；仍需把“已标记未确认后中断恢复”、非第 1 页/筛选残留和异常释放
ERP 锁做成可重复的 live smoke。真实 ERP 写入仍只在用户确认的业务活动中执行。

### P2：特殊“提示”弹窗

同一 productCode 下多比例套件可能出现订单关联提示。当前 stop-on-error 能阻止误确认；
只有该提示再次进入常规活动路径时，再将其纳入自动状态机。
