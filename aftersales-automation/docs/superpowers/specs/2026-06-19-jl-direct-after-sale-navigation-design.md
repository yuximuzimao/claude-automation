# 鲸灵售后列表固定导航设计

## 目标

消除账号注入后继承旧页面路径的风险。注入认证态后和扫描准备开始时，都把唯一目标 tab 明确导航到：

`https://scrm.jlsupp.com/micro-customer/business/after-sale-list`

用户看到的变化是：无论注入前停在登录页、旧工单详情还是其他业务页，后续登录校验、排序和列表读取都从同一个售后列表上下文开始，不再依赖首页菜单或可能遮挡菜单的弹窗。

## 已确认方案

### 步骤 04：注入后固定导航

`sessions/jl.js inject` 仍只写入认证态。`openAccountFlow` 必须把已解析且已完成 Cookie 清理二次验证的 `targetId` 传给 `04-inject.js`；04 只对该 target 调用 `cdp.navigate(targetId, AFTER_SALE_LIST_URL)` 和登录校验，不再重新选择第一个鲸灵 tab，也不调用 `cdp.reload`。导航稳定后沿用现有店铺名匹配，防止成功登录到错误账号。

为兼容 CLI 独立调用，未传 `targetId` 时可以枚举鲸灵 page target，但必须恰好一个：没有则报错，多个也报错，禁止任意 `.find()`。现有 `inject(accountNum, waitMs)` 调用保持有效；编排调用使用 `inject(accountNum, { targetId })`。

原地 reload 会继承注入前 URL。若旧 tab 停在某个工单详情，新的账号认证态会和旧工单路径组合，可能造成店铺与工单上下文错配；固定 URL 从源头切断该状态继承。

### 步骤 11：扫描准备直接进入列表

`prepareAfterSaleList({ targetId })` 必须先对传入的目标 `targetId` 调用 `cdp.navigate(AFTER_SALE_LIST_URL)`，随后再执行列表结构校验、逾期排序、排序结果校验和 48 小时列表读取。它不再调用步骤 08，也不依赖首页菜单或弹窗状态。

缺少 `targetId` 时立即报错，避免误操作其他鲸灵 tab。步骤 08 保留为独立原子工具，但退出扫描准备主链路。

### 首页提醒时序

这是**新 A1 完整闭环的目标约束**，不是全系统现状。步骤 13 当前只打开目标工单详情，不代表工单已经处理完成，因此禁止在 13 中导航首页；未来完整处理链必须在该账号全部工单处理结束后，调用现有 `lib/jl/alerts.js`，由它导航首页并读取 `.scroll-item`，且不新增主动关闭提醒弹窗的动作。

旧停用路径 `lib/server/op-queue.js:324-328` 和 `scan-all.js:154-157` 仍会在列表读取后直接调用提醒采集。它们本次不修改，但恢复任何旧扫描入口前，必须由第三步新 A1 接管提醒时序或删除旧调用，不能把旧行为视为已经满足目标约束。

账号 4-14 的弹窗枚举真机测试停止，不再通过逐账号试错确认菜单可点击；固定 URL 导航使该枚举失去必要性。本次只做纯单测，不操作真实浏览器。

### 后续 A1 固定清单闭环边界（业务口径已确认，代码待修正）

用户已确认：步骤 11 完成排序后，首次读取的全部 `<=48h` 工单构成“本轮固定清单”。后续列表新增、工单处理后消失或排序变化，都不改变本轮处理范围和顺序。步骤 10 已具备真实鼠标分页能力；步骤 12/13 已具备按工单号点击对应处理按钮并定位新详情 tab 的能力，后续直接复用，不重复实现。

固定清单逐单串联的外层顺序为：列表定位工单号 → 步骤 12/13 打开并锁定新 `detailTargetId` → 在目标详情 tab 采集、推理、判断 → 仅命中现有自动执行范围时直接处理 → 写回原售后系统 queue/simulation → 关闭详情 tab 并验证 → 回列表 tab → 处理下一单。

本功能不是新售后系统。A1 只能改变扫描与执行顺序，不能改变原售后系统的三标签分类、页面展示、归档和反馈逻辑。每张工单仍必须写入原 `queue.json` 和 `simulations.jsonl`，继续由 `/api/queue?mode=live`、`/api/simulations?mode=live` 和 `public/app.js` 原渲染逻辑展示。`manual_review` 不得作为正式状态；非自动执行/列表消失工单映射回原“待确认”（queue status `simulated`），等待重查仍为 `waiting`，自动执行仍为 `auto_executing/auto_executed`。

旧 `lib/server/pipeline.js` / `collect.js` 不能原样接入：旧路径仍可能按缓存直接调用 `sessions/jl.js inject`、自行导航详情，且 `pipeline.processOne` 不接受编排已锁定的 `detailTargetId`。当前已有 targetId-aware 适配草案，但它只解决“绑定详情 tab 采集”的入口问题；后续必须复用旧系统的数据模型、推理语义、页面状态流转和归档语义，禁止形成并行结果系统。

目标工单在当前页找不到时，定位恢复规则如下：

- `total <= 10`、确认只有页 1、页 1 激活且下一页禁用时，可判定已从待商家处理列表消失。
- 存在多页时，必须真实点击页 1，确认页 1 激活且列表刷新，再复用步骤 10 的真实翻页能力从页 1 查到末页；仍找不到才判定消失。
- 翻页失败、列表未加载、页码未确认或达到安全上限，均不得判定消失。
- 定位恢复属于逐单串联内部的异常分支，不新增独立完整分页查找模块。
- “从待处理列表消失”只表示当前无需继续处理，不等价于断言客户取消或工单已终态；落地时写入待确认人工复核结果，等待用户手动归档。

单账号固定清单全部处理完成后，等待 5 秒，切首页读取平台提醒；随后仅兜底关闭当前账号下除售后列表主 tab 外的鲸灵 tab，不动 ERP、专属售后系统或其他非鲸灵 tab，并复核只剩当前账号售后列表页。

步骤 10/12/14、target-aware collector 和自动执行 journal 已产生代码草案，但原系统数据流尚未完全接回，质量审查仍有阻断项。完整确认清单和恢复门禁见 `docs/superpowers/plans/2026-06-19-a1-fixed-batch-user-confirmation.md`。

本设计同步仍只定义后续实现边界，不授权真实浏览器操作；任何真机验证都必须由用户另行明确指定账号和工单。

## 测试边界

- 04：验证显式 targetId 只返回已清理目标；CLI 兼容路径只接受唯一鲸灵 tab；源码契约验证固定 URL、`cdp.navigate` 和禁止 `cdp.reload`，现有店铺名匹配逻辑保持不变。
- openAccountFlow：验证 `verified === true` 后把同一 `targetId` 传给 04，避免清理 tab A 后导航/校验 tab B。
- 11：依赖隔离测试验证调用顺序为固定导航、结构校验、排序、排序校验、读取，并让步骤 08 在被调用时直接失败。
- 13：成功路径调用序列只到打开详情，不出现首页提醒读取；完整处理后的首页提醒留给后续闭环测试。
