# 售后分支清单与自动处理设计

## 1. 状态与结论

> 当前状态（2026-07-27）：旧 confidence-v2 自动学习代码已删除；生产入口只允许用户从统计复盘中明确授权的最小 `caseId` 自动同意。当前开放两项：“七天无理由退货（不喜欢/不合适）+ 退货退款 + 严格精确退回”，以及“多拍/拍错/不想要 + 仅退款 + 主品与赠品全部未发货”。其余原因和分支全部保持人工。统计页只展示采集、归类完整的固定分支，按“已授权自动 → 可评估自动化 → 仅人工”排列，不提供启用按钮。

本设计取代此前的 confidence-v2 设计及其旧 16 项实施计划。

新方案不再建设自动学习、复杂证据状态机或通用置信指纹。系统只做三件事：

1. 把现有售后代码中的全部最终处理分支登记成一张清单；
2. 按不同工单分别累计出现次数、好评、差评和自动执行成功次数；
3. 只有用户明确启用的分支才允许自动处理，达到阈值不会自动开启。

第一个明确启用的分支是：

```text
七天无理由退货（不喜欢/不合适）
+ 退货退款
+ 有退货单号
+ ERP 已确认收到退货
+ 主品与赠品档案完整
+ 所有应退商品逐规格匹配
+ 实退数量等于应退数量
+ 次品为 0
+ 未匹配商品为 0
+ 关键数据无缺失、无冲突
→ 同意退款
```

用户确认该稳定场景实际已重复执行 61 次，并有多次成功自动执行记录；用户已明确授权该分支继续自动处理。实现时仍必须从当前历史重新去重统计，不能把旧快照数字或“61”硬编码为系统计数。

第二个明确启用的最小分支是：

```text
多拍/拍错/不想要
+ 仅退款
+ 主品每个子订单的 ERP 平台交易号精确匹配
+ 赠品每个子订单的 ERP 平台交易号精确匹配
+ 全部 ERP 行为待审核/待打印快递单/待发货
+ ERP 与鲸灵均没有实际运单
+ 没有额外采集错误或人工 hint
→ 同意退款
```

该授权来自统计复盘中的独立 `caseId`，不延伸到相同最终结果下的“拒收”等其他售后原因，也不延伸到“有运单但未揽收/已退回”的相邻分支。

## 2. 目标

### 2.1 用户会看到的变化

- 自动处理管理页先按自动化价值分为“已授权自动、可评估自动化、仅人工”，每张卡片再完整展示售后原因、工单类型、业务条件和最终结果。
- 每个最小分支独立显示历史工单数、好评数、差评数、自动成功数、人工处理数、备注内容分布和启用状态。
- 系统不会把不同售后原因、不同处理结果或不同异常情况合并累计。
- 新分支第一次出现时默认人工，不会由系统猜测为已有分支。
- 后续若增加设定次数，只能用于提示“可审核”，必须由用户手动启用；第一版不实现自动阈值或启用按钮。
- 采集缺失、未登记或归类异常的历史不进入本页；它们仍保留在原始记录中，始终不能自动处理。

### 2.2 要解决的问题

当前场景 key 过粗，可能把以下不同结果合并：

- 七天无理由的精确退回、少退、次品和未入库；
- 仅退款的未发货、全部退回、已签收、驿站和在途；
- 主品已退回但赠品未退回；
- 数据完整与采集缺失；
- 普通规则同意与人工 hint 覆盖同意。

新设计直接以现有最终业务分支作为累计单位，不再让系统从原始字段自动“学习”新的规则。

## 3. 非目标

- 不建立自动学习模型。
- 不根据历史记录自动创造、合并或启用规则。
- 不为个人本地系统增加通用规则语言、工作流编辑器或复杂状态机。
- 不改变主品和赠品在代码及业务展示中的区别。
- 不开放自动拒绝退款。
- 不让等待重查、人工上报、工单取消或平台终态参与 approve 的累计。
- 不把备注原文直接作为永久规则 key；备注用于拆解、审计和发现例外。
- 不因为旧 confidence-v2 已完成一部分就继续保留无实际需要的模块。

## 4. 分类顺序

每个工单严格按以下顺序分类。

### 4.1 全局前置分支

这些分支适用于所有售后原因，并且优先于正常业务流程：

| 条件 | 最终结果 | 自动处理 |
|---|---|---|
| 人工 hint/评价指令覆盖 | 人工复核 | 永不自动，不累计 |
| 客户取消或取消中 | 等待归档 | 永不自动 |
| 已退款、已关闭、已撤销等终态 | 无操作归档 | 不属于自动退款 |
| 扫描来源详情不可访问 | 保留复查 | 永不自动 |
| 非扫描来源详情不可访问 | 无操作归档 | 不属于自动退款 |
| ticket、ERP 或关键采集缺失 | 人工 | 永不自动 |
| 工单类型为换货 | 人工复核；核验通过可由人工触发系统执行 | 永不进入扫描无人自动 |
| 工单类型未知 | 人工 | 永不自动 |

`hint` 关键词可能发生优先级误判，因此所有 hinted decision 已在自动门禁统一阻断，不参与自动同意。

### 4.2 第一层：售后原因

原因原文必须保留，累计时不同原因不得共享计数。

#### 商责原因

商品破损、变形、物流停滞、签收异常、商品漏发、少件、缺件、发错商品、卖家发错货、商品与描述不符、质量问题。

正常路径全部排除扫描中的无人自动执行，但有退货单号时仍继续采集并严格核验退回事实；核验通过且动作明确时，可以推荐人工同意，并在人工确认后使用系统单笔或人工发起的批量执行。全局终态和取消分支仍按 4.1 节处理。

#### 标准非商责原因

多拍/拍错/不想要、七天无理由退货、无理由退款、无理由售后、个人原因、不喜欢、不合适。

继续进入仅退款或退货退款条件树。每个原因独立累计。

#### 其他原因

拒收、试用退货、其他、原因缺失及未来未被常量识别的原因。

继续进入条件树，但不得借用标准非商责原因的计数。

### 4.3 第二层：工单类型与最终分支

#### 仅退款

| 最小条件 | 当前结果 | 自动属性 |
|---|---|---|
| ERP 状态未获取 | 人工 | `manual_only` |
| 所有主品、赠品行均未发货且无任何运单 | 同意 | `candidate` 或按售后原因显式 `enabled` |
| 任一待打印行已有运单 | 人工拦截 | `manual_only` |
| 主品未发货、赠品 ERP 缺失或异常 | 人工 | `manual_only` |
| 主品未发货、赠品已发货但无运单 | 人工 | `manual_only` |
| 主品未发货、赠品已发货且全部退回 | 同意 | `candidate` |
| 主品未发货、赠品已签收或在驿站 | 人工 | `manual_only` |
| 主品未发货、赠品仍在途 | 等待重查 | `manual_only` |
| 待发货且无运单 | 人工 | `manual_only` |
| 待发货且有运单 | 转已发货流程 | 继续细分 |
| 鲸灵无物流，ERP 全部退回 | 同意 | `candidate`，默认仍人工 |
| 鲸灵无物流，ERP 显示签收或驿站 | 人工 | `manual_only` |
| 鲸灵无物流，ERP 在途 | 等待重查 | `manual_only` |
| 两侧都无物流 | 人工 | `manual_only` |
| 物流采集不完整或冲突 | 人工 | `manual_only` |
| 所有主品、赠品包裹全部退回 | 同意 | `candidate` |
| 主品全部退回但赠品未退回 | 人工 | `manual_only` |
| 部分签收、部分在途 | 人工 | `manual_only` |
| 已签收且无在途件 | 拒绝并提示改退货退款 | `manual_only` |
| 驿站或快递柜待取、时效充足 | 拦截并等待重查 | `manual_only` |
| 驿站或快递柜待取、时效不足 | 拒绝并拦截 | `manual_only` |
| 在途且剩余安全时间充足 | 等待重查 | `manual_only` |
| 在途且时效不足 | 拒绝并拦截 | `manual_only` |
| ERP 状态未识别 | 人工 | `manual_only` |

#### 退货退款

| 最小条件 | 当前/目标结果 | 自动属性 |
|---|---|---|
| 七天无理由退货无退货单号（特殊超期或次品退货等） | 人工查询并判断是否同意 | `manual_only` |
| 平台提示退货单号被多工单共用，关联记录不完整 | 人工 | `manual_only` |
| 平台提示共用退货单且为相同子订单重复申请 | 只核对当前工单 | 继续细分，不累计历史申请 |
| 平台提示共用退货单且为不同子订单 | 合并逐规格核对 | 继续细分；信息不完整则人工 |
| 无 ERP 入库记录，剩余时间充足 | 等待重查 | `manual_only` |
| 无 ERP 入库记录，时效不足 | 人工处理 | `manual_only` |
| ERP 有记录但未确认收货，剩余时间充足 | 等待重查 | `manual_only` |
| ERP 有记录但未确认收货，时效不足 | 人工处理 | `manual_only` |
| ERP 入库、主品与赠品逐规格精确退回、全良品 | 同意 | `candidate` 或显式 `enabled` |
| 已证明为真实多退、其他条件全部通过 | 同意 | `candidate`，从 0 重新累计 |
| 少退或缺失 | 人工 | `manual_only` |
| 含次品 | 人工 | `manual_only` |
| 未匹配或额外未知商品 | 人工 | `manual_only` |
| 商品对应表或档案缺失 | 人工 | `manual_only` |
| 多个子订单数量冲突 | 人工 | `manual_only` |
| 数据采集不完整或冲突 | 人工 | `manual_only` |

主品和赠品必须继续分开保存和展示。最终“精确退回”要求两边各自通过；不能因为处理逻辑相似而删除两者的业务边界。

## 5. 分支登记结构

每个最终分支使用一条明确登记记录，不由运行时自动创建：

```text
caseId                  稳定的分支编号
afterSaleReason         规范化后的具体售后原因
orderType               仅退款 / 退货退款 / 换货 / 未知
branchId                现有推理的最终业务分支编号
mainOutcome             主品状态或商品核对结果
giftOutcome             赠品状态或商品核对结果
warehouseOutcome        入库状态
logisticsOutcome        物流状态
itemOutcome             exact / excess / short / damaged / unmatched / incomplete
expectedAction          approve / reject / waiting / escalate / archive / skip
automationStatus        manual_only / candidate / enabled
positiveThreshold       未来可选字段；当前版本不存储、不使用
ruleVersion             规则版本
```

设计约束：

- 同一个工单只能命中一个最具体的 `caseId`。
- 不同售后原因永不共享 `caseId` 或计数。
- 不同 action 永不共享 `caseId` 或计数。
- 任一决定性字段未知时进入明确的 incomplete 分支，不使用默认值猜测。
- 新出现但未登记的组合直接人工，并显示“未登记分支”。
- 备注、账号、工单号、订单号和运单号不参与 `caseId`。

## 6. 历史累计与启用规则

### 6.1 计数口径

每个 `caseId` 分别显示：

- `occurrenceCount`：命中该分支的不同工单数；
- `positiveCount`：明确好评的不同工单数；
- `negativeCount`：明确差评的不同工单数；
- `autoSuccessCount`：有 journal 页面动作成功证据的不同工单数；
- `manualHandledCount`：人工处理的不同工单数；
- `notes`：字面“无”、有备注及脱敏后的具体备注频次。

同一工单重复扫描、等待后重扫或重复写入 simulation 都只能计一次。以该工单最新且可确认的最终分支为准；状态演进保留在审计明细，不重复增加计数。

### 6.2 状态与启用

```text
manual_only
  永远不自动

candidate
  按配置累计，但仍人工；达到阈值时页面显示“可审核”

enabled
  用户明确开启后才允许自动 approve
```

达到阈值只改变页面提示，绝不能自动把 `candidate` 改成 `enabled`。当前未实现阈值和页面启用操作：只有代码中按“分支＋售后原因”登记、且用户已经明确授权的最小案例为 `enabled`，其余 `candidate` 一律按人工处理。

如后续确认需要阈值，默认候选口径可从 20 次明确好评开始逐分支设定。已授权案例不需要重新等待迁移后的阈值，但仍必须通过本次工单的独立事实证明。

## 7. 初始分支状态

### 7.1 七天无理由退货

| 分支 | 执行时前30天不同工单 | 好评 | 自动成功 | 初始状态 |
|---|---:|---:|---:|---|
| 退货退款、已入库、主品赠品精确退回、无次品无未匹配 | 30 | 26 | 28 | `enabled` |
| 已入库但少退、次品或缺失 | 重新统计 | 重新统计 | 重新统计 | `manual_only` |
| 有记录但未入库、时效充足 | 重新统计 | 重新统计 | 重新统计 | `manual_only` |
| 有记录但未入库、时效不足 | 重新统计 | 重新统计 | 重新统计 | `manual_only` |
| 无退货单号、需要人工查询特殊退货 | 重新统计 | 重新统计 | 重新统计 | `manual_only` |
| 已证明真实多退、其余全部通过 | 重新统计 | 重新统计 | 重新统计 | `candidate` |

### 7.2 其他原因

- 商责原因、等待、拒绝、上报、取消、终态、数据缺失和 hinted 分支全部 `manual_only`。
- “多拍/拍错/不想要＋仅退款＋主品赠品全部未发货”已独立授权为 `enabled`；同原因的有运单/已退回等相邻 approve 分支，以及拒收、试用退货、无理由售后和其他原因中的 approve 分支仍分别保持 `candidate`，不得继承粗场景权限。
- 历史数据只作为展示和人工判断依据，不会自动启用这些候选分支。

## 8. 备注处理

历史清单必须显示：

- 备注字段是否存在；
- 字面“无”与真正空值分开；
- 脱敏后的具体备注原文；
- 相同备注出现次数；
- 备注对应的最终分支、好评和执行结果。

脱敏至少覆盖手机号、订单号、工单号、运单号和其他长编号。健康信息只显示“含个人健康信息，已脱敏”。

备注默认不拆分 `caseId`。如果后续确认某类备注会改变处理结果，应新增明确的结构化业务条件和新 `caseId`，不能由系统自动做文本聚类。

## 9. 精确退回证明

七天无理由精确退回在自动执行前必须重新验证：

1. 退货单号存在；若平台提示多工单共用，关联记录必须完整，并按相同/不同子订单规则处理；
2. ERP 至少有一条明确“卖家已收到退货”的记录；
3. 只使用属于已收货记录的商品明细；
4. 主品每个子订单都有对应表、商品档案和自己的 `afterSaleNum`；
5. 赠品子订单都有对应表和商品档案；
6. 每个主品和赠品子订单使用自己的 `afterSaleNum`；赠品未提供该字段时按现有业务结构计 1 件；
7. 按 `specCode` 精确匹配，不使用商品名称包含关系代替；
8. 每个 ERP 已收货行的售后单号唯一、退货单号与鲸灵一致，且 `returnQty` 等于良品与次品明细合计；
9. 每个应退规格的实退数量等于应退数量；
10. `qtyBad=0`；
11. 没有额外未知规格；
12. `collectErrors` 为空，没有关键采集错误、重复行或字段冲突。

主品与赠品的结果分别保存；只有两者同时通过，最终分支才是 exact。

### 9.1 仅退款未发货证明

“多拍/拍错/不想要＋仅退款＋主品赠品全部未发货”自动执行前必须重新验证：

1. 每个主品和赠品子订单都有且只有一组对应的 ERP 搜索结果；
2. 每组至少有一行，且每行平台交易号包含本次搜索的子订单号；
3. 每行状态只能是待审核、待打印快递单或待发货；
4. 每行 `tracking/trackings` 为空；
5. 鲸灵物流和 ERP 物流中不存在 ERP 行外的运单；
6. 除“仅退款跳过商品明细”和“无退货单号跳过 ERP 售后”外，不存在其他采集错误；
7. 工单没有人工 hint，售后原因和工单类型必须与已授权 `caseId` 完全一致。

## 10. 真实多退证明

业务上允许真实多退后同意退款，但该分支不继承精确退回分支计数，必须单独从当前历史重新累计。

只有同时满足以下条件才属于真实多退：

1. 只统计 `goodsStatus` 明确为“卖家已收到退货”的行；其他状态即使残留展开明细也正常忽略；
2. 重复使用只认平台工单详情的“多次使用”提示及其关联工单号，不主动扫描历史相同退货单号；
3. 平台提示的关联工单必须在系统中有完整记录；相同子订单按重复申请处理，不累计历史申请；不同子订单才合并核对；
4. 每行商品数量合计与 ERP 实退数量一致；
5. 主品和赠品档案全部完整；
6. 使用每个子订单自己的数量并按 `specCode` 聚合；
7. 所有应退规格均已退足、次品为 0、无未知额外规格；
8. 至少一个已知规格的良品数量大于应退数量。

非已收货残留行、相同子订单重复申请、不同子订单合并核对和关联记录不全的边界已在主干修正。分支注册表只消费修正后的结构化结论，不再自行推测历史关联。

## 11. 已完成的前置修复

### 11.1 待打印运单的首行门控

ERP 采集和状态聚合已经读取全部子订单、全部行，多包裹读取逻辑保留。实际漏洞是：

```text
第一行待审核、无运单
后续行待打印、已有运单
```

主品和赠品已统一遍历全部子订单、全部 ERP 行；任意状态只要有运单就进入实际物流核验，不再由第一行状态决定。

### 11.2 无退货单号语义

七天无理由退货没有退货单号可能是平台客服处理的超期特殊退货，也可能是次品特殊退货。该分支固定人工并提示查询，不得执行 `OVERDUE_RETURN` 拒绝，也不得计入精确退回分支。

### 11.3 多退采集重复

推理只统计“卖家已收到退货”行，其他状态的残留明细正常忽略。共享退货单只认平台提示；相同子订单忽略历史申请，不同子订单合并逐规格核对，关联记录不全时人工。

### 11.4 多个赠品子订单

保留主品与赠品的业务区别。核查发现当前退货退款采集只保存第一个赠品子订单的商品档案，尚不能证明多个赠品子订单都已精确退回。因此第一版遇到多个赠品子订单时直接进入 incomplete/manual，不自动同意；待真实业务出现后再按实际页面格式补齐采集，不能假定已经支持。

## 12. 最小实现边界

实现只需要以下组件：

1. **分支注册表**：列出全部现有最终分支及初始状态；
2. **分支分类器**：把当前推理所依据的结构化事实映射到唯一 `caseId`；
3. **计数汇总器**：按不同工单统计历史和反馈；
4. **自动门禁**：只检查 `caseId` 是否为 `enabled`，并在执行前按分支重做严格精确退回证明或仅退款未发货证明；
5. **现有统计页改造**：复用原统计区域，只读展示分支清单和计数；
6. **旧系统退役**：不读取、不更新旧 `auto-exec-confidence.json`，删除旧自动学习模块；运行数据文件暂不删除，只作为历史痕迹保留。

不增加新的后台服务、数据库、消息队列、通用规则编辑器或单独管理站点。

旧 confidence-v2 Task 1–6 只有在直接服务上述六个组件时才可复用；不能为了保留已完成工作而扩大新方案。未提交的 Task 7 `fingerprint.js` 及其测试不继续实现。

## 13. 错误处理

- 未登记分支：人工，显示缺失的事实组合。
- 多个分支同时匹配：人工，记录分类冲突。
- 必需字段缺失：进入 incomplete 分支。
- 规则版本变化或出现新差评：只作为人工复核信号，不自动改变固定授权；若要停用或重新启用，必须由用户明确修改分支配置。
- 当前工单的精确证明失败：即使分支已授权，也在执行门禁中立即阻断并转人工。
- 计数文件损坏或写入失败：禁止自动执行，不影响人工处理。
- 页面动作失败或 journal 存在未完成记录：保留现有 fail-closed 和人工恢复逻辑。

## 14. 测试与验收

### 14.1 分支完整性

- `infer.js` 每个最终出口都必须映射到一个登记分支；
- 代码新增出口但未登记时测试失败；
- 同一输入匹配零个或多个分支时测试失败；
- 商责、非商责和其他原因分别覆盖；
- 仅退款、退货退款、换货、未知类型和全局前置全部覆盖。

### 14.2 自动边界

- 七天无理由 exact 自动通过；
- 同原因下少退、次品、未匹配、未入库、无退货单号全部阻断；
- 主品 exact 但赠品非 exact 时阻断；
- 多拍/拍错仅退款只有主品与赠品逐子订单证明全部未发货时自动通过；
- 同一未发货分支的“拒收”等其他原因，以及有运单/已退回等相邻分支必须阻断；
- hinted approve 阻断；
- 达到阈值只显示“可审核”，不自动启用；
- 用户启用后才允许自动；
- 差评和规则变化不会自动改权限；当前工单证明失败时必须阻断。

### 14.3 已确认漏洞

- 首行待审核、后行待打印且有运单：主品阻断；
- 同一组合：赠品阻断；
- 多包裹、所有行无运单：保持原有正确结果；
- 非已收货残留展开行带商品明细：必须忽略，不能污染 exact 或 excess；
- 平台提示退货单跨工单复用：关联记录缺失时阻断；记录完整时按相同/不同子订单规则核对；
- 缺任一赠品档案：阻断；
- 多退只有严格证明通过时才进入 excess 分支。

### 14.4 历史校验

- 每个工单只贡献一次计数；
- 从执行时向前 30 天的历史重新拆解，全部工单都必须映射；无法映射的显示具体缺失条件；
- 七天无理由 exact 的当前去重工单、好评和自动成功数必须现场重算；用户提供的“61次”只作为核对线索；
- 备注重新统计字面“无”、真正空值和脱敏后的具体内容分布；
- 真实多退单独统计，不继承精确退回计数。
