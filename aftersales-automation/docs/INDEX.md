# 鲸灵售后处理规则索引（Agent 必读入口）

---

## §0 错误处理总则

### 0.1 错误分级

**风控敏感错误**（就地熔断，持久化到磁盘，重启不丢失）：
- HTTP 426 / `X-Tengine-Error: denied by http_ratelimit`
- 页面含 `ratelimit` `anti-bot` `captcha` `访问过于频繁` `操作频率过高`
→ 处理：`wait.js` 内就地调用 `globalThis.__tripCircuitBreaker()`，写入 `data/circuit-breaker.json`，停止所有鲸灵任务。需人工确认后执行 `node cli.js reset-circuit` 恢复。

**不可恢复错误**（报错即停，不重试）：
- `scrm.jlsupp.com` 域名下点击/提交/填写/上传类操作失败，域名自动识别强制 maxRetries=0
- 规则歧义、数据矛盾、脚本抛错
→ 处理：单次失败，记录原因，不重试。规则未覆盖的情况上报人工。

**ERP 订单搜索结果错误**（只重试搜索动作）：
- 搜索结果的平台交易号缺失，或任意一行不包含本次搜索的子订单号
- 首次搜索未真正生效，页面仍显示上一批结果
→ 处理：只重新执行一次 ERP 搜索，总共最多 2 次；第二次仍失败则立即报错，不继续物流采集、推理或整张工单流程。其他操作不得借此规则自动重跑。

### 0.2 人工上报流程（满足任意一条触发）

触发条件：
- 主商品退货含次品（qtyBad > 0）
- 赠品退货含次品（qtyBad > 0）
- 退货数量与应退数量不符，且情况不明确
- 决策树未覆盖的新场景
- 任何"说不准"的情况

**上报步骤**（依次执行，不同意也不拒绝）：

```bash
# Step 1: 工单添加内部备注
node cli.js add-note <工单号> "【待人工】原因：<触发原因> 关键信息：<核心数据>"

# Step 2: 通过「创建提醒」快捷指令创建待办（5分钟后触发）
node cli.js remind <工单号> <账号名> "<具体问题描述>"

# Step 3: 停止对该工单一切后续操作
```

处理结束后汇总输出：
```
⚠️ 需人工处理（X张）
- [账号] 工单号 | 类型 | 剩余时间 | 原因
```

### 0.3 队列紧急停止

当队列操作卡住、出错或需要立即中断时：
- **前端**：面板「🛑 紧急停止」→ 清空排队 + 中断运行中操作；运行中操作旁的「⏹」→ 单操作停止
- **API**：`POST /api/emergency-stop` — 返回 `verify.allClean` 确认停止完整性
- **验证**：`GET /api/stop-event` — 查询上次停止事件
- **恢复**：`POST /api/resume` — 清除 stop 标记，恢复队列调度
- **重启感知**：server 启动时自动检测上次 stop 事件并输出警告；紧急停止后不会自动恢复被中断任务，需用户手动决定是否重新处理
- 详见 `docs/ops-queue.md`

## §1 角色与红线

### 1.1 处理原则

- 严格串行：工单按顺序处理，不并行，不跳过
- 每步验证：操作后必须验证结果；失败处理按 §0.1 分级，鲸灵行为操作失败即停，只有 ERP 可恢复错误允许 retry
- 不自行决断：规则未覆盖的情况一律上报人工
- 证据留痕：每次拒绝退款必须上传物流截图

### 1.2 红线（绝对禁止）

- ❌ 遇到不确定情况自行猜测并操作（同意或拒绝）
- ❌ 因为"看起来应该同意"就直接同意
- ❌ 靠记忆推算商品明细（必须查商品对应表+档案V2）
- ❌ 靠商品名字判断商品是否一致（必须用规格商家编码对比）
- ❌ 赠品子订单号推算（主号+1），必须从 giftSubBizOrderDetailDTO.subBizOrderId 读取
- ❌ 并行操作（ERP 命令必须串行执行）
- ❌ 截图用于判断内容（截图只用于上传凭证）

### 1.3 处理前检查清单

```
□ 1. 读取工单列表，只处理倒计时 ≤ 2天（48小时）的工单
□ 2. 每条工单：先读详情 → 判断类型 → 按对应流程处理
□ 3. 涉及退货：去 ERP 售后工单新版验收，展开所有行
□ 4. 涉及套装/赠品：必须查商品对应表 + 商品档案V2，不靠记忆
□ 5. 最终操作（同意/拒绝）前再确认一次表单内容
```

## §3 全局判断规则

### 3.1 工单优先级

倒计时字段必须从工单卡片的 `.el-timer` 组件读取，不能用后缀文案白名单定位。数字主体为 `X天X小时X分`；后缀可能是 `后自动退款`、`后流转至客服`、`后供应商处理超时` 等，新增后缀不应影响时间解析：
- **≤ 2天** → 处理；**> 2天** → 跳过

⚠️ 快捷筛选器数字不实时，必须看每条工单的倒计时字段。

### 3.2 账号→ERP 店铺名映射

由脚本 `lib/erp/shop-map.js` 的 `getErpShop(note)` 自动处理，无需手动查表。
- 澜泽账号已显式映射到 ERP「澜泽」
- 账号11「曼龄-悦希」→ 对应 ERP「曼龄」（「悦希」是品牌名非店铺名）
- 新店铺未显式登记时只按账号 note 的 `-` 前缀临时推导，并输出警告；确认真实 ERP 店铺名后必须补入 `SHOP_MAP`

### 3.3 ERP 订单状态含义

| ERP 状态 | 含义 |
|---------|------|
| 待审核 | 无快递单号时视为未发货；异常出现单号时必须查物流 |
| 待打印快递单 | 无快递单号时视为未发货；有单号时必须查物流 |
| 待发货 | 无快递单号时视为未发货；有单号时必须查物流 |
| 卖家已发货 | 必须按快递单号查实际物流；无单号属于数据异常，转人工 |
| 交易成功 | 必须按快递单号查实际物流；无单号属于数据异常，转人工 |

仅退款必须对主品和赠品的全部子订单、全部 ERP 行逐行判断。只有每一行均确认未发货或物流已经成功退回，整张工单才能退款。创建过拦截记录不等于拦截成功，必须以实际物流退回节点为准。详见 `docs/flow-5.2.md`。

### 3.4 afterSaleNum 计算规则

- 应退主商品单品数 = 档案V2.subItemNum × afterSaleNum
- afterSaleNum=1 → 退1件套装（正常）
- afterSaleNum=2 → 退2件套装（如4盒套×2=应退8盒）
- 赠品子订单通常未提供 afterSaleNum，此时按 1 份；若页面明确提供 afterSaleNum，则使用该子订单自己的数量，不能固定写死为 1

### 3.5 退回成功判断（满足任意一条）

- 物流显示"签收，收件人：退商家"
- 物流显示"退回"节点
- 物流显示"安排退回，退回原因：客户要求退回"
- 物流显示"拒收"节点

> 不需要等仓库实际签收，有退回记录即算退回。

例外：`收件人要求退回，等待发件人确认！` 只是退回请求，不是确认退回。必须另有独立的退回、安排退回或退回商家签收节点；鲸灵和 ERP 重复出现该文案，或只有“退回件”标签，都不能作为第二个确认节点。

### 3.6 工单取消与商责/换货约束

**商责售后原因**：`MERCHANT_FAULT_REASONS` 在 `lib/constants.js` 中维护。2026-05-21 新增 `'质量问题'`——此前因漏加导致商责工单穿透到非商责流程（fb-1778868858729 / fb-1779092166923）。2026-06-11 新增 `'卖家发错货'`，覆盖鲸灵原因文案。2026-08-16 新增 `'瑕疵'`，与质量问题采用相同的商责人工约束。如需追加商责关键词，在该数组中新增。

**商责/换货与退货核验的优先级（2026-07-27）**：

1. 终态和关键采集错误仍最优先，数据不可信时立即停止。
2. “商责”和“换货”是操作约束，不再阻断事实采集。换货，或商责退货退款，只要有退货单号，就继续采集商品对应表、档案V2和 ERP 已收货明细。
3. 退回规格、数量、良次品严格一致时，推理可以输出“推荐人工同意换货/退款”；不一致、含次品或证据不完整时转人工核对。
4. 所有换货和商责推荐结果必须带明显类型提醒，设置 `requiresHumanReview + autoExecutionBlocked`，永久排除扫描中的无人自动执行。
5. “禁止无人自动”不等于“禁止系统执行”：严格核验一致并给出明确 approve/reject 动作时，设置 `humanTriggeredExecutionAllowed: true`，人工确认后可使用单笔“执行操作”或主动发起批量执行；核验不一致、含次品、证据不足或没有确定动作时不得进入批量 approve/reject。
6. 换货执行必须按类型精确点击“同意换货/拒绝换货”，不得复用“同意退款/拒绝退款”。找不到对应按钮立即停止。
7. 换货同意前必须额外确认正确商品是否已经提前人工补发/换出：若已经发出，应拒绝换货并手动归档；只有未提前发出且退回核验无误时，才执行同意换货。
8. 同时命中商责和换货时，两种风险标签都要保留，不能被“商责前置拦截”吞掉换货核验结果。
9. 商责退货退款处于申请阶段且没有退货单号时，“无单号”是正常前置状态：客户必须先获得商家同意退货，之后才能填写单号。客户选择商责原因只代表提出商责主张，不等于商责已被证实；系统只推荐拒绝退货，不提供执行入口。人工需要结合客户填写的原因、售后说明和图片寻找合理拒绝理由；只有确认确属商责且没有合理拒绝空间时，才改为同意退货。

**工单已取消/取消中**：不走自动 `skip`，改为 `wait_archive`。扫描期间发现存在已拦截或「快递行动」已标记处理的记录时，只设置“需要取消拦截”汇总标记；整轮扫描结束后最多创建一条 5 分钟后提醒的待办。工单保留在 simulated 状态，完成取消拦截后由人工归档。`infer.js` 中 `TERMINAL_STATES` 仅含已退款/已关闭/客服终态，不含取消类状态。

### 3.7 平台工单阶段观察

- 扫描 48 小时清单时，所有工单都必须保存列表中读取到的 `商家-*` 原始阶段、读取时间和来源。阶段缺失也要显式记录，不能无声丢字段。
- 平台阶段默认只作为人工核对和后续复盘的辅助数据，不覆盖现有的售后类型、物流、ERP 与退回商品综合判断。
- 当前唯一参与决策的观察期分支：`工单类型=换货` 且平台阶段精确为 `商家-待商家二次发货`。该状态表示售后判断已经完成，当前等待发货端处理。
- 观察期内该分支仍创建 queue/simulation、保留原综合推理作对照，并显示“无需处理，待人工确认后归档”；不得自动归档、不得执行鲸灵按钮、不得自动写平台内部备注。
- 前端保留“执行操作”按钮但必须置灰不可点击，人工确认无误后使用“手动归档”。
- 原综合推理必须完整保存在 observation assessment 中，不能只留动作和一句原因；重新采集推理时必须使用本次列表定位读到的新阶段，并同步更新 queue。
- 人工归档该分支时，历史来源记为“人工确认无需处理”，不得混入“人工处理/人工执行”次数。相同工单在相同阶段已确认后，后续扫描继续更新时间留痕但不重复进入待确认；阶段发生变化时重新进入正常判断。
- 该观察分支必须使用稳定、独立的 `caseId` 进入最近 30 天分支统计，不能归入“未登记分支”。
- 其他工单类型与其他平台阶段只留存和展示，不参与决策。后续是否扩大状态判断范围，必须基于历史观察人工复盘并由用户明确授权，禁止按次数自动开权。

## §4 通用操作规范

### 4.1 同意退款三步（通用）

```
1. 鲸灵工单详情页 → 点「同意退款」
2. 弹出确认弹窗 → 点「确认同意退款」
3. 若出现第三层风险提示弹窗（已发货时必现）：
   内容："若您的货物已经发出，且订单无法拦截..."
   → 点「确 认」（按钮文字含空格，必须精确匹配）
```

> ✅ cli.js approve 命令已自动处理三步（含第三层弹窗）

### 4.2 操作命令速查

```bash
# 读工单列表（≤48小时）
node cli.js list

# 读工单详情
node cli.js read-ticket <工单号>

# 同意退款（自动处理三步弹窗）
node cli.js approve <工单号>

# 拒绝退款
node cli.js reject <工单号> <原因> <详情> [图片URL]

# 添加内部备注
node cli.js add-note <工单号> "备注内容"

# 通过「创建提醒」快捷指令创建待办（5分钟后触发）
node cli.js remind <工单号> <账号名> "原因"

# 读物流信息
node cli.js logistics <工单号>

# ERP 商品对应表查询
node cli.js product-match <货号> <attr1> <ERP店铺名>

# ERP 商品档案V2查询
node cli.js product-archive <规格编码>

# ERP 订单搜索
node cli.js erp-search <子订单号>

# ERP 售后工单搜索（退货快递单号）
node cli.js erp-aftersale <快递单号>
```

### 4.3 内部备注格式规范

- 格式：**结论+动作，一句话，不写原因分析**
- 人工上报格式：`【待人工】原因：<触发原因> 关键信息：<核心数据>`
- ⚠️ 备注写 ERP shortTitle（如"KGOS保温壶1个"），不写编码（如 kgosbwh）

### 4.4 截图使用规范

**只在以下情况截图**：
- 拒绝退款时上传物流截图作为凭证
- 遇到从未见过的页面布局

**所有判断全部用 DOM 文字读取**，不截图判断。

## §6 已知坑位（通用操作层）

> 格式：`[触发次数/最后触发]` — 说明。触发次数≥3且超过2周未触发可清理。

- `[∞]` **#5 赠品子订单号禁止推算**：必须从 `giftSubBizOrderDetailDTO.subBizOrderId` 读取，禁止用主号+1推算。
- `[∞]` **#9 图片上传唯一路径**：curl+cookie → 注入 Vue `WorkOrderStateForm`。禁止 DataTransfer/本地HTTP/XHR拦截器（拦截器导致堆栈溢出）。
- `[∞]` **#24 备注写 shortTitle 不写编码**：写"KGOS保温壶1个"，禁止写 kgosbwh 等编码。
- `[∞]` **#25 备注只写结论**：一句话结论+动作，不写原因分析。
- `[∞]` **#37 内部备注入口**：必须用「致内部」按钮；严禁「+新增备注」（进供应商可见区域）。
- `[∞]` **#48 读表数据用表头定位列索引**：用 `<th>` 文本定位列，禁止用正则/关键词/长度过滤数据内容（会误杀合法编码如 kgoxnld）。
- `[∞]` **#49 验证数据=读实时源头**：→ 见全局 CLAUDE.md 浏览器操作约束。
