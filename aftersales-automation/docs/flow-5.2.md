# 仅退款-未发货处理流程（5.2）

> 前置：已读 `docs/INDEX.md`，工单类型确认为「仅退款」，且 ERP 搜索显示未发货
> 核验重点：**ERP确认商品真的未发货，且主商品+赠品均未发货**

---

## 完整流程

### Step 1：读鲸灵工单详情

```bash
node cli.js read-ticket <工单号>
```

必须记录：
- `subBizOrderDetailDTO[*].subBizOrderId` — 全部主商品子订单号
- `giftSubBizOrderDetailDTO[*].subBizOrderId` — 全部赠品子订单号（如有）

### Step 2：ERP 逐行确认主商品是否实际发货

```bash
node cli.js erp-search <主子订单号>
```

每个主商品子订单都要逐一查询。必须读取全部子订单的全部 ERP 行，不能只看第一个子订单或第一行。每行按以下规则判断：

先逐行核验“平台交易号”包含本次搜索的子订单号。合并订单格式如 `756292468；756311711`，包含搜索号即有效；任意一行缺失或不包含搜索号，整次采集失败并上报人工。

| 行数据 | 判断 | 处理 |
|-------|------|------|
| 待审核/待打印快递单/待发货，且无快递单号 | 未发货 | ✅ 该行通过，不查物流 |
| 任意状态，有快递单号 | 可能已发货 | 必须查询该单号的实际物流 |
| 有单号，但物流确认尚未揽收 | 未发货 | ✅ 该行通过 |
| 物流已有退回、拒收或安排退回等退回节点 | 已成功退回 | ✅ 该行通过 |
| 物流已发出，仍在途、已签收、驿站待取或状态不明 | 尚未成功退回 | ❌ 该行不通过，不能退款 |
| ERP 明确显示卖家已发货/交易成功，但无快递单号 | 数据异常 | ⚠️ 上报人工，不能按未发货退款 |

创建过快递拦截记录只代表系统发起过动作，不代表拦截成功。只有实际物流节点显示退回、拒收或安排退回，才能判定该行已经成功退回。

`收件人要求退回，等待发件人确认！` 只表示买家提出请求，不是已退回。只有后续另有独立的退回/安排退回/商家签收等确认节点，才算退回成功；鲸灵和 ERP 重复出现同一句话不算两个节点。

### Step 3：若有赠品，ERP 确认赠品发货状态

```bash
node cli.js erp-search <赠品子订单号>
```

每个赠品子订单都要逐一查询。赠品与主商品使用完全相同的逐行判断，不能使用另一套状态规则。赠品全部子订单、全部 ERP 行也必须逐行核对。

### Step 4：所有行均通过 → 同意退款

一张工单有多少行，就必须完成多少次判断。只有每一行都属于以下任一结果，整张工单才能退款：

- 确认未发货；
- 物流确认已经成功退回。

任意一行仍在途、已签收、驿站待取、物流不明或数据异常，整张工单都不能退款。

```bash
node cli.js approve <工单号>
```

## 决策快速参考

```
鲸灵读详情 → 主子订单号 + 赠品子订单号
  ↓
ERP读取主商品全部子订单、全部行
  ├─ 无单号且状态未发货/备货中 → 该行通过
  ├─ 有单号 → 查实际物流
  │   ├─ 未揽收 → 该行通过
  │   ├─ 已退回/拒收/安排退回 → 该行通过
  │   └─ 在途/签收/驿站/不明 → 该行不通过
  └─ 明确已发货但无单号 → 数据异常，人工
  ↓
有赠品 → 读取赠品全部子订单、全部行 → 使用同一规则
  ↓
所有行都通过 → 同意退款
```
