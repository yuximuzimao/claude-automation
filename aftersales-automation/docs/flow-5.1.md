# 退货退款处理流程（5.1）

> 前置：已读 `docs/INDEX.md`，工单类型确认为「退货退款」
> 核验重点：**客户寄回的快递是否已在ERP入库，且入库明细和数量正确**

---

## 完整流程

### Step 1：读鲸灵工单详情

```bash
node cli.js read-ticket <工单号>
```

必须记录以下字段：
- `subBizOrderDetailDTO[0].subBizOrderId` — 主子订单号
- `subBizOrderDetailDTO[0].spuBarcode` — 货号
- `subBizOrderDetailDTO[0].attribute1` — SKU属性（attr1，用于商品对应表匹配）
- `subBizOrderDetailDTO[0].afterSaleNum` — 退货SKU件数（⚠️ 必读，影响应退数量计算）
- `giftSubBizOrderDetailDTO[0].subBizOrderId` — 赠品子订单号（如有）
- `giftSubBizOrderDetailDTO[0].spuBarcode` — 赠品货号（如有）
- 客户退货快递单号（buyerLogisticsNo）
- 售后说明（buyerRemark）+ 是否有售后图片

**七天无理由退货没有退货快递单号时**：

- 可能是经过平台客服处理的超期特殊退货，也可能是次品退货的特殊处理；系统不猜测具体类型。
- 直接转人工，不自动同意、不自动拒绝，也不继续进入退货入库核验。
- 人工提示固定为：`无退货快递单号，可能为超期特殊退货或次品特殊处理，请人工查询并判断是否可以同意提前无理由退货`。

**商责退货申请没有退货快递单号时**：

- 适用于售后原因为「质量问题」「瑕疵」等商责主张，且工单仍处于商家待处理的退货申请阶段。
- 客户必须先获得商家同意退货，之后才能填写退货单号；因此当前无单号是正常前置状态，不能描述成“缺少退回核验依据”。
- 客户选择商责原因、填写说明或上传图片只代表提出主张，不代表商责已经被系统证实。系统不读取图片内容作判断。
- 默认只推荐「拒绝退货」，不提供系统执行；人工需要结合客户填写的原因、售后说明和图片，寻找平台可成立的合理拒绝理由。只有人工核实后确认确属商责、且没有合理拒绝空间时，才改为「同意退货」。
- 该分支必须标记人工复核，禁止无人自动、人工批量和直接系统执行；人工需要打开工单核实凭证后操作。

**afterSaleNum 计算规则（⚠️ 必须用，不能靠名字推断）：**
- 应退主商品单品数 = 档案V2.subItemNum × afterSaleNum
- afterSaleNum=2 → 退2件套装，应退单品数成倍增加
- 当前生产不采集赠品 afterSaleNum；赠品按真实 `giftSubBizOrderId` 对应的一套商品档案计算。共用退货单关联组继续按 `INDEX §3.4.1` 对同一赠品子订单去重

### Step 2：查退货商品明细

> ⚠️ 必须查，不靠记忆或推算

**主商品**（参考 `docs/erp-query.md`）：

```bash
# 商品对应表：货号 → 规格商家编码
node cli.js product-match <货号> "<attr1>" <ERP店铺名>

# 商品档案V2：规格商家编码 → 单品名称+数量（subItemNum）
node cli.js product-archive <规格商家编码>
```

**赠品**（如有）：赠品货号走同样路径获取规格商家编码和单品信息；同时用赠品子订单号查询 ERP 发货状态。赠品仅在实际发出或无法明确证明未发出时进入应退清单。若每个赠品子订单均成功查到 ERP，且所有 ERP 行均为「待审核 / 待打印快递单 / 待发货」、全部无快递单号，按未发货处理，不要求客户退回。

### Step 2b：包裹级明细核验（数量不符时必做）

> ⚠️ 禁止只对比总件数得出"少退"结论——必须核验哪些包裹已签收、哪些未签收

```bash
# ERP 搜主子订单号，读每个包裹的快递单号和发货件数
node cli.js erp-search <主子订单号>

# 鲸灵查物流（读各包裹最新节点）
node cli.js logistics <工单号>
```

判断：
- 签收包裹的内容已退回入库 → 正常
- 未签收包裹（驿站/在途）→ 拦截件，等待退回，**不能视为"少退"**

### Step 3：ERP 售后工单新版搜退货快递单号

```bash
node cli.js erp-aftersale <退货快递单号>
```

展开所有「货物状态=卖家已收到退货」的行，逐行核对：
- 商品全称、数量、良品/次品（qtyBad 字段）
- 同一退货快递单号可能返回多条 ERP 行；所有搜索命中的行都要检查，但只有明确为「卖家已收到退货」的行才能计入实退数量。
- 多条已收货行中出现相同 `specCode` 时，良品/次品数量必须跨行汇总后再与本工单应退的同规格总数量比较；不得把同一规格的不同入库行强行一一分配给不同主子订单，否则会制造假缺件。

非「卖家已收到退货」的行即使页面残留了已展开商品明细，也必须直接忽略；这属于正常页面状态，不能计入实退数量，也不能报成采集异常。

**平台提示退货单号被多个工单使用时**：

- 只认平台详情里的「多次使用」提示及其列出的关联工单号，不主动按退货单号搜索历史工单。
- 关联工单号优先从页面 Vue 物流结构中的 `logisticsUsedWorkOrderNumList` 读取；结构化字段缺失时，读取「多次使用」按钮 `aria-describedby` 指向的悬浮层 `textContent`。禁止继续假设关联号一定存在于 `document.body.innerText`。
- 重复退货单号的业务定义以 `INDEX §3.4.1` 为准：**工单号不同且当前同时存在于平台「待商家处理」列表，代表两张独立有效的退货申请。** 不能因为主 `subBizOrderId` 相同就把其中一张视为历史重新申请。
- 当前有效关联工单的**主品按工单逐张累计**：每张工单分别计算 `档案V2.subItemNum × afterSaleNum`，再按 `specCode` 合并；相同主子订单号也不去重。
- 当前有效关联工单的**赠品按 `giftSubBizOrderId` 去重**：同一个赠品子订单可能因平台重新判断赠送门槛而重复显示在多张工单里，但物理上只需退一套；不同赠品子订单号才分别累计。
- 合并当前关联工单的应退规格时，必须复用普通退货核对的同一口径：先排除下方免退包装配件，再按 `docs/erp-query.md` 的最终 ERP 核对编码归一后累计；禁止直接把套件 `subItems.specCode` 原样汇总，否则会把包装或悦希历史查询条码误判成应退规格。
- 平台关联工单在退货快递已签收后会统一刷新成相同的固定剩余处理时效；只有快递长期未签收时，同一退货单号的当前有效工单才可能跨越 48 小时阈值。因此 **48 小时固定批次不是当前有效关联组的完整定义**，不得用“是否进入本批”代替“是否仍在平台待商家处理”。
- 系统只在平台当前详情明确出现「多次使用」并给出关联工单号时进入本分支。对平台点名的关联工单：在本轮 48 小时固定批次中 → 只认本轮新采集；不在本轮批次中 → 只按该工单号精确查询历史 simulation。禁止脱离平台提示主动按退货单号扫描历史。
- 当前批次中的关联工单尚未采集时，必须延迟到该工单后续采集完成再回算；旧 simulation 不得顶替本轮数据。A 页面给出的 A→B 关系对本批 B 同样生效，当前批次内的关联链继续沿 A→B→C 采齐。
- 延迟等待组成员期间，立即为当前工单及尚未采集的同批关联工单写入“暂不可执行”的安全占位结果，覆盖它们可能残留的旧 approve；普通退货退款即使命中自动分支，也要等本批详情全部采集完成后再执行，避免后出现的单向关联来不及阻断退款。
- 历史关联工单**不参与当前申请数量累计**。只有历史记录明确 `decision.action=approve` 且存在 `executedAt` 时，才按该历史工单自己的应退数量记为“历史已退款占用”；随后用 `ERP 当前实收 - 历史已退款占用 = 本次可用数量`，再与当前批次关联工单的应退数量逐规格比较。历史未成功执行退款则占用为 0。
- 赠品去重跨当前组与历史已退款占用共同生效：同一个 `giftSubBizOrderId` 只代表一套实际赠品；历史已经成功退款占用过的同一赠品子订单，本次不得再重复占用一套。
- 平台点名的关联工单如果既不在本轮 48 小时采集、历史 simulation 也找不到 → 不推断是记录丢失还是特殊/恶意重复申请；推理结果必须显示缺失工单号并转人工。即使最终转人工，也必须继续展示当前已取得的订单应退规格、ERP 已收货退货明细和逐规格对应关系；这些内容只作为人工判断证据，禁止因缺失关联工单而据此单独判定多退、少退或是否应退款。
- 所有已收货行必须满足 ERP 售后单号唯一、退货单号与当前工单一致、`returnQty` 等于商品明细良品与次品合计；任一规格少退、含次品、缺少规格编码、商品档案或入库行证明不完整 → 转人工。
- 扣除历史已退款占用后，本次所有应退规格仍有足够可用实物 → 可同意；只有再扣除本次应退后仍然剩余的商品，才允许提示为实际多退。

> ⚠️ **免退配件（不计入应退/实退数量）**：以下3种包装配件无需退回，ERP入库明细中若含这些商品需排除在数量核验之外：
> - HEE悦希雪梨纸（含「悦希雪梨纸」）
> - HEE悦希印花礼袋-白（含「悦希印花礼袋」）
> - HEE悦希印花礼盒（天地盖）白色（含「悦希印花礼盒」）

**工单已有退货单号，但 ERP 搜不到对应售后入库记录时的处理**：
- 剩余时效 > 12h → 系统自动标记「等待重查」
- 剩余时效 ≤ 12h → 自动拒绝，原因"仓库暂未收到此件，已反馈快递找件"
- 下一次同账号 48 小时清单完整读取后，该自动等待项如未再出现，不继续保留旧推理；改为“未出现于本次 48 小时清单”的异常结果并进入「待确认」，不自动同意、拒绝或归档。

### Step 4：验收判断

```
主商品数量吻合 + 全良品 → ✅ 继续判断赠品
主商品数量吻合 + 含次品 → ⚠️ 上报人工（见 INDEX §0.2）

有赠品：
├─ ERP 明确未发货（待审核/待打印快递单/待发货，且无快递单号）→ ✅ 不计入应退清单
├─ 赠品有入库记录 + 数量吻合 + 全良品 → ✅
├─ 赠品有入库记录 + 含次品 → ⚠️ 上报人工
└─ 已发出或无法证明未发出，且赠品无入库记录 → 进入 Step 4b（赠品未退回）

主商品数量不符（实退 < 应退）：
├─ 先做包裹级核验（Step 2b），确认未签收包裹（在途）不算少退
└─ 排除在途因素后仍确认少退 → 上报人工核对退款金额和后续动作
    ⚠️ 当前采集只有工单级售后总金额，没有每个子订单自己的支付金额。
    多子订单部分退款不得按数量自行均摊，也不生成推荐退款金额。

全部通过 → Step 5 同意退款
```

### Step 4b：赠品未退回

```bash
# 搜唯一赠品子订单号；同一赠品子订单可能拆成多个发货包裹
node cli.js erp-search <赠品子订单号>
```

当前观察阶段采用以下边界：

- 一个工单按唯一 `giftSubBizOrderId` 识别赠品；该赠品子订单可以对应多个 ERP 发货包裹/快递单号。
- 必须以 ERP 搜索结果枚举该赠品子订单的全部运单并去重，再逐单读取物流；禁止只看第一行或第一单。
- 只有当前商品核对**已经识别为赠品未入库/不足**时，才把这些发货物流加入推理结果作为人工复核证据。赠品已经随本次退货正常入库时，不增加这组观察。
- 每个包裹独立展示是否命中现有 `hasConfirmedReturn()` 退回证据；例如仅有“收件人要求退回，等待发件人确认”时仍不算明确退回。
- 如果赠品包裹只有“收件人要求退回，等待发件人确认”等待确认态，或没有明确退回证据，继续保留人工异常，不开放退款执行。
- 如果主品按自身应退数量已经完整入库，且赠品全部发货包裹都已出现明确退回证据（包括已在退回途中、到达商家仓库、已退回签收），推理结果必须明确写成“主品完整退回 + 赠品全部进入明确退回链路，实际退回商品不存在少退”；禁止继续把主品与赠品合并后的差额描述成“主品少退/退货数量不足”。此时允许人工确认后执行同意退款，但必须保持 requiresHumanReview=true、autoExecutionBlocked=true、humanTriggeredExecutionAllowed=true，禁止无人自动执行。
- 这项观察能力不扩大现有“赠品明确未发货”规则，也不改变其它七天无理由正常工单；只补充原本已经落入“赠品未退回/入库不足”的订单。

现有未发货判断保持不变：ERP 明确未发货（待审核/待打印快递单/待发货，且无快递单号）时，仍按当前既有规则处理；本阶段不在此处新增任何新的自动通过条件。

### Step 5a：同意退款

```bash
node cli.js approve <工单号>
```

### Step 5b：拒绝退款

需要物流截图作为凭证（以下步骤依次执行）：

1. 读物流文字（已在 Step 2b 中读取）
2. 截物流截图（需先在鲸灵弹窗切换到对应包裹 tab）
3. 执行拒绝命令：

```bash
node cli.js reject <工单号> <原因> "<详情文案>" <图片URL>
```

拒绝原因文案参考：
- 赠品未退回：`已收到退回主商品，但赠品暂未收到退回，请将赠品一并退回后再申请退款`

## 决策快速参考

```
鲸灵读详情（记录货号/赠品/退货快递单号/主品 afterSaleNum/售后说明）
  ↓
商品对应表+档案V2 → 核实单品明细（必查）
  ↓
ERP售后工单新版 → 搜退货快递单号 → 展开所有入库行 → 核对名称/数量/良品
  ↓
全通过（无次品）→ 同意退款
次品 → 上报人工
赠品无入库 → 查赠品 ERP 发货状态
  ├─ 待审核/待打印快递单/待发货 + 无快递单号 → 未发货，不要求退回
  └─ 已发出或无法证明未发出 → 查赠品发出快递
      ├─ 有退回物流 → 等待入库，人工跟进
      └─ 无退回物流 → 拒绝退款（赠品未退回）
数量不符 → 先包裹级核验（未签收≠少退）→ 确认少退后人工核对退款金额
```

## 已知坑位（退货退款流程）

- `[∞/永久保留]` **#6 必须展开所有行**：ERP 售后工单新版必须展开**所有**货物状态=已收到退货的行，不能只看第一行
- `[∞/永久保留]` **#12 多包裹快递单号不同**：物流弹窗每个 tab 是不同快递单号，禁止假设多包裹快递单号相同，必须逐 tab 读取
- `[∞/永久保留]` **#13 包裹数以ERP为准**：包裹数量必须以 ERP 订单管理搜索结果行数为准，鲸灵弹窗 tab 数可能少于实际包裹数
- `[∞/永久保留]` **#15 逐一核验再同意**：ERP 搜完后必须逐一核验所有包裹物流退回状态，不能搜完直接同意
- `[∞/永久保留]` **#31 部分退货金额固定人工核对**：“退未拆的”不等于违规，但当前没有逐子订单支付金额，系统不能可靠计算部分退款比例或推荐金额；确认真实少退后交给人工处理。
- `[∞/永久保留]` **#36 必读主品 afterSaleNum**：必须从 `subBizOrderDetailDTO` 读主品 `afterSaleNum`，不能靠 attr1 文字推断应退数量；应退主商品总数 = subItemNum × afterSaleNum。赠品当前按真实 `giftSubBizOrderId` 对应的一套商品档案计算，不用主品 afterSaleNum 放大
- `[∞/永久保留]` **#44 仅退款多包裹**：必须核对「ERP发货套数 vs 买家申请套数」，ERP发货总件数 ÷ subItemNum > afterSaleNum → 上报人工
- `[∞/永久保留]` **#45 数量不符先包裹核验**：数量不符时禁止直接判"少退"，必须先做包裹级核验区分在途拦截件和真实少退
