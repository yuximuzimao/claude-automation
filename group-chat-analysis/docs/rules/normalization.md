# 消息重建与去重规则

## 原则

OCR block 不是消息。Normalize 层必须先根据几何位置、相邻关系和 UI 结构重建消息，再做跨屏去重。

缺失字段必须保持未知，不得猜测。

## 输入

Normalize 的正式输入是符合 `schemas/capture-page.schema.json` 的 page records；输入字段与类型只以该 Schema 为准。

Normalize 读取 block 时继承所属 page 的 batch/group/page 上下文。`page_index` 只表示采集顺序，不能直接当作聊天时间顺序；窗口 frame 只用于来源审计/诊断，不作为消息身份或跨页去重依据。

## 输出

输出必须符合 `schemas/message-record.schema.json`。

v1 至少区分：
- 普通文字；
- 系统文字；
- 图片占位；
- 语音占位；
- 文件占位；
- 表情/其它占位；
- unknown。

只有普通/系统文字是当前分析重点，其它类型用于说明消息流中存在非文字内容。

## 几何重建

正式算法应基于相对位置而非绝对屏幕像素。当前已用真实 QQ“聊天记录”窗口连续多页验证普通文字消息，规则如下：

1. 先应用 capture 给出的正文区域，只在消息列内参与重建；正文区域外的工具栏、日期侧栏和右侧控件即使被 OCR 成文字/符号，也不得并入消息。
2. 先按 bbox 的垂直重叠/基线把 block 归并成视觉行，再按视觉从上到下排序；同一视觉行内从左到右拼接。真实样本已出现同一行被 Vision 横向拆成两个 block 的情况，不能把两个 block 错当成两行。
3. 日期分隔文本只作为后续消息的日期上下文，不单独生成消息。
4. 普通消息头必须同时具备“文本末尾可解析为 `HH:MM`”和“小于正文主字体”两类证据。当前环境以该页普通正文 block 高度中位数为基准，头部高度上限取约 `0.95 × 正文中位高度`；QQ UI/缩放变化后必须重新校准，不能改成固定像素阈值。
5. 时间前可见文本作为 `sender_display`；如果 OCR 只识别出时间，`sender_display=null`。禁止因为相邻消息昵称相同就把上一条昵称自动继承下来。
6. 一个已确认头部之后、下一个头部或日期分隔之前的可见文字行先作为同一消息候选保留。真实样本已验证一条消息可以同时出现回复/引用提示与正文等多行可见文字；v1 不猜这些行的语义角色，统一按视觉顺序保留，并在 `content_text` 中用换行保持行边界。若两个相邻文字行之间的空白明显超过普通正文行距（当前环境保守以约 `1.5 × 正文高度中位数` 为上限）且中间没有识别到头部，则不得直接合并，应视为“可能漏识别消息头”的不确定边界。
7. 页面顶端在第一个有效头部之前出现的正文、只有头部但正文未出现的候选、以及正文贴到页面底边的候选，都视为**页边缘残片**，不得在单页阶段直接产出最终消息。真实相邻页已验证这类残片会在下一页重新出现为完整候选，应留给相邻页拼接处理。若整页只有日期 + 消息头、完全没有正文高度样本，不得因“无法估正文高度”丢弃整页；只允许用消息头高度中位数的 `1.25×` 作为结构性 fallback 来识别头部，并全部保留为 `header_only` fragment，不生成伪正文消息。
8. OCR 无法可靠识别昵称或时间时保持未知；不得模型猜测。只有日期上下文和时间文本都可靠时才考虑生成绝对 `timestamp`，否则保留 `timestamp_text` 并令 `timestamp=null`。

系统消息已有居中行真实样本，可按独立 system 候选处理。媒体方面，真实样本已确认嵌入图片中的 OCR 会表现为同一消息头下连续多行、且绝大多数行高度明显低于该页正文主高度；当前只在“至少 3 行且 ≥80% 行高度 `<= 0.85 × 正文主高度`”时保守降级为 `unknown`，`content_text` 写中性标记“非文字内容（图片/表情等，未解析）”，不把图片内 OCR 当聊天正文。无 OCR 的纯图片/表情继续忽略，不为 v1 增加额外高风险视觉识别。其它未覆盖布局先保留 unknown/不完整候选，不套用普通文字规则硬猜。普通消息内部多行可见文字仍无需先区分“自然换行 / 回复引用 / 其它附属文字”，证据不满足媒体门禁时按视觉行完整保留。

## 顺序

当前 QQ“聊天记录”窗口单页原始视觉从上到下是**新→旧**。Normalize 必须先按视觉上→下完成视觉行归并、消息头/正文分组和页边缘残片判断；只有完整消息候选在单页重建结束时整体反转为**旧→新**。

跨页：`page_index` 递增代表从新页向更旧历史采集。跨页去重只接收已经由单页重建转换成旧→新的消息列表，再利用相邻页重叠区拼接为全局旧→新顺序。

最终 messages 与 current.md 均按实际聊天时间方向由旧到新输出。

## 去重：禁止全局字符串去重

以下情况不能判重复：
- 同一个人隔一段时间再次发“好的”；
- 多个人都发同一句话；
- 广告重复；
- 相同系统提示再次出现。

所以禁止用 `sender + text` 的全历史唯一键直接删除消息。

## 跨屏去重

只在相邻/近邻屏之间做重叠消除。

优先证据：
1. 连续多条消息序列同时重合；
2. sender/text/相对顺序一致；
3. 可用时结合 timestamp_text；
4. bbox只用于页面内几何，不作为跨页身份。

推荐以“最长连续重叠序列”方式找 page N 的尾部与 page N+1 的头/中部重合。

单条短文本原则上不足以独立确认重复。

## OCR差异容忍

同一条消息在两屏中可能发生轻微 OCR 差异。v1 以“不误删真实消息”为第一优先级：

- 规范化后的昵称完全相同，才把两个已识别昵称作为同一发送者；相似昵称不做身份归并。
- 一侧昵称缺失、另一侧存在昵称时，不做破坏性去重，宁可保留重复消息。
- 双方昵称都缺失时，只能依赖连续序列、正文、时间等其它强证据；不能据此推断成员身份。
- `message_type` 必须一致；双方都识别到 `timestamp_text` 时也必须兼容，不能因为正文相同就跨类型或跨时间删除。
- 正文可在相邻页连续序列中使用受控模糊匹配；只有两条消息的最小重叠还必须存在额外强锚点。匿名长正文的精确锚点至少 8 个规范化字符。
- 同一已确认重复消息选择 canonical 时，优先保留更完整正文，再比较元数据完整度和 OCR confidence。高 confidence 不能覆盖明显更完整的低 confidence 正文。
- 头像指纹不再是 v1 正式入口门禁。以后只有真实 dry-run 证明“保守规则产生的重复量已经影响使用”时，才重新评估是否需要增加视觉身份辅助。

## 增量锚点

每日增量停止锚点必须是一个**连续消息序列**，而不是单条句子。当前正式最小锚点为上一 completed batch 的最后 2 条 canonical message，保存 `sender_display / content_text / timestamp_text / 相对顺序`；两条都必须按现有保守消息匹配规则连续命中，单条命中不足以停止。

新增量 batch 把上一 completed 的尾部锚点复制为不可变 `start_anchor`。每抓完一份 durable raw 后，对当前已抓页面做保守组装；命中 `start_anchor` 后，anchor 本身及更旧消息全部裁掉，只把 anchor 之后的新消息重新从 sequence 0 编号并提交。若同一锚点序列在已抓范围里出现多次，选择**最早的确认匹配**，错误成本偏向多保留重复而不是误删真实新消息。

0 条或 1 条新消息也必须合法：0 条时不向 `messages.jsonl` 写旧 anchor；1 条时新的 completed anchor 由“旧最后一条 + 新消息”组成。下一批仍使用新的连续尾部 anchor。
