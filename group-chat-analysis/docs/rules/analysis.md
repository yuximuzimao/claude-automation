# GPT 分析规则

用途：这是 `ANALYSIS_BATCH`、`ANALYSIS_DESIGN` 和 `PROMOTION` 的唯一分析 owner。项目级任务先由 `../OPERATING-SOP.md` 分类；采集、规范化和存储问题不在这里处理。

全量分析的工程化实施顺序、数据质量门禁、语义聚类提案和验收流程详见 `../ANALYSIS-DATA-QUALITY-SOP.md`；本文件仍是内容判断与用户终审的唯一业务规则。

## 输入

默认且唯一的日常入口：

`runtime/inbox/current.md`

除非排查采集错误，不让 GPT 日常读取 raw OCR、截图或状态文件。

## 分析目标

这个项目不是普通聊天摘要器，也不是让 GPT 替用户做最终信息取舍的“精选新闻页”。核心目标是：从高流量、低信息密度的群聊中尽可能完整地提取**第一次值得用户看一眼的有效信息**，通过话题合并、重复消除和已有知识比对降低阅读量，但把最终“有用 / 没用”的决定保留给用户。

第一轮 topic card 是**候选索引层**，不是最终展示清单。后续审阅可以在保留原卡/canonical 可追溯性的前提下：合并多个原卡、拆分混合卡、隐藏无信息增量的节点、从 canonical 补回第一轮漏掉的硬信息，或在发现串人/错链/错误总结时让旧卡退出默认审阅流。

默认用户行为模型是“看过就产生价值”：用户不要求 GPT 第一次就完全理解其已有知识。只要信息具有明确、游戏特异的事实或操作内容，且系统不能确认用户已经掌握，就应优先进入**首次阅读队列**；用户看完后只做两类终审：

- **没用**：丢弃出默认流，但记录为已阅；相同结论以后不重复展示；
- **有用**：写入本项目知识库，同时也记录为已阅；相同结论以后不重复展示。

AI 自己在展示前过滤掉的内容不等于“用户已阅”。系统过滤必须保留原因和来源；如果后续发现过滤规则有误，仍可重新进入首次阅读队列。

后续重点关联包括：职业、任务、副本、专业技能、装备、插件、防骗、经济/打金、版本与服务器等可复用信息；对当前魔兽项目有直接影响的内容；以及新出现或出现新语境的玩家黑话。普通闲聊、刷屏、广告和没有游戏特异信息增量的泛常识可以不进入展示层，但不能用关键词预筛代替完整阅读。

## 批次分析 SOP

前提：对应 capture batch 已 completed，`runtime/inbox/current.md` 已由正式 builder 生成。语义判断仍由 Codex/模型执行，但分析运行边界已有正式 CLI：先用 `python3 -m src.app.run_analysis --prepare-work` 冻结本批输入与知识基线；完成本节 1–9 的语义审阅并更新正式分析产物后，`--prepare-review` 生成与 work package/最终 artifact hash 绑定的 draft receipt；只有显式审阅为 `reviewed_analysis_ready` 后才能运行发布。

每个批次按以下顺序处理：

1. 读取并确认 batch id、群、消息数和时间范围，只使用 `current.md` 中的规范化消息；
2. 第一遍完整提取本批涉及的话题、具体说法、事实线索、攻略、经验、机会线索和黑话，不先按“现在用不用得上”删除；
3. 第二遍识别真正重复、同一讨论连续补充、跨日连续过程、新增条件、替代方案、纠错和冲突。重复的旧结论不重新占阅读队列；只有新增机制、条件、数字、操作、例外、替代方案或真正改变原结论时才重新出现；
4. 将同一讨论中互相补充的事实合成一个可读话题，不把一个完整讨论拆成多张碎卡；同一段聊天中属于不同对象的独立事实仍要拆开；
5. 在展示前补齐最小必要身份信息，让用户能立即知道“这条信息在说什么对象”。基础补齐属于分析职责，不需要用户额外下令：任务尽量补地图、正式任务名、任务 ID、简要目标；Boss 尽量补副本、等级/阶段、Boss 名称、顺序和相关难度；职业/配装尽量补职业专精、版本、具体阈值/数值和适用条件；装备尽量补正式名称/ID、部位、来源和限制。能从现有项目或可靠静态资料直接确定的应直接补；需要额外搜索、比对或研究才能形成完整结论的，标成“可补全候选”，等待用户统一下令后再查；
6. 对比已阅记录、知识库和目标项目已有事实。结论已经看过且没有新增信息时不展示；只有可信度升降、更多人重复同一结论时，后台静默更新证据状态，不重新占阅读队列；
7. 对剩余信息建立“完整可读事实 → 必要原文回链 → 可选 AI 推断”。AI 推断只在多个事实组合后能产生具体、可验证、可能改变做法的新判断时出现，不为了填栏目强行生成；
8. 核对覆盖情况，区分已归组消息、纯黑话、无语义闲聊、重复、广告/推广、泛常识、系统过滤、可补全候选和首次阅读候选；凡未进入展示层者记录原因，确保过滤逻辑可复核；
9. 完成语义更新后生成 reviewed receipt，交给正式 `run_analysis` 做质量门禁、staging 页面、immutable release 与 `analyzed` 状态推进；用户阅读页从正式 release / 本机 review server 展示，运行时内容均留在 `runtime/`，不得提交 Git；跨项目内容只标为候选。

一条消息只出现一次、篇幅很短或没有引起讨论，都不能成为降权或删除理由。只要它包含明确、游戏特异的信息增量，就可以进入首次阅读候选；来源强弱只作为后台证据状态。讨论次数和参与人数只描述聊天现象，不代表真实性，也不作为用户可见的价值排序。

分块分析时必须保持群、时间与讨论连续性。各块先宽松提取，再做跨块全局归组和排序；不得在分块前用关键词筛掉消息。

## 首次阅读队列规则

首次阅读队列回答的不是“GPT 认为最重要的是什么”，而是“这些聊天里哪些信息值得用户第一次扫一眼”。只要具有明确、游戏特异的信息增量，且未被已阅/知识库/项目已有事实覆盖，就应保守地让用户看到；不要因为当前暂时用不上、只出现一次、来自封测或仍需版本核验而自动隐藏。

优先进入首次阅读队列：

- 明确机制、数值阈值、限制条件、来源、触发关系；
- 可复用路线、玩法、操作、配置、排雷和替代方案；
- 具体任务/Boss/职业/装备/插件等对象上的新事实；
- 单次实测足以提供一个新的操作关系，即使仍需版本核验；
- 旧知识新增了机制、条件、数字、操作、例外或另一种实测可行方案；
- 封测/新版本中的琐碎事实，只要未来可以与其它证据共同形成对服务器的完整理解。

默认系统过滤：

- 纯审美、情绪、生活安排、角色目标和无决策约束的个人感受；
- 只有“发生过”，但无法补出任何机制、条件、操作或对象特异信息的经历；
- “打副本要躲技能”一类跨游戏都成立的泛常识；
- 只有方向性原则，且关键对象/门槛/输入完全缺失、当前也无法自动基础补齐的信息；
- 目标项目、已阅记录或知识库已经明确掌握，且本次没有新增边界/例外/替代方案的旧结论；
- 只有黑话/术语释义的内容；
- 把若干聊天重新包装成“玩家心理 / 团队文化 / 产品适配 / 泛化方法论”的框架，但没有留下具体对象、数值、机制、动作、门槛或可复用判断条件的内容。用户已确认这类“道理正确但不能直接拿来用”的抽象总结通常没有首次阅读价值。

当用户连续判定某一类内容“没用”并确认共同原因后，先按该原因扫描剩余队列，列出一批高概率同类候选供用户确认；不要因为一次模式识别就直接大范围自动丢弃。已经确认的一批可以正式写入 discard，边界不清的候选继续保留到用户实际看到再决定。

数值并不要求先形成完整统计模型才能展示。只要数值本身属于具体对象的重要事实或能帮助建立认知，可以作为带条件的样本出现；缺关键基线时必须把缺口写清，不能把单一样本升级成普遍规律。

用户明确判定“没用”后，该语义结论进入已阅丢弃态；用户明确判定“有用”后进入知识库。两者都不再重复占首次阅读队列，但原卡、来源和 canonical 永不删除。发现一类无价值信息时，优先提炼通用过滤规则并检查同类剩余信息，不只做单卡特例。

## 语义清洗与知识单元（Silver 层）

第一轮 topic card 只是原始语义切片，不能直接作为最终阅读单元或资料库条目。正式分析必须在 topic card 与页面之间增加一层**规范化知识单元**，职责类似数据工程中的清洗/标准化层：去重、实体对齐、跨日合并、字段化、来源追溯，但不丢失原始证据。

处理窗口以“本次需要分析的完整时间范围”为边界，不按自然日强制拆话题。同一对象/问题在 5 天或 10 天内被多次讨论，只要是在补充同一个结论，就应汇成一个知识单元；日期只作为证据时间，不作为展示拆分条件。

**分析窗口与阅读批次必须分离。** 历史补课时可以一次分析半个月甚至更长范围，以便跨日去重和合并；页面仍应把已经清洗完的知识单元切成小批次供用户逐批处理。阅读分页/批次只是 UI 负载控制，不能反过来成为语义切分边界。日常分析通常天然只有一天左右，历史回看则默认全窗口清洗后再分页。

一个规范化知识单元至少包含：

- `subject`：明确对象，例如 NAXX、双子女武神、冰DK、某任务/装备；
- `question`：这组信息到底回答什么问题；
- `kind`：信息结构类型，例如 `mechanism / ordered_route / comparison / strategy / sample / dynamic_signal`；
- `scope`：服务器、版本、阶段、区服、职业、等级、时间窗口等适用边界；
- `canonical_facts`：去重后的核心事实，不重复保存同义改写；
- `structured`：按 `kind` 使用固定结构，而不是仅保存一段自然语言摘要；
- `evidence_refs`：所有来源卡片及其角色，如 `support / concrete_sample / exception / contradiction / context`；每条引用同时标记 `coverage=full|partial`。只有该来源卡的有效语义已被 Silver 单元完整吸收时才能标 `full` 并让旧卡退出首次阅读队列；只吸收其中一个独立事实时必须标 `partial`，旧卡继续保留直到其余事实也有归属；
- `search_terms`：正式名、俗称、缩写、任务/物品/Boss ID 等可检索别名；
- `evidence_state`：后台证据强弱，可随新材料静默变化；
- `freshness`：静态知识、阶段性知识或动态信号。

关键规则：

1. **实例不重复占一条知识。** 若“199鸟德进NAXX后一车到228”只是证明“NAXX适合作为低装等追赶团本”，应挂为该结论的 `concrete_sample`，而不是再生成一条同义信息。
2. **路线必须结构化。** 学习路线、升级链、装备路线保存为有顺序的阶段/步骤，每步至少写“条件 → 做什么 → 目标/获得什么 → 备注”，不能只写一整段汇总文本。
3. **比较必须合成一条。** 例如不同区服的组团方式，应保存为同一比较对象下的多个 `variant`，不是“二区一条 + 四区一条 + 再来一条总结”。
4. **机制/攻略保存条件关系。** 优先转成“前提/触发 → 现象/机制 → 动作 → 结果/失败后果”。
5. **数值样本与规律分离。** 样本可以支持规律，但单个样本不自动变成普遍结论；其条件和日期必须保留。
6. **同义事实跨日合并。** 新一天只增加支持证据时不产生新知识；只有新增条件、例外、步骤、数值、替代方案或反例时才更新原知识单元。
7. **页面只读 Silver/Gold，不直接读原始 topic card。** topic card 只用于追溯、重建和发现遗漏；用户不应再次承担去重与结构化工作。
8. **按“决策问题”聚类，不按实体名粗暴聚类。** 同一对象可以同时回答多类问题，例如冰DK的“升级时能否保留冰天赋顶T”“双持还是双手”“P6饰品怎么分层”必须是不同知识单元；只有真正回答同一个问题的跨日材料才合并。反过来，不同日期、不同说法只要是在补同一个决策问题，就应进入同一单元。实体只用于候选召回，`question` 才是最终合并边界。
9. **已阅核心与新增边界分开处理。** 某个语义结论已被用户确认后，后续只重复支持同一结论的证据可并入原知识并静默增强；若后续新增的是条件、例外、适用边界、替代方案或纠错，则不能把整组直接升级为 knowledge，也不能让旧 knowledge 被 queue 覆盖。优先把“已知核心”保留为 knowledge，把真正新增的 delta 按它回答的新问题建立 queue 单元。
10. **Silver 默认只清洗首次阅读候选，不擅自复活旧过滤层。** 新的 `queue` 知识单元至少应包含一条当前 `v3_queue` 来源；原本属于 hidden / collection-only / archive / 已阅的卡只能作为支持证据。只有明确确认旧过滤规则漏掉了有价值信息时，才允许从非队列来源新建 queue 单元，并记录为显式补回，而不是因为它“看起来与用户当前项目相关”就重新提升。
11. **未落地的未来改动优先建 `dynamic_signal`，不要伪装成静态攻略。** 当群聊材料主要是蓝贴解读、宣传图、传闻、玩家预测或AI推演时，Silver 应保存 `current_state / indicators / unresolved / changed_at`，明确区分“已确认事实、当前体验问题、未来猜测”。只有正式规则或稳定实测出现后，才把对应部分迁移为 `mechanism / strategy / comparison` 等静态知识。
12. **具体事实优先于方法论。** 原文出现明确对象、装备名、技能名、数值、触发条件、失败现象或操作结果时，`canonical_facts` 必须先把这些原子事实写清楚；“应该综合判断”“不要机械套数字”“先看条件”等方法论只能作为补充，不能替代事实本身。
13. **`coverage=full` 必须覆盖全部独立原子事实。** 同一证据里若同时包含“装备选择 + 数值阈值 + 机制反例”等多个可独立检索、可直接使用的结论，合并进一个 Silver 后仍必须逐条保留；不能因为形成了更高层总结就把其中一部分吃掉。
14. **`kind` 与 `structured` 必须匹配页面契约。** `comparison` 必须有非空 `variants[]`，`ordered_route` 必须有非空 `stages[]`，`mechanism` 至少要有页面可展示的条件/机制/动作/结果之一。结构不匹配应在生成阶段报错，不能输出空表后交给用户发现。
15. **用户看到的 Silver 必须完整展示 `canonical_facts`。** 页面不能只展示第一条事实；结构化表格用于提高可读性，不得成为隐藏其余原子事实的理由。
16. **“卡片无用”不向下继承到原文。** 用户判定某个 Topic Card / Silver 整合主题无用时，必须先检查其原始证据里是否夹有能独立回答其他问题的具体事实；有则拆成独立知识单元后再丢弃原主题。不能因为上层总结无价值，就连带删除原文中的装备名、数值、活动周期、操作步骤或机制发现。
17. **窄用途事实不要强行扩写成大框架。** 如果原文真正可复用的只有一条针对性结论，例如“想刷某坐骑时，多角色可增加每日尝试次数”，就直接保留这条窄事实；不要为了跨日整合而附加泛化方法论、RNG常识、职业条件等无关说明，使一条本来有用的信息变得冗长难读。同一段 canonical 原文被多个 Topic Card 重复覆盖时，后台 lineage 仍保留全部 `evidence_refs`，但可对被更完整证据覆盖的重复引用标记 `display=false`，前台不重复展示；这只影响阅读体验，不改变 coverage 或来源血缘。
18. **Topic Card / Atomic Claim 是索引层，不是原文的无损替代。** `coverage=full` 只能说明当前已抽出的卡片语义被完整吸收，不能据此断言对应 canonical 原文里没有别的独立事实。人工验收若发现原文中存在未进入 Topic Card / Atomic Claim 的具体对象、数值、机制、动作、门槛或时效事实，必须回到 canonical 原文补回，并按其真正回答的决策问题更新现有 Silver 或新建独立 Silver；不能因为它与原卡时间相邻就塞回旧主题。已被用户 discard 的旧聚合不得作为新事实容器，新事实应单独进入 queue。
19. **连续原文窗口不是新的全量采矿区。** “查看原文”按已验证时间/行范围展示连续聊天，因此窗口里允许自然夹入相邻无关话题；这本身不是数据错误。二次清洗只可补回与当前 evidence discussion 明显同属一个讨论、但被上层抽取漏掉的独立事实；仅因相邻聊天“看起来有用”不得新增 Silver。无法确认是否同一讨论时宁可不救，避免证据窗口越宽、知识数量越膨胀。

推荐的结构模板：

- `ordered_route`：`stages[] = {condition, action, target_or_gain, purpose, notes}`；
- `comparison`：`variants[] = {scope, behavior, consequence}`；
- `mechanism`：`conditions[] / mechanism / action / outcome / failure_mode`；
- `strategy`：`preparation / sequence[] / switch_conditions[] / failure_modes[]`；
- `sample`：`context / observed_value / comparison_limit`；
- `dynamic_signal`：`dimension / current_state / indicators[] / changed_at / unresolved[]`。

## 页面标签与内部专题

Silver 层可以保留细粒度 `topics`，用于语义清洗、检索、资料库路径和后续聚合；这些内部专题不等于用户页面标签，禁止把任意 `topics` 原样展开成筛选按钮。

普通信息页面恢复稳定的一级专题结构。当前一级专题为：职业、副本攻略、任务与练级、装备机制、专业技能、经济 / 打金、插件 / 故障排查、防诈骗经验、PVP / 野外生态，以及兜底的“其他”。无限服不进入这套普通信息分类，继续使用独立动态专题档案；未来出现新的同类特殊专题时再单独讨论。

当前只允许两个一级专题继续下钻一层：

- **职业 → 具体职业**：DK、圣骑士、德鲁伊、猎人、法师、萨满、牧师、术士、盗贼、战士等。暂不继续细分到专精、流派或职责；
- **副本攻略 → 具体副本**：例如 NAXX、奥杜尔、TOC、ZAM 等。暂不继续细分到 Boss、机制或打法；
- 任务与练级、装备机制、专业技能、经济 / 打金、插件 / 故障排查、防诈骗经验、PVP / 野外生态当前全部保持一级扁平结构。

Silver 已有的“练级、团本、NAXX、G团、专业、插件”等细粒度语义可以保留，但展示层只把这些已知语义**映射回上述稳定一级专题**，不据此创造新的一级标签。无法稳定归入现有一级专题的内容才进入“其他”；在用户完成对当前清洗结果的验收前，不继续拆分“其他”。

职业专题只收“职业本身是结论对象或清洗后已明确标为该职业”的内容。正文中的比较对象、角色背景和顺带举例不得仅凭词面出现把信息拖入职业专题。一条知识可以同时关联多个一级专题，但页面一次只选择一个一级专题；选择职业或副本时，再可选一个对应二级标签。

## 事实优先的展示契约

用户可见的每个话题首先必须是一个**完整可判断的信息单元**，不是裸摘要。默认顺序为：

1. **对象身份 / 基础上下文**：尽量补齐地图、任务名/ID、职业专精、装备名/ID、副本/Boss/顺序、版本等最小必要上下文，让用户一眼知道自己是否接触过这个对象；
2. **新增事实**：准确说明本次群聊真正增加了什么机制、数字、条件、操作、例外或替代方案；群友说法不能冒充外部已证实事实；
3. **可选 AI 推断**：只有确实产生具体新判断时才出现，并明确与来源事实分开；
4. **原文 / 证据详情**：默认收起，用户需要时再展开查看。

原文回链必须以卡片自身保存的时间范围/来源范围为主要锚点；不得仅凭全日关键词、数字或语义相似度自动把另一段聊天当作用户可见证据。证据不足时宁可不挂猜测原文。

AI 可以从事实中进一步整理可执行攻略、经验规律、潜在机会、项目影响或多个事实组合后的新推断。推断必须有事实依据、适用条件和不确定点；没有新的具体结论就不生成“AI分析”栏目。

只有黑话、没有其它实质信息的消息，不生成普通话题，只进入黑话库。若一条实质信息同时包含黑话，事实照常保留，黑话含义另在词典中按语境更新，不复制整条信息。

## 用户判断与可信度

页面不再要求用户维护“必看 / 应该看 / 可以看 / 一般”等复杂价值等级。首次阅读队列中的信息默认已经通过最低有效信息门槛；用户终审只需要：

- **没用**：记录为已阅并从以后默认阅读队列排除；
- **有用 / 存入知识库**：写入对应专题知识库，并同时记为已阅。

用户用自然语言给出的原因仍应记录，因为它可以反向改进系统过滤规则，但不要求用户额外打分。

可信度是后台证据属性，不是默认页面的阅读优先级，也不因为证据升级就重新展示旧信息。系统可以随着单人经验、多人独立支持、游戏内证据、可靠攻略或正式资料的增加而静默调整可信度；只允许改变“证据状态”这个变量，不得因此改写原结论的语义、适用条件或用户判断。真正出现新机制、新条件、反例、替代方案或规则变化时，才作为新信息重新进入队列。

群聊信息来源天然可能不准确。知识库保存的是“用户认为值得保留的知识线索 + 当前已知证据”，不是把群聊说法自动认证为事实；真正要用到时，可以再结合用户项目、游戏内实测或网络资料核验。

讨论次数和参与人数可以提高某一说法在后台的支持度，但“很多人都这样说”本身不构成新的阅读价值。

## 连续过程、重复与信息组

“相关内容集中展示”的目标是让用户一次读完一个完整讨论，不是简单把相似卡片挨着排。同一讨论里互相补充的多个事实优先合成一个话题，话题内部列出若干新增结论；这样用户记住的是“我看过这个话题”，而不是多个碎片卡号。

连续过程聚合仍至少要求同一发言人、同一角色/对象、同一连续过程，且合并后能产生比单节点更有意义的信息。升级进度中的 78 / 79 / 80 等重复节点只作为证据，不逐条占阅读队列。

跨批次重复按**语义结论**处理，不按文本相同处理：

- 完全相同的旧结论：不展示，只可静默增加证据支持度；
- 新增具体机制、条件、数字、操作、例外：只展示新增部分；
- 新增另一种实测可行方案：保留为同一知识对象下的另一种方法，不自动把旧方法判错；
- 真正否定旧结论：展示纠错，并保留旧结论的历史纠错关系；
- 只有可信度变化：后台更新，不重新展示。

同一段连续聊天也可能包含两个完全不同的有效事实；时间相邻不代表必须合并。职业机制与具体 Boss 实战技巧等不同对象应拆成独立信息。

旧版独立“合集”页面不再作为目标 UI。强相关/跨日综合只作为专题知识或动态档案内部结构存在，不维护一套平行合集页面。

## 页面与报告视图

页面目标是**最低使用摩擦**，不是把所有分析能力做成复杂仪表盘。底层可以保存完整关系、证据和状态，但默认 UI 只保留用户真正会使用的入口。

当前目标页面只保留四个顶层入口：

- **新信息**：首次阅读队列；默认入口。只展示尚未由用户终审、且未被已有知识覆盖的有效新信息；
- **资料库**：用户明确判定“有用”的长期知识。以关键词搜索为第一入口，并按职业、副本、任务、装备、专业、插件、防骗、经济等专题分层；
- **无限服**：当前唯一动态专题档案。展示“截至现在我们对无限服知道什么”，按练级/发展、经济与打金、专业、规则风险、职业玩法、服务器生态等维度持续吸收零散证据；AI 综合判断留在专题内部，不把普通讨论热度单独当趋势；
- **黑话**：语境化词典。

职业与其它专题在“新信息”和“资料库”里都是同级入口，不做两个筛选器叠加。首层专题没有内容时不显示。关键词搜索应始终比复杂筛选更容易使用。

“可补全”不是独立知识分类。分析时如果某条信息具有潜在价值，但需要额外网络搜索/资料比对才能补足关键事实，则在新信息中标一个轻量状态；用户可以在看完本批后统一要求“把这次可补全的查一下”。

资料库的主要用途是**以后按部分关键词找回曾看过的知识**，而不是要求用户日常浏览。动态专题档案则用于把大量单独价值不高、组合后有价值的证据逐渐形成完整认知；目前只对无限服启用。

所有页面都是同一分析结果、已阅记录、知识库和动态专题状态的投影，不复制事实。旧版“主信息 / 待核验 / 合集 / 本期总览 / 长期追踪 / 攻略知识 / 项目相关”不再作为默认顶层 UI。

## 知识库与已阅状态

已阅状态只表示“用户已经看过这个语义结论，不需要重复打扰”，不等于知识被长期保存。知识库只保存用户明确判定“有用”的内容。

知识库优先支持部分关键词检索，并保留可逐层浏览的专题路径，例如：`副本攻略 → TOC → 双子女武神`、`职业 → DK → 冰DK`、`任务与练级 → 风暴峭壁 → 任务名`。知识条目保留足够的对象身份、结论、来源回链和后台证据状态，使用户只记得部分关键词时仍能找回。

用户判定“没用”时只保存最小已阅语义指纹/关系和必要来源引用，用于以后去重，不把没用内容伪装成知识库条目。系统自动过滤的内容单独保存过滤原因，不写成用户已阅。

## 无限服动态专题档案

无限服目前是唯一启用的动态专题。原因不是“讨论多”，而是它属于仍在封测、规则和经济生态尚未稳定的新服务器：大量单条价值有限的观察组合后，可能形成对未来正式开放、玩家发展和打金机会的完整理解。

动态档案至少按以下维度累积：

- 练级与玩家发展：升级节奏、副本经验、野外任务、骑术等成长摩擦；
- 经济与打金：货币稀缺、材料供需、工作室行为、服务价格、潜在赚钱方式；
- 专业与资源：专业/副职业与升级、营地、采集和制造的关系；
- 规则与风险：金币交易、代练、多开、自动化及处罚规则；
- 职业与玩法变化：与现有版本不同的职业技能、循环和系统；
- 服务器生态：只保留能解释整体发展阶段的生态变化，不单独把聊天热度当有价值趋势。

同一观察反复出现但没有新增认知时，只静默增加后台支持度；新事实仍应先进入首次阅读队列，然后再吸收到专题档案。AI 可以在专题内部综合多个观察形成阶段判断，例如经济供需或玩家发展阶段，但必须把“来源观察”和“AI 综合判断”分开。封测信息允许长期保留，并在正式开放后按实际规则逐步复核，不因“尚待正式服核验”降为无效信息。

## 黑话词典

黑话库用于解决“不了解群内语境就会读错消息”的词义问题，不是普通游戏术语百科。真实词条、原文和昵称等私密样例只保存在 `runtime/`；Git 中只保存以下长期规则。

### 收词范围

只有满足至少一项时才进入黑话候选：

- 字面义不足以理解群聊实际含义；
- 同一个词在不同副本、物品、职责、服务器或阶段存在多义，错误消歧会改变事实理解；
- 属于玩家群体约定的缩写、身份标签、团型/玩法称呼、交易或练级表达；
- 新出现的说法已经影响 topic card 的切分、分类、事实解释或话题关系。

普通正式游戏名、无需解释的常用简称、单纯昵称、OCR 错字、一次性打字错误和只靠重复频次出现的词不收。是否高频不是收词条件；低频但会造成重大误读的词仍应收录。

### 词条结构

每个词条至少保存：

- `term`：原始词形；必要时记录明确等价变体，但不能把相似字符串自动视为同义；
- `meanings[]`：一个或多个独立释义，每个释义都必须能单独附带自己的语境和证据；
- `context`：副本/装备/职业职责/玩法/招募/交易等最小消歧条件；
- `first_seen` / `last_seen`：该释义在当前资料中的首次与最近出现时间；
- `evidence`：最小必要原文或 topic/source 引用，足够证明该释义而不复制无关聊天；
- `confidence`：对“群内这个词在该语境下是什么意思”的把握程度；
- `scope`：版本、服务器、活动阶段或其它已知适用范围；未知时明确写未知；
- `verification`：`not_needed | useful | required`，区分“群内语义已清楚”和“外部机制/数值仍需核验”；
- `status`：至少区分 `active | ambiguous | deprecated_or_historical`，旧义不得因新义出现而被覆盖。

黑话的褒贬色彩、玩家态度和事实释义要分开保存。带调侃或贬义的称呼不能因此被分析成技术水平、装备水平或玩家价值判断。

### 多义与消歧

黑话必须语境化、可演化。同一个词允许同时存在多个释义，不能为了词典整洁永久绑定单一解释，也不能用“最近一次出现的意思”覆盖历史语义。

分析时按以下证据消歧：

1. 当前连续讨论明确点名的副本、装备、职业、玩法或交易对象；
2. 同一 topic card 内前后句和回复关系；
3. 同一时间段附近已确认的语境；
4. 词典中与当前条件匹配的已有释义。

仍无法唯一确定时，保持原词并标 `ambiguous/待核验`，不得按字面、最高频释义或模型常识硬猜。缩写、单字简称和数字压缩招募语尤其需要此门禁。

### 新增与跨批次更新

每个分析批次都对“新词”和“已有词的新语境”做增量检查：

- 已有释义在相同语境再次出现，只更新 `last_seen` 和代表性证据，不重复新建同义词条；
- 出现新的独立含义时，在 `meanings[]` 新增释义及自己的首次时间，不覆盖旧义；
- 新证据只是补充边界、褒贬色彩或适用条件时，更新对应释义，不伪造新的词义；
- 发现此前解释错误时保留纠错痕迹，将旧解释标为已纠正/历史，不静默改写历史分析；受影响的 topic card/collection 进入重分析候选；
- 长时间未出现不能自动删除词条；只有明确证据表明旧义已退出当前版本/服务器语境时，才可标 `deprecated_or_historical`。

首次/最近出现时间描述的是“当前已采集资料中的观测边界”，不是社区真实首创或绝对最后使用时间。

### 词义与动态事实分离

价格、补贴金额、职业强度、具体掉率、版本机制和团规数值等动态内容不得固化进永久词义。若某个黑话在特定招募或特定阶段确实包含数值，只能保存为“该语境下的解释/示例”，并带日期与范围。

“群内词义已确认”也不等于词里涉及的游戏机制已经被外部证实。例如一个词可以高置信地表示某种玩法，但该玩法当前效率、价格或合规状态仍需要单独核验。

### 与 topic card 的关系

只有黑话、没有其它实质信息的消息不生成普通 topic card，只更新黑话库并保留来源引用。实质话题里包含黑话时，topic card 仍按原本事实建立，词义作为解释引用；不得把整张事实卡复制进黑话视图。

页面的“黑话”视图从同一词典数据投影，至少允许查看词语、各语境释义、首次/最近出现、可信度、范围、新义/多义状态和代表性证据。黑话新增或语义变化可以成为批次状态提示，但不能凭词语出现频次直接提高普通话题价值等级。

## 参与者价值

活跃人员明细由当前批次分析顺手生成，不建立长期昵称注册表，也不把发言数当作主要指标。GPT 可以结合是否提供具体事实、经验、数据、纠错或可核验线索判断参与价值。

结果只保留当前批次所需的显示昵称和消息引用；相似昵称的当前批次归并不应被解释为跨批次真实身份识别。

## 对魔兽项目的边界

群聊分析项目和 `wow-quest-route` 必须分别保存资料，不共享运行时数据库，也不自动互相写入。群友说法不等于已验证任务事实。

本项目可以把信息标成“建议转入魔兽项目”，但流程必须是：

`群聊原文与分析 → 候选信息 → 用户确认 → 目标项目独立核验 → 目标项目保存`

只有用户明确要求进一步核验或写回后，才进入目标项目自己的规则流程。

## 完整历史分析的完成标准

一个时间窗口只有在以下条件都满足后，才可称“完整历史分析完成”：

1. canonical 消息完整阅读，且没有用关键词预筛代替阅读；
2. 独立候选 topic card 切分完成；
3. 跨日支持、冲突、更新、纠错关系和连续过程候选完成；
4. 主要决策型语义家族经过 coverage audit，不再靠预设栏目限制发现；
5. 高影响黑话完成语境化；
6. 首次阅读价值、后台证据状态、补全需求和时间敏感性已经分离；
7. 专题分类和页面视图经过真实历史验证；
8. 已生成首次阅读候选、系统过滤原因、必要的话题组/聚合索引，并完成与已阅/资料库/项目已有事实的比对；
9. 本轮验证出的稳定结构已写回本 owner；
10. runtime 中间产物未误提交 Git。

## 模型职责

GPT负责语义提取、主题聚类、事实与原文对应、争议识别、摘要、扩展分析和核验建议。

GPT不负责判断采集是否完整、控制 OCR 去重/滚动/重试、修改原始消息，也不得自动执行跨项目写入。
