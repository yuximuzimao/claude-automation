# CURRENT — 群聊分析

这是项目当前开发状态的唯一真值。

## 当前阶段

**阶段 0：项目建制与架构设计。**

用户已要求先完成计划、项目骨架和职责边界，再考虑正式实现。当前禁止把“已有实验脚本”直接升级成正式代码。

## 已验证事实

1. 当前 macOS/黑苹果环境中，QQ 官方客户端可由系统正常激活。
2. QQ 的 macOS Accessibility 树对聊天正文暴露不足，不能作为正文主读取通道。
3. 屏幕像素捕获 + Apple Vision 本地 OCR 已实测可识别当前 QQ 群的群名、昵称、时间和聊天正文。
4. 键盘 Page Up 受焦点影响，不适合作为正式翻页控制。
5. 将鼠标移动到聊天正文区域后发送系统滚轮事件，不点击控件，可稳定向历史方向滚动。
6. 相邻两次滚动后的屏幕内容存在合理重叠，可用于连续序列锚点去重。
7. QQ 未在当前环境阻止屏幕捕获。
8. Jev 项目仅作为采集思路参考：值得吸收“采集层可替换、OCR前图像变化检测、直接像素→Vision、保留bbox/置信度”等思路；不引入其实时浮窗、自动回复、Android伪装Accessibility等功能。
9. v1 用户明确接受只处理文字信息；图片/语音/文件内容暂时忽略。

## 尚未验证

- 用户切换 QQ 为全屏后，是否能更稳定地定位真实渲染窗口并实现“窗口级捕获”。
- 正式聊天区域的动态定位方式。
- Apple Vision 对大量连续页面的 OCR 准确率、性能和长时间稳定性。
- 昵称/时间/正文基于 bbox 的稳定消息重建规则。
- 跨屏连续序列去重的阈值。
- 首次全量历史抓取和后续每日增量停止锚点。
- 两个目标群之间的可靠切换方式。
- `runtime/inbox/current.md` 的最终批次格式与规模上限。

## 下一恢复点

用户确认架构无误后才进入阶段 1：

1. 用户配合把 QQ 切全屏。
2. 只做“真实 QQ 渲染窗口定位 + 窗口级捕获 vs 屏幕裁剪 fallback”实验。
3. 结果稳定后，再开始正式 capture 模块。

在用户明确开始前，不实施阶段 1。
