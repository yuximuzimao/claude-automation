# CURRENT — 群聊分析

这是项目当前开发状态的唯一真值。

## 当前阶段

**阶段 0 已完成；阶段 1 捕获路径定型进行中。**

当前使用 QQ 自带的“聊天记录”独立窗口作为采集对象。窗口级像素捕获、Apple Vision OCR、动态正文定位、安全滚动以及 capture 单页输出契约均已定型；正式 capture 模块尚未开始。下一步处理“窗口每次重新打开会恢复默认大小”的准备动作。

## 已验证事实

1. 当前 macOS/黑苹果环境中，QQ 官方客户端可由系统正常激活。
2. QQ 的 macOS Accessibility 树对聊天正文暴露不足，不能作为正文主读取通道。
3. QQ 自带“聊天记录”独立窗口可被 ScreenCaptureKit 稳定识别并执行窗口级捕获，不需要依赖整屏截图裁剪。
4. Apple Vision 本地 OCR 已实测可识别聊天记录窗口中的群名、日期、时间、昵称和聊天正文。
5. 聊天记录窗口每次重新打开会恢复默认大小，因此正式采集前需要窗口准备动作；窗口大小/位置属于当前环境配置，不作为正文定位唯一依据。
6. 用户当前认可的工作几何约为 `x=272, y=324, 1562×978`；该位置在右侧保留了远程控制弹窗空间。
7. 正文区域可以通过“窗口级元信息 + OCR 工具栏行”动态推导。实测窗口从 `1562×978` 临时缩到 `1120×780` 后仍能重新定位，恢复后结果稳定。
8. 正式滚动可通过 OCR 正文块动态选择安全落点，再发送系统滚轮事件；不需要点击输入框，也不需要 Page Up。
9. 当前复核中，滚动时工具栏像素差异为 `0.0000`，正文差异为 `4.7851`，反向恢复后正文差异仅 `0.0115`，说明滚轮只作用于消息正文且可逆。
10. 当前 `620/630 px` 两档滚动的相邻页 OCR block 重复比例均约为 `18.2%`，最长连续重叠为 2 个 block；可作为后续序列去重的初始滚动距离基线。
11. 相邻滚动页面存在受控重叠，可用于连续序列锚点去重；禁止用单句 sender+text 做全局去重。
12. v1 用户明确接受只处理文字信息；图片/语音/文件内容暂时忽略。
13. Jev 项目仅作为采集思路参考：值得吸收“采集层可替换、OCR前图像变化检测、直接像素→Vision、保留bbox/置信度”等思路；不引入其实时浮窗、自动回复、Android伪装Accessibility等功能。
14. capture 单页 raw 契约已固化为 `schemas/capture-page.schema.json`：`batch_id / group / page_index / captured_at / window / content_region` 属于页级元数据；block 只保存 `block_index / text / bbox / confidence`。
15. `page_index` 定义为从 0 开始的采集顺序；从最新位置向历史滚动时递增，不代表聊天时间顺序。同一 incomplete batch 恢复时沿用原 `batch_id`。
16. `bbox` 与 `content_region` 使用 Apple Vision 归一化坐标系；窗口 frame 只用于来源审计/诊断，不作为消息身份或跨页去重依据。

## 尚未验证

- 正式采集前窗口准备动作的可重复恢复方式。
- OCR 前图像变化检测的阈值、等待时间和有限重试边界。
- Apple Vision 对大量连续页面的 OCR 准确率、性能和长时间稳定性。
- 昵称/时间/正文基于 bbox 的稳定消息重建规则。
- 跨屏连续序列去重的正式阈值。
- 首次全量历史抓取和后续每日增量停止锚点。
- 两个目标群之间的可靠切换方式。
- `runtime/inbox/current.md` 的最终批次格式与规模上限。

## 下一恢复点

直接执行 `tasks/todo.md` 顶部的唯一下一步：**阶段 1-4：确定窗口准备动作**。

目标是让每次重新打开 QQ 聊天记录窗口后，都能安全恢复到适合采集的工作几何，同时满足：

1. 不依赖窗口当前默认大小。
2. 不把绝对坐标当作正文定位真值。
3. 右侧继续为远程控制弹窗保留空间。
4. 只操作聊天记录窗口自身，不触碰聊天输入或发送类控件。

本步仍不进入正式消息重建、store、两群切换或每日自动化。
