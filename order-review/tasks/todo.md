## 现役优化待办：优化“保存方案”的界面等待

- 现象：在审单悬浮窗点击“保存方案”后，界面会等待数秒才显示成功。
- 当前原因：`ui._confirm_package_plan()` 在 Tk 主线程内同步调用 `PackagePlanWorkflow.confirm()`。新案例写入需依次完成文件锁、整份状态流式序列化与 `fsync`、写前隔离进程校验、有效旧版备份、原子替换、写后隔离进程校验和未使用内存回收；这些安全步骤全部阻塞 UI 事件循环。
- 下次先做分阶段耗时记录（等锁、序列化/`fsync`、写前校验、备份、写后校验、内存回收），用真实案例文件确认主要耗时，不凭感觉删减安全门禁。
- 目标方案：把完整的 repository `confirm` 持久化移到单一后台 worker；Tk 主线程立即显示“正在保存…”并禁用重复保存、刷新和修改当前草稿。后台完成后只通过 Tk 主线程回写成功/失败状态；成功前不得清空草稿或显示“已保存”，失败时必须保留草稿以便人工重试。
- 安全边界：保留现有跨进程锁、写前/写后校验、有效备份、原子替换和失败回滚；不为提速把校验改成 best-effort。保存中关闭窗口、切换订单和连续点击必须有明确且可测试的单次任务语义。
- 验收：保存期间悬浮窗仍能绘制“正在保存…”状态；双击只产生一条案例；成功后独立读回验证；写入/校验失败保留草稿且不损坏原案例；测试前后零新增 pytest、Tk 窗口和 worker 线程残留。
