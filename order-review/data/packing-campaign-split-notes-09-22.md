### 已明确的含义

- 第一批公式只指定从勾选订单中拆出的商品编码及数量，不关联客户购买SKU的份数，也不定义剩余订单的完整内容或可审核包裹。
- “悦颜三件套”是用户的固定或习惯组合叫法；“两套”指两个礼盒。礼盒内单品的构成、每种数量必须由明细和公式确认，不能用“两套”推断每种单品各两件。
- 纯四套悦颜三件套按两套公式拆分，可形成两包，每包编码及数量与两套公式完全一致。若一份SKU含三套悦颜三件套及其他产品，公式只拆出两套；剩下的一套及其他产品仍是待判断的剩余订单，审核前不得称为已确定可发的一包。
- 批量拆分通常先按SKU ID筛选，确认所选订单商品组合与数量相同；涉及逐份拆出组合时，购买多份必须先拆成单份，再处理每份内部组合，防止不同份的剩余商品留在同一订单。不是把第二批“三份”列的完整组合也一律改为每包一份。
- 第三批列出的特定SKU ID具有用户明确说明的逐份拆出及余量一包处理方式；该说明不能推广到第一批公式处理后的任意剩余订单。
- 合并订单存在ERP拆分失败现象，原因未查明。例如合计A×4、B×2，目标为两包各A×2、B×1，数学上数量守恒仍可能拆分失败。用户目前观察单订单在无系统异常时没有这一问题；不能把观察写成已验证的ERP内部规律。本次先不研究系统异常。
- 第二、三批数字列名为“SKU ID”。商品匹配语境中的“SKU”可能指ERP套装或单品商品编码；SKU ID与店铺、链接、SKU有关，同商品不同链接或不同店铺，即使明细完全一样，也可能对应不同SKU ID，不能因数字不同就判为不同商品组合。

## 用户补充：赠品的常规处理与悦希大促例外

收录日期：2026-10-09。

### 三种情况

- **组合内赠品**：赠品直接包含在商品组合内。通常审单时不需要把它和主品区分，按正常商品主品一起处理。
- **单独赠品子订单**：赠品本来就是独立子订单，按独立订单处理；不因为它是赠品就改变普通审单逻辑。
- **悦希大促特殊组合**：在当前这类特殊活动组合中，特定主品组合和对应满赠商品被合成一个独立、便于一键下单的商品组合；它不参加正常的满赠活动，客户单独购买相同主品时，对应的满赠商品也相同。

### 只在大促启用的例外

悦希订单量大时，赠品需要在主品发货后再发。因此只有每年 3 月和 9 月的大促活动，审单拆分才需要把公式拆完后剩下的赠品部分转入异常订单，先挂起，后续再单独处理。除大促外，不需要识别或拆出赠品身份，直接按正常主品订单处理。

这条规则是当前自动化设计的业务前提：默认路径不做赠品分类；只有确认是悦希 3 月或 9 月大促，并且命中相应特殊组合时，才进入“主品先处理、赠品转异常订单挂起”的分支。活动日期、特殊组合、已拆分历史和异常订单状态必须成为可追溯输入，不能仅凭商品名称猜测。

## 自动化设计限制：SKU ID 不是规则键

收录日期：2026-10-09。

用户指出：每次活动的 SKU ID 都可能变化，不能把已经收录的 SKU ID 当成拆分规则本身。当前没有新订单可供测试，也不能把下一次活动现场测试当成算法上线前提。

因此后续设计必须区分三层：

- **SKU ID**：店铺、链接和 SKU 的平台组合标识，用于筛选同一类订单和辅助定位；它不是跨活动稳定的规则键。
- **公式签名**：按 ERP 商品编码及数量组成的规范化商品多重集合，是“这一包要拆出什么”的规则依据。新 SKU ID 只要实际明细与已知公式签名一致，就可以尝试匹配。
- **活动上下文**：活动月份、是否悦希 3 月/9 月大促、赠品延后策略和既有拆分历史，决定匹配后的剩余部分如何处理。

对没有收录过的 SKU ID，浮窗应先读取同一平台单号下全部 ERP 子订单，合并商品数量，再按公式签名做精确扣减；SKU ID只作为筛选和证据字段。匹配结果必须区分“唯一匹配”“多种匹配”“编码或数量不足”“存在赠品历史但未读到拆分状态”。无法由现有公式和订单明细确定的组合，进入人工确认，不伪造自动规则。

开发和验证不依赖下一次活动现场操作：先用已有公式构造离线回放和数量守恒测试，再把历史真实订单逐步整理成回放样本。离线匹配器可以提前验证确定性逻辑；ERP实际拆分是否成功仍是独立的执行风险，不能由公式匹配测试代替。

## 用户补充：SKU ID 是人工批量筛选条件

收录日期：2026-10-09。

SKU ID 的主要作用是人工进行批量处理时筛选订单。当前只有 SKU ID 能精准筛出同一组合的订单；商品名称、平台名称、商品编码或其他页面字段都不能替代这一筛选条件。

因此人工流程应分成两步：先按 SKU ID 筛出同组合订单，再用第一批公式指定这批订单中需要拆出的商品编码和数量。SKU ID 保证批量处理对象的组合一致，公式决定实际拆出内容；两者职责不同，不能互相替代。

## 用户补充：SKU 清单必须保留链接、SPU 与店铺身份

收录日期：2026-10-10。

用户进一步明确：不同链接可能复用相同的商品 ID/平台商品编码，因此从商品对应表读取 SKU 时，不能只按商品 ID 截取或合并。商品匹配项目已经确定的链接身份规则是 `productCode + platformCode`；其中 `productCode` 对应具体商品链接/SPU 身份，`platformCode` 对应该链接下的平台商品/规格编码。重复 `platformCode` 的不同链接必须作为不同记录保存，图片和匹配结果也不能串联。

大促期间还可能同时存在不同店铺、相同明细和相同编码的链接与 SKU。即使最终数字 SKU ID 不重复，活动清单仍需同时保留：

- 店铺标识；
- 商品链接/SPU 的 `productCode`；
- 平台商品 ID/`platformCode`；
- 平台规格编码与规格说明；
- 数字 SKU ID；
- 商品匹配项目中的 ERP 商品身份和来源。

这些字段共同构成清单的证据链。对实际批量处理而言，SKU ID 是订单筛选条件；店铺、SPU、平台商品 ID 和规格字段用于确认它筛选到的是哪一个链接及哪一组活动商品，不能因为 SKU ID 唯一就丢弃其他身份字段。一次活动是否跨多个店铺，以用户当次通知的范围为准；脚本不得默认只处理单一店铺，也不得跨店铺合并记录。
