# 审单项目总 SOP

确认日期：2026-10-11。本文件统一维护项目目标、工具分工和资料/执行流程。
它是项目整体工作方式的唯一入口；原订单与包裹语义见[根本规则](2026-07-23-package-rule-foundation.md)，
真实ERP权限与现役关卡见[AGENTS](../AGENTS.md)及[执行关卡](rules/erp-execution.md)。
实现状态只见[CURRENT](CURRENT.md)，下一阶段任务只见[待办](../tasks/todo.md)。

本文中的批量处理和浮窗装箱接入是确认后的方向，尚非已开放能力；具体页面动作、资料格式和脚本接口要随验证确定。

## 1. 项目目标与三种工具分工

这套分工是在2026-10-11讨论中形成的方向，不代表三个模块已全部实现或已确定完整方案。

| 工具 | 使用场景 | 承担的工作 |
|---|---|---|
| 装箱模拟 | 活动前组合规划；日常合并订单需要验证时 | 人工先提出大致组合，计算辅助验证指定商品、数量和合适箱型能否放下 |
| 审单浮窗 | 日常单笔订单、合并订单和复杂情况 | 整理原单信息、编辑与复用方案、保存实际处理事实；未来可按需调用装箱验证 |
| 批量处理 | 活动期间大量同类订单 | 根据提前准备完整的规则，按用户当次指定范围组合已验证的操作脚本 |

三者可以协作，但不要求一次改动同时开发，也不因为方向确认就开放ERP写操作。

## 2. 装箱辅助与日常浮窗

### 2.1 装箱模拟的目标

- 人工经验通常更快给出大致拆法；模拟用于精确验证体积、数量和摆放，减少反复人工计算。
- 活动前可以比较组合和箱型；日常可以验证一个合并订单能否一箱发。无法确认时由人工按经验拆分。
- 不把包裹数最少作为所有订单的统一目标。常用箱型、固定拆法、重量、挤压风险和仓库习惯可能使较少包裹的方案不合适。
- KGOS大组合或已有固定拆法可以直接沿用经验，不必为购买两份、三份而重新搜索一箱方案；小组合和零散合并订单需要时再算。
- KGOS零散单盒订单通常逐件扫码，不应统一套用批量打包的操作便利性评分。
- 酵素较重、可能压坏较轻商品，人工一般较少混发，但少量一至三盒有时混发；这是经验示例，不自动生成数量阈值或混装禁令。
- 几何可放只证明当前尺寸和约束下有摆法，不证明实际应当合并发货。未明确录入的重量、承重和防压因素继续由人工判断。
- 保留严格几何校验、来源追溯及UNKNOWN语义。完整1～N箱搜索是可选技术扩展，不能自动升级为开发优先级或发货决策。

### 2.2 品牌与浮窗分工

- 悦希活动单量大、组合多，通常提前确定拆分安排，避免不同固定组合混发；原有同一固定组合不同份数的累计边界仍按根本规则。
- KGOS商品种类较少，组合数量较多；允许不同SKU、不同商品的小订单合并，以节省运费，但仍遵守已确认品牌、原箱和独立发货限制。
- 浮窗最初用于收集实际单笔拆法，希望帮助形成算法。实际规则包含许多上下文和经验，不能承诺积累案例就能推导出一套完整自动决策算法。
- 保留已实现的精确历史复用、人工方案和受控单笔操作；复杂订单的信息整理与人工判断仍有独立价值。
- 装箱服务接入浮窗是未来用途，是否已接入只看CURRENT，不因本文件描述而视为可用。

## 3. 活动批量处理：研究、准备和执行

### 3.1 当前研究与未来活动准备分开

当前工作使用2026-09-22悦希活动的部分资料和历史订单，检查规则是否对应真实商品、数量和拆分结果，
据此总结未来前置资料需要准备什么。原始资料见
[`packing-campaign-split-notes-09-22.md`](../data/packing-campaign-split-notes-09-22.md)。

现有笔记只记录复杂组合和需要查阅的拆法；简单情况被人工有意省略，不是完整自动化配置。
不能把“第1～4批资料已收齐”理解为所有活动规则已覆盖。
原始笔记保留历史讨论和来源；实际工作按本SOP区分阶段，不用旧设想覆盖已确认流程。

商品对应表含其他活动和无关商品。2026-10-10观察到的133条是当时页面记录数，
不是9月22日活动SKU数，也不是本次必须全量提取的目标。
处理范围由本次实际上架的商品列表或用户明确提供的范围决定。

### 3.2 活动前置资料

先根据商品匹配结果和活动商品范围，获取店铺、SPU/链接及其各SKU的完整对应清单，再补全每个SKU ID的处理规则。
不能只保存一份SKU明细，也不能先丢失SPU/链接身份再靠数字SKU ID补猜。

前置资料至少需要覆盖以下信息类别；具体表格、JSON字段和ERP取值来源在资料验证后确定：

| 信息 | 必须能回答的问题 |
|---|---|
| 活动与范围 | 哪次活动、哪些店铺、哪些上架商品属于处理范围？ |
| 商品身份 | 店铺、SPU/链接`productCode`、`platformCode`、平台商品ID、规格编码/说明、数字SKU ID、ERP套件/单品身份及来源是什么？ |
| 商品组合 | 每购买一份包含哪些真实商品编码、各多少件，如何展开套件？ |
| 份数规则 | 是否先按份数拆分、拆成几份、每包最多几份；不同份数怎样处理？ |
| 拆分规则 | 是否需要拆分、套件转单品和公式操作，先后顺序是什么，拆出与剩余明细各是什么？ |
| 结果分类 | 主品与赠品分别有哪些商品，商品种类数和总数量是什么，页面用哪些条件筛选？ |
| 后续动作 | 主品如何处理；赠品是否转异常、按正常商品发货或采用其他已指定方式？ |
| 证据与覆盖 | 哪些由用户确认，哪些已与历史订单核对，哪些仍缺失或冲突？ |

商品匹配的链接身份继续使用`productCode + platformCode`，并保留店铺边界；
不同链接或店铺不能因某个编码相同就合并。数字SKU ID从已知平台商品ID后缀剥离，不能简单截取开头数字。

SKU ID是当次筛选定位条件；公式是要拆出的商品编码与数量，不等于购买份数或整单方案。
跨活动可复用的是经确认的组合和处理规则，新SKU仍须在前置准备中关联与确认。
不能等活动执行时通过尝试扣减公式来猜未配置SKU的完整拆法或赠品身份。

完整自动化要求实际处理范围内全部适用分支明确，包括无需拆分的简单组合。
只覆盖部分时，只允许处理已配置完整的部分；其余明确交给人工，不能把“没记下来”当成“无需处理”。

### 3.3 活动中的操作顺序

以下是用户说明的业务骨架，具体页面动作和特殊分支仍需逐环节验证：

1. 应用用户当次指定的店铺、SKU ID子集和订单截止时间等范围，与仓库发货安排配合。
2. 在时间范围内叠加单个SKU ID筛选，读取当前列表，检查购买份数是否统一、是否需要先拆分份数。
3. 需要时按该SKU前置规则先处理份数；不需要时进入后续环节。不得把所有SKU都一律先拆为一份。
4. 按适用情况完成套件转单品，再使用提前配置的该SKU拆分规则执行拆分。
5. 在SKU筛选范围内，按预先定义的商品种类、商品数量等条件筛选结果，分别处理主品和赠品。
6. 核对该环节的实际状态，再进入下一环节或停止；不凭点击成功就认定业务完成。

按SKU批次组织流程，不能为了实现方便退化为所有订单逐单点击。
每次重新筛选或进入后续环节都必须保留用户指定的范围，不能无意扩大到截止时间之后或其他SKU。
这里的运行时列表检查不是当前研究中“查找历史子订单、汇总历史拆分结果”的步骤，两者不得混写。

### 3.4 赠品在前置阶段定义

- 哪个SKU有赠品、赠品包含哪些商品及数量、怎样筛出、需要执行什么动作，必须在前置资料中写明。
- 用户当前人工流程中，主品和赠品拆后明细不同；在SKU ID筛选下叠加商品种类数与数量条件，筛出主品审核，筛出需后发赠品勾选转异常。
- 种类数和总数量是筛选条件，不能在尚未核对具体商品时当作普适唯一身份。后续验证需确认它们在该SKU内是否足以区分目标。
- 转异常后赠品不再出现在正常待审核列表，后续另行处理。不能把公式扣减后的所有余量自动叫作赠品或可直接审核的一包。
- 现有悦希3月/9月大促延后赠品策略继续按已确认组合适用；普通活动通常按正常商品处理，不自动套用转异常。
- 不强求ERP存在“平台赠品”标记，也不凭名称临时分类。重跑、部分已处理及状态不明的边界须在执行设计中验证。

### 3.5 历史订单与资料核对方式

可按SKU ID查到历史子订单，再据子订单关联标识查询当时全部拆后订单；也可导出活动几天内的订单表格进行研究。
两条路径尚未选择。导出格式、关联标识、状态和商品字段能否完整对应ERP读取内容，需要实际对照后判断。
历史汇总须保留每条ERP子订单与来源，避免同一拆后订单重复计数；同平台单号只是已有样本的关联证据，不假定所有订单都能还原完整历史。
历史研究可以按用户指定的订单管理页面或导出资料只读核对，不改变现役浮窗只读前台待审核页序号1订单的限制。
历史证据用于复盘，不作为当前订单执行状态或操作成功的证明。

输出应区分原始证据、用户解释、根据证据的推测和待确认项；检查现有公式与真实拆分是否吻合，逐项总结资料缺口。
本阶段用于研究资料格式和规则覆盖，不是未来每次活动准备时都必须重新下载并复盘历史订单的固定步骤。
只读调查、表格分析和离线模拟均不能代替真实ERP单环节验证。

### 3.6 按单个环节编写和验证脚本

用户先说明一个操作的实际做法；该环节单独成脚本，通过明确参数复用，之后再组合成流程。
例如批量拆分脚本固定操作入口和填写步骤，每次传入不同公式；不为每个SKU复制一套点击代码。
脚本划分服从实际业务步骤，不提前开发一套通用流程引擎。

每个环节设计时要明确输入参数、允许的页面/订单状态、操作范围、完成证据与返回结果。
前一步未能确认完成时不继续拼接下一步；提交不确定时先核对，不自动重复提交。
具体筛选、份数拆分、套件转单品、公式拆分、结果分类、审核、转异常等脚本尚未实现，不能引用为可运行命令。

当前没有活动订单，不要求先跑全流程或制作假订单。用户可以指定一个真实案例订单只验证一个操作，之后由用户人工复原并恢复正常处理。
每次真实业务操作仍按当前安全规则明确授权，不扩大到其他环节。
单环节证明完善后再组合验证；单环节通过不等于整场自动化已经验收。

未来可靠自动化的授权可以面向活动，但每次实际运行只覆盖用户指定的时间、店铺和SKU范围，可能随仓库进度跨天分批。
这不是“一个SKU还是整场活动”的二选一。最终执行权限、失败处理和验收机制尚待实现阶段明确；本次方向确认不授予活动写操作权限。

## 4. 从资料核对到逐环节实施

先用现有活动资料和历史订单核对规则、发现缺口，再由用户逐项说明ERP操作，验证单个环节，最后组合流程。
不要求先获得一笔活动订单跑完整流程，也不把下一次活动现场测试作为资料研究或单环节验证的前提。
具体前置资料结构、页面字段、脚本接口和失败处理仍须随验证逐项确定；总方向确认不代表这些细节已经确认。
