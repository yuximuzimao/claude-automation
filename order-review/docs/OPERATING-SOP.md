# 审单项目总 SOP

确认日期：2026-10-11。本文件是项目的分类与分流入口，不是所有业务规则和操作细节的总仓库。
它只回答：当前输入属于哪个工作域、应读取哪份唯一 owner、什么情况下可以把验证结果升级为规则。

原订单与包裹语义见[包裹规则 owner](2026-07-23-package-rule-foundation.md)，活动批量见[活动批量 owner](rules/activity-batch.md)，
装箱辅助见[装箱辅助 owner](rules/packing-assistance.md)，真实 ERP 权限见[AGENTS](../AGENTS.md)和[执行关卡](rules/erp-execution.md)。
实现状态只见[CURRENT](CURRENT.md)，未完成事项只见[待办](../tasks/todo.md)。

当前三个工具的方向已经确认，但批量处理和浮窗装箱接入尚未开放；具体页面动作、资料字段和脚本接口必须经过验证后才进入对应 owner。

## 1. 先拆信息，再分类

一条用户输入可能同时包含多种信息，先拆成独立项。不要因为它们出现在同一订单或同一次讨论里，就把事实、规则、推测和执行动作写到同一处。

| 工作域 | 典型内容 | 唯一 owner |
|---|---|---|
| `ORDER_PACKAGE` | 原订单身份、平台子订单、包裹方案、历史复用、数量守恒、运输边界 | `docs/2026-07-23-package-rule-foundation.md` |
| `ERP_EXECUTION` | 页面读取关卡、单包审核、当前拆分停点、授权和结果确认 | `docs/rules/erp-execution.md` |
| `ACTIVITY_BATCH` | 活动范围、SPU/SKU清单、公式、份数、主品/赠品、批次处理和脚本 | `docs/rules/activity-batch.md` |
| `PACKING_ASSISTANCE` | 活动前组合预估、合并订单按需装箱验证、尺寸证据和算法实验 | `docs/rules/packing-assistance.md` |
| `CURRENT_STATE` | 当前已实现能力、服务是否运行、已验证/未验证状态 | `docs/CURRENT.md` |
| `EVIDENCE` | ERP原始记录、用户原文、导出表格、截图或历史样本 | 对应`data/`原始资料；阶段材料进入`docs/archive/` |
| `TASK` | 尚未完成、待验证、待用户说明或待实现事项 | `tasks/todo.md` |

## 2. 证据升级规则

历史订单、导出表格、用户口述和模拟结果默认都是证据或待核对输入，不自动变成长期规则。

1. 先保留原始证据和来源，不改写原文、不删除冲突样本。
2. 再写出观察，并标明是事实、推测还是未知。
3. 用户确认业务含义后，才把稳定结论写入对应 owner。
4. 只对一个 SKU、一个订单或一个活动成立的结论，留在活动资料或观察记录，不升级为通用规则。
5. 无法判断时写入 `tasks/todo.md`，保持 `UNKNOWN`，不让运行时猜测补齐。
6. 只有已确认的规则才可以进入脚本输入；脚本验证通过也不等于整场活动已验收。

## 3. 按任务分流

- 日常浮窗、原订单和包裹方案：读 `CURRENT`，再按需进入包裹规则或 ERP 执行 owner。
- 活动资料和历史子订单核对：读 `CURRENT`、`tasks/todo.md` 和活动批量 owner；不把核对结果直接写入包裹规则。
- 活动前装箱辅助：读装箱辅助 owner；人工先提出组合，模拟器只做尺寸/数量验证，不替代发货判断。
- 活动中的批次操作：先应用已确认的活动前置资料，再进入 ERP 执行 owner；未配置分支交人工。
- 代码、页面、运行服务：先确认它服务哪个工作域，再只改该域 owner 和实现；不得因为文件名相近跨域修改。

## 4. 三种工具的方向

| 工具 | 主要用途 | 当前边界 |
|---|---|---|
| 装箱模拟 | 活动前组合规划；日常合并订单需要时验证能否一箱发 | 人工经验通常更快；最少包裹不是统一目标；重量、防压和仓库习惯由人工判断 |
| 审单浮窗 | 日常单笔、合并订单和复杂订单的事实整理、方案编辑与逐单受控操作 | 不承诺从历史案例自动推导完整业务算法；当前多包仍在二次确认后停止 |
| 批量处理 | 活动期间按用户指定范围执行已验证的重复操作 | 先完整准备资料，再逐环节验证脚本；规则不全只能部分自动化 |

## 5. Owner 边界

- 具体包裹业务规则不在这里重复，读包裹规则 owner。
- 具体活动字段、公式、赠品分类和脚本契约不在这里重复，读活动批量 owner。
- 具体尺寸目录、求解器实现和页面契约不在这里重复，读装箱辅助 owner及其下游计划。
- 当前测试数字、端口状态和未完成事项不在这里维护，分别读 `CURRENT` 和 `tasks/todo.md`。

## 6. 结构变更门槛

只有在现有 owner 无法无损表达已经确认的合法需求时，才做项目结构迁移。能由现有 owner 表达的内容，直接归入对应 owner，不新增平行规则文件。
每次新增、移动或删除 owner，都必须同步 `SKILL.md`、`docs/INDEX.md`、`docs/rules/README.md` 和相关 `CURRENT/README` 入口，并在归档中记录迁移原因。
