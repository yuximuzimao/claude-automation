# 单订单审单工作流只读可行性审计

日期：2026-07-23  
状态：阶段 B 完成；等待用户选择下一项功能  
边界：本次只审计代码、既有页面事实和已保存案例，不连接、不点击、不修改 ERP

## 1. 结论

当前系统已经能可靠形成**本地包裹目标**，但还不能可靠形成**可执行的 ERP 操作**。

两者必须分开：

- 本地目标：完整订单快照经过人工确认后，可以判断目标是 1 个包裹还是多个包裹，并保证商品数量守恒。
- ERP 执行：还不知道 ERP 当前是否已经拆分、具体按钮对应哪条记录、弹窗需要什么参数，以及动作后怎样证明成功。

因此，下一阶段可以安全推进“确认后的人工操作摘要”和“本地三态意图”；ERP 方面只适合继续补充结构化只读观测和 dry-run 计划。审核、拆分、合并、保存、提交等写操作必须另行讨论并逐项采样。

## 3. 四类功能边界

### 3.1 现在即可安全实现、且不写 ERP

#### A. 确认后的人工操作摘要

确认本地方案后，最有价值的信息是：

- 当前订单身份和读取时间。
- 最终包裹数量。
- 每个包裹的商品、身份摘要和数量。
- 方案来源：人工、同订单历史、精确规则或单包容量候选。
- 推荐采用后是否被人工修改。
- 本地操作意图：无需拆分 / 需要拆分 / 信息不足。
- 固定警示：`本地方案已确认，ERP 尚未执行。`
- 可复制的纯文本操作摘要，供人工在 ERP 中逐项对照。

现有界面已经显示包裹内容和“未操作 ERP”，因此后续实现主要是补足意图、来源和可复制摘要，不需要改变读取方式或碰 ERP。

#### B. 本地三态操作意图

可以可靠形成以下**本地意图**：

1. `无需拆分`
   - 订单已展开。
   - 至少有一个有效商品。
   - 所有商品数量均大于 0。
   - 本地方案已经确认并通过数量守恒校验。
   - 目标方案只有 1 个包裹。

2. `需要拆分`
   - 同样满足完整性和守恒条件。
   - 目标方案有 2 个或更多包裹。

3. `信息不足`
   - 订单未展开、商品为空或数量无效。
   - 缺少可复核的订单身份。
   - 页面刷新后订单已变化。
   - 方案未确认或数量校验失败。

这里的“无需拆分 / 需要拆分”只描述**目标形态**，不等于“ERP 当前无需动作 / 可以立即点击拆分”。在 ERP 当前状态读取完成以前，产品文案必须保留“本地目标”限定。

#### C. 只读 dry-run 数据结构

现在可以先定义而不执行：

- 目标订单身份。
- 当前 ERP 状态：已知字段、未知字段和采集时间。
- 本地目标方案。
- 理论动作列表。
- 每一步的前置条件、预期结果和停止条件。
- `blockedReasons`：无法生成计划时明确列出缺失事实。

当前只能生成“信息型 dry-run”，不能生成声称可执行的按钮步骤。

### 3.2 补充真实页面样本后可以实现的单订单操作准备

#### A. ERP 当前状态结构化只读识别

至少还要读取并验证：

- 订单行的稳定 ERP 内部身份，以及它和平台单号的对应关系。
- 当前审核状态、锁定状态、加载状态和可操作状态。
- 当前是一条还是多条 ERP 可操作记录。
- 当前是否已经拆分；若已拆分，各记录包含哪些商品和数量。
- 明细分组是否等同于 ERP 包裹。当前 `groups` 不能直接当作包裹。
- 合并状态、可合并来源和“取消合并”的作用范围。
- 每个审核、按数量拆分、按 SKU 拆分、保存入口的结构化定位、所属记录、可见性和禁用状态。
- 动作弹窗的字段、默认值、校验规则、确认/取消按钮和关闭行为。
- 页面数据版本或最后更新时间，用于发现“计划生成后订单已经变化”。
- 成功、失败和处理中状态的可重读 DOM 特征。

#### B. 可验证的 dry-run 操作计划

要把 dry-run 从说明文字升级为可信计划，需要同时满足：

1. 计划前重新读取并唯一定位订单。
2. 当前 ERP 商品和数量与本地确认快照一致。
3. 明确当前 ERP 形态与本地目标形态的差异。
4. 每个理论动作都有唯一入口和明确参数。
5. 已知动作前后的页面状态转换。
6. 已知结果验证字段，而不是只依赖 toast 或“点击没报错”。
7. 任一字段不确定时计划为 `blocked`，不能猜测补全。

示例：

```text
订单：<复核后的订单身份>
当前：未确认是否已拆分
目标：2 个包裹
计划：blocked
缺失：
- ERP 当前包裹结构
- “按数量拆分”弹窗参数语义
- 拆分成功后的可重读状态
```

#### C. 需要收集的人工操作样本

单包审核至少收集：

- 普通未合并订单。
- 带可合并标记但仍决定单包的订单。
- 已合并或可取消合并的订单。
- 按钮启用/禁用状态。
- 点击审核前后的完整 DOM、确认弹窗和最终状态。
- 成功、业务拒绝、网络超时和结果不明各一类事实。

多包拆分至少收集：

- 同 SKU 按数量拆分。
- 多 SKU 按数量组合拆分。
- 按 SKU 拆分。
- 已合并订单的拆分。
- 已存在部分拆分结果的订单。
- 拆分弹窗打开、修改、取消、保存和审核的完整顺序。
- 拆分后每条记录的商品数量、内部 ID、状态和再次读取结果。
- 参数错误、保存失败、超时和页面刷新后的表现。

每个样本都应保留：操作前结构、人工实际步骤、动作参数、操作后结构和人工认定的成功标准。只保存必要字段，避免记录无关隐私数据。

### 3.3 必须与用户讨论后才能实施的 ERP 写操作

以下任何一项都不能因为只读识别或 dry-run 完成而自动开放：

- 点击审核。
- 按数量拆分。
- 按 SKU 拆分。
- 合并或取消合并。
- 保存拆分结果。
- 套件转单品。
- 修改商品、换商品或赠品处理。
- 提交、批量处理或自动连续处理。

讨论时至少要逐项确定：

- 用户希望自动化到哪一步。
- 哪一步必须停下来让用户确认。
- 允许操作的订单类型和排除条件。
- 失败或结果未知时由谁处理。
- 是否允许撤销；若 ERP 不支持撤销，如何避免误操作。

### 3.4 当前阻塞的功能

#### 因数据不足阻塞

- 多包数量投影。
- 单包到多包的容量临界判断。
- 重量、箱规和装箱模型。
- 同结构多方案排序。
- 任何机器学习或自动置信决策。

#### 因页面事实不足阻塞

- 判断 ERP 当前是否已经达到本地目标。
- 可靠定位审核、拆分、保存入口。
- 生成带具体参数的可执行 dry-run。
- 验证拆分或审核是否成功。
- 对合并、套件和赠品状态作可靠判断。

#### 因安全闭环不足阻塞

- 真实单订单 ERP 写操作。
- 失败后的自动重试。
- 跨订单连续操作。
- 批量审核或批量拆分。

## 4. 未来单订单写操作的最小安全闭环

未来即使只开放一个订单、一个动作，也必须同时具备：

1. **身份复核**：执行前重读平台单号、ERP 内部 ID、商品和数量，并与本地确认快照一致。
2. **人工确认**：显示当前状态、目标状态、唯一动作和不可逆影响；用户针对这一次动作明确确认。
3. **单动作**：一次只执行一个业务动作，不把拆分、保存、审核连成不可中断的黑盒。
4. **无自动重试**：超时或异常后先重读；不能因为没收到成功响应就再次点击。
5. **执行日志**：记录订单身份摘要、动作、参数、执行前状态、时间和结果，不记录无关隐私。
6. **幂等键**：至少由订单身份、页面版本、动作和目标方案摘要组成；重复请求先阻止。
7. **结果重读验证**：从 ERP DOM 重新读取商品、数量、记录数和状态，与预期结果比较。
8. **unknown 状态**：无法证明成功也无法证明失败时，标记结果未知并停止，交给人工核对。

只有结果重读通过，动作才能记为成功。toast、点击返回或按钮消失都不能单独作为成功证据。

## 5. 建议的下一步选择

按风险和收益排序：

1. 定义“确认后人工操作摘要 + 本地三态意图”的数据结构和文案，不改 ERP。
2. 扩展 ERP 动作入口与当前状态的结构化只读采集，继续不点击。
3. 基于补充样本实现真正会阻塞的 dry-run 计划。
4. 收集单包审核人工样本后，再单独讨论是否开放一个订单的一次审核动作。
5. 多包拆分必须等到真实多包案例和人工拆分样本都具备后再讨论。

本报告完成后项目应暂停在讨论点；不自行实施任何 ERP 写操作。
