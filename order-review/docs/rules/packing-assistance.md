# 装箱辅助 Owner

本文件唯一负责装箱模拟的业务用途、输入证据、结果解释和与浮窗的边界。
项目分类见[项目总SOP](../OPERATING-SOP.md)，订单/包裹语义见[根本规则](../2026-07-23-package-rule-foundation.md)，算法实现见[研究](../2026-09-12-packing-algorithm-research.md)，页面契约见[阶段计划](../2026-09-08-packing-simulator-plan.md)。

## 两个使用场景

- 活动前：人工先提出商品组合，模拟器辅助验证数量、尺寸和箱型，减少人工精确计算。
- 日常浮窗：合并订单需要时验证能否一箱发；验证不确定或不适合时由人工按经验拆分。

人工经验通常更快给出大致拆法。模拟器不负责替仓库决定所有发货习惯，也不把最少包裹数作为统一目标。
常用箱型、固定拆法、重量、防压和仓库操作习惯可能使较少包裹的方案不合适。
KGOS大组合或固定拆法可直接沿用经验；小组合和零散合并订单需要时再算。悦希通常提前规划活动组合。

## 结果含义

- 几何可行只表示当前尺寸和约束下存在摆法，不表示实际一定应合并发货。
- `UNKNOWN`不等于装不下；缺尺寸、搜索预算不足或约束不完整都要保留原因。
- 重量、承重、防压和仓库习惯未明确建模时，由人工判断，不从酵素等个案推导通用阈值。
- 结果必须保留商品、数量、箱型、尺寸来源、算法版本和逐件坐标（如有）的追溯关系。
- 历史人工方案只在实验完成后作为对照，不能偷偷给求解器答案。

## 当前技术边界

单箱内核已支持严格几何校验、物件顺序、候选点和稳定性分层；`pack_order()`多箱外层仍是可选研究，不能当作当前生产能力。
装箱实验服务与正式浮窗保持隔离；服务是否运行只看`CURRENT`。实验结果不写正式案例，不触发ERP。

商品、纸箱和原箱数据分别见`data/packing-product-dimensions.json`与`data/packing-dimensions.json`，原始资料和估计值要保留来源。当前几何算法只接受整数毫米；用户已确认实物包装中0.5mm级差异不会实质影响装箱，可在模拟输入中向下取整到整数毫米，但必须同时保留原始测量值，避免资料精度丢失。纸箱采购报价不是箱型固定价格；如记录价格，应按“采购数量 + 对应单价 + 确认日期/来源”成组追加，后续不同数量报价不得覆盖既有记录。
