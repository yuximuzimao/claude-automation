## 2. 已确定的业务概念

### 2.1 商品身份、固定组合、平台 SKU 分开

- 商品身份保留当前实际商家编码、完整商品名称、简称、平台来源，不因包装等体积而换成另一种商品。
- 完整商品名称逐字保留空格、全角/半角括号、`*`、单位和符号，简称单独存。展示时可以换行，但不能改写源字段；复制完整名称与复制简称是不同操作。
- SKU 是查出商品组合和数量的来源，不是固定组合身份。不同 SKU 可以对应同一个单商品或同一固定组合的不同份数。
- 悦希正常快递不跨不同固定组合合单。固定组合可以只有一种商品，也可以是明确的多商品套餐；水1瓶与水2瓶可以累计，但水套餐与乳套餐不能因此合并。
- 单一商品可按商品身份累计数量。多商品组合必须先有用户确认的组成与计量单位，不能自行用数量最大公约数或相同比例推断“同一套餐”。赠品、礼盒、礼袋及活动差异不得自动忽略。
- 固定组合定义基于明细；匹配完成后由平台 SKU 明细关联到组合。不是把规则永久绑在某个 SKU 编码上。哪些活动配置构成同一组合由用户逐条确认。
- KGOS 没有悦希这类跨固定组合合单限制，但仍受品牌箱型、原箱专用、玉米片独立发货等约束。
- 第一期只接受已有订单快照，不开发 ERP 筛单、跨订单收集或合单。资料中的合单政策不构成 ERP 合单授权。

### 2.2 实际入箱物与原订单明细分开

- 普通商品使用塑封后销售纸盒的外尺寸。商品半毫米按用户口径向上取整，原值保留；不能先将厘米数取整再换算。
- 活动组装礼盒：内部配方经用户确认后，按一个装好的礼盒和配套礼袋计算；内部商品仍用于来源、数量核验，不能又作为散件重复占空间。额外单品单独保留。
- 修颜礼盒：自身就是封装成一个商品的成品，直接按该成品编码和数量处理；成品外尺寸已于2026-09-09补为190×228×55 mm，不做内部配方投影。
- 一个组合含4套礼盒、购买1份，对应4个礼盒和4只礼袋；购买份数变化须同步乘算。物理单元必须能反查原始明细，不能改写 ERP 套件或绕过现役套件阻断。
- 礼袋是柔性包装。没有折叠尺寸时不填0厚度、不丢弃、不将完全展开面积作为刚性尺寸。

### 2.3 证据等级与展示含义

至少分开三个维度，不用一个“成功”掩盖差别：

| 维度 | 示例 | 用途 |
|---|---|---|
| 资料来源 | 用户实测/明确确认、图纸、估计、缺失 | 判断输入能否作确定依据 |
| 业务适用性 | 可用、规则直接支持、禁止、待确认 | 品牌、用途、原箱和固定组合边界 |
| 几何结果 | 已找到并验证坐标、必要条件证明放不下、未知、未运行 | 判断是否有真实摆放证据 |

- 命中原箱/固定容量规则但无尺寸时，显示“规则支持，未计算摆放”，可以画数量组合示意，不能伪造三维坐标。
- 只有基于已确认尺寸、保守可用内径并通过独立校验的坐标，才记为确定几何证据；外尺寸边界能放不够。含估计尺寸的结果即使有坐标，也标为估算布局，不计入确定几何通过率。
- 箱体反推礼盒只能作为明确标注的估算示意。先按“礼盒＋礼袋”整体画占位，比给两个对象各猜一个厚度更稳妥；不写入实测商品尺寸。
- 不能用某箱容量反推尺寸，再算出该箱能放，最后称为独立几何验证。此类反推不进入几何通过率，不据此放行额外散件或计算确定的剩余空间。
- 半透明箱壁、利用率和剩余空间都是辅助信息，不能代替包装适用性。没有通用“利用率超过某值就合格”的规则。

### 3.4 2026-09-09礼盒/礼袋适配检查

本次用户提供：印花礼盒制作尺寸303×79×202 mm（平放303×202×79 mm），印花礼袋225×305×5 mm；修颜礼盒
190×228×55 mm，修颜礼袋237×215×5 mm。最初测量以厘米给出，印花礼盒现以用户确认的毫米制作尺寸为准；最后一维5 mm的
礼袋厚度为估计，前两维和礼盒外尺寸按用户提供记录。原始值、轴向来源和完整
坐标保存在尺寸资料的 `pendingMappings` / `giftPackingFitChecks`。

显式构造方式：当前记录使用“礼袋平铺、礼盒叠放”的一种可行坐标来证明边界与无碰撞；
多套记录同样保留对应数量物件。不额外折叠或压缩，不使用箱体反推尺寸。该坐标曾
同时通过现有“完整支撑”校验，但用户2026-09-09进一步明确：完整底面支撑不应被视为
装箱几何可行性的硬条件，现实中部分悬空仍可装箱，且整箱换面会改变重力方向。因此
这里的支撑通过仅是旧校验器事实，不作为业务规则或未来求解器必须保持的物理前提。

| 组合 | 保守内径 mm | 平铺叠放占用 mm | 三轴余量 mm |
|---|---|---|---|
| 印花单套箱：1盒＋1袋 | 310×227×90 | 305×225×84 | 5 / 2 / 6 |
| 印花三套箱：2盒＋2袋 | 310×227×280 | 305×225×168 | 5 / 2 / 112 |
| 印花三套箱：3盒＋3袋 | 310×227×280 | 305×225×252 | 5 / 2 / 28 |
| 修颜专箱：1盒＋1袋 | 240×225×130 | 237×215×60 | 3 / 10 / 70 |
| 修颜专箱：2盒＋2袋 | 240×225×130 | 237×215×120 | 3 / 10 / 10 |

结论：所给尺寸与此前人工确认的箱规相容，按礼袋5 mm厚度假设可以适配；不再
依赖“纸箱小一圈”作为本批礼盒输入。2 mm仅为薄礼袋外廓的宽度余量；礼盒
本体平面余量是7×25 mm，不能据此把整箱描述为只有2 mm或很拥挤。用户确认
礼袋为硬纸、厚度可轻微挤压，实际摆放较宽松；未量化压缩量，计算继续保留
5 mm估计厚度。整组外廓只是边界，不等于每个高度层都被占满；额外单品仍需
按实际空间核验，不能直接用外廓余量或用户的宽松感推算件数。

**必须保留的求解回归样本：** 早期自动求解在印花单套、修颜1套/2套返回
UNKNOWN，而上述同输入存在明确的边界内、无碰撞摆放。已确认至少有两个独立问题：
一是搜索固定按体积从大到小增量放置，不会回头改变已放物件的相对上下关系；二是
`_fully_supported()` 把完整底面支撑作为硬门禁，这一假设已被用户否定为普遍物理约束。
2026-09-12后的实现已把物件顺序纳入搜索并用礼袋反例做回归，也已将“箱内且无碰撞”
的几何可行性与“运输稳定性/摆放偏好”分层。本段保留早期反例作为回归依据；不得靠增大
节点预算、缩小礼袋尺寸或把UNKNOWN解释为装不下来掩盖新的遗漏。

## 4. 页面方案

### 4.1 页面只承担两个主要任务

主导航为“装箱实验”“包装资料”。历史比较放在实验中；包装资料只保留“包装纸箱 / 单品尺寸 / 包装规则”三个入口。产品原箱并入包装纸箱并打标签，待补尺寸跟随对应纸箱或单品显示，不再单独建技术资料标签。

```text
装箱实验  |  包装资料
┌──────────────────┬────────────────────────────────────┐
│ 选择商品           │ 装箱模拟                           │
│ 品牌按钮           │ 纸箱：自动 / 手动指定               │
│ 搜索添加商品       │ 真实摆放图 / 顶视 / 分层             │
│ 本次商品滚动列表   │ 算法判断按需展开                    │
│ 历史订单入口       │ 历史订单时附人工原方案只读对照        │
└──────────────────┴────────────────────────────────────┘
```

- 装箱实验是纯算法验证层：使用商品尺寸、纸箱尺寸和必要品牌边界，不读取已确认固定箱量、固定拆箱答案或历史人工方案给算法提示答案。固定包装规则保留为资料，未来正式接入审单浮窗时再作为生产前置判断。
- 实验页只展示用户直接识别的信息：商品简称、数量、纸箱名和结果。商品编码、商品尺寸、纸箱尺寸、原始证据字段放到“包装资料”，不占实验操作区。
- 商品匹配只提供已经确认映射中的 ERP 标准全名：模拟器遍历 `product-mapping/data/products/*/features.json` 时只读取每个条目的 `erpName`，不读取顶层识图名、颜色、特征、别名或活动 `sku-records`。`product-mapping/data/products/erp-identities.json` 只是2026-09-11的200条 ERP 身份只读快照，用于补正式简称、主商家编码和少量规格商家编码；有没有该快照都不能改变商品匹配原有运行逻辑。
- 审单自己的 `data/packing-product-dimensions.json` 只按 ERP 标准全名与商家编码关联商品尺寸、零体积配件和仓库排除项；不再使用视觉 `productKey`。`data/packing-dimensions.json` 继续保存纸箱、原箱、规则、待补和证据。
- 纸箱是可选条件：留空时当前页面在同品牌可计算纸箱中尝试寻找可行单箱；手动指定时锁定该纸箱，失败不能偷偷换箱。页面当前仍只开放 KGOS 单箱实验，这是前端能力边界，不是算法最终架构；完整算法以 `1～N箱外层 + 单箱几何内核` 设计。
- 禁用跨品牌选择；普通未知组合可以做纯尺寸实验，但“几何可放”不自动升级为正式业务箱规。
- 三维图直接消费校验后的逐件坐标；历史订单中的人工原方案只作为求解完成后的只读对照，不给算法提示答案。
- 资料页可以查看全部待补项和来源；第一版以展示、标记补充需求为主，不另建复杂资料编辑后台。若增加修改入口，只改实验副本并明确保存，不能更改原订单/正式案例。

### 4.2 视觉与交互约定（设计建议，实施时遵循用户反馈）

- 主体是可操作的装箱工作台，无宣传头图。保留较大的三维视图区；细节按需展开，避免窄浮窗承载复杂校准。
- 颜色：工作台背景 `#EEF2F6`、面板白 `#FFFFFF`、正文 `#233044`、主操作蓝 `#2C63C8`、估算/待确认琥珀 `#B87412`、阻断红 `#B63A46`。商品配色与状态色分开并带文字图例。
- 字体：标题用本机 PingFang SC 中等字重，正文用系统中文无衬线；尺寸、编码与坐标用 SFMono/Menlo 等等宽字体。不开远程字体下载。
- 特色交互是“逐层剖开纸箱，图中物件与原单明细同步高亮”，不是商品飞入动画。保留键盘焦点、文字可复制、减少动态效果选项。
- 首要验收是用户能认出用哪个箱、装了什么、还缺什么证据；不用漂亮图形掩盖未知。

## 5. 最小技术路线

### 5.1 复用现有 Python 核心

- 保留 `carton_packing.py` 的单箱求解与坐标结构、`dimension_catalog.py` 的目录及原箱定义、`package_plan.py` 的原单引用和数量守恒能力。
- 现有 `assess_catalog_carton()` 是裸几何入口，没有品牌/用途门禁。页面不能直接把任意箱号交给它就宣称可发货。
- 提炼一个可被模拟器和未来浮窗共用的装箱服务入口，负责输入检查、业务约束、规则解释、求解、独立复核。不要复制离线审计的私有判断到多个入口。
- 当前 `packing_case_audit` 的 supported 同时包含原箱、固定规则和几何证据，不能直接当作“算法重算成功率”。现役礼盒排除尚不支持新的物理单元投影。
- 浏览器仅负责交互与三维绘制，不维护第二套 JavaScript 装箱算法。建议轻量本地页面＋Python本地接口；3D库使用本地固定版本资源，执行前核实官方文档/版本并锁定依赖，不用运行时 CDN。
- 本地服务只绑定回环地址，使用独立入口启动；不随浮窗自动启动，不增加长期调度。首版无 ERP/CDP 依赖。

### 5.2 候选与实验记录的最小契约

一次输入至少包括：实验ID、源快照/版本、真实商品引用与数量、品牌、手选/自动模式、箱型限制、资料版本、求解预算。组合定义引用仅在已确认时填写。

一次输出至少包括：请求ID、资料及算法版本、业务适用性、几何状态、证据来源、每包箱型及商品分配、逐件坐标（若存在）、搜索耗时、未知/阻断原因。没有证明更少包裹不可行时，结果只称“找到可行方案”，不能称“最少包裹”。

- 真实商品引用 → 物理单元 → 输出摆放实例必须一一可追溯。相同编码来自不同平台子订单时也不能丢来源。
- 资料原始文本、计量单位、计算值分别保留；未知用显式状态表示，不以0充当未知尺寸。
- 缓存键至少含输入商品与数量、必要来源结构、箱型限制、资料版本及算法版本；计算预算影响未知缓存，不能把低预算未知永久当无解。
- 一次只运行一个交互求解任务；新任务/换单/换箱使旧结果失效。默认整次计算预算建议先设2秒并用实际基准校准；节点上限保留，但不能代替墙钟超时和取消。
- 后台任务不得阻塞界面；所有箱型/分区搜索共用整单截止时间，不给每个子问题重新分配一整份预算。
- 未知、超时或取消不得把部分结果升级为完整拆法。只有整单每一包均独立验证、数量守恒的完整候选可保留，并标注搜索/最优性未完成；只算出部分包裹的结果仅显示进度，不称为候选方案。所有实验结果均不能直接执行ERP。
- 实验记录单独持久化，建议置于既有应用数据目录的实验子目录；包括输入副本、版本、结果和人工反馈。不可写 `cases.json`、订单采用关系、正式推荐事件或审核日志。

### 5.3 独立复核

在展示为有效候选前独立检查：输入物件全部出现且仅一次、每个原商品数量守恒、包裹非空、实例ID唯一、尺寸与允许朝向吻合、箱内边界、无碰撞、品牌和用途限制满足、证据版本与当前任务匹配。支撑/稳定性若保留，应作为独立风险或偏好结果，不再默认混入几何有效性的硬条件。

现有 `layout_is_valid()` 把边界、碰撞和完整支撑混在同一个布尔结果里，甚至空集合也会通过；外围已经补逐件完整性复核，后续求解器阶段仍需拆分支撑语义。缺失原件、替换尺寸、重复实例、旧请求结果和错误箱型都要有拒绝用例。
