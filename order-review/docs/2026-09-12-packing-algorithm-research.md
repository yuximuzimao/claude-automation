# 1～N 箱三维装箱算法研究

日期：2026-09-12  
状态：研究结论；未修改求解器、未接入 ERP、未读取历史保存方案作为算法答案

## 1. 本轮问题定义

这次不再把“指定单箱能否放下”当成最终算法，而是从完整问题定义出发：

- 输入：订单内实际发货物理单元、每件外尺寸/允许朝向、候选运输纸箱、产品原箱及硬业务适用边界。
- 输出：1～N 个包裹的完整方案，每包必须有真实箱型、完整商品分配和经验证的逐件三维坐标。
- 单箱只是 N=1 的特例；算法结构本身必须能继续搜索 N=2、3……。
- 盲算阶段不读取历史保存方案、历史人工拆法或固定容量答案来决定结果；历史只能在求解完成后作为独立对照样本。
- “产品原箱”作为一种受硬适用条件约束的候选容器处理；它不是历史答案，也不能被普通商品借用。
- 第一目标是找到完整可行方案；随后按包裹数最少优先。没有穷尽更少包裹搜索时，只能称“找到可行方案”，不能称全局最少。
- 继续保留当前严格语义：必要条件能证明失败才是 `PROVEN_IMPOSSIBLE`；搜索预算耗尽或当前策略未找到时是 `UNKNOWN`。

这是带现实约束的 offline 3D variable-sized bin packing，而不是单纯的“体积塞箱”。

## 2. 当前实现本质上是什么

`src/order_review/carton_packing.py` 当前单箱内核是：

1. 为每件商品生成允许的 90° 朝向；
2. 做单件越界和总体积两个必要条件剪枝；
3. 商品按体积从大到小固定排序；
4. 候选坐标取已放物件各右/后/上表面坐标与 0 的笛卡尔积；
5. 对朝向和候选坐标做深度优先回溯；
6. 每次放置检查边界、重叠和完整支撑；
7. 达节点上限仍无解则返回 UNKNOWN。

它已经具备一个安全的“几何验证型回溯器”，但不是完整的 3D-BPP 求解器。

### 已确认的结构缺口：固定物件顺序

当前会回溯：

- 物件朝向；
- 物件位置。

当前不会回溯：

- 物件放置顺序。

因此“必须先铺一个体积很小但底面积很大的支撑件，再放体积更大的物件”会被漏解。

2026-09-09 的礼袋样本已经提供了最小反例：

- 印花单套箱显式布局：礼袋 305×225×5 在 z=0，礼盒 303×202×79 在 z=5，可通过完整几何校验；
- 当前自动求解却返回 UNKNOWN（9 个节点）；
- 原因不是节点不足，而是体积排序先放礼盒，之后礼袋无法插到礼盒下面。

这证明“只增加节点上限”不能修复问题。

## 3. 成熟算法/开源实现给出的几个关键启发

### 3.1 Martello–Pisinger–Vigo：单箱装填器 + 外层 branch-and-bound

经典 3D-BPP 工作《The Three-Dimensional Bin Packing Problem》(Operations Research, 2000, DOI 10.1287/opre.48.2.256.12386) 明确把问题分为：

- 单个 bin 的装填/可行性；
- 外层最少 bin 数 branch-and-bound。

这与本项目应采用的结构一致：不要把“单箱页面”当算法架构；单箱应是完整 1～N 箱搜索中的 N=1 状态。

我们不需要照搬其完整精确算法，但应抄它的分层思想：

`多箱状态搜索 -> 单箱候选生成/验证 -> 下一个多箱状态`

### 3.2 Crainic–Perboli–Tadei：Extreme Points

《Extreme Point-Based Heuristics for Three-Dimensional Bin Packing》(INFORMS Journal on Computing, 2008, DOI 10.1287/ijoc.1070.0250) 的核心不是某个固定排序，而是：摆完物件后维护少量“值得尝试的极点”，避免在连续三维空间盲目枚举坐标。

当前实现的候选坐标已经有类似思想，但使用的是所有已放物件右/后/上坐标的笛卡尔积，不是真正的 EP 集合。

可借鉴：

- 把候选摆放点作为显式搜索状态维护；
- 新放置一个物件后增量生成/裁剪候选点；
- 优先低 z、靠角、减少碎片空间或更好支撑的点；
- 候选点策略与物件排序解耦。

第一版不必立即完整重写成论文级 EP，但设计上应留出 `placement_points` 层，避免候选坐标逻辑永久绑死在 `_candidate_positions()`。

### 3.3 skjolber/3d-bin-container-packing：小订单暴力 + 对称去重 + deadline

GitHub `skjolber/3d-bin-container-packing`（Apache-2.0）同时提供 LAFF 和 brute-force。它对我们最有价值的不是 Java 实现本身，而是三个工程策略：

1. 小件数订单可以实际枚举物件顺序和旋转；
2. 相同尺寸物件、对称旋转不重复生成等价排列；
3. 暴力搜索必须共享 deadline，超时后返回未完成，而不是把超时当无解。

其 README 明确说明 brute-force 会遍历 box order、rotation 和 placement，并跳过相同尺寸导致的等价 permutation/rotation；同时建议实时系统必须使用 deadline。

这正好补当前内核的最大缺口。

### 3.4 py3dbp / gedex 系：可以参考，不适合直接替换

`enzoruiz/3dbinpacking`（py3dbp，MIT）及其 Go 来源 `gedex/bp3d` 的核心也是：

- 商品排序；
- 从已放物件表面产生 pivot；
- 尝试六种旋转；
- first-fit 式把物件放进去。

`jerry800416/3D-bin-packing` 又增加了 `fix_point`、稳定性比例、放置顺序等功能。

它们适合作为“工程实现长什么样”的参考，但不适合整库替换当前内核：

- 本项目现有完整支撑校验更严格、语义更清楚；
- 当前 `FOUND / PROVEN_IMPOSSIBLE / UNKNOWN` 对审单安全非常重要；
- py3dbp 体系偏启发式 first-fit，找不到并不能形成可靠无解证明；
- 直接换库还会把业务适用边界、证据版本、实例追溯和独立复核重新耦合进去。

结论：抄搜索思想，不抄黑盒结果语义。

### 3.5 LAFF：适合作为快速上界，不适合作为唯一求解器

LAFF（Largest Area Fit First）按大底面积物件建立 level，再在层内继续填充。它速度快、适合快速给出一个可行上界。

但本项目存在薄礼袋铺底、不同高度混装、完整支撑等结构，单纯 level-based 贪心不能保证覆盖这些情况。

可借鉴：把 LAFF/greedy 作为“快速先找一个解”的 fast path，为后面的有界搜索提供上界；不能用它的失败代替 UNKNOWN。

## 4. 推荐的新求解器结构

不建议大改成单一算法，而是分四层。

### Layer A：输入正规化与硬约束

只做算法必须知道的事实：

- 物理单元及来源；
- 尺寸、允许朝向、stackable/support policy；
- 可用运输箱；
- 产品原箱的适用商品条件；
- 品牌/用途等硬兼容限制。

盲算阶段不加载历史保存方案、历史人工分包和已知“这个组合通常用某箱”的答案。

### Layer B：单箱内核 `pack_one_bin()`

保留现有严格 verifier，但搜索改成“多策略、共享预算”：

1. 快速必要条件：单件朝向、总体积；
2. 快速 greedy / 当前 volume-first；
3. 支撑感知排序：底面积大且薄的支撑候选优先；
4. 受限 permutation search；
5. 每个顺序内部继续枚举朝向和候选 placement points；
6. 所有策略共享同一 deadline/node budget；
7. 找到布局后统一交给独立 verifier；
8. 预算耗尽仍未找到 -> UNKNOWN。

这里不应直接生成 n! 个带实例 ID 的排列。先按“几何/约束等价类”压缩：相同尺寸、相同旋转策略、相同支撑属性的实例视为同类，只枚举类序列；输出时再映射回具体实例 ID。

### Layer C：1～N 箱外层搜索 `pack_order()`

从 N=1 开始，不把单箱作为独立产品逻辑。

建议流程：

1. 先用快速 greedy 得到一个完整方案，作为当前上界 `UB`；
2. 计算一个保守下界 `LB`（至少包含总商品体积/可用箱容积的容量下界，以及任何单件/硬兼容导致的下界）；
3. 对 `N = LB ... UB-1` 依次尝试完整可行性；
4. 外层状态不是“先决定所有箱再算坐标”，而是逐包构造：为某个允许箱型选择一组剩余物件，调用 `pack_one_bin()` 验证；成功后递归剩余物件；
5. 已证明在某箱不可行的子集可缓存；UNKNOWN 只能缓存为“本预算未决”，不能当失败；
6. 对相同商品集合/相同箱型做 canonical key，避免重复拆分；
7. 一旦 N 包完整方案全部通过独立复核，即得到 N 的可行解；只有所有 `<N` 都被真正证明不可行，才能声称 N 为最少，否则标记“当前最少已找到/最优性未证明”。

这与经典 branch-and-bound 的精神一致，但可以先做有界工程版，而不是追求论文级完全精确。

### Layer D：完整方案评分与业务次目标

首要目标固定为：

1. 全部商品被装入且数量守恒；
2. 包裹数更少。

同包裹数下再比较：

- 箱型是否更小/总空隙更少；
- 子订单拆分数量；
- 其他经用户明确确认的次目标。

历史方案只能在算法完成后用于“这次算的与人工过去怎么做有何差异”，不能进入盲算评分，否则验证会泄漏答案。

## 5. 第一版应该“抄”什么

明确建议：

| 来源 | 借什么 | 不借什么 |
|---|---|---|
| Martello/Pisinger/Vigo | 单箱内核 + 外层最少箱数 B&B 的分层 | 完整精确算法的全部复杂剪枝 |
| Extreme Points | 候选点独立成层、增量维护、点排序 | 一次性重写全部现有坐标搜索 |
| skjolber | permutation/rotation 对称去重、低件数 brute force、共享 deadline | Java 整库、其结果语义 |
| LAFF | 快速构造上界 | 把贪心失败当无解 |
| py3dbp/jerry800416 | pivot/旋转/稳定性工程实现参考 | 替换当前 verifier 或直接信任 fitted/unfitted |

也就是说，第一版真正要复制的是“搜索骨架”，不是复制某个仓库。

## 6. 最小实现次序

下一阶段如获开发授权，建议按下面顺序，不再按旧 P1=只做单箱、P2=以后再多箱的算法顺序：

1. 把当前 `search_packing()` 拆出可传入 `unit_order` / ordering policy 的内核，不改变 verifier；
2. 加 3～5 个确定性排序策略，并首先用礼袋反例证明 fixed-order 漏解被修复；
3. 加等价实例/旋转去重和整次 deadline；
4. 把候选点生成封装成独立策略接口，先保留现有坐标法，再加入更接近 extreme-points 的生成/排序；
5. 建立 `pack_order()` 外层，从 N=1 开始，在同一求解 API 内继续 N=2...；
6. 用历史订单做盲测：算法运行时禁用历史答案，完成后再比较人工包数/箱型/拆分；
7. 只有数据证明当前搜索覆盖和耗时合理，再讨论接入实验页面。

其中第 1～3 步是修正“礼袋先铺底”问题的最小闭环；第 5 步才把单箱能力正式变成完整 1～N 箱算法。

## 7. 验证口径

必须分开报告：

- 找到完整可行方案率；
- 1箱 / 2箱 / 3箱等包数分布；
- “当前最好包数”与“已证明最少包数”；
- UNKNOWN 比例及原因（deadline / node budget / 缺尺寸）；
- 与历史人工方案相同率；
- 算法找到更少包但历史更多包的差异案例；
- 礼袋等支撑敏感反例通过率；
- p50 / p95 / 最大耗时和搜索节点数。

历史一致率不是唯一目标。人工方案本身可能不是最少箱；差异订单必须回到实物规则和仓库操作判断，而不是自动把算法或历史其中一方判错。

## 8. 研究结论

当前底座不需要推翻。

最值得保留的是：严格边界/碰撞/完整支撑验证、可解释坐标、必要条件证明和 UNKNOWN 语义。

最需要补的是：

1. 物件顺序本身必须成为搜索维度；
2. 用等价类去重控制 permutation 爆炸；
3. placement point 从当前笛卡尔坐标生成逐步升级到 extreme-point 思路；
4. 所有策略共享 deadline；
5. 外层从第一天就是 1～N 箱搜索，单箱只是第一层；
6. 历史方案只用于盲测后的比较，不参与算法得答案。

这比直接采用 py3dbp 更适合当前审单项目，也比仅给现有搜索增加“礼袋优先”特判更通用。
