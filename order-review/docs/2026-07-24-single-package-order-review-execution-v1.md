# 单包订单人工触发审核 v1 实施方案

日期：2026-07-24  
状态：业务流程已确认，待实施  
目标项目：`/Users/chat/claude/order-review`  
业务边界：仅实现用户点击悬浮窗按钮后，对当前单包订单执行一次普通审核  
讨论证据归档：`archive/2026-07-24-single-package-review-alignment/README.md`

## 1. 目标

在用户已经确认本地包裹方案，并确认快递、地址、备注及其他订单设置均无问题的前提下，为目标为 1 个包裹的当前订单提供一次人工触发的 ERP 普通审核。

完整链路为：

```text
读取当前订单
→ 人工确认单包方案
→ 用户点击“审核当前订单”
→ 系统重新核对订单身份和页面状态
→ 精确勾选目标订单
→ 双重核对勾选数量和订单身份
→ 打开操作栏普通“审核”
→ 核对确认弹窗的处理范围和数量
→ 点击一次“确定”
→ 捕获临时结果并等待页面刷新
→ 重新读取 ERP 验证目标订单已离开待审核列表
```

本功能不是自动连续审单，也不是确认包裹方案后自动执行。每个订单都必须由用户单独点击一次“审核当前订单”。

## 2. 已确认的业务假设

本阶段只处理以下场景：

- 当前订单只需要判断是否分包。
- 用户已经确认除分包外的快递、地址、备注和其他设置没有问题。
- 本地包裹方案已经确认且目标包裹数为 1。
- 当前运输决策不是“物流发货”。
- ERP 当前页面是“订单处理 → 待审核订单”。
- 当前订单仍处于待审核状态。
- 用户点击一次按钮，只允许操作当前这一个订单。

本功能不替用户判断快递、地址、备注、赠品、套件、合并、异常订单等其他业务条件是否正确。

## 3. ERP 订单身份

当前只读页面样本确认，订单行中可见的系统订单号同时存在于：

- 订单行可见文本前部。
- DOM 属性 `uniqueid`。
- DOM 属性 `sid`。

示例：

```text
系统订单号：5945697152129529
uniqueid="5945697152129529"
sid="5945697152129529"
```

右键菜单顶部显示的 `订单: 5945697152129529` 与该系统订单号一致。

后续执行定位必须以保存下来的系统订单号为主身份，并要求：

```text
row.uniqueid == targetSystemOrderId
或
row.sid == targetSystemOrderId
```

序号 1 只能用于当前读取入口，不能作为执行身份。页面刷新或订单变化后，不得把新的第一行视为原目标订单。

页面中的 `taobaoid`、`tids`、平台单号或其他来源编号属于不同身份层级，不能单独替代系统订单号。

## 4. 审核方式选择

### 4.1 v1 统一使用操作栏普通审核

v1 不使用订单行右键审核，统一采用：

```text
精确勾选目标订单
→ 操作栏“审核”悬停菜单
→ 点击普通“审核”
→ 核对提示弹窗
→ 点击“确定”
```

选择该方式的原因：

- 可以核对实际被勾选的订单身份。
- 可以核对页面底部勾选订单数。
- 可以在弹窗中再次核对处理范围和数量。
- 可以明确区分普通“审核”和“强制审核”。
- 后续拆分订单也可以复用相同审核入口。
- 比右键后直接执行多一层安全确认。

### 4.2 暂不使用右键审核

右键审核暂时只保留为人工备用方式，不进入程序执行流程。

即使后续证明可以通过 `uniqueid` 精确右键，仍需单独评估以下风险：

- 右键位置偏移。
- 菜单绑定到错误订单。
- 菜单出现后直接执行，没有数量确认弹窗。
- 审核后订单消失导致列表结构变化。
- 单包与拆分订单需要维护两套不同流程。

### 4.3 永不使用强制审核

本功能只允许普通“审核”。

任何情况下不得点击“强制审核”，也不得在普通审核无法使用时降级为强制审核。

## 5. 状态模型

建议新增独立执行状态，不与本地方案确认状态混用：

```text
idle
preflight_checking
selecting_order
selection_verifying
opening_audit_menu
audit_dialog_verifying
submitting
result_verifying
success
stopped
unknown
```

含义：

- `idle`：尚未开始 ERP 审核。
- `preflight_checking`：重新读取页面和目标订单。
- `selecting_order`：正在勾选目标订单。
- `selection_verifying`：核对勾选数量和选中行身份。
- `opening_audit_menu`：打开操作栏普通审核入口。
- `audit_dialog_verifying`：核对提示弹窗。
- `submitting`：点击一次确定并等待结果。
- `result_verifying`：等待页面稳定并重新读取目标订单。
- `success`：已证明目标订单离开待审核列表。
- `stopped`：执行前或提交前发现异常，未继续操作。
- `unknown`：已经点击确定，但无法证明成功或失败；必须停止并交给人工。

只允许用户从 `idle` 或已经明确结束的状态发起新的一次操作。

## 6. 执行前核对

用户点击“审核当前订单”后，不得立即点击 ERP。必须重新读取页面并同时满足以下条件：

1. 当前存在唯一的 ERP 待审核标签页。
2. 页面路由仍为 `#/trade/toaudit/`。
3. 页面不处于明显加载、遮罩或刷新状态。
4. 当前本地包裹方案已经确认。
5. 本地目标包裹数为 1。
6. 当前运输决策不是“物流发货”。
7. 当前确认方案绑定的源订单快照仍有效。
8. 已保存目标系统订单号。
9. 页面中只存在一个可操作订单行满足 `uniqueid` 或 `sid` 等于目标系统订单号。
10. 目标行当前状态仍为“待审核”。
11. 目标行的商品身份和数量仍与确认方案对应的源快照一致。
12. 当前页面没有任何已勾选订单。
13. 页面底部勾选计数为 0 或不存在有效勾选状态。
14. 当前没有其他审核、拆分、保存或确认弹窗。

任何一项不满足，进入 `stopped`，不得点击复选框或审核入口。

需要特别防止：

- 用户确认方案后页面已经自动刷新。
- 第一行已变成另一订单。
- 同一系统订单号出现多条可操作记录。
- 页面已经有人工勾选的其他订单。
- 订单商品或数量发生变化。

## 7. 勾选目标订单

### 7.1 定位

只允许通过目标系统订单号定位订单行：

```text
uniqueid == targetSystemOrderId
或
sid == targetSystemOrderId
```

定位结果必须唯一。

复选框必须位于该唯一订单行内部，并且元素本身唯一、可见、可点击、未禁用。

### 7.2 点击限制

复选框只点击一次。

点击后不得假设成功，必须重新读取页面状态。

若点击前目标复选框已经选中，应停止，不得通过再次点击尝试纠正。

### 7.3 勾选后的三重核对

点击后必须同时满足：

1. 页面实际选中订单行数量为 1。
2. 唯一选中行的系统订单号等于目标系统订单号。
3. 页面底部显示的已勾选订单数为 1。

底部文案可能类似：

```text
已勾选：订单数：1
```

不能只检查数字 1；还必须证明选中的就是目标订单。

任何一项不符合，立即进入 `stopped`。程序不得尝试自动取消、重新勾选或改选另一订单。

## 8. 打开普通审核入口

勾选核对通过后：

1. 找到页面操作栏中的“审核”入口。
2. 入口必须唯一、可见、可交互。
3. 使用悬停触发下拉菜单。
4. 等待下拉菜单稳定出现。
5. 核对菜单中同时存在：
   - 普通“审核”。
   - “强制审核”。
6. 普通“审核”必须可唯一定位。
7. 只点击普通“审核”一次。

以下情况全部停止：

- 操作栏存在多个无法区分的审核入口。
- 下拉菜单未出现或出现多个。
- 普通审核与强制审核无法稳定区分。
- 普通审核不可见或不可点击。
- 菜单文字、层级或结构与已知样本不同。

不得在菜单异常时改用右键审核。

## 9. 提示弹窗核对

已知普通审核弹窗标题为“提示”，包含两个处理范围：

1. `处理列表页勾选的订单`
2. `处理查询结果中的订单`

截图样本中第一项被选中，并在其后显示红色文案：

```text
已勾选 1 条订单
```

在点击“确定”前，必须同时验证：

1. 页面只出现一个目标审核提示弹窗。
2. 弹窗标题为“提示”。
3. 第一项“处理列表页勾选的订单”处于选中状态。
4. 第二项“处理查询结果中的订单”没有被选中。
5. `已勾选 1 条订单` 与第一项属于同一个选项区域，而不是第二项区域。
6. 弹窗显示的已勾选数量为 1。
7. 页面底部此前读取到的勾选数量也为 1。
8. 唯一选中订单仍是目标系统订单号。
9. “确定”和“取消”按钮均可识别。
10. “确定”按钮唯一、可见、可点击。

这构成提交前的三层证明：

```text
选中行身份 = 目标订单
＋
列表页勾选数量 = 1
＋
弹窗处理范围为列表页已勾选订单，弹窗数量 = 1
```

全部满足后，才允许点击一次“确定”。

任意条件不满足，进入 `stopped`。提交前停止时不得点击“确定”。可以保留弹窗供人工查看，或在能证明是本次打开的目标弹窗时安全点击“取消”；v1 更保守的默认行为是停止并提示用户人工处理，不自动纠正选项。

## 10. 提交与结果验证

### 10.1 提交前观察器

ERP 成功提示可能快速消失，点击“确定”前应安装只读 DOM 观察器，用于捕获临时消息，例如：

```text
成功审核1单
```

观察器只能用于记录证据，不能因没有捕获到提示而触发再次点击。

### 10.2 点击限制

“确定”只点击一次。

点击后无论超时、页面卡顿、网络异常或未出现提示，都不得再次点击“确定”或重新执行审核。

### 10.3 成功判定

临时提示只能作为辅助证据，不能单独证明审核成功。

成功必须至少满足：

1. 页面完成审核后的自动刷新或稳定状态转换。
2. 页面仍处于原待审核查询环境。
3. 目标系统订单号不再存在于当前待审核列表的可操作订单行中。
4. 目标审核提示弹窗已经消失。
5. 页面没有残留本次目标订单的选中状态。
6. 页面没有显示明确失败、业务拒绝或异常信息。

辅助证据：

- 捕获到 `成功审核1单`。

最终成功状态应记录：

```text
审核成功
目标系统订单号：<targetSystemOrderId>
提交后已确认该订单离开待审核列表
```

### 10.4 结果未知

已经点击“确定”，但出现下列任一情况时，进入 `unknown`：

- 页面长时间未稳定。
- 无法重新读取 ERP。
- 目标订单是否仍存在无法确定。
- 页面刷新后查询环境发生变化。
- 临时提示与最终页面状态矛盾。
- 目标订单仍存在，但无法判断审核失败还是刷新延迟。
- 出现网络超时、浏览器断连或结果不明。

`unknown` 必须显示：

```text
结果未知，已停止。请人工核对 ERP，不会自动重试。
```

## 11. 绝对停止规则

任意步骤与预期正常流程不一致，立即停止。

包括但不限于：

- 找不到目标订单。
- 找到多个同系统订单号订单行。
- 页面已有其他勾选订单。
- 目标订单已被勾选。
- 勾选数量不是 1。
- 唯一选中行不是目标订单。
- 商品或数量与确认快照不一致。
- 目标订单不再是待审核。
- 操作栏审核入口不唯一。
- 普通审核与强制审核无法区分。
- 提示弹窗结构发生变化。
- 弹窗选中了查询结果订单。
- 弹窗数量不是 1。
- 数量文案无法证明属于第一项。
- 点击确定后结果无法确认。
- 页面出现未知弹窗、遮罩或错误信息。

## 12. 禁止自动重试

下列动作一律不得自动重试：

- 勾选订单。
- 悬停或打开审核菜单后再次点击审核。
- 点击普通审核。
- 点击弹窗确定。
- 页面超时后再次提交。
- 结果未知后重新审核。

允许的只是只读重读和有限等待，用于判断页面是否已经稳定；不能把只读等待演变成重复业务操作。

最终结果只能是：

```text
审核成功
执行前已停止
结果未知，已停止
```

不得使用模糊的“可能成功”状态，也不得自动将未知结果认定为失败后再次执行。

## 13. 悬浮窗 UI

### 13.1 确认方案后

单包方案确认后，显示最小必要信息：

```text
目标订单：<系统订单号>
本地方案：1 个包裹
ERP 状态：尚未审核

[审核当前订单]
```

按钮只在以下条件下启用：

- 本地方案已确认。
- 目标包裹数为 1。
- 存在可靠系统订单号。
- 当前没有正在执行或结果未知的审核。

### 13.2 执行进度

在现有窗口内显示操作状态和进程，不需要另做复杂操作摘要：

```text
正在核对当前订单
正在勾选目标订单
正在核对勾选数量和身份
正在打开普通审核
正在核对确认弹窗
正在提交审核
正在验证刷新结果
```

### 13.3 最终状态

成功：

```text
审核成功
```

执行前停止：

```text
已停止：弹窗选中了“处理查询结果中的订单”，未点击确定
```

结果未知：

```text
结果未知，已停止：提交后无法确认目标订单是否已离开待审核列表
请人工核对 ERP，不会自动重试
```

错误信息必须指出停止在哪一步和具体不符合项，不能只显示“操作失败”。

## 14. 操作日志

每次用户点击“审核当前订单”都应保存本地执行日志，但不得记录无关隐私。

至少记录：

- 执行 ID。
- 目标系统订单号。
- 本地确认案例或 assignment ID。
- 源快照 ID。
- 目标包裹数。
- 用户点击时间。
- 每个状态开始和结束时间。
- 执行前读取到的订单身份摘要。
- 勾选数量和选中订单 ID。
- 弹窗处理范围和数量核对结果。
- 是否点击确定。
- 是否捕获临时成功提示。
- 提交后是否仍能找到目标订单。
- 最终状态：`success`、`stopped` 或 `unknown`。
- 停止原因或未知原因。

日志必须明确区分：

- 本地包裹方案确认。
- ERP 审核执行。

不能因为本地案例已保存就记录为 ERP 已审核。

## 15. 技术实现约束

- ERP 执行必须绑定唯一待审核 CDP target，执行过程中 target 变化立即停止。
- 每次关键动作前后都重新读取必要 DOM 状态。
- 不依赖固定坐标执行关键业务动作。
- 订单行必须通过稳定身份属性定位，不依赖序号或视觉位置。
- 复选框、操作栏、普通审核菜单项、弹窗选项和确定按钮都必须唯一定位。
- 对临时 toast 使用提交前安装的观察器。
- 对刷新结果使用目标系统订单号重新扫描，而不是继续持有旧 DOM 节点。
- 页面元素或文字结构变化时应 fail closed。
- ERP 业务动作串行执行，同一时间只允许一个审核执行会话。
- 未完成或结果未知时禁止开始下一订单。
- 不允许任何 ERP 写操作测试使用真实订单，除非用户在当次操作中明确点击悬浮窗按钮。

## 16. 实施顺序

### 阶段 1：只读探测与 dry-run

先实现完整探测，不点击任何 ERP 业务按钮：

- 读取系统订单号。
- 定位唯一目标行和复选框。
- 读取当前勾选行及底部计数。
- 定位操作栏审核入口及菜单结构。
- 定位审核提示弹窗结构和选项归属。
- 定位临时消息容器和页面加载状态。
- 定义执行状态、日志和错误类型。

提供开发模式 dry-run，输出每一步是否可唯一识别，但不勾选、不审核。

### 阶段 2：受控单订单真实执行

在阶段 1 通过真实页面样本验证后，再接入写操作：

- 仅用户点击按钮后执行。
- 一次只操作一个单包订单。
- 先勾选并验证。
- 再打开普通审核并验证弹窗。
- 最后点击一次确定并验证结果。

不得跳过 dry-run 探测直接实现全流程点击。

## 17. 测试与验收

### 17.1 单元测试

至少覆盖：

- 系统订单号从 `uniqueid`、`sid` 和可见文本一致提取。
- 多个相同系统订单号时阻断。
- 页面已有勾选订单时阻断。
- 选中数量为 1 但选错订单时阻断。
- 选中目标订单但底部数量不是 1 时阻断。
- 普通审核与强制审核区分。
- 第一项选中、第二项未选中的弹窗解析。
- 数量属于第一项与错误属于第二项的区分。
- 弹窗数量不是 1 时阻断。
- toast 捕获与最终结果验证分离。
- 提交后目标订单消失判定成功。
- 提交后结果不明判定 unknown。
- 任意写动作不会自动重试。
- 审核执行日志不把本地确认误记为 ERP 成功。

### 17.2 DOM 固件测试

保存脱敏后的 HTML/结构固件，至少包括：

- 正常待审核单包订单。
- 页面无勾选状态。
- 目标订单勾选后底部显示 1。
- 正常审核下拉菜单。
- 普通审核提示弹窗截图对应结构。
- 错误选中“处理查询结果中的订单”的弹窗。
- 数量不是 1 的弹窗。
- 审核成功后的列表刷新状态。

### 17.3 真实执行验收

首次真实操作必须由用户在场并主动点击。

建议按以下顺序逐单测试：

1. dry-run 只读识别，不点击。
2. 允许勾选，但在弹窗前停止并人工核对。
3. 打开普通审核弹窗，但不点击确定，人工核对后取消。
4. 用户明确同意后完成一次真实单包审核。
5. 核对执行日志、页面结果和订单是否正确消失。
6. 多次正常单包订单验证稳定性。

每增加一个可写步骤，都必须先验证前一阶段采集到的页面事实稳定。

## 18. 本轮明确不做

- 右键审核。
- 强制审核。
- 确认包裹方案后自动审核。
- 连续自动处理下一订单。
- 批量审核。
- 拆分订单。
- 拆分后多订单审核。
- 搜索拆分后订单号。
- 合并或取消合并。
- 套件转单品。
- 修改快递、地址、备注或商品。
- 自动重试任何 ERP 写动作。
- 无人工点击的自动执行。

## 19. 拆分订单的后续方向

拆分订单不纳入 v1，但保留以下已确认方向：

- 拆分完成后优先在当前页面识别 ERP 自动显示的拆分结果，不优先重新搜索订单号。
- 拆分前正常状态应为没有任何已勾选订单。
- 拆分后正常情况下，拆分结果订单会被自动勾选。
- 审核仍统一使用操作栏普通审核，而不是逐行右键审核。
- 原订单可能仍显示为第三行，但可能不可操作；不能仅以总行数判断异常。
- 后续必须识别“可操作且已勾选的拆分结果行”和“不可操作、未勾选的原订单残留行”。
- 拆分结果的商品和数量组合必须与本地确认的多个包裹方案一致。
- 需要真实拆分样本确认新旧订单之间的稳定关联字段、原订单残留特征和拆分成功状态。

拆分流程必须另立文档和实施计划，不得在单包审核 v1 中顺带实现。

## 20. 完成标准

只有同时满足以下条件，单包订单人工触发审核 v1 才算完成：

- 用户必须点击悬浮窗按钮才会开始。
- 系统以稳定系统订单号唯一定位目标订单。
- 执行前验证订单、商品、数量、状态和无其他勾选。
- 勾选后验证数量和身份。
- 只使用操作栏普通审核。
- 弹窗处理范围和数量经过严格核对。
- “确定”只点击一次。
- 无任何业务写动作自动重试。
- 提交后通过重新读取 ERP 证明目标订单离开待审核列表。
- 不能证明结果时进入 unknown 并停止。
- 悬浮窗显示清楚的进度和停止原因。
- 日志区分本地方案确认与 ERP 审核执行。
- 完整测试通过。
- 拆分、批量和自动连续操作均未被引入。
