# 审单与包裹规则根本约束

日期：2026-07-23  
状态：根本规则，长期有效；基础实现已完成  
适用范围：订单识别、历史方案恢复、包裹规则复用、复杂合并订单案例、推荐算法与 ERP 执行规划

## 0. 变更治理

本文件记录订单审核系统的根本业务语义。除非后续针对具体冲突进行明确讨论并主动修改本文件，否则：

- 后续代码、算法、界面、计划和文档不得与本文件冲突。
- 不得因为实现方便而合并本文明确区分的业务概念。
- 新样本若与本文依据的 ERP 页面规律不一致，必须先记录样本、讨论影响，再修改规则；不得静默改变判断方式。
- 归档文档、旧计划和现有代码只能作为实现事实参考，不能覆盖本文件。

## 1. 必须分开的四个概念

### 1.1 同一订单已经保存过方案

当前扫描到的订单，与历史中某条已经确认保存的订单，在“平台子订单号及其对应商品明细”上完全一致。

含义：这是同一个已经处理过包裹方案设定的订单，不需要再次设定或重复保存方案。

### 1.2 不同订单精确复用历史方案

平台子订单号不同，但每个子订单的商品构成和数量与历史结构完全一致。

含义：这不是同一订单，而是新的订单命中了已经确认过的精确包裹规则。系统可以默认采用方案，但必须允许人工修改。

### 1.3 商品总量相同但子订单结构不同

全部商品汇总后的身份和数量相同，但各个平台子订单分别包含哪些商品、各有多少不同。

含义：对于多包拆分，这不是精确规则复用，可能需要形成新的复杂合并订单案例；对于单包方案，子订单结构差异通常没有保存新案例的价值。

### 1.4 ERP 执行状态

包裹方案是否已经存在，与 ERP 是否已经完成审核、拆单或其他操作是两个独立状态。

命中历史方案或推荐规则不能被解释为 ERP 操作成功。未来必须单独记录未执行、执行成功、执行失败或结果不确定。

## 2. ERP 页面已观察到的拆分与合并规律

以下规律来自人工实际观察，不保证 ERP 永远不存在例外：

1. 一个订单拆分后再原样合并，可能重新显示为一条合计商品行，例如 `商品 A ×6`。
2. 也可能在同一个平台单号下显示两条身份相同的商品行，例如 `商品 A ×3` 和 `商品 A ×3`。
3. 在上述两种显示方式中，业务含义均可规范化为同一平台单号下的 `商品 A ×6`。
4. 合并订单可能沿用其中一个原订单的系统单号或内部单号；这不影响当前包裹规则判断，因为商品明细和平台子订单结构仍是主要依据。

因此，同一平台单号下身份相同的商品行必须先汇总数量。不能因为 ERP 将同一商品显示为一行还是多行，就判定订单或规则发生变化。

## 3. 商品与子订单的规范化

### 3.1 商品身份

当前实现可使用以下结构化字段共同确认商品身份：

- 商家编码
- 主商家编码
- 平台商品 ID
- 平台 SKU ID
- ERP 标准商品名称
- 必要时保留平台规格、平台名称和商品简称作为校验或审计信息

商品身份规则后续可以因真实数据质量而调整，但不得仅按页面行位置或显示顺序识别商品。

### 3.2 同一平台子订单内的汇总

对每个平台单号分别处理：

- 身份相同的多条商品行合计数量。
- 商品行顺序不参与比较。
- 同一商品显示为一行或多行不影响结果。
- 平台单号相同的商品归入同一平台子订单进行规范化。

### 3.3 多个平台子订单

不同平台单号必须分别保留其对应商品明细。不能为了比较方便，只保留整个合并订单的商品总和。

SID、OID、ERP 内部单号和系统单号继续完整保存，供审计和未来 ERP 执行定位使用；当前“同一订单已经保存过方案”的主要业务判断直接使用平台子订单号及对应商品明细。

### 3.4 等体积口味只在包裹方案层互换

用户明确确认以下商品包装大小相同，历史拆包方案可以在同规格内互相复用：

| 规格组 | 商品一 | 商品二 |
|---|---|---|
| 咖啡正装 | 美式咖啡（绿） `6977987940138` | 生椰拿铁（新包装） `6979151090014` |
| 咖啡体验装 | 美式咖啡（绿）体验装 `6979499760068` | 生椰拿铁体验装 `6978430740022` |
| 黑茶正装 | 茉莉味 `6979499760044` | 普洱味 `6979265440002` |
| 黑茶体验装 | 茉莉味体验装 `6979499760099` | 普洱味体验装 `6979265440019` |
| 蛋白粉正装 | 牛油果猕猴桃味 `6977987940046` | 莓果味 `6977987940039` |
| 蛋白粉体验装 | 牛油果猕猴桃味三袋体验装 `6977987940107` | 莓果味三袋体验装 `6977987940084` |
| 气垫正装 | 亮肤色 `6938582367386` | 自然色 `6938582367409` |
| 气垫替换装 | 亮肤色 `6938582367393` | 自然色 `6938582367416` |

边界：

- 只在历史包裹方案匹配、容量比较和方案投影时视为等体积商品。
- 正装只能替换正装，体验装/试用装只能替换同规格体验装，气垫正装与替换装也必须分组；八个规格组之间不得交叉。
- 同一订单识别、原商品引用、案例快照、界面名称和 ERP 审核核对仍保留真实口味及真实商家编码。
- 应用历史方案时必须重新映射到当前订单的 `sourceProductId` 和商品名称，不能复制历史口味的原商品引用。
- 白名单以商家编码为准；名称相似、未知口味或未登记编码不得自行推断为等体积。

## 4. 同一订单已经保存过方案

### 4.1 判断规则

将当前订单规范化为：

```text
平台子订单号
→ 该平台子订单下汇总后的商品身份与数量
```

只有以下内容全部一致，才属于同一订单：

- 平台子订单号集合一致。
- 每个平台子订单号对应的商品身份集合一致。
- 每项商品的汇总数量一致。
- 不存在多出或缺少的平台子订单。

比较时忽略平台子订单排列顺序、商品行排列顺序以及同商品被拆成几行显示。

### 4.2 命中后的行为

- 直接加载并显示此前已经确认的包裹方案。
- 明确告诉人工：该订单已经保存过方案。
- 不要求再次选择单包、拆包或采用推荐。
- 不重复追加一条完整案例。
- 保留人工修改方案的能力。
- 人工修改后不得覆盖旧方案，也不得追加成无法关联的重复案例；当前确定保存为“同一订单的方案版本”，保留上一版本引用和版本号，后续如需改为其他模式必须先重新讨论并修改本文件。
- 同一订单再次出现只表示重新读取到原订单，不增加规则强化次数。

## 5. 不同订单精确复用历史方案

### 5.1 判断规则

平台单号具体值不同，但忽略单号文本后，各个平台子订单的商品构成和数量形成的多重集合完全一致。

例如：

```text
历史：
- X：A ×2
- Y：B ×2
- Z：C ×2

当前：
- M：A ×2
- N：B ×2
- P：C ×2
```

这不是同一订单，但属于完全相同的子订单结构，可精确复用历史包裹方案。

### 5.2 命中后的行为

- 唯一且无冲突的精确方案可以默认采用。
- 默认采用后直接进入现有可编辑包裹方案，不需要人工重新逐件设定。
- 无需修改时，用户可直接点击审核或拆分并审核；精确匹配结果只作为本单内存执行方案，不再要求额外点击“保存方案”，也不写规则采用关系或次数。
- 人工必须可以修改方案。
- 系统不得把它显示成“该订单已经处理过”；应显示为“已采用完全匹配的历史方案”一类语义。
- 未修改并直接使用时，不重复保存完整相同案例，也不增加规则采用统计；订单明细精确一致本身就是复用依据，不依赖累计使用次数提高置信度。
- 修改后确认时，形成或命中一个方案分支，并记录人工修改事实。

## 6. 商品总量相同但子订单结构不同

例如历史结构：

```text
- 订单 1：A ×2
- 订单 2：B ×2
- 订单 3：C ×2
```

当前结构：

```text
- 订单 4：A ×1 + B ×1
- 订单 5：B ×1 + C ×1
- 订单 6：A ×1 + C ×1
```

两者的商品总量都是 `A ×2 + B ×2 + C ×2`，但子订单结构不同。

### 6.1 多包方案

如果商品不能单包，需要拆成多个包裹：

- 不能视为同一订单。
- 不能视为子订单结构精确匹配。
- 不能仅因商品总量相同而自动套用原多包方案。
- 可以由“历史包裹模块精确覆盖”算法处理：算法只能把人工已经确认过的完整
  单包裹作为模块，逐商品精确覆盖当前订单总量，不得按比例缩放、拆减模块数量
  或用单包容量近似补足余量。
- 组合候选属于新的近似推荐，不属于精确规则复用；唯一且无冲突的精确模块组合
  可以自动进入可编辑草稿，无需额外点击保存，但不得自动确认或操作 ERP。用户
  点击拆分并审核时才在同一次点击中保存当前完整案例并进入受控执行。
- 多种不同包裹组合都能精确覆盖时必须显示冲突并交给人工选择，不能静默按历史
  次数决定唯一答案。
- 确认得到新的多包方案后，应保存为一个完整的新复杂案例，因为不同子订单构成可能影响拆分方式。

### 6.2 单包方案例外

如果全部商品能够作为一个包裹发货：

- 子订单如何组成不影响最终包裹结果。
- 相同商品总量的单包能力可以跨不同子订单结构复用。
- 不因子订单结构变化保存新的完整复杂案例。
- 只记录单包规则被再次采用即可。

## 7. 包裹规划的长期优先原则

当前系统暂不引入完整运费计算。未来包裹规划遵循：

1. 先判断能否单包发货。
2. 单包不行，再判断能否使用两个包裹。
3. 两个包裹仍不行，再考虑三个、四个或更多包裹。
4. 在现有能力边界内，优先使用满足要求的最少包裹数。

### 7.1 平台子订单完整性是多包拆分优先级

用户在 2026-08-13 明确：不同平台子订单的商品允许进入同一个实体包裹。平台
子订单不是禁止混装的硬边界，而是在整单无法单包、必须拆分时使用的操作优先级：

1. 先忽略平台子订单边界，判断合并订单的全部商品能否进入同一个包裹。能单包时，
   子订单结构不影响结果。
2. 必须拆分时，先把每个平台子订单视为不可拆的完整块。完整块之间允许合装，
   并在不拆开任何子订单的前提下寻找可行的最少包裹方案。
3. 如果完整块方案不可行，再只拆开无法整体安排的子订单；可以把不同子订单中的
   同款或其他商品重新分配到多个包裹。
4. 同样包裹数下，优先选择拆开子订单更少、跨包片段更少的方案。不得为了形式上
   “平均”而把原本可以完整保留的两个子订单都拆散，再让两个包裹同时包含两边商品。

人话：系统先回答“这些东西能不能一起发”；确实要拆时，尽量做到一个原订单的
商品不被拆散。只有某个原订单按整体确实放不下或受离散箱规限制，才进入跨订单
调量。这个偏好不禁止完整的多个子订单共用一个包裹。

这条优先级只用于生成和排序新的尺寸拆分方案。已经精确命中的历史方案仍按历史
事实恢复，不因新排序规则自动改写。

暂不纳入：

- 不同纸箱规格的组合优化
- 商品重量和包裹总重量的完整模型
- 收货地址差异
- 地区和快递公司的运费阶梯
- 以真实运费最低为目标的全局优化

当前“能否单包”或“某个多包组合可行”的依据主要来自人工确认过的历史规则。没有可靠历史或容量模型时，不得假装系统已经知道包裹容量。

“历史包裹模块精确覆盖”不等于系统掌握了纸箱容量。它只复用历史中原样出现过
的包裹商品与数量，且同一模块至少需要 3 个独立有效案例，并至少有 1 次在
多包订单中被人工划为独立包裹边界。每个模块内部数量不可缩放，但同一个已经
达到证据门槛的完整模块可以重复使用，例如历史包裹 `6 防晒 + 2 面膜` 与
`3 防晒 + 1 面膜` 可以精确组成 3、4、5、6 份同结构商品。组合后仍必须无余量、
无超量，不得按比例推算或拆改单个模块。第一版最多组合 5 个包裹，与当前非物流案例的已观察上限一致；
唯一最少包裹解可以自动进入可编辑草稿，多个最少解仍显示冲突并等待人工选择；
超出时只保留人工或物流判断，不继续扩大搜索。

### 7.2 物流发货是独立运输决策

当人工判断按快递会形成较多包裹、包含重货，或商品组合复杂到不值得继续精确装箱时，可以直接选择“物流发货”。系统本身没有箱规和体积模型，不得把件数提醒描述成系统已经估算出包裹数。

物流发货必须与普通单包严格分开：

- “ERP 暂不拆单”不等于“物理上只有一个包裹”。
- 物流案例不得参与普通单包容量、单包总量或精确包裹方案推荐。
- 相同商品结构再次出现时，只能提示“历史同类订单选择过物流”，不能自动确认物流。
- 总件数达到 `70` 时可以显示物流复核提醒，但件数只能用于提醒，不能自动决定运输方式；完整原箱等情况可能件数很高但包裹数很少。
- 人工估计达到约 `5～6` 箱以上、重货多箱或复杂混合大单时，可以标记物流。
- 物流判断允许保存粗略包裹区间和原因，不要求生成仓库级精确装箱方案。
- 物流订单不得进入普通单包 ERP 审核流程，直到物流模板、运单和 ERP 操作方式另行确认。

2026-07-27 首批三条物流案例的有效快照总件数分别为 `121`、`97`、`85`，已从普通单包学习中迁出。随后人工又保存了 `239` 件物流案例。以上案例均保留完整订单快照和人工判断证据，但不作为系统已掌握包裹数的证明。

### 7.3 单件非套件默认单包

订单已展开、商品总数量恰好为 `1` 且展开明细未识别为套件时，普通单包是确定结果，不再需要用历史案例或人工确认来证明装箱能力。

- 无论当前订单命中同订单已保存方案、历史规则，还是没有任何历史方案，都直接生成内存中的普通单包执行方案。
- 用户点击“审核当前订单”就是本单唯一一次 ERP 操作授权；执行前不保存完整案例、不记录规则采用，也不要求额外点击“保存方案”。
- 单件直审方案只服务当前订单，不把这次确定性结果写入案例库，也不参与规则统计，因此不会触发大型案例文件重写。
- 套件订单继续阻断，不得因总数量为 `1` 绕过“套件转单品”前提。
- 已明确保存为物流发货的同订单历史仍保持物流状态，不进入普通单包审核。

### 7.4 纸箱适配不是连续容量上限

用户在 2026-07-29 明确确认：实际装箱使用有限且离散的纸箱规格，商品允许旋转、侧放和叠放，但“物理上装得下”不等于“存在合适纸箱”。纸箱空余空间过大时也不能采用。

已确认反例：

- 同一商品“酵素4.0”`18` 盒可使用约 `20` 盒规格纸箱单包。
- 同商品 `9` 盒没有合适纸箱，需要拆成 `6 + 3`；其中 `3` 盒使用小箱，`6～7` 盒使用更大一档纸箱。
- 因此，历史较大数量已经单包，不能推出所有较小数量也可以单包。

当前边界：

- `single_package_capacity` 只表示“历史较大数量曾单包”的人工参考候选，不是可靠装箱结论，不得自动确认或直接驱动 ERP。
- 如果同一商品身份集合已经出现“某个数量单包、另一个不超过该数量的组合却需要
  多包”，说明这组商品的连续容量假设已被真实案例否定。后续不同数量订单不得再
  生成可采用的 `single_package_capacity` 方案，只能提示历史证据互相冲突并要求
  人工创建方案。该阻断只使用订单加载前已经确认的案例，不把当前订单或未来案例
  反向泄漏进推荐判断。
- 相同商品和相同数量已有精确历史方案时，优先使用精确历史，不得被跨数量容量候选覆盖。
- 线上包裹规划统一采用“确认规则与精确保存方案优先、尺寸计算兜底”：同一订单
  已有保存方案、不同订单命中唯一无冲突精确方案、相同总量单包、唯一无冲突的
  历史包裹模块精确组合、固定业务规则或已确认箱规时，直接使用结果，不运行三维
  求解。只有这些结果都没有命中时，才进行包裹尺寸计算。
- 多个精确规则互相冲突时必须提示人工选择，不能调用尺寸计算替其中一个分支背书；
  `single_package_capacity` 等近似历史参考不属于确认规则，不能阻断更可靠的尺寸
  计算。离线历史审计允许继续计算作对照，但不得追溯改写保存方案。
- 2026-08-13 已建立独立的第一版离线三维装箱底座，考虑商品与纸箱的长、宽、高，
  允许 90° 旋转、侧放和叠放，并返回逐件坐标；当前不接入线上推荐。
- 当前已提供的纸箱尺寸是外尺寸，统一按长、宽、高各减 `5 mm` 得到保守可用
  内径；用户确认按该内径找到摆放就一定能放下。搜索未找到或超限必须返回未知，
  不得伪装成确定装不下。
- 商品重量暂时无法准确获得，不纳入第一版；纸箱承重、缓冲材料预留也暂不纳入。
- 不建立跨产品通用的最大空隙比例。原箱是否可在未满箱时使用，主要看剩余空间是否
  仍在人工确认的合理范围内，并按每种产品分别记录最低可发数量；不得把某一产品的
  缺口数量或空隙经验直接外推给其他产品。
- 专用原箱只允许原产品或用户明确确认的同规格口味共用，不得把原箱剩余空间拿来
  混装其他品类。当前确认的原箱可发区间为：咖啡 `54～60` 盒（两个确认等体积口味
  可混装）、酵素4.0 `15～20` 盒、无花果果冻 `56～64` 盒；低于各自下限不能借用
  原箱规则。益生菌100盒和黑茶72盒仍只有完整容量才作为原箱关闭发货单元，直到
  用户另行确认合理余量。
- 无花果果冻使用现有普通纸箱时，仓库实测单箱最多 `28` 盒；`1～28` 盒按单包
  直接推送，超过 `28` 盒必须拆单。无花果果冻 `56～64` 盒属于前述专用原箱例外，
  优先按64盒原箱作为一个关闭发货单元，不套用普通纸箱的 `28` 盒上限。
- 蛋白粉和酵素3.0已经停售，蛋白粉七盒箱、酵素3.0三盒箱和十盒箱的现有库存
  允许装其他KGOS产品；库存耗尽后由用户单独通知停用。箱名仍只是标签，不形成
  商品绑定，但不得跨品牌给悦希使用。
- 纸箱品牌是几何求解前的强制条件：前12种普通箱及KGOS原箱只装KGOS商品；悦希
  纸箱只装悦希商品并继续遵守瓶装范围、礼盒专用或固定方案。跨品牌即使物理尺寸
  放得下也不可采用。
- 玉米片两个口味使用KGOS原箱，每箱固定10包；单口味10包和两个口味 `5+5` 均
  视为完整原箱，不再匹配其他纸箱。物流判断仍独立处理。
- 悦希新精油使用仓库确认的小箱，每箱最多5瓶。礼盒单盒装属于扁平结构，不用于
  普通单品发货；其大受力面积和较弱支撑会增加快递破损风险，不能仅凭三维放得下
  就将其列为候选。
- 咖啡正装合计36盒使用两个咖啡箱发货。`18+18`能让客户更容易理解为两个分包、
  降低误认为少发的风险；`16+20`也可接受。无论单一口味还是两个确认等体积口味
  混合，36盒都不使用酵素存量大箱形成一包。
- 咖啡三、七、十、十六、二十和二十四盒装纸箱的对应咖啡数量均为用户确认最大
  容量；这条容量证据只属于咖啡正装，不能外推为其他商品的数量容量。
- 悦希礼盒商品暂不进入通用尺寸求解。除修颜礼盒固定按一套或两套使用专用纸箱、
  大于两套时每两套拆一箱外，其余礼盒继续复用人工保存的包裹配置。
- 悦希单品四盒装是瓶装品类箱，不绑定单一产品；已确认品类白名单外的悦希商品
  不得仅凭名称自动纳入。

## 8. 方案分支与确定性复用

### 8.1 不保存独立的打回记录

当前只持久化人工修改后形成的新方案事实或同订单版本。精确匹配后的直接使用、取消、未确认或单纯离开，都不写采用次数、修改次数或独立“打回案例”。

### 8.2 多分支方案

同一子订单结构可能存在多个已确认方案分支，例如 `3+3` 与 `2+2+2`。

- 不得覆盖或丢失已有分支。
- 人工修改后的最终结果若与现有分支相同，直接复用该分支，不增加采用次数；若修改的是同一订单已保存方案，同时新增一个关联上一版本的订单方案版本。
- 若形成新的有效结果，则增加一个新分支。
- 分支是否匹配只看订单明细签名和方案内容，不使用采用次数、修改次数或最后使用时间提高置信度。
- 具体默认排序算法尚未确定，没有真实业务规则前不得提前固化复杂排序。

现阶段若存在多个不同分支，必须保留人工可见和可修改能力，不得按历史采用次数静默选择。

## 9. 规则强化与完整案例保存边界

### 9.1 不新增完整案例

以下情况不需要重复保存完整案例：

- 同一订单再次出现并恢复原方案。
- 不同订单精确命中同一子订单结构，直接采用原方案。
- 商品总量相同且已确认可以单包，即使子订单结构不同。

这些情况只需在当前订单内恢复或复用方案，不写新的案例、订单采用关系或采用次数。

### 9.2 需要新增完整案例或版本

只有在以下情况下才有新增完整案例或版本的学习价值：

- 同一订单的已保存方案被人工修改时，新增关联上一版本的同订单方案版本。
- 不是同一订单。
- 不能直接按单包规则处理。
- 子订单商品结构与已有精确案例不同。
- 人工或未来算法确认了一个有效的多包方案。

## 10. 与 ERP 受控执行的关系

任何执行流程必须分成两层：

```text
规则层：当前订单应该形成哪些包裹
执行层：ERP 需要执行哪些审核、拆单或后续动作
```

- 已有历史方案不等于已经执行。
- 规则命中只提供目标包裹方案。
- 当前 ERP 订单是否已经符合目标、是否需要拆单、审核是否成功，必须由执行层单独判断。
- 当前已开放的执行只有用户逐单点击触发的普通单包审核，以及多包混合拆分后按目标包裹总数继续普通审核；授权不能沿用到下一单，结果不确定时不能自动重试。
- 正常成功处理的订单通常不会继续留在“订单处理”页，因此当前规则无需提前覆盖修改地址、快递拦截、异常退回等独立流程。
- 修改地址、原快递单号拦截和异常订单属于后续单独维度，不得反向污染当前包裹规则判断。

## 11. 对当前实现的直接约束

当前代码必须持续满足以下语义约束：

1. 新增“同一订单已经保存过方案”的独立匹配，不再依赖完整页面快照哈希表达业务身份。
2. 保留“不同订单精确复用规则”的匹配，但必须与同一订单历史恢复使用不同状态和界面文案。
3. 同一平台单号下的相同商品行先汇总，兼容拆分后重新合并的两种页面显示。
4. 单包规则允许基于商品总量跨子订单结构复用。
5. 多包精确规则继续保留子订单结构；商品总量相同但子订单结构不同不能直接视
   为精确匹配。只有历史包裹模块能逐商品精确覆盖时，才可在精确匹配之后生成
   组合候选；唯一且无冲突的候选可自动进入可编辑草稿，冲突候选必须人工选择。
6. 精确历史复用不记录订单采用关系和采用次数；只有人工修改形成的新事实才写入完整案例或版本，避免案例文件被确定性重复订单污染。
7. 所有自动采用结果继续可编辑；人工修改进入方案分支语义。
8. 推荐和草稿模块不得自行执行 ERP；只有独立执行层可以在用户针对当前订单明确点击后运行已经开放且经过验证的动作。
9. 物流发货作为独立运输决策保存，并从所有普通包裹方案推荐中排除。
10. 总数量为 `1` 且非套件、且同订单未明确保存为物流时，直接生成仅用于当前订单的单包执行方案；点击审核前不保存、不确认、不记录规则采用。
11. 包裹方案匹配只允许第 3.4 节白名单内的同规格口味互换，不得改变真实商品身份或跨规格猜测。

## 12. 尚未确定、不得擅自推断的实现问题

以下不属于根本业务规则，实施时需单独设计或再次讨论：

- 多分支方案存在时的默认排序公式。
- 历史遗留的规则采用次数、修改次数和最后使用时间只保留兼容读取，不再参与推荐置信度、排序或执行判断。
- 在线尺寸求解的具体候选数据结构、耗时上限和界面呈现；调用顺序已确定为确认规则
  与精确保存方案优先，仅在没有可复用结果时计算。
- 如何把离线三维摆放结果与实际箱型、可接受空隙和仓库操作限制结合；第一版不
  纳入重量、承重或缓冲预留。
- 合单、套件转换、批量处理等尚未开放 ERP 写操作的成功判定和幂等机制；不得从现有单包审核或混合拆分链路直接类推。

## 14. 其他长期基础约束

本节补充此前已经确认、但原先只存在于阶段需求或实现约束中的规则。它们与前述订单识别和包裹复用规则具有相同优先级。

### 14.1 原订单事实层不可变

- ERP 当前读取结果是原订单事实输入；包裹方案、推荐结果和人工编辑都不得反向修改原订单商品、数量、平台单号或其他标识。
- 每次确认必须保留完整原订单快照、最终包裹明细和决策来源，不能只保存包裹结果。
- 界面折叠、隐藏或只展示部分字段，不得导致持久化快照丢失已经读取到的原始数据和结构化字段。
- 已确认的原订单快照和案例不得被静默覆盖。日常方案修正必须通过同一订单方案版本、方案分支或后续明确设计的撤销记录实现。只有用户明确要求删除已确认的错误数据时，才允许作为人工数据修复处理：先停应用并创建有效备份，精确删除错误案例及关联索引，排除其他案例引用后原子写入和独立读回；原审核执行日志仍按事实保留。

### 14.2 草稿生命周期与确认硬约束

- ERP 刷新、目标订单变化或重新读取后，刷新前尚未确认的草稿和推荐投影必须失效，不能继续套用到新的事实快照。
- 包裹项只能引用当前原订单快照中的商品，不得凭空创建商品，也不得引用其他订单快照的商品行。
- 确认前必须满足逐原商品数量守恒：分配总量必须等于原数量，不允许负数、超分配或漏分配。
- 至少保留一个包裹，且不允许确认空包裹。
- “保存方案”只表示本地包裹决策已经确认并持久化，不代表 ERP 已审核、拆单、合单、保存、提交或发货。
- 点击“保存方案”时如仍有未分配商品，应按 ERP 的最终剩余包语义处理：优先填入已有的空最后一包，否则新增最后一包承接全部余量；不得把余量追加到已有商品的当前包裹。

### 14.3 推荐可追溯、冲突可见和人工最终控制

- 所有推荐必须能够追溯到来源案例或规则，并保留规则 ID、匹配类型和算法版本；不得只输出一个无法解释的结果。
- 唯一且无冲突的精确规则可以自动填入可编辑草稿；用户点击当前订单的审核或拆分按钮后，可直接把该内存方案交给 ERP 执行层，不先持久化采用关系。没有用户当次点击时仍不得操作 ERP。
- 人工始终可以修改自动采用的方案；修改后的结果进入同订单版本或方案分支语义。
- 同一匹配条件下存在多个不同方案分支时，不得因为实现方便静默覆盖或丢弃分支，也不得把其中一个伪装成唯一确定答案。
- 多分支默认排序规则未明确前，应保留冲突提示、其他分支可见性和人工选择能力；不得使用历史采用次数代替业务规则。
- 证据不足、仅近似匹配或无法安全投影时，不得把候选显示成“完全匹配”或生成看似完整但无法解释的方案。

### 14.4 ERP 子订单与赠品标记的解释边界

以下同样属于 ERP 页面观察结论，遇到反例时按第 0 节流程讨论修订：

- ERP 当前视角通常是平台子订单或合并后的子订单集合，不得假设系统能够稳定还原一个平台主订单结构。
- 平台活动赠品可能在 ERP 中表现为独立子订单，并且不一定带有明确的“赠品”标记。
- ERP 内部赠品标记与平台活动赠品不是同一个概念，不能仅凭该标记判断平台满赠关系、订单是否相同或包裹应如何拆分。
- 缺少 SPU、SKU 或其他结构化标识时，不得自行补齐或猜测；应保留原始数据并采用保守匹配，避免把身份不确定的商品错误合并。

### 14.5 匹配和处理优先级

同一批当前订单同时可能命中多种历史信息时，固定优先顺序为：

1. 先查同一订单最新方案；若它明确保存为物流，保留物流状态并阻断普通审核。
2. 总数量为 `1` 且非套件、且不属于第 1 条物流例外时，直接生成当前订单的单包
   内存执行方案，不再恢复普通包裹历史、匹配推荐、保存或记录采用。
3. 其他订单若命中同一订单已保存的普通包裹方案，恢复该订单最新方案版本。
4. 否则判断不同订单的子订单结构是否精确匹配历史规则；唯一无冲突方案可作为
   本单内存执行输入，不要求保存采用关系。
5. 精确结构没有命中时，再判断相同商品总量是否存在已确认的单包能力。
6. 再判断是否存在唯一无冲突的历史包裹模块精确组合、固定业务规则或确认箱规；
   命中后直接复用，不调用尺寸计算。
7. 前述确认结果均未命中时才运行三维装箱；精确规则冲突时停止并交给人工，不用
   尺寸结果静默选边。`single_package_capacity` 等近似容量只能显示为参考，不能
   阻断更可靠的尺寸计算。
8. ERP 执行输入必须来自人工保存、单件确定性或可靠无冲突规则，并仍须用户对
   当前订单明确点击；规则或尺寸命中本身都不等于 ERP 执行成功。
