## 1. 要解决的问题

当前正式悬浮窗启动后约占用 `247 MiB` RSS，持续审单约 16 分钟后增长到约 `940 MiB`。真实 `cases.json` 约为 `26 MiB`。这已经影响长期常驻使用，新增业务功能前必须先定位和压住增长。

现在只能确认“进程 RSS 明显增长”，不能直接断言是哪一种原因：

- Python 活对象被持续引用，属于真实泄漏。
- Tk 控件虽然 `destroy()`，但 Tcl 命令、变量、绑定或回调仍被保留。
- 每个订单重新解析大案例文件，临时对象已经释放，但 Python 分配器没有把高水位归还系统。
- 上述原因同时存在。

## 2. 最直接的排查顺序

### A. 建立可重复基线

在同一个正式进程中记录：

- 启动稳定后。
- 完成第 1、5、20 次订单刷新后。
- 完成一次单包审核和一次多包拆分并审核后。
- 闲置 5 分钟后。

每个节点同时记录 RSS、Python 已追踪堆大小、Tk 控件数量、待执行 `after` 任务数量、当前案例快照对象数量和线程数。只看活动监视器的单个 RSS 数字无法区分原因。

### B. 用对象差异定位增长

- 使用 `tracemalloc` 对相邻节点做快照差异，找出持续增长的文件和类型。
- 对 `SidebarView`、`SourceSnapshot`、案例对象、Tk `StringVar` / `Text` / `Frame`、回调闭包和执行日志对象做数量检查。
- 在每次重绘后确认旧控件、绑定、Tcl 命令和数量输入延迟任务都已释放。
- 确认审核线程、事件队列和轮询 `after` 在成功、停止和异常路径都归零。

### C. 区分泄漏与高水位

- 如果 Python 活对象和追踪堆持续增长，修复持有链。
- 如果活对象稳定但 RSS 上升，重点减少大对象反复创建；优先缓存案例仓库快照，并按文件修改时间或成功写入事件失效，而不是每个订单重新解析完整 JSON。
- 不先引入数据库或大规模重构。只有轻量缓存仍无法满足稳定性时，再评估 SQLite 或预计算索引。

## 3. 用户可感知的验收

最低验收必须同时满足：

- 连续处理 20 个订单后，RSS 不再近似随订单数持续线性增长。
- 关闭包裹编辑、刷新订单和完成审核后，Tk 控件、后台任务、线程和队列回到稳定基线。
- 单包审核、多包拆分并审核、推荐恢复和案例写入功能不回退。
- 完整测试结束后没有新增 pytest、Tk 窗口或审单进程残留。
- 输出一次可复现的前后内存对比，不能只用“重启后变小”作为完成证据。

具体稳定阈值应根据基线测量确定；在根因未明前不武断写死一个可能不现实的绝对 MiB 数字。

## 4. 内存稳定后的业务方向

原计划下一项是商品与纸箱尺寸基础数据。2026-07-30 因当前没有合适订单完成
连续 20 单验收，用户明确允许先实施历史包裹模块精确组合；该算法已按
`historical-package-composition.md` 完成第一版，只复用原样确认
包裹并生成需人工采用的草稿。

商品与纸箱内部尺寸基础数据仍作为后续方向：

1. 录入实际可用纸箱的内部长、宽、高。
2. 录入商品包装长、宽、高和可旋转方向。
3. 先离线回放历史案例，只给出可解释候选，不自动确认或操作 ERP。
4. 用实际装箱样本确定可接受空隙，再讨论最少包裹推荐。

原因是现有历史已经证明纸箱规格不连续：较大数量能装入某档纸箱，不代表较小数量一定有合适纸箱。先解决内存稳定性，再补尺寸数据，才是风险最低且对日常审单最有价值的顺序。
