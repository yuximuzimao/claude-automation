## 2. 已确认的业务前提

本次讨论只解决“单个订单在包裹方案确认后，如何由用户点击按钮执行一次普通审核”。

用户确认的前提：

- 当前单个订单只需要分析是否分包。
- 快递、地址、备注及其他 ERP 设置已经由用户确认没有问题。
- 本地包裹方案已经确认。
- 单包订单可以形成完整审核流程。
- 每个订单都必须由用户主动点击悬浮窗操作按钮后才能执行。
- 现阶段不讨论无人值守、自动连续或长期自动化授权。
- 是否能进一步自动化，需要经过较长时间和大量真实测试后再决定。

因此，程序的审核按钮不是“自动判断所有订单条件并审核”，而是：

```text
用户已经完成其他业务核对
＋
本地单包方案已经确认
＋
用户针对当前订单再次点击
→
系统执行一次受控普通审核
```

## 3. 已确认的审核入口选择

ERP 提供两种人工审核方式：

### 3.1 订单行右键审核

人工操作：

1. 在目标订单所属正常订单行内右键。
2. 右键菜单顶部显示 `订单: <系统订单号>`。
3. 核对系统订单号。
4. 点击菜单中的“审核”。
5. ERP 直接显示快速消失的成功提示，无第二层数量确认弹窗。

优点：步骤少、单包人工操作简洁。

未采用原因：

- 需要证明程序可以稳定右键到正确订单行。
- 右键位置或命中区域偏移可能打开错误订单菜单。
- 只有系统订单号一个主要核对点。
- 点击菜单审核后直接执行，没有列表勾选数量和确认弹窗两层保护。
- 订单审核后立即消失，列表结构发生变化。
- 拆分后若逐个右键，审核第一条后剩余行重新排列，定位规律不稳定。
- 单包和拆分后审核会形成两套执行路径。

结论：右键审核暂时只作为人工备用方式，不进入 v1 程序执行。

### 3.2 列表勾选 + 操作栏普通审核

人工操作：

1. 勾选当前目标订单。
2. 核对页面底部 `已勾选：订单数：1`。
3. 鼠标悬停操作行“审核”。
4. 下拉菜单包含“审核”和“强制审核”。
5. 点击第一个普通“审核”。
6. 弹出“提示”对话框。
7. 核对处理范围和 `已勾选 1 条订单`。
8. 点击“确定”。
9. 捕获 `成功审核1单`，页面刷新，已审核订单消失。

优点：

- 可以核对实际选中行身份。
- 可以核对列表底部数量。
- 可以核对弹窗处理范围和数量。
- 可以明确排除“强制审核”。
- 单包与拆分结果审核可以共享同一入口。

结论：v1 统一使用列表操作栏普通审核。

## 4. 提交前必须形成的多层证明

用户明确要求审核前尽可能增加核对步骤，任何不符合正常流程的状态都立即停止。

提交前至少需要证明：

### 第一层：目标订单身份

- 通过系统订单号唯一找到订单行。
- 系统订单号来自 `uniqueid` / `sid`，不能依赖序号 1。
- 目标订单的商品和数量仍与本地确认快照一致。
- 当前状态仍为“待审核”。

### 第二层：列表选中状态

- 执行前页面没有任何已勾选订单。
- 点击后实际选中行数量为 1。
- 唯一选中行就是目标订单。
- 页面底部已勾选订单数为 1。

仅看到数字 1 不够，因为可能选错一个订单。

### 第三层：审核菜单

- 操作栏审核入口唯一。
- 下拉菜单结构符合样本。
- 普通“审核”和“强制审核”可明确区分。
- 只选择普通“审核”。

### 第四层：确认弹窗

- 弹窗标题为“提示”。
- 选中“处理列表页勾选的订单”。
- 未选中“处理查询结果中的订单”。
- `已勾选 1 条订单` 属于第一项区域，不是第二项区域。
- 弹窗数量、列表底部数量、实际选中行数量均为 1。
- 实际选中行身份仍为目标订单。

只有上述证明同时成立，才允许点击一次“确定”。

## 5. 成功与异常的业务定义

### 5.1 成功

快速消失的 `成功审核1单` 只作为辅助证据。

最终成功必须通过页面刷新后的重新读取证明：

- 仍处于待审核查询环境。
- 目标系统订单号已经不在待审核可操作列表中。
- 审核弹窗消失。
- 没有残留本次目标订单选中状态。
- 没有明确失败或业务拒绝信息。

### 5.2 执行前停止

未点击确定前发现任何不一致，状态为：

```text
执行前已停止
```

必须指出具体步骤和不符合项。不得只显示“操作失败”。

### 5.3 结果未知

已经点击确定，但无法证明成功或失败，状态为：

```text
结果未知，已停止
```

此时必须交给人工核对，禁止自动重试。

## 6. 绝对禁止事项

- 不使用强制审核。
- 不因普通审核入口异常改用右键审核。
- 不自动重试勾选、审核菜单、普通审核或确定按钮。
- 不因没捕获到 toast 再次提交。
- 不把点击无报错等同于业务成功。
- 不在用户未点击当前订单按钮时执行。
- 不自动继续下一订单。
- 不扩展到批量审核。
- 不把单包方案确认等同于 ERP 已审核。

## 7. 悬浮窗产品形态

用户认为当前不需要复杂的操作摘要或待办系统。

v1 只需要：

- 目标系统订单号。
- 本地方案为 1 个包裹。
- ERP 尚未审核。
- `审核当前订单` 按钮。
- 当前执行步骤。
- 成功、停止原因或结果未知。

建议进度文本：

```text
正在核对当前订单
正在勾选目标订单
正在核对勾选数量和身份
正在打开普通审核
正在核对确认弹窗
正在提交审核
正在验证刷新结果
```

用户暂时无法确认且本轮不需要回答的问题：

- 复杂操作摘要应包含哪些内容。
- 是否需要长期待办状态。
- 哪些动作未来可以无人值守。
- 自动审核的置信门槛。

这些问题不阻塞人工点击触发的单包审核 v1。

## 8. 实施门禁

讨论最终确认采用分阶段开放：

1. 先只读探测和 dry-run，不点击 ERP。
2. 再允许只勾选目标订单并验证，不打开审核。
3. 再允许打开普通审核弹窗，但不点击确定。
4. 用户再次明确授权后，才允许完成一次真实单包审核。

任何实施代理不得因活动方案已经描述完整流程，就跳过上述真实页面门禁。
