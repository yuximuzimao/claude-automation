# 拆分订单后续方向与待验证细节

日期：2026-07-24  
状态：方向已讨论，真实页面事实不足，暂不实施  
前置活动方案：`../../../docs/2026-07-24-single-package-order-review-execution-v1.md`

## 1. 当前结论

拆分订单不纳入单包审核 v1。

后续更合适的总体路线是：

```text
在当前页面执行拆分
→ ERP 自动显示拆分结果
→ 识别自动勾选的可操作拆分结果行
→ 核对商品和数量与本地多包方案一致
→ 统一使用操作栏普通审核
```

不优先采用“拆分后重新按订单号搜索”的方案。

## 2. 两种候选方案

### 2.1 重新搜索拆分结果订单

可能方式：

- 使用原订单号搜索。
- 使用拆分后新订单号搜索。
- 使用 ERP 内部 ID 或其他关联字段搜索。

当前问题：

- 尚不知道拆分后的两个订单号如何生成。
- 尚不能证明原订单号与两个结果订单之间存在稳定、唯一、可查询的关系。
- 可能出现原订单、拆分结果、平台单号和 ERP 系统订单号等多个身份层级。
- 搜索结果可能受查询条件、排序和刷新影响。
- 即使搜到两条，也仍需证明它们就是当前拆分产生的两个结果。

结论：在找到稳定关联字段前，不采用重新搜索作为主路径。

### 2.2 保持当前页面并识别自动勾选结果

用户人工经验：

- 正常拆分前，页面没有任何已勾选订单。
- 拆分完成后，当前页面会自动显示拆分后的两个订单。
- 两个拆分结果通常处于已勾选状态。
- 可以直接通过操作栏普通审核处理这些已勾选订单。

优点：

- 与人工现有操作一致。
- 不需要猜测新订单号搜索逻辑。
- 拆分前后可以通过页面差异识别结果。
- 可以继续使用“列表选中状态 + 弹窗处理范围和数量”的审核安全门禁。

结论：后续优先研究当前页面差异识别。

## 3. 正常页面可能出现的两种形态

### 3.1 两个结果行

理想状态：

```text
拆分前：
- 目标原订单 1 行
- 已勾选 0 行

拆分后：
- 拆分结果 A，可操作，已勾选
- 拆分结果 B，可操作，已勾选
- 原订单不再显示
```

### 3.2 两个结果行 + 原订单残留行

用户观察到 ERP 可能显示三行：

```text
- 拆分结果 A，可操作，已勾选
- 拆分结果 B，可操作，已勾选
- 原订单残留行，仍显示但不可操作
```

因此，拆分后总行数为 3 不能直接判定异常。

允许这种状态的前提必须是：

- 只有两个可操作且已勾选的结果行。
- 两个结果行的商品和数量与本地两个包裹完全对应。
- 原订单残留行可以被稳定证明不可操作。
- 原订单残留行没有被勾选。
- 弹窗处理的订单数量为 2，而不是 3。

如果第三行身份或可操作性无法证明，必须停止。

## 4. 为什么不建议逐行右键审核

即使单包订单右键审核较简洁，拆分结果逐行右键存在额外风险：

1. 审核第一条后，该行立即消失。
2. 剩余订单重新排列。
3. 页面可能自动刷新或改变选中状态。
4. 第二条的视觉位置和 DOM 顺序不再稳定。
5. 原订单残留行可能占据原位置。
6. 需要再次判断当前剩余行究竟是结果订单还是原订单残留。
7. 右键审核没有批量数量确认弹窗。

结论：拆分后审核也统一使用操作栏普通审核，避免维护逐行消失后的二次定位逻辑。

## 5. 拆分后审核的目标证明

假设本地确认方案有 N 个包裹，拆分后审核前至少需要证明：

```text
拆分前已勾选订单数 = 0
拆分后可操作且已勾选结果行数 = N
弹窗“处理列表页勾选的订单”数量 = N
```

并逐包核对：

- 每个结果行包含哪些源商品。
- 每种商品数量。
- 结果行之间合计数量守恒。
- 结果行集合与本地确认的 N 个包裹方案一一对应。
- 没有混入其他订单。
- 不可操作的原订单残留不进入已选集合。

只核对“已勾选 N 条”不够，因为 ERP 可能选中了错误行或混入无关订单。

## 6. 必须采集的拆分前后字段

每次真实人工拆分样本应在操作前后保存脱敏结构化快照。

### 6.1 拆分前

- 待审核 CDP target。
- 页面查询条件和排序。
- 原订单系统订单号 `uniqueid` / `sid`。
- 平台单号和可见其他编号。
- 商品身份、数量和原始分组。
- 当前可操作状态。
- 当前勾选行集合与底部计数。
- 可见拆分入口及其禁用状态。

### 6.2 拆分弹窗

- 拆分入口类型：按数量拆分或按 SKU 拆分。
- 弹窗标题、字段和默认值。
- 每个输入字段对应的商品/数量语义。
- 新增或删除包裹的操作方式。
- 保存、取消和关闭行为。
- 输入错误时的校验提示。
- 保存是否是最终提交，还是仍需额外确认。

### 6.3 拆分后

每个可见订单行记录：

- `uniqueid`
- `sid`
- `taobaoid`
- `tids`
- 其他可见或 dataset 关联字段
- 可操作/不可操作状态
- 选中状态
- 商品身份和数量
- 订单状态
- 是否有审核入口
- 是否保留原订单号或出现新系统订单号

同时记录：

- 页面底部已勾选数量。
- 是否自动刷新。
- 原订单是否残留。
- 原订单残留如何表现为不可操作。
- 是否出现两个以上结果行。
- 拆分失败、结果未知和部分成功的表现。

## 7. 需要建立的稳定关联

后续实现前，至少要找到一种能证明“这些结果来自刚才这个原订单”的关系。

可能证据组合包括：

- 拆分前后时间窗口内新增的系统订单行。
- 原订单内部 ID 与结果行某字段的关联。
- 平台单号或交易号继承关系。
- 商品总量守恒。
- 拆分结果行集合与本地包裹方案完全一致。
- ERP 页面显式父子或来源标记。
- 页面自动选中集合。

单一证据通常不够。推荐使用：

```text
稳定身份关联
＋
新增行差异
＋
商品数量一一匹配
＋
自动选中集合
```

若只能依赖“刚好出现两行”，不得实施。

## 8. 拆分异常分类

### 8.1 提交前异常

- 原订单身份变化。
- 商品或数量变化。
- 页面已有其他勾选订单。
- 拆分入口不唯一。
- 弹窗字段与样本不一致。
- 本地多包方案无法映射到拆分参数。

处理：不点击保存，进入 `stopped`。

### 8.2 提交后可确认失败

- 页面显示明确失败信息。
- 原订单保持原状态且没有结果行。
- 页面返回业务拒绝。

处理：记录失败并停止，不自动重试。

### 8.3 提交后结果未知

- 页面刷新或 CDP 断连。
- 只出现部分结果行。
- 出现额外可操作行但来源不明。
- 原订单和结果行关系无法确认。
- 商品数量与本地方案不一致。

处理：标记 `unknown`，人工核对，禁止重复拆分。

## 9. 后续开放顺序

拆分能力应采用比单包审核更严格的门禁：

1. 只读采集拆分入口和弹窗，不点击。
2. 用户人工拆分，程序只记录前后 DOM。
3. 使用多个正常和异常样本建立结构化解析。
4. 实现拆分 dry-run，只生成理论参数，不点击。
5. 允许程序打开拆分弹窗但不保存。
6. 用户明确授权后，尝试一次真实拆分。
7. 证明结果行集合正确后，才讨论统一操作栏审核。

单包审核稳定不能自动授权拆分，因为拆分会改变订单结构和系统身份。

## 10. 数据成熟度要求

拆分执行设计不仅需要页面样本，还需要真实多包业务案例。

至少需要出现：

- 已确认的多包本地方案。
- 同 SKU 按数量拆分样本。
- 多 SKU 组合拆分样本。
- 按 SKU 拆分样本。
- 两行结果状态。
- 三行含原订单残留状态。
- 明确失败样本。
- 结果未知或页面异常样本。

当前真实案例历史仍以单包为主，不能从单包容量规则推导拆分参数。

## 11. 当前明确不做

- 不实现拆分按钮点击。
- 不实现拆分弹窗填写。
- 不实现拆分保存。
- 不根据行数猜测结果。
- 不搜索未知的新订单号。
- 不逐行右键审核拆分结果。
- 不把原订单残留直接当作异常或直接忽略。
- 不自动重试拆分。
- 不批量处理多个原订单。

## 12. 未来文档要求

当真实样本足够时，应新建独立活动文档，至少包含：

- 拆分动作的具体业务范围。
- 允许的订单类型和排除条件。
- 拆分参数映射。
- 原订单与结果订单身份模型。
- 正常两行和允许三行状态机。
- 保存前、保存后核对。
- unknown 和人工恢复流程。
- 拆分后统一审核流程。

不得直接在单包审核 v1 文档中追加并顺带实现。
