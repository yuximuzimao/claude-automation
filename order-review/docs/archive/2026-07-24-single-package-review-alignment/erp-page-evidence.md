# ERP 待审核页与普通审核弹窗证据记录

日期：2026-07-24  
采集方式：CDP 只读读取现有待审核标签页；没有激活、勾选、右键、悬停、点击或提交  
用途：解释单包审核 v1 的身份字段和弹窗核对来源

## 1. 证据限制

本文件记录一个真实页面时间点的结构和用户提供的审核弹窗截图内容。

它只能证明这些字段和文案在该样本中出现过，不能证明 ERP 永久保持相同 DOM、类名、顺序或布局。

实施时必须：

- 对当前页面重新只读采样。
- 唯一定位每个元素。
- 页面结构不符合样本时 fail closed。
- 不得用旧截图或旧 DOM 事实强行继续真实点击。

原始弹窗图片来自当前业务讨论中的用户附件。本仓库保存可见文字、选项归属和布局关系的转录，不将对话附件本身视作运行时依赖。

## 4. 系统订单号字段结论

用户说明右键菜单顶部显示：

```text
订单: 5945697152129529
```

只读 DOM 中：

```text
uniqueid = 5945697152129529
sid = 5945697152129529
```

并且行可见文本前部也出现相同编号。

因此当前业务定义为：

```text
systemOrderId = uniqueid / sid 对应的 ERP 系统订单号
```

执行定位主规则：

```text
row.uniqueid == targetSystemOrderId
或
row.sid == targetSystemOrderId
```

推荐再核对：

- `uniqueid` 与 `sid` 同时存在时必须相等。
- 可见系统订单号如可稳定解析，应与属性值相等。
- 同一个 `targetSystemOrderId` 在可操作订单行中必须唯一。

以下字段不能单独替代系统订单号：

- `taobaoid`
- `tids`
- 平台单号
- 子订单号
- 当前序号 1
- `data-index`

它们属于其他身份层级或易变位置。

## 5. 普通审核人工流程证据

用户确认的人工步骤：

1. 勾选当前订单。
2. 页面最下方出现：

```text
已勾选：订单数：1
```

3. 鼠标悬停操作行“审核”。
4. 下拉框有两个按钮：
   - 第一个：`审核`
   - 第二个：`强制审核`
5. 点击普通“审核”。
6. 出现标题为“提示”的确认弹窗。
7. 核对弹窗后点击“确定”。
8. 页面上方快速出现：

```text
成功审核1单
```

9. 页面自动刷新，已审核订单从待审核列表消失。

## 6. 审核确认弹窗截图转录

截图尺寸约为横向小型确认对话框。可见结构如下：

```text
提示                                      ×

● 处理列表页勾选的订单    已勾选 1 条订单
○ 处理查询结果中的订单

                              取消    确定
```

视觉关系：

- 第一项左侧单选圆点为蓝色选中。
- 第二项左侧单选圆点为空心未选中。
- 红色 `已勾选 1 条订单` 位于第一项文字右侧的同一行区域。
- `取消` 为普通灰色按钮。
- `确定` 为蓝色强调按钮。
- 右上角有关闭 `×`。

实施不能只用整窗文本包含关系判断，因为 `已勾选 1 条订单` 必须证明属于第一项区域，而不是第二项或其他隐藏区域。

建议 DOM 解析结果至少包含：

```text
dialogTitle
listSelectionOption.checked
listSelectionOption.count
queryResultOption.checked
confirmButton.unique
cancelButton.unique
```

提交门禁：

```text
listSelectionOption.checked == true
queryResultOption.checked == false
listSelectionOption.count == 1
```

同时还必须满足列表页实际选中行身份和底部计数核对。

## 7. 三种数量不能混同

审核前需要同时读取并比较：

1. DOM 中实际处于选中状态的可操作订单行数量。
2. 页面底部 `已勾选：订单数：N`。
3. 弹窗第一项区域 `已勾选 N 条订单`。

单包 v1 要求三者均为 1。

仅核对任一数字存在以下风险：

- 底部为 1，但选错了另一个订单。
- 实际选中多行，但某个文本解析错为 1。
- 弹窗选中了“查询结果中的订单”，红色数量却来自其他区域。
- 页面原本已有人工勾选，程序又勾选当前订单。

因此必须使用“身份 + 三个数量/范围事实”共同证明。

## 8. toast 与最终成功证据

已知临时提示：

```text
成功审核1单
```

特点：

- 位于页面上方。
- 显示时间很短。
- 审核后页面自动刷新。

建议在点击确定前安装 MutationObserver 或等价只读观察器，记录：

- 出现时间。
- 完整文本。
- 消失时间。

但 toast 不是唯一成功证据。最终仍需重新扫描待审核列表，证明目标系统订单号不再存在于可操作订单行。

未捕获 toast 时不得重新点击确定。

## 9. 当前尚未采集的 DOM 事实

本次没有真实打开审核菜单和弹窗，因此以下内容仍需阶段 1 dry-run 或用户人工打开样本后确认：

- 订单行复选框稳定选择器。
- 选中行的稳定 class / aria / input 状态。
- 页面底部已勾选计数容器。
- 操作栏“审核”入口和悬停触发区域。
- 下拉菜单容器及普通审核、强制审核的稳定层级。
- 弹窗根节点、单选项、数量文本归属、确定/取消按钮选择器。
- 页面加载遮罩和刷新稳定状态。
- toast 容器及成功、失败、警告消息的 DOM 特征。
- 审核失败、业务拒绝和网络异常样本。

这些缺失事实是阶段 1 只读探测的工作内容，不能在真实订单上通过猜测点击补齐。

## 10. 证据驱动的实现原则

- 保存目标系统订单号后，每个关键阶段重新扫描 DOM。
- 不跨刷新持有旧订单行节点。
- 不使用固定坐标。
- 不以第一行、序号或 `data-index` 作为业务身份。
- 属性身份、可见身份、商品数量和待审核状态互相校验。
- 所有元素要求唯一、可见、可交互。
- 页面事实不完整时停止，而不是寻找“差不多”的按钮。
