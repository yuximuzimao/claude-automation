范围：dry-run、参数映射、受保护执行和拆分结果验证

> 归档说明：本文保留本阶段的原始采样与实施顺序。当前能力、已知边界和下次复验入口以同目录 `neat-handoff.md`、项目 `README.md` 与 `AGENTS.md` 为准。

## 1. 本阶段解决什么

当本地已经确认 2 个或更多包裹时，工具需要先把“本地目标”和“ERP 已经发生的事实”分开：

- 本地目标明确展示每个包裹的商品与数量，并证明总量守恒。
- ERP 当前是否已经拆分、应使用哪种拆分入口、弹窗参数如何对应商品，必须来自真实页面采样。
- 页面事实不完整时，计划只能显示为 `blocked`，不能猜测按钮步骤或开放真实操作。

用户会看到本地多包方案和“拆分当前订单”按钮；只有主动点击按钮才会操作 ERP。

## 2. 强制安全边界

- 不复用单包普通审核的“唯一选中 1 行、弹窗数量 1、底部 2+ 阻断”规则。
- 常规 UI 已提供受保护的“拆分当前订单”按钮；只有用户针对当前订单主动点击后，才连续执行混合拆分、添加待拆分、两次确定和结果核对。
- 本阶段拆分成功后停止，不自动继续审核，也不自动处理下一单。
- 不把当前订单明细分组直接解释为 ERP 包裹。
- 不只根据拆分后行数猜测成功；必须同时验证前 N 条有效行的真实勾选、子订单号全集、逐包明细和总量守恒。
- 不自动重试，不搜索未知的新订单号，不批量处理。
- 每次真实页面交互必须由用户针对当前样本明确授权，且拆分、保存、审核分别授权。

## 3. 实施顺序

### 阶段 1A：信息型 dry-run

- 根据已确认原订单快照和多包方案生成本地三态意图。
- 展示目标订单、目标包裹数、逐包商品数量和数量守恒。
- dry-run 固定说明它只验证本地方案；真实 ERP 写操作只能由用户主动点击受保护的“拆分当前订单”按钮触发。
- 在多包历史方案和新确认方案下展示，不提供 ERP 操作按钮。

### 阶段 1B：只读页面样本

- 采集拆分前订单行、选择状态、入口可见性和可操作状态。
- 由用户人工打开拆分入口后，只读采集弹窗标题、字段、默认值、校验、取消和保存结构。
- 由用户人工完成拆分后，只读记录结果行、原订单残留、选择状态、商品数量和身份字段。
- 正常、失败和结果未知样本分开保存为脱敏结构化固件。

### 阶段 1C：可验证 dry-run

- 将当前 ERP 结构与本地多包方案对照。
- 只有订单身份、商品数量、入口、参数和结果验证字段全部具备时，才生成具体理论步骤。
- 任一前置条件缺失或冲突时保持 `blocked`。

2026-07-29 首个真实混合拆分样本已证明：

- 拆分弹窗商品明细顺序与展开后的原订单商品明细顺序一致，同时保留 `tid/sid/oid/outerId` 等稳定身份字段；执行时以稳定身份为主、顺序为第二校验。
- “添加待拆分”后，新包裹插入页面下方包裹框最前面；包裹框显示顺序不能作为本地包裹编号。
- 全部商品分配后，9 个数量输入框全部禁用，可拆数量全部归零。
- 主“确定”后还存在“您是否确定进行订单拆分？”二次确认。
- 弹窗关闭和加载层消失并不足以证明拆分落库；首轮程序化确认曾出现这些过程信号，但刷新后订单结构未变化。
- 实际成功后，目标 3 个包裹对应页面前 3 条有效订单行，三行均保持勾选。
- 结果行顺序为 `20、9、7`，与本地方案顺序 `20、7、9` 不同；必须将逐包明细作为无序多重集合比较。
- 原平台子订单号在结果行中允许重复，例如同一个平台子订单按数量拆成 `2` 和 `7` 后出现在两个包裹；所有结果行平台子订单号汇总去重后必须与拆分前全集一致。
- 所有结果包裹按“平台子订单号 + 真实商品身份”汇总后的数量必须与原订单一致。
- 页面会保留宽高为 0 的旧订单 DOM；结果扫描必须排除不可见旧节点，否则可能读到拆分前数据。

- 有效多包方案生成 `需要拆分`，但状态必须为 `blocked`。

- 结果验证器必须拒绝：勾选行数不等于目标包裹数、结果行不是前 N 行、子订单号全集变化、单包裹明细不匹配或总量不守恒。
