# 拆分结果读取稳定性阶段归档

日期：2026-08-06  
状态：执行链路已修复、已回归、正式悬浮窗已重启；下一阶段转向算法精细化

## 阶段结论

当前拆分与审核执行版本暂未发现明显问题，可以继续日常使用。本阶段解决的是
拆分成功后的结果读取与审核衔接稳定性，不代表包裹推荐算法已经成熟。

下一阶段不再以执行链路微调为主，核心任务是细化拆分推荐算法。现有算法可作为
安全基线，但真实使用中仍存在较多误推荐、无推荐和边界问题，必须先建立固定案例
回放与问题分类，再讨论具体策略。

## 本阶段修复

- 拆分结果读取器原本返回 ERP 原始 `OrderSnapshot/Product`，核对器却按规划层
  `SourceSnapshot/SourceProduct` 使用，导致读取成功后访问 `match_key` 崩溃。
  当前在读取边界完成显式转换，不通过给原始商品对象临时补属性绕过模型分层。
- 逐包读取后会真实滚回第 1 行，再次复核系统订单号和唯一勾选状态；随后等待
  `100ms`，让滚动、展开动画和虚拟 DOM 稳定，再做最终页面探测并进入审核。
- 瞬时读取失败仍只允许重试读取；拆分、审核和确定等真实业务动作仍不重试。

## 验证与运行状态

- 新增“真实读取器输出直接进入拆分核对器”的接口回归，防止读取层和核对层各自
  测试通过、串联后却发生对象类型错接。
- 滚动回归明确断言向下滚动、向上滚回第 1 行、原有每步 `180ms` 等待以及新增
  审核前 `100ms` 稳定等待的顺序。
- 定向回归：`21 passed`。
- 完整自动化回归：`221 passed`。
- 2026-08-06 只读案例健康检查为 `348` 个案例、错误和警告均为 `0`；推荐事件
  `1205` 行全部有效。离线回放覆盖 `123 / 340`（`36.2%`），错误候选 `1`、
  主动不推荐 `217`，说明下一阶段不能只看已有候选的历史命中率，还要补真实
  错误案例和推荐缺口评估。
- 正式悬浮窗已单实例重启；验证期间未对真实 ERP 订单执行拆分、审核或确定。

## 下一阶段边界

1. 先收集并分类真实误推荐、无推荐、冲突候选和人工修改案例，形成固定离线回放集。
2. 分开评估候选生成、过滤、冲突展示/取舍和最终包裹方案，不把问题笼统归为
   “匹配不准”。
3. 结合离散纸箱尺寸、商品尺寸、旋转方向和可接受空隙讨论算法；不得把历史单包
   最大数量解释为连续容量上限。
4. 所有近似结果仍须可解释、可编辑和人工采用；算法升级不得扩大 ERP 自动操作
   权限，也不得静默选择冲突分支。
