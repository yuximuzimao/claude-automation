## 0. 用户意图校正

近似推荐第一版完成后，不能把“暂时没有足够案例继续扩展拆包算法”误解为“整个审单项目应该停止开发”。

当前需要分开两条路线：

1. **案例与规则基础路线**：数据安全、数据质量、效果验证和案例成熟度。
2. **人工审单与单订单操作路线**：当前订单如何完成判断、形成明确操作意图、辅助人工执行，以及未来如何安全接入 ERP 单订单操作。

现在应该暂停的是缺少真实案例支撑的推荐算法扩张，例如多包数量投影、箱规推理和复杂分支置信排序；不是暂停整个审单工作流和操作能力建设。

## 1. 当前代码与数据事实

截至本文件建立时（实施前基线）：

- 同一订单历史恢复、同订单方案版本、不同订单精确规则复用和单包跨分组复用已经实现。
- 数量变化近似推荐第一版已经实现：仅支持商品身份集合一致、当前数量不超过历史已确认单包容量的保守候选。
- 近似候选不会自动采用，仍由人工进入可编辑草稿。
- 当前真实案例共 25 个，全部为单包案例，没有可用于验证多包投影的历史数据。
- 当前完整回归为 `75 passed`。
- ERP 仍严格只读。

因此，现阶段继续推导多包算法缺少业务证据，但仍然可以完成一批不依赖多包案例的基础工作和单订单流程准备。

## 2. 第一条路线：现在应完成的数据与运行安全

这部分属于进入长期实际使用前的必要基础，不是可选的“工程美化”。

### 2.1 P0：防止案例静默丢失

#### 单实例与并发写入保护

当前案例仓库使用临时文件、`fsync` 和 `os.replace`，可以避免半截 JSON，但不能自动防止两个应用实例同时读取旧状态后互相覆盖。

需要实现：

- 审单悬浮窗单实例保护。
- 第二个实例启动时不得继续独立运行和写案例。
- 案例仓库增加写入互斥或等价的并发版本校验，避免旧状态覆盖新状态。
- 单实例属于数据安全，不能仅归入 macOS 图标或应用名称等低优先级体验工作。

#### 版本化备份与恢复

当前案例文件：

```text
~/Library/Application Support/Order Review/cases.json
```

实施前的工作区备份只打包 `/Users/chat/claude`，不包含该文件，并采用单代覆盖。

需要实现：

- 每次覆盖正式案例文件前，只对“能够成功读取并通过基础校验”的现有文件创建备份。
- 使用带时间戳的滚动备份，不只保留单个 `.bak`。
- 设置合理保留数量，例如按时间保留 20～30 个有效版本；案例文件体积较小时不应过度节省。
- 每周工作区备份同时包含审单案例文件。
- 周期备份改为多代保留。
- 提供人工明确触发的恢复命令。
- 恢复前先校验备份、再备份当前文件、最后原子替换。
- 启动失败时不得未经确认静默回滚，避免掩盖数据问题。

同机备份只能防误删和逻辑损坏；后续还应确保至少一份副本位于其他磁盘或其他备份介质，但不需要在本阶段引入云端系统。

### 2.2 P1：防止脏数据污染规则

增加统一的只读案例校验能力，并由以下入口共同复用：

- 手动案例健康检查。
- 正式写入后的验证。
- 创建备份前的验证。
- 恢复备份前的验证。
- 历史回放前的验证。

建议提供：

```bash
PYTHONPATH=src python3.13 -m order_review.case_audit
```

必须检查：

- JSON 和 schema 能否完整读取。
- 案例 ID、assignment ID 是否重复。
- 包裹商品是否都来自对应原订单快照。
- 每种原商品数量是否守恒。
- 是否存在负数、超分配、漏分配或空包裹。
- `previousCaseId` 版本链是否断裂、成环或跨越无关联订单。
- `previousAssignmentId` 是否有效。
- `orderAssignments` 是否指向不存在的案例。
- 同一订单是否出现两个无法确定先后的最新方案。
- 规则统计是否存在明显孤立或无效结构。
- 商品身份字段是否大量缺失。

报告必须区分：

- **错误**：会破坏数量、引用或版本完整性，必须处理。
- **警告**：例如旧数据缺少可选字段、SPU/SKU 缺失或存在合法多分支，不得误判为损坏。

同一订单多个版本和同结构多个方案分支是合法业务结构，健康检查不能把它们简单当作重复案例。

### 2.3 P1：最小推荐效果事件

当前规则统计已有直接采用次数、修改次数和最后使用时间，但缺少推荐展示基数。

进入正式使用前，建议增加最小化、只用于报告的事件记录：

- `shown`：候选已经展示。
- `confirmed_direct`：未修改直接确认。
- `confirmed_modified`：修改后确认。
- `abandoned_unknown`：没有形成确认，原因未知。

约束：

- `abandoned_unknown` 不能算作拒绝，也不能自动降低规则权重。
- 展示事件需要按当前订单签名、推荐 ID 和应用会话去重，避免刷新造成虚增。
- 事件必须保留匹配类型、算法版本、规则 ID 和来源案例。
- 先采用简单的追加式记录即可，不需要案例管理后台。

### 2.4 P2：无数据泄漏的历史回放和成熟度报告

历史回放不能把被测试案例同时作为规则来源，否则会产生自我验证和虚高覆盖率。

必须采用以下任一种隔离方式：

- 按时间回放：某案例只能使用其确认时间之前的历史。
- 留一回放：测试某案例时排除该案例、同订单版本链及其直接派生关联。

报告至少包含：

- 完整案例数与独立订单数。
- 单包、多包案例数。
- 可推荐覆盖率。
- 系统主动放弃推荐的比例。
- 直接确认、修改后确认和未知离开数量。
- 单包容量规则覆盖率。
- 多包规则覆盖率。
- 出现多个数量档位的商品组合。
- 已观察到的单包到多包临界样本。
- 同结构多分支数量。
- 当前数据尚不足以支持的规则类别。

同一订单多个版本不能虚增独立样本数；规则采用关联可以作为使用证据，但不能冒充新的完整案例多样性。

## 3. 第二条路线：可以提前推进的人工审单与单订单操作

以下工作不依赖多包数量投影数据，可以独立评估和分阶段推进。

### 3.1 单订单处理状态模型

当前系统已经生成本地包裹方案，但还缺少从“方案结果”到“人工下一步做什么”的明确中间层。

可以先定义只读的单订单处理状态或操作意图，例如：

- 当前信息不足，不能继续判断。
- 当前订单已有历史方案，仅需核对。
- 当前方案为单包，理论上无需 ERP 拆包。
- 当前方案为多包，理论上需要 ERP 拆分操作。
- 存在历史冲突或人工修改，需要再次核对。
- 本地方案已确认，但尚未执行 ERP。
- ERP 当前状态与目标方案是否一致仍未知。

这些状态只能表达“本地判断和操作意图”，不能提前宣称 ERP 已处理成功。

### 3.2 确认后的人工操作摘要

在不写 ERP 的前提下，可以增加对人工有直接价值的结果区：

- 最终包裹数量。
- 每个包裹应包含的商品和数量。
- 该方案来源：人工、同订单历史、精确规则、单包容量候选。
- 是否经过人工修改。
- 当前理论操作类型：无需拆分 / 需要拆分 / 暂无法确定。
- 明确提示“本地方案已确认，ERP 尚未执行”。
- 可复制的操作摘要，方便人工对照 ERP 操作。

这类功能不需要更多案例，也不会污染推荐算法，可以提前做。

### 3.3 ERP 当前状态只读识别

在实际点击 ERP 之前，可以先扩展只读采集，回答：

- 当前订单在 ERP 中是一条还是多条可操作记录。
- 当前是否已经存在拆分结果。
- 页面上可见哪些审核、拆分、合并或保存入口。
- 当前按钮是否可用、是否存在弹窗或异常状态。
- 本地目标包裹方案与 ERP 当前结构是否已经一致。

这一阶段只观察和记录，不点击、不提交。它可以为后续操作设计提供真实页面事实，避免依靠猜测编写执行代码。

### 3.4 ERP 操作计划的 dry-run 层

在只读状态识别可靠后，可以生成“如果要处理这个订单，理论上需要哪些步骤”的操作计划，但不执行。

示例结构：

```text
目标：2 个包裹
当前 ERP 状态：未确认
预计步骤：
1. 打开拆分入口
2. 建立第 2 个包裹
3. 按本地方案分配商品数量
4. 校验总量
5. 保存拆分
6. 审核
```

要求：

- 操作计划必须来自当前订单快照和已确认包裹方案。
- 每一步都要有前置条件和预期结果。
- 不得把 dry-run 展示成已经执行。
- 计划生成失败时应明确说明缺少什么页面事实。

这个层可以提前实现，并且是未来受控执行的重要边界。

### 3.5 实际单订单 ERP 操作的安全演进路线

实际写操作不是当前立即实施项，但可以提前完成可行性审计和页面样本收集。建议未来严格按以下顺序推进：

1. 只读识别当前 ERP 状态。
2. 生成不执行的操作计划。
3. 收集人工完成“单包审核”和“多包拆分后审核”的真实操作样本及成功页面特征。
4. 每次只允许一个明确订单、一个明确动作，人工逐步确认。
5. 执行前再次核对订单身份、商品数量和目标方案。
6. 执行后通过页面状态重新读取验证成功，不能只根据点击无报错判断。
7. 建立执行日志、幂等键和未知结果状态。
8. 任何失败不得自动重试，除非后续针对具体操作明确讨论并允许。
9. 单订单稳定以前不得扩展到批量操作或自动连续处理。

实际执行功能必须在专门讨论后才能实施，不能因为 dry-run 已完成就默认开放 ERP 写操作。

## 4. 当前不应做的事情

现阶段不建议：

- 基于 25 个单包案例继续猜测多包数量投影。
- 引入数据库或复杂案例管理后台。
- 引入机器学习、向量相似度或不可解释评分。
- 根据商品名称相似度替代稳定商品身份。
- 引入重量、纸箱、运费和地区快递模型。
- 直接做批量审核、批量拆分或无人值守 ERP 操作。
- 把推荐未采用直接视作负反馈。
- 把 ERP 点击成功等同于业务处理成功。

## 5. 当时给 Codex 的执行顺序（已完成）

### 阶段 A：先完成可以确定的数据与运行安全

按顺序实施并测试：

1. 单实例和案例并发写入保护。
2. 版本化案例备份、验证和人工恢复。
3. 修改每周工作区备份，使其包含案例文件并保留多个代次。
4. 统一案例校验库和 `case_audit` 命令。
5. 最小推荐效果事件记录。
6. 无数据泄漏的历史回放与成熟度报告。

实施时必须先检查当前代码，避免重复实现 Codex 已经新增的能力。所有迁移必须向后兼容现有 `cases.json`，不得自动删除或重写真实案例。

### 阶段 B：完成后提交单订单功能可行性报告

阶段 A 完成后，不要立即添加 ERP 写操作。先对当前项目和真实 ERP 页面做一次只读功能审计，输出单独报告，至少分为：

- 现在就能安全实现、且不写 ERP 的人工辅助功能。
- 需要补充真实页面样本后可以实现的单订单操作准备。
- 必须与用户讨论后才能实施的 ERP 写操作。
- 当前被数据、页面事实或安全机制阻塞的功能。

重点回答：

1. 单订单确认方案后，人工下一步最有价值的辅助是什么。
2. 能否可靠判断“无需拆分”“需要拆分”“信息不足”。
3. ERP 当前状态还缺哪些只读字段。
4. dry-run 操作计划需要哪些页面事实。
5. 单包审核和多包拆分分别需要收集哪些真实操作样本。
6. 实际单订单操作的最小安全闭环是什么。

完成报告后暂停，不自行实现 ERP 写操作，等待下一轮讨论决定具体功能。

## 6. 验收原则

阶段 A 的验收要求：

- 两个应用实例不能静默覆盖案例数据。
- 案例文件损坏、误写或错误升级时存在多个可验证恢复点。
- 健康检查可以发现引用、数量、版本和结构问题，并区分错误与警告。
- 推荐展示和确认结果可以离线统计，但未知离开不被误算为拒绝。
- 历史回放不存在明显自我验证数据泄漏。
- 现有根本规则和原有回归继续成立，并新增对应测试。

阶段 B 报告必须保持 ERP 只读，不得点击审核、拆分、合并、保存或提交。
