## 本轮完成范围

### 1. 三类独立签名

新增 `src/order_review/order_identity.py`，分别实现：

- 同一订单签名：平台子订单号及其对应的规范化商品明细。
- 子订单结构签名：忽略平台单号具体值，但保留每个子订单的商品构成和数量。
- 商品总量签名：忽略子订单结构，汇总全部商品身份和数量。

同一平台单号下身份相同的多条商品行会先汇总，因此 `A×6` 与 `A×3 + A×3` 等价。商品行顺序和平台子订单排列顺序不影响结果。

### 2. 同一订单历史恢复

`PackagePlanWorkflow.load_order()` 会优先按同一订单签名查询历史：

- 命中后直接显示已保存的包裹方案。
- 不进入普通历史推荐流程。
- 不要求重新选择单包或拆包。
- 不重复保存完整案例，也不增加规则强化次数。
- 界面保留“修改已保存方案”入口。

### 3. 同一订单方案版本

同一订单的已保存方案被人工修改后：

- 不覆盖旧方案。
- 保存新的完整方案版本。
- 新版本保留 `previousCaseId` 和递增的 `orderVersion`。
- 当前订单下次出现时恢复最新版本。
- 即使订单最初只是采用了其他订单的历史规则，后续修改仍能建立属于当前订单的关联版本。

### 4. 不同订单精确规则复用

平台单号不同、子订单商品结构完全一致时：

- 唯一且无冲突的历史规则自动采用为可编辑草稿。
- 人工可以修改、重置或取消。
- 未修改直接确认时，不重复保存完整案例。
- 只保存当前订单与来源案例/规则的关联，并增加规则采用统计。
- 界面不会把这种情况错误显示为“该订单已经处理过”。

### 5. 单包跨子订单结构复用

如果精确子订单结构没有命中，但历史案例证明相同商品总量可以单包：

- 可以按商品总量复用单包方案。
- 子订单结构变化不会新增无价值的复杂案例。

如果历史方案是多包，则仍严格要求子订单结构匹配。商品总量相同但子订单结构不同，不会被误判为精确多包规则。

### 6. 持久化与统计

`cases.json` 继续向后兼容旧的 `schemaVersion: 1`，并新增可选根字段：

- `orderAssignments`：当前订单到案例/规则的关联和版本链。
- `ruleStats`：规则直接采用次数、人工修改次数和最后使用时间。

确认案例新增：

- `previousCaseId`
- `orderVersion`

订单规则采用记录保留：

- 来源案例
- 规则 ID
- 匹配类型（精确子订单结构 / 单包商品总量）
- 推荐算法版本
- 决策来源

取消、未确认或单纯离开不会新增独立“打回案例”。旧的 `recommended_rejected` 枚举仅用于兼容历史数据，不再由新流程生成。

归档完成后再次审计了此前阶段需求和 ERP 页面事实，并将以下长期约束补入主目录根本规则文件第 14 节：

- 固定匹配优先级：同一订单历史恢复 → 精确结构规则 → 单包总量规则 → 近似/复杂/人工方案。
