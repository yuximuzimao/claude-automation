# 包裹方案阶段需求

日期：2026-07-22  
状态：已完成并归档  
范围：在现有只读订单悬浮窗基础上增加“包裹方案”工作区、方案确认记录和历史推荐能力；本阶段仍不执行 ERP 审核或其他写操作。

## 完成情况

本阶段已经实现并通过完整测试：

- 原订单事实层与本地包裹决策层分离，ERP 始终只读。
- 单包与逐包拆分编辑，支持手输数量、紧凑增减和 `MAX`。
- 一次只编辑一个包裹，新包裹只展示尚未分配商品。
- 数量守恒、空包裹、超分配、漏分配、重复确认和刷新失效均有硬校验。
- 本地案例原子保存完整原订单快照、最终包裹方案和决策来源。
- 推荐算法 v1 只匹配商品、数量和订单分组结构完全一致的历史案例。
- 推荐可以直接采用、修改后确认或拒绝，并保留案例与算法版本追踪。

当时的下一阶段方向现归档于
`../2026-08-14-carton-packing-foundation/approximate-recommendation-direction.md`。

## 1. 产品定位

悬浮窗分为两个职责严格不同的区域：

1. **原订单信息区**：只读展示 ERP 当前序号 `1` 订单的原始信息。
2. **包裹方案区**：基于原订单商品创建、编辑、确认和保存人工包裹方案。

原订单信息是事实输入，包裹方案是人工决策结果。两者不能混在同一数据结构或界面操作中。

后续若增加 ERP 审核、拆单或其他实际操作，必须以“已经生成且确认无误的包裹方案”为前置条件。包裹方案阶段本身不是审核流程，也不应直接操作 ERP。

## 2. 原订单信息区

当前已经实现的以下板块都属于只读原订单信息：

- 商品总量
- 按订单查看
- 后台明细

约束：

- 所有内容来自当前 ERP 页面序号 `1` 的已展开订单。
- 用户不能在这些板块修改商品、数量、平台单号或任何标识。
- 刷新 ERP 数据时，重新生成一份新的原订单快照。
- 包裹方案只能引用原订单快照中的商品，不得反向修改快照。
- 完整原始 payload 和已经解析的结构化字段都必须保留，用于后续筛选规则、审计和问题追踪。

### 2.1 当前有用的结构化字段

订单维度至少保留：

- 平台单号列表
- ERP 页面分组信息
- 可合单标记
- 页面来源和读取时间
- 完整原始 payload

商品维度至少保留：

- ERP 标准商品名称
- 商品简称
- 数量
- 商家编码
- 主商家编码（与商家编码不同时）
- 平台商品 ID
- 平台 SKU ID
- 平台规格
- 平台名称
- 商品在原订单中的来源分组和稳定引用

人工界面可以只展示有用字段，但保存的原订单快照不能因为界面折叠或隐藏而丢失数据。

## 3. 包裹方案区

包裹方案区是独立的可编辑区域。它不改变原订单，只记录“这些原订单商品最终如何分配到一个或多个包裹”。

### 3.1 初始入口

当前没有历史推荐时，至少提供：

- `单包方案`
- `拆分包裹`

`单包方案`表示人工确认当前订单组的全部商品可以放入一个包裹。它不是“发货”或“审核”按钮，也不触发 ERP 操作。

`拆分包裹`进入自由分配模式，允许创建任意数量的包裹，并把原订单商品数量分配到各包裹。

### 3.2 编辑能力

拆分模式至少支持：

- 新增包裹
- 删除空包裹
- 调整包裹内商品数量
- 同一商品按数量拆到多个包裹
- 在包裹之间移动商品数量
- 重置为未分配状态
- 取消本次编辑
- 所有商品完全分配后确认方案

### 3.3 完整性约束

确认前必须满足：

- 每个原订单商品的已分配数量等于原订单数量。
- 任一商品的分配数量不能小于 `0`。
- 任一商品的分配总量不能超过原订单数量。
- 不允许确认空包裹。
- 至少存在一个包裹。
- 包裹商品必须引用当前原订单快照中的商品，不能凭空创建商品。
- 原订单刷新或目标订单变化后，未确认方案必须失效，不能错误套用到新订单。

## 4. 确认与保存语义

“确认方案”只表示人工确认包裹分配结果正确，并将案例写入本地持久化记录。

确认后仍不执行：

- ERP 审核
- ERP 拆单
- ERP 合单
- ERP 保存或提交
- 发货、生成运单或修改商品

未来实际审核或拆单动作必须作为后续独立阶段设计，并且只能消费已确认的包裹方案。

## 5. 确认记录的数据模型

一次确认记录必须同时保存两部分：

1. **原订单快照的全部详情**
2. **最终确认的包裹方案**

不能只保存包裹结果，否则后续无法分析“在什么订单条件和筛选规则下产生了该方案”。

建议记录结构：

```json
{
  "schemaVersion": 1,
  "caseId": "唯一案例编号",
  "confirmedAt": "绝对时间",
  "sourceSnapshot": {
    "snapshotId": "原订单快照编号",
    "platformOrderNumbers": ["756863430"],
    "products": [
      {
        "sourceProductId": "快照内稳定商品引用",
        "standardName": "ERP 标准商品名称",
        "shortName": "商品简称",
        "quantity": 3,
        "merchantCode": "6979151090007",
        "mainMerchantCode": null,
        "platformProductId": "js4.0-cx",
        "platformSkuId": "130292115",
        "platformSpec": "酵素4.0 3盒装;KGO",
        "platformName": "平台商品名称",
        "sourceGroup": "原订单来源分组"
      }
    ],
    "rawPayload": {}
  },
  "packagePlan": {
    "packages": [
      {
        "packageId": "package-1",
        "items": [
          {
            "sourceProductId": "快照内稳定商品引用",
            "productName": "酵素4.0",
            "quantity": 3
          }
        ]
      }
    ]
  },
  "decision": {
    "source": "manual",
    "recommendationId": null,
    "recommendationModified": false
  }
}
```

### 5.1 包裹维度的最小事实

从包裹能力学习的角度，一个包裹最终只需要表达：

- 这个包裹包含哪些商品
- 每种商品各有多少件

人工界面显示“商品名称 + 数量”即可。

但持久化记录中每个包裹商品仍必须带 `sourceProductId`，用于关联原订单快照，防止同名商品、改名商品或不同 SKU 被误认为同一商品。这个引用是数据完整性字段，不要求在界面展示。

## 6. 合并订单示例

假设当前 ERP 订单组包含平台订单 A 和 B：

- 订单 A：C 商品、D 商品
- 订单 B：C 商品、D 商品

人工确认方案：

- 包裹 1：全部 C 商品
- 包裹 2：全部 D 商品

最终案例必须保存：

- A、B 两个原订单的全部结构化信息和原始快照
- C、D 每条原始商品明细及其来源订单关系
- 包裹 1 中 C 商品的合计数量
- 包裹 2 中 D 商品的合计数量
- 包裹商品到原始商品行的引用关系

因此系统既能从包裹角度学习“一个包裹能装下什么组合”，也能从订单角度分析“哪些订单筛选条件可以稳定命中特定拆分方案”。

## 7. 推荐能力的演进

历史案例不是只用于回答“单个包裹能不能装下”。最终目标分为三层。

### 7.1 单包裹能力案例

学习一个已确认包裹能够容纳的商品组合和数量，例如：

```text
包裹：C ×4 + D ×2
```

这是一条包裹容量经验，可用于后续相同组合或保守子集的候选推荐。

### 7.2 多包裹拆分模板

学习一个完整订单组合应如何拆成多个包裹，例如：

```text
原订单组合：C ×4 + D ×2
方案：
- 包裹 1：C ×4
- 包裹 2：D ×2
```

相同订单组合再次出现时，可直接展示完整拆箱推荐，而不是分别猜每个包裹。

### 7.3 批量筛选与固定拆单规则

更进一步的目标是从完整原订单快照中提炼筛选条件：

- 哪个平台或店铺
- 哪些平台商品 ID / SKU ID / 商家编码
- 哪些平台单号或订单分组关系
- 哪些商品组合和数量
- 是否合并订单
- 其他后续确认有价值的订单属性

当一批订单满足同一组复杂筛选条件时，系统可以应用固定的多包裹拆分规则，然后进入后续自动拆分和审核流程。

目标链路：

```text
展示原订单明细
→ 展示拆箱推荐
→ 人工确认或修改
→ 保存案例
→ 自动拆分
→ 审单
```

当前阶段只实现到“保存案例”和基于历史案例展示推荐；自动拆分和审单仍是后续阶段。

## 8. 推荐来源和反馈

每次确认应记录方案来源：

- `manual`：完全人工创建
- `recommended_accepted`：历史推荐直接采用
- `recommended_modified`：基于推荐修改后确认
- `recommended_rejected`：拒绝推荐并重新创建

历史推荐必须可追溯到使用的案例或规则，不能只输出一个无法解释的结果。

相同订单组合出现冲突历史时，不应静默选择其中一个方案。应显示候选方案、使用次数和冲突状态，由人工确认。

## 9. 数据边界与版本化

- 原订单快照确认后不可变。
- 包裹方案确认后生成不可变案例；修正应创建新版本或撤销记录，不能静默覆盖历史。
- 每条案例包含 `schemaVersion`，方便未来字段升级。
- 规则和推荐算法也应有版本号，保证后续可以解释某次推荐的来源。
- 持久化失败时不能显示“确认成功”。
- 同一原订单重复确认需要显式处理，避免无意产生重复训练案例。

## 10. 界面分层

建议保持以下顺序：

```text
只读原订单信息
├── 商品总量
├── 按订单查看
└── 后台明细

包裹方案
├── 历史推荐（存在时）
├── 单包方案 / 拆分包裹
├── 包裹编辑器
├── 完整性校验
└── 确认方案
```

视觉上必须清楚区分只读信息和可编辑方案：

- 原订单区不出现编辑控件。
- 包裹方案区可以编辑，但不能让用户误认为已操作 ERP。
- 任何未来 ERP 操作区应放在包裹方案确认之后，并作为第三个独立区域。

## 11. 当前不做

本阶段不做：

- ERP 自动审核
- ERP 自动拆单、合单或保存
- 自动点击页面元素
- 运单或发货操作
- 基于体积和尺寸的通用装箱算法
- 未经人工确认直接执行推荐
- 从少量案例直接生成不可解释的复杂筛选规则

## 12. 实现前的非阻塞技术决策

以下内容需要实现者选择，但不改变上述业务需求：

- 本地持久化使用 JSON、SQLite 或其他存储。
- `sourceProductId` 的具体生成方式。
- 案例去重和撤销的具体交互。
- 推荐索引的内部结构。
- 未来筛选规则使用声明式 JSON、代码规则还是独立规则引擎。

实现时应优先保证快照不可变、数量守恒、案例可追溯和推荐可解释。
