# 拆分结果滚动与确定性直审阶段归档

日期：2026-08-05  
状态：已完成、已回归、悬浮窗已重启

## 用户可见变化

- 拆分包裹较多时，程序会像鲸灵售后工单列表一样对 ERP 结果列表执行真实滚轮
  滚动，把屏幕外的第 3 条及后续目标行移入视口后再读取，不再用“收起上一条”
  代替滚动。
- 总商品数量为 `1` 且非套件、且同订单未明确保存为物流时，直接显示普通审核
  入口。点击后不保存方案、不确认方案、不记录采用关系或次数。
- 已保存的普通方案、唯一无冲突的精确历史方案和唯一无冲突的历史模块组合，未
  经人工修改时直接作为本单内存执行输入。点击审核或拆分不再为了“采用历史”
  重写大型案例文件，因此消除了无业务价值的数秒保存等待。

## 异常根因与修复

异常 `拆分已成功，但审核已停止：读取已勾选结果明细失败：SEQ_3_NOT_FOUND`
发生在 ERP 拆分成功之后。结果列表采用虚拟渲染：第三条虽然可以通过人工向下
滚轮看到，但当时程序只在当前 DOM 窗口按序号查找，并尝试通过展开/收起行推进，
没有真正滚动列表，因此第三条未挂载时被误判为不存在。

当前读取链路对每个目标序号执行以下门禁：

1. 在结果列表上发送真实 `mouseWheel`，把目标行滚入视口。
2. 按序号重新定位，复核系统订单号和勾选状态，防止滚动后对象漂移。
3. 展开并读取完整商品明细；虚拟列表卸载较早行时保留已经验证的证据。
4. 仅对瞬时读取失败重试；拆分、审核、确定等真实业务动作仍然不重试。
5. 所有目标包裹核验通过后，才继续普通审核门禁。

因此本次异常不会触发第二次拆分或第二次审核提交，风险仍保持在“证据不足即停”。

## 规则收口

- 订单明细和方案完全匹配时，历史复用是确定性映射，不需要像售后工单一样用
  采用次数提高置信度。旧统计字段只兼容读取，不参与推荐、排序或执行判断。
- 精确复用不新增订单采用关系，也不重写案例文件；只有人工修改或近似容量确认
  产生新的装箱事实时才保存完整案例或版本。
- 单件非套件优先于普通历史推荐，但同订单明确保存为物流时仍保留物流状态。
