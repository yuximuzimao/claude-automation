# 审单悬浮窗第一阶段设计记录

日期：2026-07-09  
归档日期：2026-07-22  
状态：历史设计，第一阶段已完成  
范围：快麦 ERP「订单处理 / 待审核订单」页面，当前序号 1 订单的只读读取和桌面悬浮窗展示

> 当前方向见 `../../2026-07-22-approximate-recommendation-direction.md`。本文保留第一阶段设计背景和早期页面事实，不应覆盖当前代码与 `AGENTS.md` 中已经更新的字段语义。

## 1. 项目目标

审单项目最终目标仍然是逐步走向审单自动化，但当前第一阶段只做只读辅助，不做真实业务动作。

第一阶段要解决的问题是：用户在 ERP 待审核订单页面查看当前订单时，系统能把展开后的商品明细读出来，用一个桌面悬浮窗清楚展示“商品是什么、数量是多少、是否具备继续人工判断的前提”。

当前阶段不做自动审核、不做自动合单、不做自动拆单、不做套件转单品、不提交、不保存、不修改 ERP 数据。

## 2. 业务背景和边界

用户主要在快麦 ERP 的「订单处理 / 待审核订单」里审单。订单审核经常受活动组合、商品简称、SKU、SPU、数量、箱规、满赠和合单拆单经验影响，无法一开始写成完整机械规则。

ERP 里的关键限制：

- ERP 视角通常是子订单，不要假设能稳定还原平台主订单。
- 平台端满赠在 ERP 里常表现为独立子订单，不一定有“赠品”标记。
- ERP 内部赠品标记和平台端赠品不是同一个概念，当前不作为判断依据。
- 当前阶段不设计合单 / 拆单动作落地路径。

当前路线：

1. 先做读取和展示。
2. 用户根据悬浮窗信息人工判断。
3. 后续再记录人工判断，沉淀固定规则。
4. 固定规则足够多后，再讨论批量处理、点击后脚本操作或自动审单。

## 3. 悬浮窗形态

悬浮窗是桌面级独立窗口，不注入 ERP 页面 DOM，不占用浏览器内部空间。

确认形态：

- 贴在 Chrome / ERP 浏览器窗口左侧外面。
- 不遮挡 ERP 内容区和前台操作区。
- 不遮挡序号、展开按钮、商品数量、订单操作等 ERP 左侧关键列。
- 窗口竖向排布，像浏览器外侧的一块延伸区域。
- 参考 `codex-monitor` 用量统计软件已有悬浮窗经验。

当前实现尺寸：

- 宽度：`360px`。
- 高度：`760px`，内容内部滚动。
- 不做宽面板；复杂订单靠紧凑列表和折叠详情处理。

可复用的 `codex-monitor` 经验：

- 用 Tkinter `Toplevel` / `overrideredirect` / `-topmost` 做桌面浮窗。
- 第一版已支持拖拽；位置持久化暂未实现。
- macOS 上避免反复销毁重建浮层；需要隐藏和再显示时优先复用窗口，用 `withdraw()` / `deiconify()`。
- UI 先稳定可读，不追求复杂视觉效果。

技术倾向：第一版优先用 Python Tkinter，原因是轻量、启动快、已有本地浮窗经验可参考。

## 4. 读取对象和安全边界

读取对象固定为 ERP 当前页面中“序号”列显示为 `1` 的订单。

不按以下方式定位：

- 不按 DOM 第一项。
- 不按当前状态第一项。
- 不按视觉位置猜测。

读取前提：

- 必须读取展开后的订单明细。
- 未展开状态下的信息不能作为判断条件。
- 如果序号 1 未展开，悬浮窗只显示：`判断：请先展开订单`。
- 后续是否由工具自动点击展开按钮，需要单独确认；当前设计以用户展开后读取为可靠前提。

安全边界：

- 不点击 `审核`。
- 不点击合单、拆单、套件转单品、保存、修改商品、换商品、管理赠品等业务动作。
- 不提交、不确认、不修改任何 ERP 数据。
- 只读取页面上已有 DOM 文本、属性和结构化 `data-*` 字段。

## 5. 页面事实

已确认 ERP 页面事实：

- 待审核订单页标题：`快麦ERP--待审核订单`。
- URL hash：`#/trade/toaudit/`。
- 订单行不是标准 `el-table`，而是 `.module-trade-list-item`。
- 展开后的商品明细在 `tr.order-temp` 中。
- 商品行上有结构化字段，例如 `data-tid`、`data-sid`、`data-oid`、`data-numiid`。
- `data-numiid` 对应平台商品 ID / SPU，不是 SKU ID。
- 可合单标记 DOM 为 `trade-icon-canmerged`。

当前读到的典型商品明细形态：

```text
商品标题：KGOS灵芝金花黑茶固体饮料（茉莉花茶味）1g*21（KGOS黑茶 茉莉味）
平台ID（skuId）：kgoshcml-cx（130292082）
主商家编码：6979499760044
商家编码：6979499760044
数量：7 / 7
```

字段含义：

- `kgoshcml-cx` 是平台商品 ID / SPU。
- `130292082` 是平台 SKU ID。
- 最后一个括号前是 ERP 标准商品名称。
- 最后一个括号内是 ERP 商品简称。

## 6. 有效字段

悬浮窗主视图保留：

- 一行判断结果。
- 商品种类。
- 商品总数量。
- 商品明细列表。
- 每个商品的 ERP 商品简称。
- 每个商品的单品数量。
- 每个商品的 ERP 标准商品名称。
- 商家编码。
- 主商家编码，仅当它与商家编码不一致时显示。
- 平台商品 ID / SPU。
- 平台 SKU ID。
- 可合单标记：只显示有 / 无。

商品名称展示规则：

- 主标题优先显示商品简称，便于人工快速识别。
- 标准商品名称作为小字显示，供脚本判断和规则沉淀。
- 后续脚本判断优先使用 ERP 标准商品名称，人工查看优先使用商品简称。

商品编码展示规则：

- 商家编码和主商家编码一致时，只显示商家编码。
- 两者不一致时，分别显示。
- 商家编码可作为辅助筛选项，但当前不作为主判断依据。

平台 ID 展示规则：

- SPU 和 SKU ID 保留，但暂不固定判断逻辑。
- 后续批量处理时，平台 SKU ID 可能适合作为固定组合筛选条件。
- 某些平台 SPU 下多个 SKU 本质是同一商品的不同规格，人工可能按 SPU 合并处理；这类规则等待实际样本后再设计。

## 7. 无效或暂不使用字段

以下字段不进入判断，不放主视图：

- `序号 1 · 待审核` 这类标题。
- 内部单号。
- 店铺 / 订单类型图标里的 `16`。
- ERP `标签` 列，包括标签列里的 `套件转单品`。
- 平台名称。
- 平台规格。
- 商品总重量、单品体积、订单体积。
- 金额类字段，包括应付金额、成交金额、平台实付、单价、折后单价、成本等。
- ERP 内部赠品标记。
- 可合单标记点击后的数量明细。
- 隐藏菜单里的作废、加急、订单挂起、复制新建等动作入口。

说明：

- 平台名称等于链接标题，对审单判断意义不大。
- 平台规格是对外展示的 SKU 组合名称，实际审单更依赖商品名称、简称和编码。
- 重量体积在系统中没有实际录入价值，不能用于箱规判断。
- 金额目前对审单判断无意义，先忽略。
- ERP 赠品标记不能判断平台端满赠。

## 8. 套件判断

是否需要套件转单品，只看展开后的商品明细。

阻断条件：

- 商品明细中仍出现 `【套件】`。
- 或展开明细中存在 `套件明细` / `套件转单品` 这类商品操作。

不作为阻断条件：

- ERP `标签` 列显示 `套件转单品`。

判断结果示例：

- `判断：请先展开订单`
- `判断：请先套件转单品`
- `判断：可进入人工判断`
- `判断：待人工确认`

判断结果只显示一行，不单独做“建议状态”栏目。

## 9. 商品明细展示

商品区参考商品匹配项目核对页面右侧明细部分：名字 + 数量是核心。

每条商品默认只展示人工最常用的识别信息：

```text
KGOS黑茶 茉莉味                         x7
展开详情
```

展开详情后展示可沉淀为筛选条件或判断条件的字段：

```text
KGOS灵芝金花黑茶固体饮料（茉莉花茶味）1g*21
编码：6979499760044
SPU：kgoshcml-cx
SKU：130292082
```

拆分订单或特殊订单可能缺少 SPU / SKU ID。前端不显示空字段，不用 `无` 占位；后端模型仍保留 `spu_id` / `sku_id` 字段，方便后续规则或筛选条件使用。

多商品和重复商品原则：

- 不按名称模糊合并。
- 只有关键字段完全一致，才允许在展示上聚合数量。
- 暂定聚合 key：`ERP 标准商品名称 + 商家编码 + SPU + SKU ID`。
- 商品简称相同但编码、SPU 或 SKU ID 不同，必须分开显示。
- 多个子订单合并后如出现同一 SPU 或同一 SKU 下多个商品，第一版先分行展示，后续根据实际样本再决定是否聚合。

页面结构倾向：

- 采用“明细核对优先”。
- 商品卡片默认折叠详情，降低多商品订单的视觉拥挤。
- 不做“筛选条件候选”区域。
- 不做“人工反馈栏”区域。
- 不做“建议状态”独立区域。
- 简单订单自然显示很短；复杂订单靠列表和内部滚动。

## 10. 箱规策略

当前不做箱规体积算法。

暂不做的原因：

- 给每个产品录尺寸、给箱子录尺寸，再做装箱算法，复杂度高。
- 当前箱规判断主要靠经验，无法一次抽象成可靠通用算法。
- 过早做算法会让第一阶段变重，且容易误判。

当前策略：

- 先只展示商品和数量。
- 用户人工判断是否可审核、是否需拆分、是否需合单。
- 后续记录人工判断，沉淀固定规则。
- 固定规则足够多后，再讨论是否引入尺寸和体积算法。

规则沉淀方向：

- 先做固定规则记录。
- 规则足够多后，再评估非标准商品是否需要算法。
- 算法只作为后续增强，不进入第一版。

## 11. 可合单标记

可合单标记目前只保留为有 / 无提示，不参与判断。

已确认：

- 标记 class：`trade-icon-canmerged`。
- `data-title`：`点击查看未合并订单明细`。
- 点击后只出现状态数量提示，例如未付款、待审核、已审核、已发货数量。
- 当前读不到对审单有用的候选合单订单明细。

展示方式：

```text
可合单标记：有
```

不做：

- 不点击展开可合单提示。
- 不基于该标记建议合单。
- 不读取点击后的数量明细作为判断条件。

## 12. 暂不做内容

第一阶段明确不做：

- 自动审核。
- 自动合单。
- 自动拆单。
- 自动套件转单品。
- 自动保存或提交。
- 批量处理。
- 筛选条件候选设计。
- 人工反馈栏。
- 完整规则引擎。
- 置信系统。
- 箱规体积算法。

这些不是永久放弃，而是等读取和展示稳定后再单独设计。

## 13. 当前实现

已实现的最小可用版本：

1. 启动桌面独立悬浮窗，贴在 ERP 浏览器窗口左侧外面。
2. 启动后自动读取一次，并提供 `刷新` 按钮手动重读。
3. 通过 Chrome DevTools `localhost:9222` 定位当前 ERP `#/trade/toaudit/` tab。
4. 找到序号为 `1` 的 `.module-trade-list-item`。
5. 如果未展开，只显示 `判断：请先展开订单`。
6. 如果已展开，读取 `tr.order-temp` 商品明细。
7. 解析商品简称、ERP 标准商品名称、数量、商家编码、SPU、SKU ID。
8. 检查展开明细是否仍为套件。
9. 用侧边悬浮窗展示判断结果和商品列表，商品详情默认折叠。

模块边界：

- `erp_reader`：只负责 CDP 读取和 DOM 解析。
- `models` / `parser`：把 DOM 结果整理成结构化订单和商品模型。
- `rules`：只做前提判断，例如未展开、套件阻断、可进入人工判断。
- `ui`：只展示结构化结果，不直接写 DOM 解析逻辑。
