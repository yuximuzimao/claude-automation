# 混合拆分并审核闭环 — neat 归档

日期：2026-07-30  
状态：功能与真实订单验证已完成  
项目：`order-review`

## 阶段结果

已确认的多包方案现在显示“拆分并审核当前订单”。用户针对当前订单点击一次后，工具会在同一次明确授权内完成：

```text
前置核对
→ 混合拆分
→ 主确认与二次确认
→ 拆分接口结果核对
→ 打开普通审核
→ 核对弹窗处理范围和已勾选总数
→ 点击一次确定
→ 验证审核结果
```

用户已经用真实订单确认最终流程成功。它不会自动处理下一单，也不会在拆分或审核结果不确定时重试。

## 最终业务与页面规则

- 目标为 N 个包裹时，只将前 N-2 个包裹逐个加入“待拆分”。
- 倒数第二包只填写数量，不点击“添加待拆分”，直接点击主“确定”；ERP 同时确认该包并把最终剩余量生成最后一包。
- 填写、添加包裹和两级确认之间保留 `300ms` 人工可见停顿；状态轮询仍使用 `100ms`。
- 已分完的商品行可能保留本次填写数量并禁用输入框；验证必须结合剩余量和禁用状态，不能要求所有输入框恢复为 `0`。
- 拆分接口成功证据为 HTTP 2xx、顶层 `result=1` 且 `increaseSplitCount=N-1`。真实响应缺少 `splitResult.success` 时属于未知字段，不是失败；明确返回 `false` 时仍阻断。
- 拆分结果列表是虚拟列表。展开前两条结果行可能使后续行退出 DOM，因此拆分成功后不再逐行展开商品明细。
- 拆分后审核不复用单包流程的唯一系统订单号和底部计数规则。提交前必须证明审核弹窗选择“处理列表页勾选的订单”，危险查询范围未选中，且“已勾选 N 条订单”精确等于目标包裹数。

## 关键修复

- 修正了“所有包裹都点击添加待拆分”的错误操作模型，改为最终两个包裹由一次主确认完成。
- 修正真实成功响应缺少 `splitResult.success` 时被误判失败。
- 移除会被 ERP 虚拟列表破坏的拆分后逐行展开验证。
- 将拆分后的普通审核纳入同一次用户授权，并为多包数量建立独立弹窗门禁。
- 保留操作间可见停顿，让人工能看清填写、添加和确认过程。
- Tk 测试 fixture 在成功或异常路径都取消后台任务并强制销毁唯一根窗口；测试前后必须检查新增审单/pytest 进程为零。
