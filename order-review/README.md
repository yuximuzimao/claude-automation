# 审单悬浮窗

快麦 ERP 待审核订单的桌面辅助工具。

当前已完成只读订单展示、本地包裹方案和人工触发的单包普通审核：工具读取 Chrome 前台的快麦 ERP「待审核订单」页面，定位序号 `1` 的订单。默认是手动刷新模式，启动时不会点击 ERP；用户可以亲自点击顶部“刷新”，或明确开启“自动刷新”进入连续审单模式。单次刷新流程最多尝试展开一次，失败后程序不会自动重试。用户可以在独立工作区创建单包或多包方案、确认保存，并复用历史案例。只有可靠的普通单包方案会显示“审核当前订单”，且必须由用户对每个订单单独点击后才会执行一次 ERP 普通审核。

用户点击“审核当前订单”后，程序会先自动执行只读安全检查，核对目标系统订单号、唯一目标行、复选框、当前勾选、底部计数、页面加载状态和页面是否已有弹窗。检查不通过时不会勾选或提交；检查通过后才进入后续执行关卡。开发命令仍可单独运行只读检查，用于诊断页面状态。

“自动刷新”默认关闭。开启后，审核成功不再依赖固定等待时间：程序每 `500ms` 只读检查一次新的序号 `1` 系统订单号；只有新订单号连续两次一致且稳定至少 `0.5` 秒、页面没有勾选、弹窗或加载状态时，才自动刷新并最多尝试展开一次。真正展开前还会再次核对预期系统订单号；订单中途变化、读取失败或展开失败都会停止自动模式且不重试。点击“停止自动刷新”会立即回到手动模式，并让已经在途的旧探测结果失效。可靠的历史单包方案默认折叠显示为“修改方案”和“审核当前订单”；点击审核即采用当前显示方案，有疑问时再进入完整包裹编辑。

执行流程在每一步都重新核对：只允许勾选当前目标订单；底部订单数出现 `2` 或更大立即停止；只打开普通“审核”，不使用强制审核；弹窗必须选择“处理列表页勾选的订单”并显示已勾选 `1` 条，危险的“处理查询结果中的订单”必须未选中。全部通过后只点击一次“确定”，随后以原订单离开待审核列表、弹窗关闭、真实勾选清零和页面加载完成共同判断成功。结果不确定时不会重试，也不会继续下一单。

## 根本业务规则

订单识别、历史方案恢复、不同订单精确规则复用、单包跨分组复用、复杂合并案例、方案分支和未来执行状态的长期规则见：

- [审单与包裹规则根本约束](docs/2026-07-23-package-rule-foundation.md)

除非后续经过明确讨论并主动修改该文件，否则代码、算法、界面和其他文档不得与其冲突。基础规则校正和保守的数量变化近似推荐均已完成；当前继续积累真实案例，不扩展缺少证据的多包投影。

当前界面中的以下区域全部只读：

- 商品总量
- 按订单查看
- 后台明细

后台明细只展示已经解析的有用字段，例如平台单号、平台商品 ID、平台 SKU ID、平台规格、平台名称和商家编码；完整原始 payload 仍保留在内存快照中。

“包裹方案”与原订单事实层完全分离：刷新订单会丢弃未确认草稿，确认前必须满足逐商品数量守恒、无空包裹、无超分配和无漏分配。确认只写入本地案例，不执行 ERP 审核、拆单、合单、保存或提交。

“物流发货”是普通单包和拆分包裹之外的独立运输决策。总件数达到 `70` 时界面显示“建议复核物流”，但系统只按总件数和历史案例提醒，不估算包裹数；最终必须由人工结合原箱、重量和商品组合判断。物流案例不会进入普通单包容量学习，也不会启用普通单包 ERP 审核。总商品数量为 `1` 且非套件时，系统会直接生成单包草稿，仍需人工确认保存。

包裹编辑以“待分配库存”为中心：一次只编辑一个包裹，已完成包裹折叠为摘要；新增包裹只展示尚未分配的商品，返回编辑旧包裹时则展示该包已有商品和当前待分配商品。数量可用紧凑的 `− / +` 微调、直接输入（停顿后自动生效或按回车），也可点 `MAX` 一次加入该商品的最大可用量。只有存在待分配商品且当前包裹已有商品时才能新增下一个包裹；最后一个包裹不能删除；“恢复初始方案”会恢复进入当前方案时的原始分配。窗口中的商品、订单号、后台明细、推荐内容和方案信息均可拖动选中，并使用 `⌘C` 复制。

历史复用与推荐当前按根本规则拆分为互不混淆的状态，并显示来源案例、历史使用次数和算法版本：

- 同一订单已经保存过方案：恢复原方案，不重复保存；人工修改后保存为关联上一版本的同订单方案版本。
- 不同订单结构精确相同：默认采用可编辑的历史方案，并更新规则统计。
- 商品总量相同且已有单包能力：允许跨子订单结构复用单包方案。
- 商品总量相同但子订单结构不同的多包情况：不得冒充精确匹配。

上述基础语义校正已经完成并通过测试。数量不同情况下的近似推荐第一版也已完成：当当前商品身份集合相同、且每种商品数量都不超过历史已确认的单包数量时，界面会显示带数量差异说明的单包参考候选；系统不会自动采用，仍由人工决定是否进入同一套可编辑草稿。真实案例已证明纸箱适配不是连续容量上限：同一商品 `18` 盒可使用约 `20` 盒箱单包，`9` 盒却因没有合适箱型需要拆成 `6 + 3`。因此较大数量单包不能证明所有较小数量都可单包；在商品与纸箱尺寸模型完成前，这类候选不得解释为可靠装箱结论。任何商品数量增加到历史证据之外、多包数量投影和多分支排序仍不实现。

### 相同包装规格的口味互换

以下商品经人工确认包装大小相同，拆包历史可以在同规格内双向复用：

| 规格 | 可互换商品 |
|---|---|
| 咖啡正装 | 美式咖啡 ↔ 生椰拿铁 |
| 咖啡体验装 | 美式体验装 ↔ 生椰体验装 |
| 黑茶正装 | 茉莉味 ↔ 普洱味 |
| 黑茶体验装 | 茉莉味体验装 ↔ 普洱味体验装 |
| 蛋白粉正装 | 牛油果猕猴桃味 ↔ 莓果味 |
| 蛋白粉体验装 | 牛油果三袋体验装 ↔ 莓果三袋体验装 |

这只是复用“怎么装包”。系统不会把两种口味认成同一个商品：订单身份、商品编码、案例快照和 ERP 审核核对仍使用当前订单的真实口味；正装与体验装也不会互相套用。完整商家编码白名单见[根本业务规则](docs/2026-07-23-package-rule-foundation.md#34-等体积口味只在包裹方案层互换)。

## 运行

前提：Chrome 已使用远程调试端口 `9222` 打开 ERP 页面，并将前台标签页切换到标题为 `快麦ERP--待审核订单`、路由包含 `#/trade/toaudit/` 的页面。

```bash
PYTHONPATH=src python3.13 -m order_review.app
```

开发模式审核前检查：

```bash
PYTHONPATH=src python3.13 -m order_review.audit_dry_run
```

命令只读取当前已展开的序号 `1` 订单；未展开时直接停止，不会代替用户展开。检查结果追加到：

```text
~/Library/Application Support/Order Review/audit-executions.jsonl
```

日志仅保存系统订单号、确认快照/案例引用、状态、检查结果和时间，不保存完整商品原文或原始 DOM payload。

程序带跨进程单实例保护。已有悬浮窗运行时再次启动会直接退出，不会出现两个审单进程，也不会形成两个进程同时写案例的风险。案例仓库本身另有跨进程读改写锁，作为第二道保护。

## 本地案例数据

确认后的不可变订单快照和包裹方案目前保存在：

```text
~/Library/Application Support/Order Review/cases.json
```

- 文件根节点和每条案例都带 `schemaVersion`。
- 每次写入都在跨进程锁内完成“读取 → 计算 → 校验 → 备份 → 原子替换 → 写后校验”，避免并发进程用旧状态覆盖新数据；写后校验失败时会隔离失败文件并自动恢复写入前的有效版本。
- 只有通过统一健康检查的旧文件才会进入正式备份；应用内按时间滚动保留 30 份有效旧版本。
- 当前实现按业务语义区分“同一订单恢复”“规则采用统计”和“新复杂案例”；近似容量候选直接确认时会保存当前数量的新完整案例，确保再次打开同一订单时能恢复正确数量。
- 如需清空历史案例，应先退出悬浮窗并备份或移走该文件；工具本身不提供删除历史案例的入口。

### 案例健康检查

只读检查真实案例，不会修改文件：

```bash
PYTHONPATH=src python3.13 -m order_review.case_audit
```

检查覆盖 JSON/schema、数量守恒、案例和 assignment 引用、版本链和循环、重复 ID、规则统计以及商品/订单身份缺失。错误会阻止正式写入和备份；警告用于提示数据质量风险。

### 多版本备份与人工恢复

应用内备份位于：

```text
~/Library/Application Support/Order Review/backups/
```

查看有效备份（跨 `cases-*`、`pre-restore-*` 等前缀统一按文件时间排序；
文件名没有有效时间戳时回退到修改时间）：

```bash
PYTHONPATH=src python3.13 -m order_review.case_restore --list
```

恢复必须明确指定来源并加 `--yes`：

```bash
PYTHONPATH=src python3.13 -m order_review.case_restore \
  --from "/完整路径/backups/cases-时间戳.json" \
  --yes
```

执行恢复前必须先退出审单悬浮窗；命令会尝试获取单实例锁，程序仍在运行时直接拒绝恢复。恢复来源按实际读取字节重新校验：当前正式文件有效时先创建 `pre-restore`，当前文件损坏时原样隔离为 `cases.corrupt-时间戳.json`，然后原子恢复并再次校验。恢复失败时来源备份和故障文件均保留，不会静默删除或自动掩盖问题。

根工作区备份脚本 `/Users/chat/claude/backup-workspace.sh` 会纳入有效案例和已经存在的推荐事件文件，默认按时间保留 8 代工作区归档。若案例校验失败或正式 `cases.json` 缺失：

- 校验失败的故障文件改名为 `cases.invalid.json`，不会冒充正式案例。
- 归档附带跨前缀统一排序后时间最新的 3 个有效应用内案例备份。
- 校验失败写入 `ORDER_REVIEW_CASES_INVALID.txt`；正式文件缺失写入 `ORDER_REVIEW_CASES_MISSING.txt`。
- 独立健康文件 `order-review-health.txt` 标记为 `degraded`。
- 工作区其他内容继续归档，但脚本最终返回退出码 3，让 launchd 能识别降级状态。

推荐事件损坏时采用同样的隔离和降级策略。原有 launchd 调度仍为每周日 08:07。

### 推荐事件与离线回放

推荐效果事件独立保存在：

```text
~/Library/Application Support/Order Review/recommendation-events.jsonl
```

事件只有 `shown`、`confirmed_direct`、`confirmed_modified` 和 `abandoned_unknown`。同一应用会话内按订单签名和推荐 ID 去重；`abandoned_unknown` 只代表没有得到确认结果，不会被当作拒绝或负反馈，也不会改变规则采用统计。事件写入是 best-effort：失败只记录警告，不能让已经成功保存的案例显示失败，也不能阻断刷新、切换订单、人工创建方案或关闭窗口。

只读检查推荐事件 JSONL：

```bash
PYTHONPATH=src python3.13 -m order_review.recommendation_event_audit
```

坏行会在健康检查和备份状态中明确显示；离线统计仍只读取有效行，不让辅助事件损坏阻塞案例报告。

只读生成历史回放和数据成熟度报告：

```bash
PYTHONPATH=src python3.13 -m order_review.case_replay
```

回放按确认时间隔离历史、排除被测试订单自身，并把同订单版本链折叠为一个独立样本，避免自我验证和样本虚增。历史表现使用订单首次确认方案作为测试目标，统计唯一候选完全一致、候选包含实际方案、冲突、错误推荐和无推荐；当前单包/多包成熟度使用每个订单最新有效版本。报告同时按匹配类型给出覆盖率和实际方案命中率。
