# Order Review Agent Notes

本项目是快麦 ERP 待审核订单的桌面辅助工具。所有对话和说明使用中文。

## 安全边界

- ERP 访问默认只读。审核、合单、拆单、套件转单品、保存、提交等真实业务动作，只有在用户针对当次、当前订单明确授权后才允许执行，授权不得沿用到下一单。单包普通审核中，用户点击“审核当前订单”只授权当前已确认订单完成一次受保护的勾选、普通审核、确定和结果核对链路；即使用户开启自动刷新，也不得自动审核下一单、连续处理或重试确定。
- 只读取 Chrome 当前前台标签页，标题必须为 `快麦ERP--待审核订单`，路由必须包含 `#/trade/toaudit/`；订单管理页和后台标签页一律拒绝。
- 当前只读取页面“序号”列为 `1` 的订单。默认手动刷新模式下，应用启动和后台不得点击展开；只有用户亲自点击顶部“刷新”，或明确开启“自动刷新”模式后，才允许对当前稳定订单点击一次左侧展开加号并读取明细。展开失败不得自动重试，仍提示 `判断：请先展开订单`，不能用列表明面信息代替展开明细。
- “自动刷新”必须默认关闭，并提供同一位置的“停止自动刷新”按钮。开启后，审核成功不再依赖固定秒数缓冲，而是每 500 毫秒只读探测一次；新系统订单号必须连续两次一致且稳定至少 0.5 秒，页面没有勾选、弹窗或加载状态，才允许自动刷新并最多展开一次。真正展开前必须再次核对预期系统订单号。停止模式时必须使在途旧探测结果失效；读取失败或订单在读取前再次变化时自动退出连续模式。
- 单包审核阶段 1 的“审核前检查”允许只读扫描当前待审核页所有可见订单行的系统订单号、复选框状态和勾选计数，用于证明目标订单唯一且页面没有其他勾选；商品明细仍只读取序号 `1` 的目标订单。该检查只在审核执行尚未开始时生效，不得点击、悬停、打开菜单或弹窗。
- 审核开始后的选中状态、菜单和弹窗必须使用各自独立的执行中关卡，不能继续拿“审核前检查”充当安全证明。弹窗若选择“处理查询结果中的订单”，必须停止且不得自动改选、取消或确定。
- 单包单订单审核以真实选中行和系统订单号为主证据，弹窗“已勾选 1 条订单”为提交前第二主证据。ERP 底部计数会残留历史数据，因此勾选前只记录、不参与放行；单包审核完成勾选后，底部 `0` 或 `1` 不作正向证明，出现 `2` 或更大时必须阻断。该规则不得套用于拆分包裹流程，拆分只核验真实选中行和目标订单身份。
- 套件阻断只看展开后的商品明细，不看 ERP 标签列。
- 包裹方案允许在本地创建、编辑和持久化，但不得因此自动触发 ERP；人工保存的方案，以及单件非套件或唯一无冲突精确历史形成的本单内存方案，可由用户单独点击对应审核入口执行，两者均只授权当前订单的一次受控执行。
- “物流发货”是独立运输决策，不等于普通单包；物流案例不得参与普通单包推荐，也不得进入普通单包 ERP 审核流程。
- 总商品数量为 `1` 且展开明细不是套件、且同订单未明确保存为物流时，普通单包是确定结果。无论命中已保存方案、历史规则还是没有历史，都直接生成当前订单的内存执行方案；用户点击“审核当前订单”后不得再保存、确认或记录规则采用。套件与已保存物流仍保持阻断。
- 订单历史规则只要明细签名和方案完全匹配，就是确定性复用；不得像售后分支一样用采用次数提高置信度。未修改的精确历史方案直接作为本单内存执行输入，不保存订单采用关系、不累计采用次数，也不因点击审核或拆分而重写案例文件；人工修改产生的新方案或版本仍须保存。
- 混合拆分只能在多包方案已经确定后由用户单次点击触发；方案可以来自人工保存，也可以来自唯一无冲突的精确历史内存方案。拆分成功后可在同一次明确授权内接续审核，但不得套用单包普通审核的订单身份、底部数量或结果规则。合单、套件转换、批量处理及其他 ERP 写操作仍须作为独立阶段设计。

## 根本业务规则

订单识别、历史方案恢复、规则复用、复杂合并案例、单包优先和方案分支的长期规则统一见：

- `docs/2026-07-23-package-rule-foundation.md`

该文件是本项目的根本业务约束。后续代码、算法、界面、计划和文档不得静默与其冲突。只有在用户明确讨论并主动改变相关规则后，才允许同步修改该文件及实现。

基础语义和数量变化近似推荐已实现。纸箱规格是离散集合；
`single_package_capacity` 只作人工参考。现有签名、订单版本和单包例外仍是前置，
历史规则统计只兼容读取，不参与推荐或执行判断。

商品真实身份与包裹规划身份必须分开。只有根本规则第 3.4 节列出的八个等体积规格组可以在历史包裹方案中互换；正装、体验装、气垫正装与替换装和不同品类不得交叉。订单身份、案例快照、原商品引用和 ERP 审核核对必须始终保留当前订单的真实口味与编码。

## 界面与数据分层

- `商品总量`、`按订单查看`、`后台明细`属于只读原订单信息，禁止提供人工修改能力。
- `包裹方案`是独立的可编辑决策层，只能引用原订单快照中的商品，不能反向修改原订单。
- 原订单刷新、平台单号变化或目标订单变化后，未确认包裹草稿必须失效。
- 包裹确认必须满足数量守恒：每个原商品在所有包裹中的分配总量等于原订单数量；不允许空包裹、超分配或漏分配。
- 确认记录必须同时保存完整原订单快照和最终包裹商品明细。包裹项需保留到原商品的稳定引用，界面可只显示商品名称和数量。
- “保存方案”发现未分配商品时，已有空的最后一包则填充该包，否则新增最后一包承接全部余量；不得把余量追加到已有商品的当前包裹。
- 历史推荐必须可追溯到案例或规则；冲突历史不得静默自动选择。同一订单方案修改必须保存为关联上一版本的方案版本。
- 采用任何精确或近似推荐都只能生成本地可编辑草稿，不能在后台自行操作 ERP；唯一无冲突的精确方案可在用户点击审核入口后直接作为内存执行输入，近似方案仍须人工保存。人工修改后必须记录为 `recommended_modified` 并保留推荐来源和算法版本。

## 读取与字段约定

- CDP 通过 Chrome `localhost:9222` 直连：HTTP `/json` 查找 tab，`Runtime.evaluate` 执行只读页面 JS，JS 返回 JSON。
- 商品标题最后一个全角括号前是 ERP 标准商品名称，括号内是商品简称。
- `平台ID（skuId）`一行中，括号外是平台商品 ID，括号内是平台 SKU ID；`data-numiid` 是平台商品 ID，不是 SKU ID。
- 页面可见的“平台单号”在当前 DOM 中可能存放于 `data-tid`，业务语义必须显示为平台单号，不能称为主订单号。
- ERP 内部 SID/OID 不展示为平台订单号，也不进入人工后台明细。
- 商品名称、数量、平台商品 ID、平台 SKU ID、平台规格、平台名称和编码只能从商品自身节点解析；完整 `tr.order-temp` 只能用于提取该行平台单号。
- 每次刷新必须保留页面分组、商品来源分组、平台单号、商品结构化字段和完整原始 payload。
- 后台明细只展示拆分后的有用字段，不显示原始页面文本、ERP 内部 SID/OID 或其他 `data-*`。

设计或实现下一阶段前必须按顺序阅读：

1. `docs/CURRENT.md`
2. `docs/2026-07-23-package-rule-foundation.md`
3. 只有继续尺寸推荐集成时再读
   `docs/archive/2026-08-14-carton-packing-foundation/neat-handoff.md`

基础匹配、历史模块精确组合、案例安全、逐单 ERP 执行和离线三维装箱底座均已
实现。真实成熟度以即时 `case_replay` 和 `packing_case_audit` 为准；尺寸求解尚未
接入线上推荐。

单包审核、物流隔离和混合拆分均为已完成能力，授权仍只来自用户对当前订单的单次点击。拆分接口成功后必须证明真实勾选行恰好为前 N 条；读取每个目标结果行前，按鲸灵售后列表同类方式对 ERP 结果列表执行真实 `mouseWheel` 滚动，把该行移入视口，再按序号复核系统订单号与勾选状态。只读取这 N 条，按无序包裹集合核对全部明细、平台子订单号全集和商品总量；虚拟列表卸载较早行时保留已验证证据。全部读取后必须滚回序号 1，复核系统订单号和唯一勾选，等待 `100ms` 页面稳定后才可最终探测并审核。打开审核菜单和点击审核子菜单前还要分别重查恰好前 N 条仍被勾选，弹窗必须选中“处理列表页勾选的订单”且显示精确 N 条。任一不符即停止；只允许对瞬时读取失败重试，拆分、审核或确定等业务动作一律不得重试。

线上包裹决策固定为“确认规则优先、尺寸计算兜底”。同订单保存方案、唯一无冲突
精确历史、相同总量单包、唯一历史模块精确组合、固定业务规则和确认箱规均直接
复用；规则冲突交给人工。只有没有可靠结果的新组合才运行三维求解，
`single_package_capacity` 等近似参考不能阻断尺寸计算。

新尺寸方案先判断整单一箱；确需拆分时先保持平台子订单完整，再只拆无法整体安排
的子订单。同包裹数下依次减少被拆子订单、跨包片段和交叉混装片段。精确历史只作
事实恢复，不受新排序追溯改写。

尺寸目录区分内/外尺寸和证据来源；当前纸箱外尺寸按三轴各减 `5 mm` 得到保守
内径。品牌隔离、专用原箱、固定容量、礼盒排除和存量箱用途均先于几何搜索；完整
规则以根本约束和 `data/packing-dimensions.json` 为准。搜索超限或未找到时返回
未知，不伪装成确定装不下。

已完成阶段和业务讨论证据位于 `docs/archive/`，仅供追溯，不得覆盖长期规则、代码事实或新采集页面事实。

混合拆分弹窗添加包裹后，ERP 会让已经分完的商品行保留本次填写数量并禁用输入框；只有仍有剩余量的行才恢复为 `0` 且保持可编辑。结果验证必须按“剩余量 + 禁用状态”联合判断，不能要求所有输入框都恢复为 `0`。填写、添加包裹和两级确认之间保留 `300ms` 人工可见停顿，状态轮询间隔仍为 `100ms`。

混合拆分目标为 N 个包裹时，只把前 N-2 个包裹逐个加入“待拆分”；倒数第二包填写数量后不点“添加待拆分”，直接点“确定”，由 ERP 同时确认当前数量并把最终剩余量生成最后一包。确认前必须证明当前填写量等于倒数第二包，且扣除后剩余量精确等于最后一包。

混合拆分接口的成功证据是 HTTP 2xx、顶层 `result=1` 且 `increaseSplitCount=N-1`。真实成功样本中 `splitResult.success` 既可能缺失，也可能为 `false`，该字段不代表本次整体拆分失败，只保留作诊断信息；增加数量与目标不符时仍必须阻断并且不得重试提交。

拆分填写完成并点击主“确定”后必须等待 `1s`，再探测二次确认；拆分接口确认成功后等待 `300ms`，再开始探测结果行；每次真实展开结果行后等待 `600ms`，才允许读取完整商品明细；全部结果明细核对通过后再等待 `1s`，才探测普通审核菜单入口。所有等待结束后仍须重新核对目标系统订单号、勾选状态、明细完整性和审核入口，不能用等待替代验证，也不能靠延长总超时反复滚动页面。

## 数据与运行安全

- 应用必须由单实例锁保护；案例仓库的完整读改写事务必须持有跨进程文件锁。
- macOS Tk 界面测试在同一测试进程中只允许创建一个根窗口；新增状态场景优先并入该窗口或使用无窗口纯逻辑测试，不得为测试隔离反复创建、销毁 `tk.Tk()`。fixture 必须用 `finally` 取消 `after` 任务并强制销毁根窗口，不能依赖可能因业务状态拒绝关闭的正式 `close()` 完成测试清理。
- 每次 Tk 测试前后必须按精确命令检查审单/pytest 进程；测试结束应为零新增进程和零新增窗口。若 pytest 挂起或留下窗口，先停止并清理本次测试 PID，再定位原因；不得并行或反复启动新的 GUI 测试放大残留。
- 正式案例写入前后都必须通过统一校验，替换旧文件前只备份有效版本；写后校验失败必须隔离错误文件并恢复有效旧版本。
- 人工纠正正式案例必须先退出悬浮窗、创建有效备份、锁定精确案例及关联索引并排除外部引用，再原子写入和独立读回；审核执行日志是事实审计记录，不得为匹配新案例 ID 而改写。
- 不得在启动时自动恢复备份；恢复只能由人工明确指定来源并确认，必须阻止程序运行期间恢复。损坏正式文件先原样隔离，再恢复有效备份。
- 推荐事件只用于离线统计，`abandoned_unknown` 不得解释为拒绝或写入负反馈。事件写入必须是 best-effort，不得改变核心案例操作的成功或失败。
- 历史回放必须隔离测试目标自身，并折叠同订单版本和历史遗留采用关联，不能虚增独立样本。历史表现使用首次确认，当前成熟度使用最新有效版本。
- 工作区归档遇正式案例缺失或损坏时，必须继续归档其他内容、标记 `degraded`、返回退出码 3，并附带跨 `cases-*`、`pre-restore-*` 等前缀统一选出的时间最新有效应用内备份；`case_restore --list` 与归档必须共用同一有效备份排序。
- 真实 `cases.json` 的验证默认只读；写入、并发和恢复测试必须使用临时目录。
- 单次订单加载必须复用一个仓库快照，禁止为查找、推荐和统计重复解析大体积
  `cases.json`。
- 案例写入须流式序列化；大文件校验放在短生命周期隔离进程，保留有效备份、原子
  替换和失败回滚，禁止在 UI 进程重新构造整份案例字典。
- 内存回归继续使用 1/5/20 次 RSS、Python 活对象和 Tk 计数，不得靠重启掩盖增长。
