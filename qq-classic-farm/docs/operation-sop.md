# QQ 农场按次操作决策

本页是用户说“操作农场／收菜／跑一轮”时的脚本选择入口。用户只需发起操作，无须逐项列脚本；Agent 根据当前日期、已完成动作和田内状态选择。用户本次指定范围优先。用户说“施肥收菜”默认包含收获后按已批准计划补种，不能收完就关闭；只有明确说“只收不种”才停在空田。只处理QQ；单次定时执行以CURRENT明确授权为准，不自动续跑。

## 1. 操作前读取

读 `CURRENT.md` 的当前实种批次、种植时刻和当日日常完成记录，以及 `../data/operation-plan.json` 的下一次计划。库存以 `seed-catalog` 最近现场读取加已记录增减为准；正常开窗不重扫仓库。用户报告买种、卖种、误种或库存异常时才核实受影响状态。

日期按 Asia/Shanghai 的自然日，以 00:00 为界。开窗次数不是每日任务完成次数；各项独立记账，未完成不能因“今天已来过”被跳过。跨日只重置当天资格，不补跑错过日期。用户人工完成的项目也记为已完成。记录不确定时先核实，不直接重做。

每次开窗：`farm_window.py open --platform qq --execute` → `farm_home_check.py --live --prepare`（激活、等待5秒、窗口与首页检查）→ 仅当 `ready_for_input=true` 才选择下列分支。失败时先交Agent核实原因，不自动重试、重开或点击田内。确认完成后固定动作串行执行，不逐步插入例行截图。报错即停；仅在核清部分完成情况、修正原因后从未完成步骤恢复，不重跑整条链。

### 实种记录的必检规范

实种记录是上一轮实际完成种植的完整记录，放工作区 `_sandbox/` 并显式传入；它与唯一下一批 `data/operation-plan.json` 分开。从已完成种植记录保存完整结构，再与CURRENT批次核对，禁止为了通过校验从下一批计划复制并冒充当前实种。种植后的页槽变化不回写历史实种记录。

正式结构沿用种植计划格式：顶层必须且只能有 `qq`、`wechat`；两平台各自必须有 `planting`、`daily`，未使用平台也保留 `special: []`、`ordinary: null` 和三个false日常字段。`planting` 包含 `special`、`ordinary`，耗尽混种可带 `ordinary_after_exhaustion` 数组；每项必须记录非空 `seed_name` 和正整数 `quantity`，四格每项数量只能为1，同时保留原有 `plot/page/slot/page_items` 字段及类型约束。四格入口不得重复、重叠或落入禁用组，且必须有直接确认的收获点。普通数量加四格占地不得超过24；整轮收种要求合计恰好24格。

**写完或修改实种记录后立即读回并校验，在本轮种植收尾时完成，不留到下次操作。** 正常满田批次执行：

```sh
python3.13 scripts/farm_harvest_once.py --platform qq --planted-plan ../_sandbox/本批实种.json --check-plan
```

该命令校验完整记录、24格数量和收获点，不查询窗口、不截图、不点击。缺字段、类型错、数量不符、占地冲突、未登记收获点等一律返回非0及 `rejected_rewrite_required`；**当场打回重写，读回并重新校验，直到通过才把记录登记为已完成**。没有通过时不能宣称本轮记录收尾完成。CURRENT中的实种记录路径应指向已通过校验的文件；以后修改该文件也必须立即重验。语法校验不能证明记录符合田内事实，写入时仍须核对本批实际动作、种植时间和人工改动。

下一次操作直接使用这份已校验记录，不再把单独运行 `--check-plan` 或整轮dry-run列为正常开工步骤。非空田显式传 `--harvest-plan`，不得直接指向 `operation-plan.json`；空田不需要实种记录。执行入口保留本地参数防错检查，防止文件在收尾后被误改、丢失或传错；这属于异常兜底，不替代写完即验，也不增加一轮窗口检查、截图或Agent审核。兜底失败仍在任何田内动作前停止，不补默认值、不绕过。

四格固定点收获的前置条件：标准无遮挡首页已通过；当前实种记录有效；已到自然成熟时间，或本批全部作物已进入最后非零阶段且普通肥本季可用、施肥脚本成功并等待2.2秒。条件成立后不再识别“可摘”星标。独立收获传 `--mature-confirmed` 表示已核实上述条件；整轮 `tail` 分支只在施肥成功并等待后才调用带此参数的收获脚本，`mature` 由Agent按批次成熟时间确认。提醒只是提示，混种要确认全部待收作物的最后阶段都已开始，不能只依据最早一株的提醒时刻。

纯普通作物独立收获明确传 `--ordinary-only`（例如白萝卜双肥循环），不能省略记录来默认为纯普通田。`--ordinary-only` 与 `--planted-plan` 互斥。

## 2. 土地状态决定收获方式

| 现场与当前批次记录 | 本次动作 |
| --- | --- |
| 作物已成熟 | `farm_harvest_once.py`，不先施肥；四格按当前实种记录传 `--planted-plan`，并确认成熟前置条件 `--mature-confirmed` |
| 尚未成熟，已进入最后非零阶段，普通肥本季尚可用 | `farm_fertilize_once.py` 普通肥一次 → 等 2.2 秒 → 收获 |
| 尚未到最后阶段 | 不提前施肥、不铲掉作物、不种萝卜；可处理符合条件且当日未完成的日常，按当前批次维护提醒后关闭 |
| 土地全空 | 跳过初始施肥/收获，直接进入当天剩余萝卜循环或正式种植 |
| 多季收获后仍在再生，或仅部分地可收 | 不假定全田空；保留作物，按实种季数与阶段处理，不执行全田萝卜或普通一键补种 |
| 遮罩、误种、时刻不明、界面与记录冲突 | 先核实，不按旧快照推断可执行步骤 |

一键务农仅由施肥脚本在需要时前置处理，不单独执行。仓鼠出现时沿用已有“气泡出现就购买”规则，通过 `farm_hamster_once.py` 处理；分享按当前明确授权执行，完整链验收状态见Todo；放虫和种草按mischief专项流程独立执行，使用默认完整额度流程，不再附加限一位参数。

## 3. 每日项目与补货

2026-11-11用户确定：固定日常按免费化肥→分享→好友全扫→种草/放虫顺序，每自然日最多一次；每日任务脚本省去，用户确认已完成未领取的奖励次日会发农场邮箱，不自动操作邮箱。白萝卜仍在当天首次收获且全田为空时补足当日轮数。仓鼠在收种前顺带检查；自己田地务农只保留施肥脚本前置，不单独执行。当前单次定时授权和具体日期见CURRENT，不能把每日一次上限理解为已授权无限周期调度。

| 项目 | 什么时候做 | 什么时候跳过 |
| --- | --- | --- |
| 白萝卜经验循环 | 当天尚未完成 5 轮，并且全田已空；运行 `farm_radish_xp.py --rounds 剩余轮数 --execute`，成功轮次逐项记账 | 当天 5 轮已完成、田未空，或用户要求只收获；中断后只补剩余轮数 |
| 白萝卜补货 | 已知库存小于本次剩余轮数 ×24 时，先用 `farm_radish_restock.py` 月度补货，再按完成次数记账 | 库存足够时一律跳过，不因跨日或再次开窗重复购买 |
| 每日任务 | 当前不单独执行；通过收菜、好友全扫完成条件，未领按用户确认由次日邮件补发 | 定时任务不传 `--tasks`，不调用每日任务脚本 |
| 好友全扫 | 当天尚未完成时，按固定日常顺序运行 `farm_friend_sweep.py`；用户明确再扫时可单独运行 | 当天正常日常已经扫过则默认跳过，不随收菜频次重复扫 |
| 免费化肥 | 当天未领则 `farm_daily_fertilizer_reward.py`；无需等待田空 | 已领取则跳过 |

种草／放虫当天未确认共享余额归零时，在其它日常后独立运行 `farm_mischief_once.py --execute`；两处灰色0才记完成，访问上限或异常停止不能记为完成。

`CURRENT.md` 记录各项日期、完成轮数/状态。当天若只来过但没有收获，不能把萝卜和每日任务算完成。萝卜使用双肥；实际经验受游戏每日上限影响，不以理论轮数收益代替到账数据。

## 4. 正式种植与耗尽补种

正式种植只用唯一 `operation-plan.json`。`slot` 是页内种子序号，`page_items` 是当时该页剩余种类数；居中换算见 `gameplay-rules.md`。库存扣到 0 后，该种子从选择器消失，后续种子的页槽与末页数量必须重新计算。萝卜脚本从当前有效库存顺序计算位置，不写死末页槽位。

四格 `special` 为顺序列表，每颗覆盖2×2；`ordinary` 为第一种普通种子或null。计划内 `daily` 三个布尔字段仅作为待执行提示，不会由种植脚本自动执行，日常仍按第3/5节选择独立脚本。

具体种子、预期数量与耗尽前后位置由唯一计划文件维护，批次含义见CURRENT。普通一键种植依靠第一种剩余库存耗尽，再用第二种填剩余空地；`quantity` 是预期消耗，不是游戏输入数量。库存发生变化时先重算。

`ordinary_after_exhaustion` 是按执行顺序排列的补种数组；每项都提供轮到它时的 `page`、`slot`、`page_items` 与预期 `quantity`。第一种普通种子及全部补种数量之和必须等于四格种植后剩余的格数，脚本在任何点击前验证。前面的普通种子必须确实会耗尽，不能用 `quantity` 限制游戏的一键种植数量。

混种时普通选种单独计次，入口固定为 `24 → 23 → 22`；四格种植使用自己的明确入口，不占这个计数。纯普通单一种植保留01入口；纯普通多种混种也从24递减。计数只属于本次计划，从头执行的新一轮会重新从24开始，不跨收获周期累计。

脚本一次串行执行四格、第一种普通种子和全部补种；普通种植每段等待2.8秒，再在下一入口打开选择器、定位第一页、翻到计划页槽并选种。不再退出等待Agent看图选空地，也不提供人工传入补种地块的参数。入口落入禁点（例如第4段普通种植会到21）或四格覆盖时，整份计划在点击前报错；不跳号、不猜替代空地。该递减流程只用于已清空田地起步且按计划耗尽接续的轮次，不用于部分田地、误种或中断后的盲目恢复。

任一控件识别或点击失败就停，后续段不执行、不自动重试。出错后先核实已完成部分，禁止从头重跑本批。

## 5. 脚本组合与收尾

独立脚本是正式执行单位。`farm_qq_round.py` 仅按Agent已确定的参数串行，不负责自动判断页面或日期：

- `--field-state tail|mature|empty` 必填；未到尾段不使用整轮入口。非空田必须传已通过上述校验的 `--harvest-plan`，无默认实种记录。
- `--radish-rounds 0..5` 默认0；只填当日剩余轮数。
- `--friends --reward` 按当次授权范围与当天完成记录显式选择，默认不做；例行安排不传`--tasks`。
- 种植脚本完成所有段后才继续后续日常；任一段失败立即停止整轮，不重跑已完成部分。

实际收获的四格位置以CURRENT实种记录为准，不能用刚更新的下一批计划替代事实。

完成正式种植后，写入实种记录并立即按本页规范校验，通过后登记CURRENT；按实际动作扣库存，更新当日日常记录和新批次种植时刻；仅正式种植创建最后阶段收菜提醒并读回核验，再关闭小程序并确认。没有新种植时不重复创建同批提醒。规则细节分别以SKILL种植收尾与工作区提醒协议为准。
