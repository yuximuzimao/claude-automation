# 无效早期项目候选归因修复设计

## 目标

修复 Codex 会话从工作区根目录启动时，前 200 行把任务名误当成项目名并提前结束扫描，导致本应归入真实项目的 token 落入“其他”的问题。

本次只处理主要误差，不增加子代理父会话继承、项目别名映射或中心化硬编码表。

## 当前问题

`infer_project_from_handle()` 默认先扫描 200 行。只要此时存在唯一候选，就立即返回；聚合层随后要求 `/Users/chat/claude/<候选>/CLAUDE.md` 存在。若候选其实是任务名，聚合层会将整段会话归入“其他”，即使第 201–1000 行已经出现真实项目。

真实样本中：

- 200 行候选：`aftersales-confidence-safety-v1`，不是实际项目目录。
- 1000 行候选：`aftersales-automation`，存在项目说明文件。
- 约 43.21M token 因此被错误归入“其他”。

## 方案比较

### 方案 A：无条件扫描 1000 行

实现最少，但会改变所有长会话的投票窗口。实测 306 个会话中有 12 个结果会变化，其中部分是有效项目之间的变化，历史归因影响过大。

### 方案 B：无效早期候选才继续扫描（采用）

前 200 行的候选只有在对应项目 `CLAUDE.md` 存在时才提前返回；否则继续扫描到 1000 行。这样保留现有有效项目的快速路径，只修复任务名抢占真实项目的情况。

### 方案 C：子代理继承父会话项目

能进一步修复约 0.99M token，但需要解析父子线程关系并做跨会话二次归因，改动和测试面明显更大，本次不做。

## 设计

为 `infer_project_from_handle()` 增加一个可选的“候选是否有效”判断。默认调用行为保持兼容；Codex 本地 reader 传入基于现有项目 `CLAUDE.md` 的判断。

数据流：

1. 扫描前 200 行并产生唯一候选。
2. 候选对应真实项目时立即返回。
3. 候选不是已知项目时继续扫描，最多到 1000 行。
4. 返回最终唯一候选；聚合层继续执行现有项目存在性校验。

不读取或修改会话正文以外的新数据源，不改写本地 JSONL，不维护项目名称映射。

## 行为边界

- 已正确识别的有效项目会话保持原结果。
- 无效候选在 1000 行内找到真实项目时得到纠正。
- 1000 行后仍只有无效任务名时，聚合结果继续为“其他”。
- 今日总量、近 30 天总量和配额数据不变，只改变项目分布。
- 子代理独立会话仍可能进入“其他”，留作后续观察。

## 验证

1. 新增回归测试：前 200 行只有无效任务名，第 201–1000 行出现有效项目时，返回有效项目。
2. 保留测试：前 200 行已经是有效项目时仍可提前返回。
3. 运行全部单元测试与 `compileall`。
4. 运行真实 `--smoke-aggregate`，确认主要会话归入“鲸灵售后自动化”，总 token 不变。
5. 重启常驻 App 后读回界面数据。
