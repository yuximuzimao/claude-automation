# Codex Monitor 后续优化方向

本文只记录尚未排期、但值得保留的长期方向。当前版本已经可用，除非触发条件成立，否则不要据此主动重写现有 UI。

## 原生 macOS 材质 UI

### 目标

在不重写统计核心的前提下，使浮窗的磨砂材质、文字合成、圆角和动态明暗响应更接近 macOS 原生桌面组件。

### 当前架构及上限

当前 UI 由两条渲染链路叠加：

1. Python/Tkinter 负责文字、圆环、布局和交互。
2. PyObjC/AppKit 在 Tk 窗口下方维护独立的 `NSWindow + NSVisualEffectView`，负责采样桌面并生成磨砂背景。

这种架构可以获得真实桌面模糊，但无法与原生组件完全一致：

- Tk 文字和 Canvas 图形不会进入 macOS vibrancy/material 合成流程，只能以固定颜色栅格化后覆盖在磨砂层上。
- 前景和磨砂不在同一棵 AppKit/SwiftUI 视图树中，系统无法统一处理字体抗锯齿、动态对比度、色调、圆角裁切和阴影。
- 两个窗口需要手动同步位置、层级、显示和隐藏，材质行为容易受 Tk/macOS 窗口生命周期影响。
- 继续微调 Tk 颜色或 blur alpha 只能改善近似效果，不能消除上述结构性差异。

### 推荐迁移方向

保留现有 Python reader、聚合、项目归因和限额解析逻辑，将 UI 外壳逐步替换为原生 macOS 实现：

- 浮动常驻形态：优先评估 `NSPanel`/AppKit 承载 SwiftUI 内容，使用系统 `Material` 或原生 `NSVisualEffectView`。
- 数据边界：Python 继续输出结构化快照；原生前端通过本地 JSON 文件、子进程标准输出或轻量本地 IPC 读取。具体协议在真正排期时再设计。
- 真正桌面组件：只有在接受 WidgetKit 的刷新频率、交互和生命周期限制时才评估 WidgetKit；当前需要拖动、即时刷新和弹层交互的形态更适合 `NSPanel`。
- 迁移应先做一页原型，对比材质、字体、功耗、启动方式和后台常驻行为，再决定是否替换 Tk 前端。

### 不在当前范围

- 不因为视觉近似不足就重写 reader 或聚合层。
- 不在现有 Tk 版本上继续堆叠字体描边、伪透明 Canvas 图层或多层窗口补丁。
- 不在没有原型验证和迁移计划时引入 Xcode/Swift 构建链。

### 触发条件

满足以下任一条件时再立项：

- 当前材质与原生组件的差异再次成为高频使用障碍。
- 需要系统级 vibrancy、动态深浅模式或更可靠的原生字体合成。
- Tk/AppKit 双窗口同步持续出现无法低风险修复的残影、层级或生命周期问题。
- 用户明确接受新增 Swift/AppKit 工程和双语言构建维护成本。

### 验收标准

原生原型至少应验证：

- 深色和浅色壁纸上均接近系统组件的材质与文字对比度。
- 收起、展开、项目弹层和拖动过程没有双窗口残影。
- 继续使用现有统计口径，真实数据与 Python 版本一致。
- 后台空闲 CPU、内存和登录启动体验不劣于当前版本。
