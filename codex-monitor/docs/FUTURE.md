# Status Island 后续优化方向

本文记录尚未实现的长期方向和技术选型边界。Status Island 已确认采用双设备协作方向，第 1、2 阶段架构讨论完成，第 3 阶段任务入口与触发源映射进行中。黑苹果登录 / Session 同步及两端账号数据归属已确认；下一项讨论 Mac mini 售后网页调用黑苹果本地浏览器 / 登录桥接服务，再完成剩余入口映射；之后讨论停止 / 失联 / 恢复安全、状态反馈协议、逐项目验收，最后进入产品形态和 UI 技术选型。本文不构成安装 Autoloop、配置 Tailscale、部署 Mac mini 或修改生产入口的授权。当前稳定的用量统计核心继续保留。

## 桌面状态岛（Status Island）

**状态：双设备部署方向已确认；第 3 阶段任务入口映射进行中；尚未实现。**

目标是在现有用量监控应用基础上扩展常显状态岛，不另建完整中台。黑苹果保留本地用量统计和状态岛主界面；Mac mini 运行独立状态岛、售后业务服务和自动化执行环境。两端都能独立运行，不互相依赖。

- 黑苹果负责 Codex 用量统计、状态总览和人工浏览器操作；Codex / CodexPro 只在黑苹果使用。
- Mac mini 负责售后业务服务、唯一业务数据源、自动化调度和自动化 Chrome，并保留完整桌面状态岛供远程查看。
- 两台设备各自维护本地任务队列和桌面资源；交换任务请求与状态，但不建设跨设备单一全局队列或复杂多节点集群。
- 售后业务服务集中在 Mac mini；黑苹果访问同一售后网页，人工平台操作使用黑苹果本地 Chrome，自动化操作使用 Mac mini Chrome。
- 初步计划使用 Tailscale 私人网络，尚未安装配置；当前不购买固定公网 IP、VPS 或独立公网服务器。数分钟级传输延迟可以接受。
- 不开发 iPhone 客户端；iPhone 继续通过远程桌面软件连接黑苹果。

状态岛队列只显示**下一项任务**：定时任务与普通任务统一展示，定时任务显示倒计时，普通即时任务显示“即将执行”；不展示完整等待队列。状态岛还显示当前任务和异常信息。

黑苹果人工注入鲸灵账号前，先检查 Mac mini 的售后平台操作状态：Mac mini 正在执行售后平台操作时提示占用；其他不冲突项目运行不阻塞注入；售后空闲时自动授予短时许可，不要求人工释放。许可时长和定时任务恰好撞时的处理仍待确认。

Autoloop 可继续作为本地调度内核候选研究，但不能再把 2026-11-06 的单一串行 group 解释为跨设备全局队列。各项目仍拥有自己的业务规则、安全门禁、内部重试和异常处理。

**详细设计与当前恢复点：**见工作区归档 `../../docs/archive/2026-11-09-status-island-dual-device-design/README.md`。本文件保留长期方向；当前讨论进度与下一步见 `tasks/todo.md`。UI 技术选型继续评估 Tk / AppKit 与 NSPanel / SwiftUI，不代表已批准迁移。

## 原生 macOS 材质 UI

### 目标

在不重写统计核心的前提下，使浮窗的磨砂材质、文字合成、圆角和动态明暗响应更接近 macOS 原生桌面组件。

### 当前架构及上限

当前 UI 由两条渲染链路叠加：

1. Python/Tkinter 负责文字、圆环、布局和交互。
2. PyObjC/AppKit 在 Tk 窗口下方维护独立的 `NSWindow + NSVisualEffectView`，负责采样桌面并生成磨砂背景。

这种架构可以获得真实桌面模糊，但无法与原生组件完全一致：

- Tk 文字和 Canvas 图形不会进入 macOS vibrancy/material 合成流程，只能以固定颜色栅格化后覆盖在磨砂层上。
- 前景和磨砂不在同一棵 AppKit/SwiftUI 视图树中，系统无法统一处理字体抗锯齿、动态对比度、色调、圆角裁切和阴影。
- 两个窗口需要手动同步位置、层级、显示和隐藏，材质行为容易受 Tk/macOS 窗口生命周期影响。
- 继续微调 Tk 颜色或 blur alpha 只能改善近似效果，不能消除上述结构性差异。

### 推荐迁移方向

保留现有 Python reader、聚合、项目归因和限额解析逻辑，将 UI 外壳逐步替换为原生 macOS 实现：

- 浮动常驻形态：优先评估 `NSPanel`/AppKit 承载 SwiftUI 内容，使用系统 `Material` 或原生 `NSVisualEffectView`。
- 数据边界：Python 继续输出结构化快照；原生前端通过本地 JSON 文件、子进程标准输出或轻量本地 IPC 读取。具体协议在真正排期时再设计。
- 真正桌面组件：只有在接受 WidgetKit 的刷新频率、交互和生命周期限制时才评估 WidgetKit；当前需要拖动、即时刷新和弹层交互的形态更适合 `NSPanel`。
- 迁移应先做一页原型，对比材质、字体、功耗、启动方式和后台常驻行为，再决定是否替换 Tk 前端。

### 不在当前范围

- 不因为视觉近似不足就重写 reader 或聚合层。
- 不在现有 Tk 版本上继续堆叠字体描边、伪透明 Canvas 图层或多层窗口补丁。
- 不在没有原型验证和迁移计划时引入 Xcode/Swift 构建链。

### 触发条件

满足以下任一条件时再立项：

- 当前材质与原生组件的差异再次成为高频使用障碍。
- 需要系统级 vibrancy、动态深浅模式或更可靠的原生字体合成。
- Tk/AppKit 双窗口同步持续出现无法低风险修复的残影、层级或生命周期问题。
- 用户明确接受新增 Swift/AppKit 工程和双语言构建维护成本。

### 验收标准

原生原型至少应验证：

- 深色和浅色壁纸上均接近系统组件的材质与文字对比度。
- 收起、展开、项目弹层和拖动过程没有双窗口残影。
- 继续使用现有统计口径，真实数据与 Python 版本一致。
- 后台空闲 CPU、内存和登录启动体验不劣于当前版本。
