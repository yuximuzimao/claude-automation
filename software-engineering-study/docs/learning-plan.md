# 第一阶段学习计划

更新时间：2026-11-11  
计划状态：已确认；正式学习尚未开始  
计划窗口：2026-11-10 至 2026-11-30

## 1. 目标与完成标准

第一阶段目标是在预期的 2026 年 12 月 Chat/Codex 额度调整前，建立一套可用于审查 AI 辅助开发方案的软件工程判断框架。

重点能力：
- 从模糊业务描述中发现隐含需求、未说明条件和验收标准。
- 识别业务边界、系统边界、模块职责和接口契约。
- 发现状态转换、数据归属、并发、超时、重试、恢复等设计风险。
- 判断测试是否覆盖关键业务行为、异常路径和模块协作。
- 判断系统是否具备足够的日志、事件、Trace 和运行反馈。
- 识别 AI 实现偏离需求、架构约束或项目约定的情况。

完成标准不是读完五本书，而是能够在新场景中独立提出关键问题、说明风险来源，并判断还需要什么证据。第一阶段不要求掌握编程语言、独立实现大型系统或完整掌握形式化方法。

额度调整日期属于当前计划依据的预期时间，不视为已核实的官方日期。学习节奏以理解质量为先，必要时可以延后或缩减单元。

## 2. 教材阅读顺序

按知识依赖和本地资源可读性，顺序固定为：

1. 《实例化需求：团队如何交付正确的软件》——先学目标、范围、实例和可验证需求。篇幅较短，适合作为入口；扫描样本清晰，但无电子书签。
2. 《软件需求（第3版）》——扩展到完整需求工程，包括业务需求、需求获取、数据、质量属性、确认和变更。篇幅长，扫描略淡，只按重点章节学习。
3. 《软件设计的哲学（第2版）》——从需求进入模块边界、抽象、信息隐藏和复杂度管理。OCR 有错误，术语和引文必须核对原页。
4. Effective Software Testing: A Developer's Guide——学习规格测试、契约、性质测试、可测试性和测试质量。使用英文原版，保留英文术语和原始页码。
5. 《可观测性工程》——学习事件、Trace、SLO 和故障诊断。中文版具体出版版本未确认，第一阶段只用于概念学习，不直接依赖其中可能过时的工具配置。

## 5. 2025–2026 AI Harness 实践的结合方式

传统教材提供相对稳定的软件工程原理；AI Harness 资料用于核对这些原理在 Agent 开发环境中的应用。实践文章是具体工程案例，不自动视为普遍标准。

- OpenAI, Harness engineering（2026-02-11）：Agent 可理解的代码库上下文、架构与文档约束、日志/指标/Trace、静态检查和持续清理。重点结合单元 09。
- Anthropic, Effective harnesses for long-running agents（2025-11-26）：跨上下文窗口的长程任务、环境初始化、进度持久化、增量执行和端到端验证。重点结合单元 09。
- Google Developers, The Anatomy of Harness Engineering（2026-09-09）：行为评估、迭代反馈、护栏和回归判断。重点结合单元 12。

其他贯穿主题：渐进式上下文加载、模块接口契约、架构约束、静态检查、文档与代码一致性、风险驱动测试、知识过期，以及形式化规约的成本收益判断。状态机、数据归属、并发、幂等、超时和故障恢复也会贯穿项目案例，但首批选读章节不保证完整覆盖这些专题；第一阶段先建立识别能力，综合检验发现缺口后再按需补充资料。TLA+ 不列入第一阶段必修。

## 6. 项目案例

- 主要案例：售后自动化与 Status Island。用于讨论需求边界、任务状态、队列、模块职责、接口、异常恢复、资源冲突和运行反馈。
- 辅助案例：QQ 农场自动化。用于讨论状态判断、操作契约、边界用例、测试设计和自动化偏差。
- 案例只用于应用和检验理论，不把某个项目的局部做法直接当成普遍规则，也不在学习过程中擅自修改业务项目。

## 7. 单元教学方法

每个知识单元默认采用两层解释，并根据难度裁剪：

1. 教材原文：先给准确章节、书页/PDF 页和必要原文证据。
2. 小白版：用生活化语言和具体例子说明概念解决什么问题；类比只是解释，不是教材原文。
3. 专业版：使用准确术语，说明核心机制、前提、适用边界和常见误解。
4. 术语对应：整理生活化说法与专业术语的对应关系。
5. 误区与反例：列出容易理解错的地方，以及不适用或会失败的情况。
6. 项目映射：转化为审查 AI 方案时可以提出的问题，并说明哪些属于项目建议。
7. 理解检查：设计三个问题，分别检查概念理解、边界/反例判断和新场景迁移。默认一次问一个，先让用户作答，再反馈理由；不以术语记忆代替理解。

严格区分五类内容：教材原文、AI 解释、推论、项目建议、实际验证。具体规则以 learning-method.md 为准。

## 8. 全书原文预处理与证据处理

原文预处理范围与正式学习范围分开管理：

- 预处理：五本教材全部正式编号章节逐章建立原文缓存；有实质内容的附录、练习答案等列为后续独立单元。
- 正式学习：仍按本计划选定的知识单元推进，不因全部章节已提取而要求全部阅读。
- 原始 PDF 主副本保持不变。逐章处理、独立复核、修订和进度状态，统一遵循 [book-processing-protocol.md](book-processing-protocol.md)。
- Workbuddy / DeepSeekPro 是唯一流水线主控，负责 OCR、章节定位、页码映射、原文稿、单文件复核资料包 PDF、修订和最终文件。
- 千问办公是默认独立复核模型；额度不足时可替换为 Kimi K2.8 或 Kimi 3.1 Pro。替代模型沿用同一份复核提示词和完全相同的报告文件名规则，不改变 DeepSeek 的处理流程。
- DeepSeek 每次处理完一章后，明确告诉用户唯一需要交给复核模型的 PDF 文件名和路径。用户把复核报告直接附加到 DeepSeek 下一次会话，DeepSeek 根据报告文件名中的章节 ID 自动匹配当前待复核章节。
- Workbuddy 与复核模型工作区相互隔离，不假设跨工作区自动联动。用户只负责移动整个交接文件夹、将 DeepSeek 指定的单一 PDF 交给复核模型、再将报告交回 DeepSeek。
- 交接文件夹目前位于 Workbuddy 自己的“杂事”工作区。全部正式章节和已登记补充处理单元完成后，用户将整个文件夹移回 resources/processed-books/教材流水线/；如果用户忘记，Codex 应根据 Todo 在 Workbuddy“杂事”工作区定位并整体迁回。
- Chat 负责教材讲解、推论标注、项目映射和理解检查。正式学习时只读取当前知识单元对应的最终章节文件，不加载整本教材。
- 原文缓存、PDF副本和最终章节只用于个人学习，不提交 Git、不公开分发。必须区分初次 OCR 错误、已修正错误、未解决疑点、图表疑点，以及印刷页码的直接读取和推定。
- 每章必须完成“提取 → 独立复核 → DeepSeek核实修订/确认”闭环，才能登记为已完成。

## 9. 第一阶段结束时的综合检验

使用未在教学中提前讲解的新场景，要求用户能够：
- 补充原始需求中未表达的目标、角色、条件和验收标准。
- 识别系统边界、模块职责和接口前提。
- 主动检查状态转换、重复执行、并发、超时、重试、部分成功和恢复。
- 指出 AI 方案中的假设，并区分哪些已被证据支持、哪些仍需验证。
- 设计能发现关键风险的测试或运行观察点。
- 说明何时需要更多原文、官方资料、项目证据或实际测试。

综合检验不以一次答对所有问题为要求；结果用于确定 12 月之后的后续学习重点。
