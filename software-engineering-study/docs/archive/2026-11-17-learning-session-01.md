## 已学习内容与理解状态

### 2.1 从目标中获取范围

- 用户能将 Status Island 的业务目标概括为「避免多设备操作冲突」。
- 初始实现范围包含设备在线状态、当前任务、下一项任务、倒计时和占用情况。
- 纠正并确认：设备状态可见（A）和互斥任务串行执行（B）都属于软件实现范围；A偏状态监控/信息呈现，B偏任务协调/互斥控制。B虽然直接实现目标，仍不是业务目标本身。
- 进一步明确：界面呈现也可以是实现范围的一部分，不能简单等同于“不是实现能力”；关键是区分软件需要提供的能力与具体 UI 方案。

### 2.2 协作制定需求说明（Collaborative Specification）

- 用户理解到业务人员、开发人员、测试人员和技术专家参与需求制定，可以提前汇集不同专业视角，避免需求在交接和解释中丢失信息，减少交付后返工。
- 说明：四类角色代表四种专业视角，不要求每个需求都机械安排四个人参加。
- 术语：Collective Ownership（集体所有权），指参与者共同理解、参与并认可需求，不是简单平均分配责任。
- 理解检查：通过。

### 2.3 举例说明（Illustrate Requirements）

- 用户以「异常的时候提醒我」为例，识别出自然语言中多个未明确维度：异常的定义、提醒渠道、触发时机、提醒内容、提醒后是否继续或重试。
- 用户进一步用售后自动化实例说明：商责工单可创建1分钟后的 Mac 提醒并等待人工处理；平台注入失效则立即弹出独立窗口并禁止重试。具体实例可以把处理边界和预期行为明确下来。
- 用户也识别了需求示例与关键实例的区别：仅附上参考图片或普通例子不一定消除歧义；例子需要表达预期结果和必要边界。
- 补充纠正：Key Examples（关键实例）不只包含异常边界，也包括正常情况下软件应如何工作的实例。
- 理解检查：通过。

### 2.4 提炼需求说明（Refine the Specification）

- 用户能区分必要的信息需求与具体界面实现方案：订单金额、物流信息、售后原因、AI 预处理结果属于业务判断所需的信息要求；侧边栏或独立页面属于可讨论的 UI 方案。
- 进一步明确：开发人员可以提出信息是否必要的质疑和替代方案，但不能在不了解业务依据时自行删掉用户提出的信息要求。若金额较大代表更高业务风险，这个理由需要在协作中说明并共同确认。
- 用户理解到从实际使用场景出发描述需求是有效起点；需要训练的是从场景中区分业务目标、业务约束、信息需求、软件能力和实现细节，而不是放弃场景描述。
- 本次补充了一个教学分析框架：Business Goal（业务目标：希望得到什么结果）、Business Rule（业务规则：业务判断条件与约束）、Scope（实现范围：软件要提供什么能力）、Technical Implementation（技术实现：具体如何实现）。这是辅助分析框架，不应误称为本章作者明确列出的四层分类。
- 复杂场景迁移检查尚未进行。用户希望暂缓公式化简单案例；计划在第5章「从目标中获取范围」学习时再做综合训练。

## 本次确认的教学方法

用户确认采用「先讲解，再回读原文」：

1. 原文定位：先说明教材、章节、小节、PDF页码和书籍印刷页码。
2. 术语定位：保留关键英文原词及中文译名；必要时给出简短原文片段，再按原文解释。
3. 先行讲解：教师先用小白版和专业版解释概念、机制、前提和边界，明确区分教材原文、解释、推论与项目建议。
4. 回读原文：用户在讲解后阅读对应教材原文；讲解不能替代原文。
5. 理解检查：默认一次提出一个开放问题，让用户用自己的语言回答，再纠错和补充；不提前给标准答案。
6. 案例训练：优先使用贴近售后自动化、Status Island 等真实项目的案例。需要检验迁移能力时，使用有竞争条件、易混淆的复杂案例，不用简单 A/B 选择题代替理解检查；如果后续章节会系统讲授该能力，则标记并留到对应章节，不提前重复训练。
