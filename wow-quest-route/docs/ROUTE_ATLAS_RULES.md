# Route Atlas 总规则

状态：长期权威规则。本文只保存跨会话、跨地图、跨批次仍应遵守的方法与产品约束；地图特定状态、某批角色经验、R快照、局部路线尝试和一次性异常必须放在对应CURRENT、NEAT或日期化分析文档中。

发生冲突时，永久方法以本文为准；具体当前状态以`docs/verified-routes/CURRENT.md`为准；某地图已验收的局部事实仍以该地图任务知识、实跑记录和最新Questie/用户现场证据为准。

## 1. 产品分层与职责

Route Atlas不是单纯的路线图片，也不是Questie的替代品。长期分层固定为：

`Questie Raw（不可改写） → Questie Effective/派生事实 → 单任务知识节点 + typed relations + numeric features → 路线版本/路线节点 → HTML执行工作台`

- Questie Raw保存插件原始事实，实跑观察不得回写覆盖。
- 单任务知识节点保存与某条具体路线无关的可复用知识。
- 路线节点保存“这次为什么把该任务放在这里、与谁合并、产生多少边际移动/服务成本”等版本特定信息。
- HTML是当前唯一主前端。地图承担宏观走向，Questie继续承担游戏内精确目标定位，任务知识卡承担需要额外记忆和解释的信息。

## 2. 任务知识不是操作备注

每个任务知识节点应能够关联或保留：

- Questie派生事实；
- typed facts；
- typed relations；
- numeric features；
- 稳定的人类可读标签；
- Target Cluster与必要时的Spatial Instance；
- 五开机制、地形、特殊操作、掉落与等待风险；
- 任务物品的可交易性与拍卖行可购买性；这两项使用`true / false / unknown`三态并保存实跑验证来源，未知不得自行推断；
- 对掉落物必须记录真实五开拾取机制：若一次击杀后同一尸体可供五号分别取得同一任务物，则期望击杀次数不得机械乘五；只有每件物品实际消耗一次独立掉落机会时才按五号总需求累计；
- source / confidence；
- 实跑observation与历史纠错。

稳定标签用于解释，不替代底层事实。常用家族包括`scope:*`、`objective:*`、`chain:*`、`trip:*`、`terrain:*`、`route:*`。机器关系至少支持`precedes`、`same_accept_npc`、`same_turnin_npc`、`same_direct/resolved_creature`、`same_direct/resolved_object`、`same_required_item`、`spatial_overlap`、`same_chain`、`same_excursion_block`等。

Questie已经直接显示的普通等级、经验、基础坐标、基础目标默认不占前端卡片版面，但后台数据不得因此删除。

## 3. 从零复用主路线与当前执行路线必须分离

永久保留两类路线：

1. **从零复用主路线**：面向下一批从该地图正常起步的角色，必须包含本批已经做过但下一批仍需要的任务。
2. **当前执行路线**：只服务当前角色的真实任务状态，可删去已完成任务、改变起点、局部重排和重新选择炉石节点。

当前角色完成某任务时：

- 只从当前执行路线删除相应执行动作；
- 不从从零复用主路线、任务知识节点、任务宇宙、关系库或历史快照删除；
- 删除后必须重新检查剩余目标的几何关系、前置链、Hub停靠和炉石收益，不能只是把原路线节点挖空后机械连接前后两点。

当前路线的起点不必等于从零路线起点。应以“当前状态下最低剩余总成本”为准选择可执行起点。

## 4. 当前状态与证据新鲜度

回答“现在还要做什么”时必须优先使用最新状态，不能让旧缓存覆盖新证据。默认优先级：

1. 用户在当前会话明确给出的现场状态、等级、经验和异常行为；
2. 当前客户端最新Questie人物历程/现场可接状态；
3. 项目中最近一次明确标记为当前的结构化状态；
4. 较旧的脱敏人物缓存、历史CURRENT、旧路线版本；
5. 通用数据库和历史资料只用于补任务结构，不能覆盖当前时光服实况。

Questie历程能证明接取、完成/交付、放弃、等级和时间戳；不能证明死亡、真实移动路线、找怪耗时、暂停原因或目标进度细节。

任务“当前是否可接”不得只看任务前置和等级。Questie WotLK compact quest DB 的`requiredMinRep`（字段19）与`requiredMaxRep`（字段20）属于硬可用性约束，`reputationReward`（字段26）属于状态转移；路线事实层必须保留这些字段。最低声望采用`current_rep >= requiredMinRep`，最高声望采用`current_rep < requiredMaxRep`。声望状态尚未进入路线状态机时，带声望约束的任务不得静默进入自动优化器，只能作为受约束任务等待状态解析。

## 5. 异常顺路行为只更新状态，不自动学习成路线

玩家可能因为学技能、买物品、处理现实事务、测试机制等原因临时跨图，并顺手完成或接取任务。

这类事件：

- 完成/接取结果必须进入当前状态真值；
- 临时绕路本身不得自动写进从零复用路线；
- 只有当独立成本分析或后续多轮实跑证明该绕路本身更优时，才可升级为长期路线规则。

即“结果影响剪枝，原因不自动成为路线证据”。

## 6. Target Cluster、Spatial Instance与Background Layer

- 完全相同的真实目标实体优先形成Target Cluster。
- Questie刷新点或静态坐标不能直接代表真实可走的一次服务区域。
- 必须人工结合道路、桥梁、洞穴、地形和实跑，把目标簇解析为真实Spatial Instance。
- 广域累计、沿途杀怪、背景拾取、低掉率自然触发等任务应进入Background Layer。
- Background Layer跟随主体路线完成；主体路线不得为了背景任务反向绕路，除非边际成本经过单独验证后确实值得。

## 7. 路线构建的长期方法

当前冻结的方法改为“候选生成 + 逐约束门控 + 只在可行候选中比成本”，不得再让模型一次性凭上下文直接决定插入位置。

基础流程：

1. 建立Questie/人工事实层；
2. 形成Target Cluster；
3. 建Prerequisite / Availability Network；
4. 人工解析Spatial Instance；
5. 分离Background Layer；
6. 以当前真实玩家状态建立路线State；
7. 对待插入任务/任务簇枚举受影响窗口内的候选位置；
8. 每个候选必须逐项通过全部Hard Validator；任一失败立即淘汰并记录失败原因，不进入成本比较；
9. 只有全部Hard Validator通过的候选才计算时间成本、折返、未来遗憾和炉石收益，并选成本最优者；
10. 选中的候选插入后重新计算受影响窗口内的状态，再进入下一个任务/任务簇；
11. 已验收旧路线默认冻结，只重新打开受影响窗口；但若新增硬约束使窗口边界后的状态也失效，窗口必须向后扩张，直到重新达到稳定状态；
12. 不同Target Cluster默认没有先后关系，只有显式前置、Availability约束或真实成本证据才建立顺序。

### 7.1 Hard Validator固定清单

每个候选插入位置必须至少独立检查以下条件；不能把多项检查压成一段自然语言推理：

1. `player_state`：当前位置、当前等级/经验区间、已接/已完成/未见任务状态是否与候选动作一致；已接任务不得再次A，已完成任务不得再次C/T。
2. `quest_prerequisite`：preQuestGroup / preQuestSingle / parent / chain等任务前置是否满足。
3. `availability`：等级、requiredMinRep、requiredMaxRep、职业/种族/技能/法术及其他Questie可用性条件是否满足；声望变化必须作为状态转移传播到后续候选。
4. `objective_ready`：执行C时任务必须已接且目标尚未完成；执行T时所有目标必须完成。
5. `xp_deadline`：计划T(Q)时最高/最快号不得超过`last_full_xp_level`；若超过则候选硬失败。
6. `transport`：炉石绑定地点、冷却、飞行点是否已开启、交通动作是否真实可用；不得把旧版本炉石位置当作既定阶段边界。
7. `branch_state`：条件任务/声望分支/机会任务必须以当前状态裁成真实分支；不可执行分支不得继续以死节点留在线性路线中。
8. `fivebox_mechanic`：共享击杀、同尸体多人拾取、可交易物品、个人拾取/个人交互等五开机制必须与服务时间和动作数量一致。
9. `spatial_service`：目标区域必须至少能定位到正确的宏观Spatial Instance。若宏观区域已知、只是区域内部“怎么绕一圈/从哪个入口刷/局部采集圈怎么走”未知，可标记为`MANUAL_SPATIAL_REVIEW`并把目标点云、候选入口和任务说明放进HTML，由用户看地图决定局部刷法；这种情况不得伪造为0秒背景服务或宣称局部最优。若连宏观服务区域都不确定并会影响任务插入到哪一段，则仍视为未解决UNKNOWN。
10. `background_capacity`：背景杀怪/拾取只有在预计沿主体路线的覆盖量足以满足需求时才能继续作为Background Layer，否则必须转成显式服务段。
11. `no_dead_step`：候选插入后不得产生已经完成、条件必定为假、或被更早步骤覆盖后的无动作停靠点。
12. `state_continuity`：不要求插入后的RouteState与旧冻结边界完全相等。必须从候选插入点向后逐动作重放冻结后缀，验证每个后续动作在新的任务/声望/经验/炉石/库存状态下仍合法；若某动作失效，说明受影响窗口必须扩大，而不是强行把状态接回旧值。

Hard Validator返回值固定为`PASS / FAIL(reason) / UNKNOWN(reason)`，但UNKNOWN必须按来源单独处理，不能统一静默通过或统一永久删除：

- 可通过公开数据库、官方/可靠网页或项目已有资料验证的事实：先主动查询，查询完成后重新判定；
- 五开拾取、跟随、共享尸体、多人交互等只能由实际客户端/多开机制证明的事实：直接向用户提出具体问题，由用户给决策；
- 宏观区域已知、仅局部执行几何未知：转成`MANUAL_SPATIAL_REVIEW`，允许任务保留在宏观路线中，并在HTML显式展示供用户现场决定局部刷法；
- 其它仍无法消解且会影响路线合法性或宏观排序的UNKNOWN：保留为未解决候选，不得发布成已验证执行路线。

`FAIL`只否决“当前状态下任务Q放在位置P”这一候选，不永久删除任务Q；如果之后状态发生变化，相关任务必须重新进入候选检查。

### 7.2 可行候选之间才允许比较成本

当且仅当候选通过全部Hard Validator后，才比较：

`added_wall_clock → extra_travel → service_time → forced_wait → backtrack → xp_deadline_slack → future_route_regret → hearth_opportunity → stable_id`

其中前五项直接反映当前墙钟成本；后续项用于在近似同成本候选间减少未来返工。`future_route_regret`必须包含**跨地图终点成本**：当当前地图接近收尾且下一张地图/跨图breadcrumb已知时，不能只优化“本图最后一个任务怎么交最快”，还要比较最终停靠点到下一地图入口、首个任务中心或必须交付breadcrumb的真实增量墙钟。若为了交一个可提前处理的清理任务把角色从下一地图方向拉回反向Hub，应优先尝试把该清理任务前移，使当前地图最终停靠点自然朝下一地图出图。对于“已接取任务 + 已完成全部目标”的READY任务，必须从其READY时点开始向后扫描后续自然Hub/任务走廊，优先寻找零增量交付或最小增量插点；不得因为历史版本把T动作放在“最终收尾”就继续冻结到最后。若另一个已接任务可在同一窗口顺路完成，应对该窗口各合法边枚举插入增量后再决定位置。禁止用加权总分让一个硬约束失败被其它优点“抵消”。

### 7.3 每次插入必须保留验收轨迹

每个最终采用的插入至少保存：

- 枚举过哪些候选位置；
- 每个被淘汰候选失败在哪个Validator；
- 所有PASS候选的主要成本；
- 最终为什么选中当前位置；
- 插入后受影响窗口是否扩大。

这样以后出现实跑错误时，可以定位到“事实层错误 / Validator漏项 / Validator实现错误 / 成本排序错误”，而不是重新依赖模型回忆当时为什么这样排。

### 7.4 声望不足任务库与阈值触发重试

所有因`requiredMinRep`不足而暂时不可接的任务，不删除，进入按`(faction_id, required_value, stable_id)`排序的“声望不足任务库”。每个阵营至少维护：当前声望、下一最低门槛、该门槛对应的待解锁任务。

每次RouteState发生该阵营声望变化时固定执行：

1. 先记录`rep_before → rep_after`；
2. 在应用声望增加前，检查是否会跨过某个`requiredMaxRep`上限，避免尚未接取的低声望任务被无意永久关闭；
3. 应用声望变化；
4. 检查声望不足任务库中的**当前最低门槛**；若`rep_after`达到/跨过该值，只激活这个门槛上刚解锁的任务；
5. 即使同一门槛同时解锁多个任务，也按稳定顺序一个一个抽出，每次只处理一个任务的候选插入、Validator、成本比较和状态重放；一个任务稳定后再处理同门槛下一个；
6. 当前最低门槛的任务全部处理完后，才显示下一最低门槛；未达到的更高门槛不提前参与路线排序；
7. 任何新插入任务如果再次改变声望，立即递归触发同一流程，而不是等整批任务插完后统一补算。
8. Questie compact quest DB field 24 `specialFlags`的bit 1必须作为Repeatable真值；状态机仍要记录`turnin_count`，避免把重复任务误记成一次性completed。但当前项目目标是练级效率：**重复任务完成第一轮后不再生成第二轮候选**；若某个任务本身就是无经验的重复后续（例如赞加9727《既然我们仍是朋友......》），默认不接。只有用户明确切换到声望/物品等非练级目标，或该重复动作是有经验任务的硬前置时，才允许单独例外。
9. 因此声望不足阶段默认只比较“仍有经验/必要前置价值的一次性任务”“自然击杀产生的声望”“其它不会牺牲练级效率的状态变化”；不得为了凑声望主动安排零经验重复交付。若自然刷怪分支已经被实跑证明能在某个节点解锁下一任务，可先把该节点作为实跑门槛证据；使用拍卖行/交易替代刷怪时必须重新验证，因为会失去沿途击杀声望。

因此“一个一个插”在声望场景下是事件驱动的：某个任务此前因声望不足失败，只是当前候选失败；一旦状态达到它的最低门槛，就把它从声望不足库单独抽出来重新寻找最佳位置。

“一个一个插”指路线构建与可审计快照粒度，不意味着每插一个任务就做一次全图动态图审查。

## 8. 删除已完成任务后的恢复流程

当根据最新历程裁当前路线时，固定流程为：

1. 识别任务状态：completed / active / unseen / conditional；
2. 从当前执行动作中移除completed任务；
3. 检查active任务是否仍需C/T，以及unseen后续是否由剩余路线正常解锁；
4. 对因为删除节点而改变的局部区域重新排列，不机械保留旧顺序；
5. 检查原本隐藏在已完成任务之后的关键前置是否仍会及时接取；
6. 重新评估起点、Hub停靠、炉石落点和条件分支；
7. 完成整张当前路线恢复后再看动态图全局异常；
8. 当前裁剪结果另存，不覆盖从零复用主路线。

## 9. 炉石与时间成本

炉石是独立可重算的路线资源，不是固定“一图一次”：

- 每次局部稳定后都应重新评估；
- 只要冷却与收益成立，可以0次、1次或多次；
- 不为等待炉石冷却而停工；
- 炉石节点必须明确绑定地点和使用目的；当前客户端实跑口径下，炉石本身还必须计入约10秒施法/交互墙钟，不能把回城边当作0秒瞬移。
- 炉石收益不能只比较“当前位置→Hub”的纯移动时间。若不炉石的自然回城路径能够顺路完成后续本来还需要专程外出的任务、抽水泵/场景交互、背景击杀或机会事件，必须用“当前继续走完这些生产性动作并回Hub”对比“现在炉石 + 以后从Hub再次外出完成这些动作”的完整增量墙钟。只有后者更低才使用炉石；禁止为了眼前回城更快而制造未来往返。
- 地图平面距离不能默认按陆地坐骑速度折算。只要候选边穿过大面积水域、需要游泳、绕岸或存在明显不可骑乘地形，就必须切换到对应移动模式/实跑耗时代理；特别是“任务目标在水里、完成后继续沿水面回Hub”的边，不能因为直线距离短就判定骑回优于炉石。若用户实跑已确认某条水路显著慢于陆路，后续该局部边以实跑事实覆盖平面距离模型。多个目标即使属于同一任务，也不得因为“同任务”就默认连续执行：若两个目标之间需要重复出水/进水、绕岸或跨移动模式，必须比较“连续串联”与“拆到后续自然经过”的真实墙钟；已验证的水域服务包可以绑定执行，但包结束后应优先退出低速移动模式，除非下一个目标确实在同一连续水域且无需额外出入水成本。
- 炉石不是已经冻结的路线起点/阶段边界，而是可移动的交通资源。后续新增任务或实跑信息影响某个炉石附近时，冻结该候选窗口之前的前缀，只重新打开“受影响任务簇 + 炉石 + 其后的局部后缀”；先临时移除炉石边，比较不使用炉石时后段如何自然排列，再按冷却和收益把炉石重新插入最佳回城边。不得因为旧版本曾在某处使用炉石，就强迫下一段继续从该处开始或重排整张地图。
- 若新增/修正的真实服务时间可能使炉石冷却跨过30分钟阈值，必须重新扫描该局部后缀的炉石机会；此前炉石位置不具有锁定权。
- 新地图不得默认先专程跑完整张地图开飞行点/绑定炉石。必须比较两种交通初始化方案：A. 专门预跑飞行点并提前绑定炉石；B. 沿主体任务路线首次自然经过时再开点/绑定。只有A的额外初始化墙钟能够被后续少跑的骑行/回程明确覆盖时才采用A；否则默认B。飞行点本身在第一次自然经过时必须顺手开启，不允许后续为漏开的飞行点专程返工。

总成本长期按以下结构理解：

`T_total = T_travel + T_objective_service + T_accept_turnin + T_forced_wait + T_other_known_cost`

角色移动速度变化只作用于真实受该效果影响的纯移动段。坐骑光环、骑术或装备加速不得乘到护送、脚本飞行、战斗、拾取、交互、炉石和等待时间上。具体速度数值属于当前角色参数，不是永久常量。

### 9.1 任务满经验交付截止必须进入Route Atlas硬审计

- WotLK口径固定为`last_full_xp_level = quest_level + 5`，该值必须物化到每个一次性任务知识节点，而不是只存在于外部规则文档。
- 每个`T(Q)`交付节点至少保存/计算：`predicted_level_before_turnin`、`predicted_xp_before_turnin`、`predicted_reward_at_level`、`predicted_level_after_turnin`、`predicted_xp_after_turnin`、`last_full_xp_level`。
- 保证“经验一定够”仍使用最低号下界账；保证“任何一个号不会把低级任务交进衰减区”使用最高/最快号的累计上界账。两套账不得混用。
- 最终路线复审时，只要任一计划交付节点出现`predicted_level_before_turnin > last_full_xp_level`，即判定该路线需要调整；不得因为该交付与现有Hub同点、零新增移动就继续后置。
- 修正时只重新打开能把该任务提前兑现的最小相关窗口，优先调整同地图局部顺序/Hub交付，再考虑跨地图穿插，避免为了经验截止无必要地洗牌整张地图。

## 10. 精确优化器的定位

PC-SP、state-space DP / labeling、MILP、Branch-and-Cut、CP-SAT、flexible service location、shared-service/covering等模型保留为：

- 理论母模型；
- 局部插入成本估计；
- 顺序枚举；
- 异常检测；
- 与人工路线对照。

它们不直接替代玩家路线。只有模型边界、地形、服务位置和状态约束都足够准确且求解器证明optimal时，才允许称“理论全局最优”。

## 11. 动态整图审查的固定时机

动态图是固定验收流程，但执行时机为：

- 先完成整张地图的任务插入或当前状态恢复；
- 再生成/播放全图动态路线；
- 检查大范围反向折返、异常跨图、炉石落点、阶段切换和局部顺序；
- 发现异常后回到对应局部修正。

不得在每插一个任务后都做整图动态图审查。前端可直接建立在这份动态HTML之上。

## 12. HTML前端长期约束

当前稳定交互与视觉约束：

- 地图全宽置顶；地图左上角使用固定宽度、内容高度自适应且可收起的当前任务预览框；任务知识卡放在地图下方，完整步骤列表更下方。
- 当前任务预览框统一承载：目标停靠点、到达该点的移动/炉石坐标、到达后的动作汇总、再下一站，以及本停靠点内所有真正有执行帮助的任务备注；若本步没有有效备注，则不显示备注区。
- 前端语义固定为“停靠点动作”：地图上的当前点是本段最终要到达的目标点，预览框显示到达这个点之后要做什么；连线只回答“从上一个停靠点怎样到这里”，不得把起点动作挂在向下一目标移动的长连线上。原地脚本、接取、交付等没有开放世界位移的动作继续归属于当前停靠点。
- “任务备注/攻略”只允许写能直接帮助玩家完成任务的机制、操作、条件、等待/不等待等信息。路线为什么合并、为什么绕行、为什么裁剪等设计因素必须放在“当前路线为什么这样排”，不得污染攻略备注。
- 页面避免重复展示同一当前步骤信息；坐标与当前步骤合并进入地图预览框，不再另设重复的地图标题栏。
- 当前执行页默认不展示角色经验对比；右上角版本信息只保留执行所需的路线总起点、当前炉石绑定等少量状态，除非用户明确要求扩展。
- 播放控制至少区分“只播放当前段”和“播放完整剩余路线”；点击上一段/下一段后自动播放一次所选当前段。
- 玩家步骤以中文任务名和“接/做/交”语义显示，任务ID只作为内部键。任何`A1234 / C1234 / T1234`式内部动作记号、裸任务ID、或“编号代替任务名”的文本都禁止进入标题、步骤、HUD动作、备注、图例、页脚等用户可见内容。
- **HTML发布门禁**：每次新建或修改执行HTML后，必须对所有用户可见路线字符串做任务ID泄漏扫描。只要发现内部`A/C/T + quest_id`或已知任务ID仍出现在可见文本中，该HTML即视为未验收，不得登记为当前执行稿；必须替换为“接/完成/交《中文任务名》”后重新检查。
- 多任务步骤可点击任务名切换知识卡。
- 标记为`MANUAL_SPATIAL_REVIEW`的任务必须在HTML显示其可用目标点/区域边界、当前宏观进入方向和“局部刷法待现场决定”提示；不得为了让动画完整而虚构一条局部最优折线。用户给出实际刷法后再把该Spatial Instance升级为verified。
- 知识卡优先显示稳定标签、关系、Target Cluster/Spatial Instance、当前路线编排理由和可审计数值特征；执行备注优先汇总到地图预览框，不在知识卡重复展示。
- Questie普通基础字段默认隐藏但后台保留。
- 地图底图以“几何一致前提下的清晰度”优先，不再为了内嵌中文地名退回低分辨率图片。替换底图前必须配准到既有0–100坐标框架；只有边界/比例/锚点通过后才能切换，避免路线坐标随图片来源漂移。
- 高清底图若没有中文地名，中文只作为独立HTML/SVG提示层叠加：使用小号、低干扰、可开关的参考标签，不烘焙进底图，也不作为路线坐标真值。跟随/裁剪改变SVG `viewBox`时，标签必须同步到当前视窗；中文提示效果不理想时优先保留高清底图。可靠的经典旧世界/TBC区域本地化统一生成到`data/routes/maps/labels-zhcn.json`（`scripts/build_route_map_labels.py`），后续生成器按`zone_id`通过`lib/route_map_assets.py`读取；没有可靠zhCN区域数据的地图允许只使用高清英文底图，不得机器直译后冒充客户端真值。
- 可携带执行版采用固定目录契约：HTML统一位于`data/routes/`，所有地图底图统一缓存于同级`data/routes/maps/`，HTML只能通过`maps/<地图文件>`引用底图，不得依赖`../route-atlas/`、Python、manifest、网络请求或项目其他目录。玩家迁移到游戏电脑时只需完整复制HTML及同级`maps/`目录即可离线运行；中文地名等运行时所需数据必须在生成HTML时内嵌，不能要求目标电脑再读取项目JSON。将来合并为单一全地图HTML时继续复用同一`maps/`资源池。
- `data/routes/maps/`应一次性缓存当前任务宇宙覆盖的全部地图，而不是每生成一张攻略再临时下载。地图文件以`<zone_id>-<slug>.<ext>`稳定命名，并保留`manifest.json`记录来源与缺失/回退情况；普通本地化底图批量刷新由`scripts/download_route_map_assets.py`负责且不得清除既有`hd_*`元数据，存在经过配准/源完整性验收的高清源时由`scripts/build_hd_route_maps.py`生成HD变体并在manifest中记录来源、尺寸、拼接方法与验证模式。`lib/route_map_assets.py`仅允许在项目机器的“生成阶段”按`zone_id`解析应写入HTML的静态相对路径；最终HTML必须直接写成`maps/<实际文件名>`，不得在浏览器运行时调用该模块或读取manifest。默认优先`hd_file`，只有manifest明确回退时才把普通本地化底图的相对路径写入HTML。
- 路线箭头视觉冻结：普通线宽`1.25`，当前段`3.0`，炉石普通`1.8`、当前炉石`3.4`，箭头marker `5×5`，使用`markerUnits="strokeWidth"`和`vector-effect="non-scaling-stroke"`。

除非用户明确要求改变视觉系统，否则后续版本不得无理由漂移这些参数。

## 13. 永久规则与阶段文档的边界

应写入本文的内容：跨地图、跨批次仍然成立的方法、证据优先级、数据分层、恢复流程、前端长期契约。

只写入日期化NEAT/analysis/version文档的内容：

- 某地图R1–Rn快照；
- 某批角色等级/经验；
- 某次Questie哈希与任务状态集合；
- 某次临时跨图行为；
- 地图特定条件任务、掉率、局部顺序和炉石次数；
- 当前尚在验证的假设或优化实验；
- 理论模型某次求解结果。

阶段性结论只有在被明确提升为长期规则时，才迁入本文；迁入后，日期文档保留形成过程与证据，不再作为永久规则的唯一入口。
