# 人工核验任务库

这个目录保存已经为实际五开路线逐任务核验过的事实。它不是自动候选表，也不是按任务类型批量生成的评分表。

## 单任务卡片必须包含

1. 任务完整名称和ID。
2. 当前版本的任务等级、最低接取等级、完整前置和直接后续。
3. 接取、目标和交付位置；洞穴入口、楼层、山路、护送路线等新手容易出错的信息必须单列。
4. 预计执行时角色等级、交付时实际任务经验、目标怪常见等级，以及等级差是否适合五个当前职业角色。
5. 每个目标的真实数量；五开时是共享击杀、五号累计普通任务物、个人独立判定、固定物逐号点击还是一次事件全队完成。
6. 随机掉落至少记录数据库参考概率和公开玩家实跑反馈；两者冲突时保留冲突，不能只取看起来更好看的数字。
7. 与当前路线其他任务的真实重叠：同一批怪、同一洞穴、同一条山路、同一交付点分别写清，不能只写“顺路”。
8. 当前结论只能是：必做、条件做、自然获得才做、跳过、尚未核验。结论必须限定角色等级和路线上下文。
9. 证据来源、核验日期和置信度。用户当前服务器实测永远覆盖数据库和公开攻略。

## 更新规则

- 设计路线前先查本库；卡片存在且适用等级、版本、队伍和路线上下文没有变化时直接复用，不重复计算。
- 卡片不存在、适用条件变化或来源互相冲突时，才对该任务重新核验。
- 实服发现错误时，当场修改卡片中的当前有效事实，同时把旧值、修正值、原因和日期追加到`data/observations/task-efficiency-corrections.json`；不能为了保留历史而让错误继续留在当前字段。
- 自动脚本最多检查字段缺失、任务ID格式和前后矛盾，不能自动决定任务是否值得做。

## 发布前对抗式复审

攻略成稿后，复审者必须暂时摒弃写稿时的路线理由，从玩家当前点重新阅读一次，并主动尝试推翻以下假设：

- 这个任务现在真的能接吗？
- 交任务时经验是否已经衰减？
- 目标怪等级、密度和五开战斗是否合适？
- 所谓共享、个人掉落和固定物机制是否有证据？
- 所谓“顺路”是否真的不产生折返、额外上山或重复进洞？
- 新手只看正文能否找到入口、楼层和交付NPC？
- 任一任务失败、未掉落或被删后，路线是否仍能自然接到下一段并闭合到55？

发现任一问题，先改任务卡片的当前有效事实，再改攻略正文，最后从问题点重新向后复审。
