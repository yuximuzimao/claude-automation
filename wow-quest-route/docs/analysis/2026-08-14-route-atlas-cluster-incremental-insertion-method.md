# Route Atlas：目标簇驱动的增量插入式路线构建方法

日期：2026-08-14
状态：方法论冻结 v1
适用范围：赞加沼泽 Route Atlas 第一版，以及后续同类地图的人工可审计路线构建

## 0. 为什么重构方法

前一版路线的问题并不主要来自任务目标坐标。Questie 的 NPC、任务怪、物品、调查点和人工核验的特殊机制入口，大部分坐标本身是可信的；真正的问题在于“点位动作”的生成逻辑过于线性：一旦任务进入 Ready，就倾向立即执行对应 Objective/Service，导致同一批怪被不同任务重复访问、同一片区域被提前清空、任务链与目标重叠关系没有被充分利用。

因此，Route Atlas 后续不再以“任务 A/C/T 动作按全局算法一次性求序”为核心，而改为：

1. 先构建任务目标关系；
2. 再构建目标簇；
3. 再构建前置网；
4. 再把目标簇落实到真实空间实例；
5. 最后使用增量插入法逐簇构造路线。

路线不是一次性求出来，而是逐层人工可审计地收敛。

---

## 1. 基础事实层

每个任务先只保存事实，不提前生成路线动作。

任务对象至少包含：

- quest_id
- 任务名
- 当前玩家状态：未接 / 已接未做 / 已完成
- 直接前置：preQuestSingle / preQuestGroup
- 任务目标实体：NPC / creature / item source NPC / object / trigger / manual mechanism point
- 每个目标的真实坐标或真实点云
- 特殊机制人工覆盖

本层只回答：

> 这个任务是什么？它要求什么？这些东西实际在哪里？

不回答：

> 现在是不是应该做？应该先去哪？

---

## 2. 目标簇（Target Cluster）

### 2.1 第一轮目标簇定义

第一轮只看“完全相同的实际任务怪”。

如果多个任务引用同一个实际 creature/entity ID，则它们之间建立共享目标关系。

例如：

- 孢子之翼：9806 / 9807 / 9899
- 沼泽之鞭：9806 / 9807 / 9895
- 枯萎的巨人：9743 / 9744 / 9772
- 血鳞女巫、血鳞驱奴者：9726 / 9727 / 9728
- 大头目格罗阿克：9708 / 9820
- 安葛洛什殴斗者、食魂者、戈尔费斯：9709 / 9823

这一层暂时不考虑：

- 前置；
- 距离；
- 路线；
- 是否当前可接；
- 是否值得等待；
- 是否任务链；
- 是否掉落共享。

目标簇是最底层的任务聚合事实。

### 2.2 目标簇不是地图点

目标簇是“语义簇”，不是天然的单一地理节点。

同一任务怪类型可能分布很广，因此目标簇可能拥有多个真实空间实例。

例如巨人簇至少拆成：

- 东北死亡泥潭实例；
- 西南孢殖林实例。

成熟孢子基础簇甚至可以是全图背景层，不应伪造一个中心点。

因此必须区分：

`Target Cluster（目标簇）`

和

`Spatial Instance（目标簇空间实例）`

---

## 3. 前置网（Prerequisite Network）

### 3.1 只使用真实前置语义

Questie：

- preQuestSingle = OR
- preQuestGroup = AND

不得再次把两者混淆。

### 3.2 逐层向上展开

构建方式：

1. 先给每个任务标一轮直接前置；
2. 再检查这些前置自身是否还有前置；
3. 逐层向上直到根；
4. 每轮都保留原始任务 ID 和前置语义。

不需要一次性把所有祖先链写成一个长字段；前置关系本身组成 DAG/网。

### 3.3 用目标簇替代可被目标簇吸收的前置任务节点

如果任务 X 是任务 Y 的直接前置，而 X 已属于一个或多个目标簇，则主体结构中优先表示为：

`目标簇(X) → Y`

而不是只写：

`X → Y`

如果 X 同时属于多个目标簇，则保留多个关联，不在这一层判断哪个空间实例才是实际完成 X 的最佳来源。

### 3.4 三种重要结构

#### 自环

如果同一个目标簇内部存在任务前后代：

`簇内任务 A → 簇内任务 B`

则形成目标簇“自环语义”。

它不表示地图上真的绕圈，而表示：

> 同一批怪承担连续两代任务。

典型：

- 9726 → 9727，且两者共享血鳞女巫/驱奴者；
- 9743 → 9744，且共享多类巨人；
- 9806 → 9807，且共享大量孢子怪。

这是后续动作层最重要的“不要过早刷完”信号。

#### 汇聚

不同任务链汇入同一目标簇。

例如安葛洛什终局簇同时受到：

- 9708 → 9709；
- 9820 → 9822 → 9823。

#### 跨簇解锁

某目标簇中的任务完成后，会解锁另一个目标簇中的任务。

例如：

- 泥爪毁坏者簇中的 9845 → 穆拉格什簇中的 9903。

## 4. 空间实例层

### 4.1 不允许自动质心代替真实地图判断

剩余任务目标的空间归位必须逐个查看：

- Questie 实际坐标/点云；
- 地图实际区域；
- 是否同一个营地；
- 是否同一湖区；
- 是否同一条进出路径；
- 是否属于同一个局部 excursion。

禁止用：

- 最近邻自动归类；
- 固定距离阈值；
- 点云质心；
- bbox 中心；

直接代替人工判断。

这些计算可以作为参考，但不能作为最终归类依据。

### 4.2 可以出现三种空间对象

#### 强空间实例

明确属于同一局部区域，应一次处理。

例如东南：

- 9788《阴冷之地》
- 9894《保护观察者》
- 10096《拯救孢子人》

#### 目标簇空间实例

同一个语义目标簇在不同地图区域的局部实例。

例如巨人核心簇：

- 东北死亡泥潭；
- 西南孢殖林。

#### 背景层

目标分布太广，不允许成为独立路线中心。

例如：

- 9770 沼牙撕裂者；
- 9808/9809 亮顶蘑菇；
- 9806/9807 的广域孢子怪；
- 9773 暗泽鳗鱼；
- 9842 的广域沼牙切割者。

背景任务必须跟随主体路线自然累计，不能反过来驱动主体路线。

## 5. 最核心的逻辑前提：不同目标簇默认无先后

这是路线构建的关键逻辑约束。

### 5.1 目标簇编号不是顺序

“目标簇 1 / 目标簇 2 / 目标簇 3”只是为了引用和讨论。

不能推出：

`簇1完成 → 才能做簇2`

也不能因为空间骨架把簇2画在簇1后面，就把它们变成强制任务顺序。

### 5.2 不同目标簇默认独立

如果两个目标簇之间没有真实前置边，则它们之间没有逻辑先后。

因此：

> 第二个目标簇的接任务动作完全可以插入第一个目标簇路线的前半段；
> 第二个目标簇的做任务动作也可以穿插在第一个目标簇多个动作之间；
> 只要前置满足、空间合理、插入后更优即可。

### 5.3 唯一例外：显式前置关系

如果 Questie/人工核验明确存在跨簇前置：

`簇 A 中任务 X → 簇 B 中任务 Y`

则这一条边构成真实先后约束。

所以更严格地说：

> 不同目标簇之间默认无顺序；只有显式前置边才建立跨簇先后。

这条规则必须高于“空间上哪个更靠前”。

---

## 6. 空间骨架不是最终路线

可以先根据真实地图关系给若干空间块建立一个“自然浏览顺序”，用于帮助理解地图：

例如：

`东部 → 东北 → 中北 → 中部 → 西部 → 西南 → 南部 → 回东部`

但这个顺序只是空间参考骨架，不是动作约束。

它的作用是：

- 帮助决定一个新 Objective 插入哪里更自然；
- 帮助判断一次局部 excursion 的边界；
- 帮助发现明显横穿地图的错误；

它不能直接决定任务 A/C/T 的最终顺序。

## 7. 动作层：A / C / T

每个任务仍然可以拆成：

- A(Q)：Accept，接任务；
- C(Q)：Complete / Service，完成任务目标；
- T(Q)：Turn-in，交任务。

但不再把 A/C/T 一次性扔给全局求解器决定全部顺序。

A/C/T 只在“增量插入阶段”被逐步加入已有路线。

特殊任务可以有扩展动作：

- SCRIPT / USE / ESCORT / TRANSPORT / FIND_NPC 等；

但仍然作为该任务在某个真实空间点的动作处理。

### 7.1 目标簇中的 C 可以只是“局部进度”

目标簇按共享真实目标实体建立，因此某个任务出现在目标簇中，不代表访问这个目标簇后整个任务一定完成。

例如：

- 9817《血鳞纳迦的领袖》要求击杀弗亚希王女，访问“弗亚希王女簇”后可直接完成该任务；
- 9728《热情的欢迎》只是把弗亚希王女列为“纳迦爪子”的一个合法来源，而任务本身还需要继续累计其完整需求。

因此动作层必须区分：

- `C_full(Q)`：此次目标簇动作使整个任务达到可交状态；
- `C_partial(Q, cluster)`：此次只为任务 Q 提供该目标簇对应的部分进度。

只有任务全部 Requirement 满足后，`T(Q)` 才允许进入路线。不能因为一个共享目标簇被访问，就提前插入该任务的 Turn-in。

## 8. 增量插入法（Cluster Incremental Insertion）

这套方法是新的核心路线构造方式。

它更像插入排序，而不是冒泡排序。

### 8.1 第一个目标簇

先选一个最适合作为起始局部块的目标簇/空间实例。

把该簇涉及的任务全部拆成：

- A：接任务点；
- C：任务目标点；
- T：交任务点。

只处理这一簇，人工排出第一条最小稳定路线 R1。

例如抽象形式：

`A1a → A1b → C1a → C1b → T1a → T1b`

R1 必须先人工验收。

### 8.2 插入第二个目标簇

不要把第二簇机械追加在 R1 末尾。

按三个阶段分别插入：

#### 第一步：插入 A2

逐个检查第二簇的接任务点。

如果 A2a 与 R1 前段某 NPC/Hub 同点或顺路，则直接插入那里。

例如：

原：

`A1a → A1b → C1`

如果 A2a 就在 A1a/A1b 同 Hub：

新：

`A1a → A2a → A1b → C1`

不能因为 A2 属于“第二簇”就强制放到 R1 之后。

#### 第二步：插入 C2

查看第二簇真实空间实例。

如果 C2 与 R1 某个空间块相同，则允许穿插/合并：

`C1a → C2a → C1b → C2b`

如果属于相邻区域，则插在最小新增移动成本的位置。

前置约束必须满足，但簇编号不产生额外约束。

#### 第三步：插入 T2

如果 T2 与已有交任务/接任务 NPC 同 Hub，则合并停靠：

`T1 + T2 + A3`

而不是为了任务归属拆成三次访问。

完成后形成稳定路线 R2。

### 8.3 继续处理第三、第四……目标簇

每个新簇重复：

`插 A → 插 C → 插 T → 局部验收 → 固化`

直到所有主体目标簇进入路线。

最后才处理此前暂不归簇的背景/零散任务。

---

## 9. “已有路线只能局部重排”原则

这是保证路线逐步收敛的第二条核心原则。

### 9.1 已验收路线不能反复整体洗牌

如果 R4 已人工确认：

`① → ② → ③ → ④`

插入第五簇时，原则上只允许：

`① → ② → [新动作] → ③ → ④`

或者：

`① → ② → ③ → ④ → [新动作]`

以及对插入点附近做有限局部交换。

不能因为新簇加入，就重新把整条 ①②③④ 彻底换序。

### 9.2 什么时候允许破坏旧顺序

只有发现明确错误时：

- 前置逻辑违反；
- 实际地图不可达；
- 同一目标被明显重复刷；
- 旧路线产生巨大不必要往返；
- 玩家实跑证明旧顺序错误。

才允许重新打开更大的局部窗口重排。

### 9.3 目的

每一步只要求：

> 当前新动作插入已有稳定路线时，在满足逻辑约束的前提下，选择当前最优/最合理插入位置。

不是每一步重新求整个地图的全局最优。

这使路线可解释、可审计、可逐步稳定。

---

## 10. 插入时的人工判断顺序

每个新动作插入时，按以下优先级人工检查：

1. 前置是否满足；
2. 是否同 NPC；
3. 是否同 Hub；
4. 是否同真实空间实例；
5. 是否同营地/洞穴/湖区/局部 excursion；
6. 是否可以与已有目标共享任务怪；
7. 是否会导致后续需要重新回来刷同一批怪；
8. 是否属于背景任务，应只顺带累计；
9. 新增移动是否明显；
10. 插入后是否破坏已经验收的局部顺序。

这不是一个自动加权分数，而是一套可人工检查的决策顺序。

---

## 11. 同一目标簇内部的特殊原则

同一目标簇是最需要处理“等待后续”的地方。

例如：

`9806《成熟的孢子》 → 9807《更多成熟的孢子》`

且两者共享同一批怪。

此时同簇内部存在真实前后关系。

不能简单：

`接9806 → 把怪全刷完 → 交9806 → 接9807 → 再刷同一批怪`

需要在动作层特别检查：

- 第一代任务需要做到什么程度才能交；
- 是否应该保留同区剩余目标给下一代；
- 是否可以通过路线自然经过第二次；
- 是否值得先做别的任务再回来；

因此：

> 同目标簇内部的任务链，是强制顺序 + 共享目标优化问题。

而不同目标簇之间，则默认只是自由插入问题。

---

## 12. 不同目标簇之间的典型案例

假设：

- 簇 A 的接任务 NPC 在塞纳里奥；
- 簇 B 的接任务 NPC 也在塞纳里奥；
- 簇 A 的目标在东北；
- 簇 B 的目标在中北；
- A/B 无任务前置关系。

错误思路：

`接A → 做A → 交A → 接B → 做B → 交B`

正确的增量思路可能是：

`接A + 接B → 做A → 做B → 回Hub交A+交B`

因为 A/B 不同簇之间没有先后关系。

另一个例子：

如果 B 的接任务点恰好在 A 的回程路径：

`接A → 做A → 路过时接B → 做B → 一起回交`

也完全合法。

目标簇只是组织信息，不是路线阶段锁。

## 13. 炉石作为每次插入后的独立交通重置层

炉石不参与目标簇、前置网和A/C/T逻辑本身，只在每次新簇插入完成后单独重新评估。

当前约定：

- 炉石绑定点：萨布拉金；
- 冷却：30分钟；
- 路线先按正常骑行逻辑成立；
- 然后扫描整条当前路线中所有“需要回萨布拉金”的移动边；
- 对每个候选点计算从上一次炉石使用（或路线开始时炉石已可用）到该点的累计实际时间；
- 只要冷却已经恢复且该次炉石能明显减少回程，就允许使用；
- **一条路线里可以使用多次炉石**，不是每轮最多一次。若两次有价值的萨布拉金回程之间累计时间 ≥30分钟，则可以在两个位置分别使用炉石；第三次、第四次同理；
- 每加入下一个目标簇后重新计算整条路线的炉石使用序列，之前的炉石节点允许局部移动、增加或删除；
- 不允许为了迁就炉石，反过来制造假的任务先后或改变显式前置；
- 如果某次候选回程在冷却未恢复前发生，则正常骑行，不为了等炉石而停留；
- 如果当前部分路线里不存在值得炉石替代的萨布拉金回程，则本轮不强行使用。

因此每轮正式流程变为：

`插A → 插C → 插T → 局部稳定 → 扫描全部萨布拉金回程 → 按30分钟冷却安排0/1/多次炉石 → 得到新R`

炉石标注只替换移动边，不删除真实的交/接任务节点。例如：

`C9845 → 骑回萨布拉金 → T9845`

若满足冷却和收益条件，则显示为：

`C9845 → 【炉石→萨布拉金】 → T9845`

而不是删除T9845。

如果后续又出现：

`C下一簇 → 萨布拉金T/A`

并且从上一次炉石到这里的累计路线时间已经 ≥30分钟，则允许再次：

`C下一簇 → 【炉石→萨布拉金】 → T/A`

### 13.1 版本快照是强制步骤

每次准备插入新目标簇之前，必须先冻结当前路线版本，形成独立历史档案：

- R1：第一目标簇稳定后；
- R2：插入第二目标簇后；
- R3：插入第三目标簇后；
- ……

历史快照只新增，不覆盖。即使后续发现旧版本局部顺序不优，也只在新版本中修正，旧版本保留原样。

最终所有目标簇插完后，要按 `R1 → R2 → R3 → … → Rn` 回放审计：

- 当时为什么把新动作插在这里；
- 当时的局部最优是否被后续新增信息推翻；
- 哪些旧局部顺序需要在最终路线中重新打开；
- 炉石使用点是否因为后续路线延长而出现第二次/第三次可用机会。

所以每轮完整流程实际为：

`冻结R(n-1)快照 → 插新簇A/C/T → 局部重排 → 重算0/1/多次炉石 → 保存Rn快照`

## 14. 背景任务的加入时机

像：

- 沼牙撕裂者；
- 亮顶蘑菇；
- 广域孢子怪；
- 暗泽鳗鱼；

这类任务暂时不参与主体目标簇增量构造。

主体路线成型后，再把它们作为背景层插入：

- 在经过覆盖区域时提示“顺带累计”；
- 不单独制造跨图往返；
- 最后检查是否还差数量，再决定是否补刷。

原则：

> 背景任务跟随主体路线，主体路线不跟随背景任务。

---

## 14. 与旧全局算法的关系

旧 solver / exact / CP-SAT / MIP 不删除，但降级为：

- 对照工具；
- 异常检测工具；
- 局部插入成本参考；
- 发现明显更短替代方案的提示器。

它不再直接生成玩家最终路线。

原因：

- 模型容易把“Ready 就做”当成自然动作；
- 对目标簇的多代任务、背景任务、空间实例、人工机制入口理解不足；
- 数学上低成本不等于玩家实跑语义正确。

最终路线必须通过当前文档规定的逐簇人工可审计流程构建。

---

## 15. 前端 Route Atlas 应如何对应这套方法

页面最终显示的不是“算法166个动作”，而是人工稳定路线中的真实动作。

每个地图步骤来自：

- 某个已插入的 A/C/T/特殊动作；
- 真实 NPC/目标/机制坐标；
- 所属目标簇；
- 所属空间实例。

地图只画真实坐标。

页面可以进一步提供：

- 当前目标簇；
- 当前空间实例；
- 当前动作；
- 当前动作为什么插在这里；
- 关联任务；
- 下一步。

不要再用宏观虚拟点。

## 16. 路线构建的正式流程

```text
任务事实
  ↓
完全相同任务怪
  ↓
目标簇
  ↓
直接前置 + 向上追到根
  ↓
目标簇/任务组成前置网
  ↓
真实地图人工拆空间实例
  ↓
剩余固定目标人工归入空间实例
  ↓
背景目标暂存
  ↓
选择第一个主体目标簇/空间块
  ↓
拆 A/C/T，得到 R1
  ↓
插入第二簇 A → C → T，得到 R2
  ↓
插入第三簇 A → C → T，得到 R3
  ↓
……
  ↓
主体路线稳定
  ↓
插入背景任务
  ↓
插入飞行点 / 炉石 / 交通动作
  ↓
重新计算移动时间 / 每圈时间
  ↓
Route Atlas 页面实跑
```

## 17. 每次插入的验收模板

每加入一个新目标簇，都必须回答：

### A. 逻辑
- 它有哪些真实前置？
- 是否存在跨簇前置？
- 是否有同簇多代任务？

### B. 接任务
- 所有 A 点在哪里？
- 能否与已有 Hub 停靠合并？
- 有没有为了“第二簇”而错误延后接取？

### C. 做任务
- C 属于哪个真实空间实例？
- 是否与现有 C 同区域？
- 是否共享怪？
- 是否应该延迟等待同簇后续？

### D. 交任务
- T 点在哪里？
- 是否与已有 A/T 合并？
- 是否会解锁下一层目标簇？

### E. 路线变化
- 新动作插在哪里？
- 为什么？
- 改动了旧路线的哪一个局部窗口？
- 是否破坏已验收部分？

只有这些问题回答清楚，这个簇才算完成插入。

## 18. 当前下一步

在继续构建路线前，本方法论先冻结。

下一步从第一个主体空间块开始，不再直接使用旧17圈或旧166动作路线作为展示真源。

第一块需要先制作完整任务表：

`任务ID / 状态 / 所属目标簇 / 直接前置 / A坐标 / C坐标或空间实例 / T坐标 / 特殊机制`

然后人工构造 R1。

R1 验收后，才开始插入第二个目标簇。

---

## 19. 一句话原则

> 目标簇负责回答“哪些任务应该一起考虑”；前置网负责回答“哪些动作不能颠倒”；空间实例负责回答“实际在哪里做”；增量插入负责回答“新动作现在应该插到已有路线的哪里”。不同目标簇默认没有顺序，除非存在显式前置；已有稳定路线只做局部重排，不反复全局洗牌。
