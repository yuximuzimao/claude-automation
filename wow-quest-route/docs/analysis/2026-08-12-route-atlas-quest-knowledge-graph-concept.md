# 地图分圈可视化＋任务知识图谱：需求记录与初始设计想法

状态：下一会话讨论入口。本文只负责完整记录用户提出的新方向与当前初始想法，不代表已经定稿或开始实施。

## 一、用户需求原意完整记录

用户对任务本身不熟，因此希望把每张练级地图做成更直观的“看图走路线”系统，而不是主要依赖文字任务顺序。

核心想法：

1. 每张地图找一张清晰、适合定位的游戏地图作为底图。
2. 按“圈”拆路线：有几圈就做几张图，每张图只展示这一圈。
3. 每圈在地图上直接标记路线走向，用坐标进行精准定位。
4. 路径直接连线，玩家应当能一眼看出从哪里出发、按什么方向走、沿路做哪些任务；理想状态是只需要跟着路线方向走就能完成这一圈。
5. 任务本身的详细攻略不全部堆在地图上。地图负责导航，任务详情另外做成可调用的小卡片。
6. 小卡片要承载：任务目标、特殊操作方式、复杂地形、洞穴/楼层/入口、容易做错的机制、五开时需要特别提醒的事项等。
7. 希望进一步逐任务分析并建立任务之间的关联，包括但不限于：
   - 任务目标区域相近；
   - 同一批怪/同一目标物；
   - 接任务点相近或同一NPC/任务中心；
   - 交任务点相近或同一NPC/任务中心；
   - 任务链前置/后续关系；
   - 可能需要同一趟完成的任务；
   - 可能因为交一环后解锁下一环而需要再次进入同一区域的任务；
   - 其他对路线设计有价值的关系。
8. 整体资料组织希望有点像 Obsidian 的数据库/双链笔记：不是一条线性的攻略，而是多个资料节点相互交织、可以从任务、区域、NPC、任务链、路线圈等不同入口互相跳转。
9. Questie 插件中已经存在的基础数据应优先直接利用，不要重复人工整理已有字段；项目重点应放在 Questie 没有直接给出的“关系、路线、五开经验、实跑纠错和人类可执行说明”。
10. 用户希望下一会话继续详细讨论这个方向，因此本文必须足够完整，使下一会话无需重新复述需求。
11. 用户允许并希望助手对任何细节提出问题。

## 二、我的初始判断

这个方向很适合当前项目，而且比继续堆“第1步/第2步/第3步”的长文字攻略更符合用户的实际执行方式。

我认为最终应拆成三个彼此独立但互相引用的层：

### A. 地图路线层：Route Atlas

玩家真正执行时首先看这一层。

建议每一圈一张图，图上只保留执行必须的信息：

- 圈编号与起点/终点；
- 一条明确的主路径折线；
- 带方向的箭头；
- 关键坐标锚点；
- 任务目标点编号，例如 `①②③`；
- 接任务点、交任务点、飞行点、洞口等少量特殊图标；
- 必须折返/必须回交的位置；
- 必要时标出“这里先不要做/等下一链一起做”。

地图不应该塞大量文字。地图的职责是回答：

> 我现在在哪里？下一步往哪走？沿路依次处理哪几个点？什么时候回任务中心？

每个编号再链接到任务卡片。

### B. 单任务卡片层：Quest Card

现有 `docs/task-library/README.md` 已经定义了一个不错的任务卡方向，但现在应该把它升级成真正可复用的“节点”。

建议一张任务卡包含：

- 任务ID / 中文名；
- 任务等级、最低等级；
- 接取NPC和坐标；
- 交付NPC和坐标；
- 目标怪/目标物/事件；
- 目标区坐标范围；
- 前置、直接后续；
- 五开机制：共享击杀、个人掉落、逐号点击、一次事件全队等；
- 地形：洞穴、山路、楼层、入口、上下层、是否易迷路；
- 操作提醒：道具怎么用、需要站在哪、是否先清怪等；
- 与其他任务的强关联；
- 当前实跑结论；
- 来源与证据等级；
- 历史修正记录。

这张卡不应该写路线顺序，因为同一个任务以后可能在不同批次、不同路线中被放到不同圈。

### C. 关系图谱层：Quest Knowledge Graph

这是最有长期价值的部分。

不要只存“任务A后续任务B”这一种边，而应该给任务之间定义多种关系类型。例如：

- `precedes`：前置/后续；
- `same_target_mob`：同一种目标怪；
- `same_target_object`：同一种目标物；
- `target_area_overlap`：目标区高度重叠；
- `same_accept_hub`：同接取中心；
- `same_turnin_hub`：同交付中心；
- `same_npc`：共享NPC；
- `same_cave`：同洞穴；
- `same_route_corridor`：同一条道路/山谷/营地动线；
- `unlock_then_return`：交完A后B解锁且返回相同区域；
- `fivebox_synergy`：五开时一起做收益明显；
- `fivebox_conflict`：一起做反而有冲突，例如任务物容量、逐号操作等；
- `natural_drop_trigger`：怪物掉物触发任务；
- `hub_entry` / `hub_exit`：某任务承担进入/离开任务中心作用。

关系本身最好也带：

- 强度/置信度；
- 为什么关联；
- 坐标距离；
- 是否已实跑验证；
- 哪一次实跑支持这个关系。

这样以后“分圈”就不是人工凭感觉写，而是可以从关系图谱中推导候选组合，再由人做最终路线选择。

## 三、数据结构初步建议

我倾向不要把所有东西都塞在 Markdown 里。Markdown适合人读，但关系和自动生成地图需要结构化数据。

建议底层至少有这些实体：

### quest
- quest_id
- name
- quest_level
- required_level
- accept_npc_ids
- turnin_npc_ids
- objective_mob_ids
- objective_object_ids
- prerequisite_ids
- next_ids
- questie_raw_fields / source reference

### npc
- npc_id
- name
- spawn/interaction coordinates
- hub_id

### area
这是 Questie 不一定直接有的“人类任务区”实体，例如：
- 塞斯高
- 远征军械库
- 大裂隙
- 阿苟纳之池
- 某个矿洞

字段：
- area_id
- name
- polygon / point cluster / bounding box
- entrance coordinates
- notes

### quest_relation
- source_quest_id
- target_quest_id
- relation_type
- strength
- evidence
- verified_by_run

### route_circle
- map_id
- route_version
- circle_no
- start_anchor
- end_anchor
- ordered_waypoints
- included_quest_ids
- expected_turnin_hub
- notes

### waypoint
- coordinate
- waypoint_type
- linked_quest_ids
- short instruction
- card/link id

### observation
保存实跑经验，不覆盖理论数据：
- run_id
- quest_id / area_id / circle_id
- user observation
- time cost
- deaths
- actual density
- actual mechanism
- correction

这样“Questie事实”和“用户实跑经验”不会混在一起。

## 四、地图生成的初步实现方向

我目前更倾向于最终做成“结构化路线数据 → 自动生成地图”，而不是每次手工P图。

一个可能的流程：

1. 找到一张固定尺寸、坐标体系稳定的地图底图。
2. 建立游戏坐标 `(x, y)` 到图片像素 `(px, py)` 的线性转换。
3. 每圈路线保存为一组 waypoint。
4. 自动把 waypoint 连成折线并加箭头。
5. 在每个点旁自动标 `①②③...`。
6. 根据类型显示不同图标：接取、击杀区、拾取区、洞口、交付、飞行点。
7. 同时自动生成对应的“本圈任务清单”和卡片索引。

只要底图坐标对齐，后续改路线只改JSON/数据，不需要重新手动画图。

### 关于目标区域

单个Questie点不能总当作真实目标区。因此建议分两类：

- 精确目标：NPC、固定物、洞口、Boss → 单点；
- 分布目标：怪群、拾取区 → 区域轮廓或半透明热点区。

地图中的路线应该连接“区域入口/最佳刷点”，不是机械连接Questie所有散点。

## 五、我认为这个系统最重要的价值

不是“地图好看”，而是把当前项目三个一直反复出现的问题统一解决：

1. 用户不熟任务名：地图位置比任务列表更容易执行。
2. 不同任务链互相穿插：知识图谱能显示跨链重叠，不再只看单链。
3. 首跑不断产生新经验：观察记录可以回灌到任务卡和区域节点，而不是每次只修改一份线性攻略。

最终理想状态应该是：

> 地图负责执行；卡片负责查细节；知识图谱负责设计和复盘；Questie负责提供基础事实；实跑记录负责纠错和优化。

## 六、初步建议的最小可行版本（MVP）

不要一开始做整个1—80数据库。下一次讨论后，建议直接拿“地狱火半岛”作为样板地图做第一版。

第一版只做：

1. 一张可靠地狱火底图；
2. 选当前已经实跑过的一圈或两圈；
3. 生成每圈一张路线图；
4. 建10—20个任务卡；
5. 建立这些任务之间最重要的5—8类关系；
6. 验证用户在实际游戏中能否做到“只看地图就走”；
7. 再决定是否值得做交互网页、完整数据库和全外域扩展。

这样可以尽早发现：地图是否够清楚、编号是否太多、卡片应该多详细、坐标误差是否可接受。

## 七、下一会话希望优先确认的问题

### 1. 最终查看载体
你更希望是哪一种？

- A. 每圈一张PNG/JPG，手机/第二屏直接看；
- B. 一个HTML网页，地图上点击编号弹出任务卡；
- C. 两者都要：网页作为数据库，自动导出每圈静态图。

我的初始倾向是 C，因为静态图最适合实战，网页最适合维护关系。

### 2. 地图底图风格
你希望：

- 完全接近游戏世界地图；
- Questie/Atlas类高清地图；
- 还是允许重新绘制一张更干净、只保留道路/地形/营地的路线专用地图？

### 3. 一张圈图的信息密度
地图上你希望直接看到任务名称，还是只显示编号＋极短动作，例如：

`①杀噬骨兽人` / `②烧投石车` / `③回断背岗哨`

然后详细任务名点卡片看？

我的初始倾向：地图只放“编号＋短动作”，否则地狱火这种任务密集图会很乱。

### 4. 路径线代表什么
你希望路线线条是：

- 精确到“尽量按这条路骑”；
- 还是只表达大方向和访问顺序？

如果要精确到道路，需要额外建立“可骑乘道路/山口/洞口”的地形图层，工作量明显更高，但实用价值也很高。

### 5. 多个任务目标在同一区域时怎么显示
例如一个区域同时有4个任务。你更喜欢：

- 一个大编号，点开后显示4个任务；
- 还是4个编号叠在同一区域？

我倾向一个“任务区节点”聚合多个任务，否则地图会爆炸。

### 6. 卡片调用方式
你说“做成一张小卡片来调用”，我理解有两种：

- 地图上点击节点直接弹卡片；
- 聊天时你说任务名，我调用对应卡片告诉你。

我认为两种都应该支持，但需要确认你实际想象中的使用方式。

### 7. 路线版本是否保留多方案
同一地图未来可能存在：

- 首跑学习版；
- 第二批速度版；
- 老手路线对照版；
- 五开安全版。

我建议数据库允许多个 route_version，而不是只存“当前路线”。是否符合你的预期？

### 8. 是否记录“失败/不采用关系”
例如我们曾认为A和B应一起做，后来实跑发现不值得等。我建议这种负面经验也要保留：

`relation_status = rejected` + 原因。

否则几个月后很容易再次提出同一个错误优化。

## 八、下一会话建议讨论顺序

1. 先确认上面8个问题；
2. 确定地图最终载体；
3. 选地狱火一圈作为样板；
4. 先画一张低成本原型；
5. 用户实际看图判断是否符合“一眼能走”；
6. 再定数据库字段和全图扩展方式。

不要一开始先写大量代码或整理全外域；先证明“地图＋任务区节点＋卡片”的执行体验成立。
