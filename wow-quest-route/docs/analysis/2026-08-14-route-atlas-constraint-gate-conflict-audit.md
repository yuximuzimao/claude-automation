# Route Atlas 约束门控规则冲突审计

日期：2026-08-14
状态：用户已逐项确认，相关语义已写入`docs/ROUTE_ATLAS_RULES.md`并开始代码化。

## 结论

“候选生成 → Hard Validator逐项门控 → 仅对全部可行候选比较成本”的方向正确，但当前长期规则与实现之间存在4个需要先定义语义的冲突/边界。若不处理，新的算法仍可能在赞加声望链、当前状态恢复或从零复用路线中出现假可行/假不可行。

## 冲突1：UNKNOWN阻断最终路线 vs 增量构建必须允许待证候选继续存在

长期规则7.1规定：Hard Validator返回PASS/FAIL/UNKNOWN，UNKNOWN不得按PASS进入最终路线。

这个结论适合作为“最终可执行路线”的门槛，但如果候选搜索把UNKNOWN与FAIL完全等价并永久丢弃，会产生新问题：

- 9814《爆顶蘑菇》真实本地采集圈时间尚未测量时，所有包含9814的候选都会被永久删除；
- 从零孢子村路线在未建模杀怪声望时，9919/9806/9726跨声望阈值的位置全部无法继续探索；
- 玩家正在实跑补证据时，算法没有地方保存“逻辑可能正确但证据尚缺”的候选。

用户确认后的固定语义：

- FAIL = 当前状态下不可行，淘汰当前候选位置；状态变化后如Availability可能改变，可重新枚举。
- UNKNOWN不统一处理，而是逐任务/逐事实消解：公开可查事实先联网/数据库核验；五开机制等只能由真实客户端证明的事实直接问用户；宏观区域已知、仅局部刷法未知的空间问题进入HTML人工空间复核；其余会影响宏观合法性的未知继续阻断执行稿。
- PASS = 才能进入自动成本排序；`MANUAL_SPATIAL_REVIEW`属于“宏观位置可用、局部刷法交给用户”的显式例外，不等价于模型已验证局部最优。

也就是说，UNKNOWN既不能默认通过，也不能机械永久删除，必须先判定它属于哪一种可解决来源。

## 冲突2：逐任务/逐簇插入 vs 声望解锁需要状态包和候选重试

R5第一次插9726时，若新Validator存在，会因Sporeggar声望<3000直接FAIL。这是正确的。

但9726不是永远不可做：9739/9743/9742/9744/9919/9806/9808以及杀怪声望会改变阵营970的状态，之后9726应重新进入候选。

若“一个一个插”被实现为“某任务本轮失败后永远跳过”，算法仍然错误。

用户确认后的固定语义：

- Availability失败只否决“任务Q放在位置P”这一候选，不否决任务Q本身；因`requiredMinRep`不足的任务进入声望不足任务库。
- 声望不足任务库按门槛从低到高排序，只显示当前最低未达到门槛；声望变化达到该门槛时，只抽出刚解锁任务重新插入，不把更高门槛任务提前混入排序。
- 同一门槛若同时解锁多个任务，也按稳定顺序一个一个处理：任务A插入并完成状态重放后，再处理任务B；若A又改变声望，立即再次触发门槛检查。
- 每次声望增加前先检查`requiredMaxRep`任务是否会因跨上限而关闭；这是3000这类非单调边界的前置保护。
- 其它Availability状态转移（等级、物品、技能等）沿用同样“状态变化→只重新激活受影响任务”的事件驱动原则。

## 冲突3：state_continuity不能要求与冻结后缀“状态完全相等”

新增动作经常会带来额外但合法的状态：更多声望、更多背景目标进度、提前获得任务物、提前完成机会任务。若要求插入后的状态与旧冻结边界完全相等，很多正确插入会被误判FAIL。

但简单使用“新状态是旧状态的超集”也不安全：Sporeggar存在`requiredMaxRep < 3000`，声望提高反而会让9739/9743/9808等任务消失；多出来的状态并不总是单调有利。

用户确认后的固定语义：

`state_continuity`应检查“冻结后缀每个动作的前置/可用性是否仍成立”，而不是比较两个RouteState是否相等，也不是简单做集合包含。

这意味着声望、任务可见性、炉石CD等非单调状态必须按动作重放验证。

## 冲突4：R4是声望错误前的插入基线，但不是新的从零交通合法基线

历史R4在声望问题上是最后一个未插入9726的版本，因此适合作为R5以后重建的逻辑基线。

但R4自身已经包含`炉石1→萨布拉金`，而新的长期交通规则要求从零角色不能假定萨布拉金炉石已经绑定。此前计算也表明专程全图预开/绑定不划算。

因此：

- “从R4重建”只能理解为恢复R4的任务/目标簇状态；
- R4的炉石位置不能作为冻结事实；
- 从零版第一次自然到萨布拉金之前，所有使用萨布拉金炉石的候选都应由transport Validator判UNKNOWN/FAIL，并重新打开该运输窗口。

这是历史基线与新永久规则的冲突，不应为了保持R4形状而偷偷保留旧炉石。

## 当前不构成冲突、但必须继续补模型的两点

### A. XP deadline

规则本身没有冲突，但滚动XP状态尚未完成。任务基础经验与`last_full_xp_level`已经物化；缺的是杀怪经验、服务器升级曲线和全路线滚动上界。完成前不能声称“所有T节点已经通过XP Validator”。

### B. shared/background service

Hard Validator可以判断某个背景服务是否“覆盖不足”，但当前总时间模型仍需要避免把同一批怪对多个任务的共享服务机械相加。R6的9709+9823、用户本轮“满地图都是需要打的怪”都说明移动边本身可能同时承载战斗服务。这是成本模型问题，不是Hard Validator本身的冲突。

## 用户确认后对赞加重建的执行原则

1. R4只作为任务插入回滚基线，不冻结炉石；运输状态继续动态验证。
2. 已知声望门槛按硬约束执行；因minRep不足的任务进入排序后的声望不足任务库，达到最低门槛时逐任务重新插入。
3. 每次声望增长前检查maxRep关闭风险，增长后检查minRep新解锁事件。
4. 未知杀怪声望只形成显式`REP_GATE`，不假造跨阈值的精确时点；公开可查部分主动核验，客户端/五开专属部分直接问用户。
5. 局部Spatial Instance怎么绕不清楚但宏观位置明确时，允许进入HTML人工空间复核，不伪造局部最优路线。
6. 9729（阵营970声望>=42000）从普通练级线性路线移出，仅保留条件模块。
7. 9911《沼泽中的伯爵》升级为全局机会事件：满足掉落条件后任何自然经过昂古拉都可触发，不再只在9842走廊阶段才开始关注；仍不得为刷新原地等待。
8. 插入后的冻结后缀使用动态State Replay逐动作验证，不要求新旧RouteState相等。
