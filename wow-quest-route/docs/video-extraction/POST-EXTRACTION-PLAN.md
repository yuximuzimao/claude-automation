# 视频事实提取完成后的路线参考与纠错阶段

状态：已于2026-08-20执行并闭合。本文件保留为该阶段的方法/审计记录，不再作为待执行入口；以后只在规划具体地图时按需复用已经生成的视频索引和审计结果。

## 1. 触发条件

只有在以下条件全部满足后才进入本阶段：

- 第1—53集均有独立`episode-N-extraction.md`；
- 第1—53集均有可解析的`episode-N-events.json`；
- `docs/video-extraction/CURRENT.md`明确写为“第一阶段完成”；
- 每集剪辑缺口、不确定等级和未确认任务均已保留，而不是被静默补齐。

当前这些条件已经满足。

## 2. 第一目标与视频用途

本阶段没有独立于项目的“视频整理目标”。所有合并、索引、审计和报告都只为了本项目自己的任务打金路线参考与纠错服务。

项目唯一第一目标仍由`docs/rules/README.md`定义：**用尽可能少的玩家真实墙钟，获得尽可能高、可持续、可重复的净金币产出。** 视频只是证据工具，不是上位路线。

按`docs/rules/route-atlas-optimization.md`的永久规则，视频在路线层只允许两种用途：

1. **路线顺序/邻接对照**：过滤联盟专属、副本、互斥和本项目已明确排除项后，只比较双方共同保留任务的相对顺序、同片区组合和交通邻接，检查我们是否存在额外折返、过早/过晚交付或不必要的地图振荡。
2. **遗漏审计**：检查视频出现、而本项目任务池/正式路线没有纳入且又不属于明确排除范围的任务；发现后必须回到Questie、任务知识层和当前服务器事实核验，视频本身不能证明“必须加入”。

视频可以作为上述两类审计的支持证据，提供实际任务顺序、任务中心往返、交通节点、同区任务组合、作者跳过/放弃/延后信号和某任务在真实升级过程中的阶段位置。

视频不能直接证明：

- 联盟任务适用于部落；
- 单人打法适用于五开；
- 视频作者的任务选择或地图轴更优；
- 视频时长等于真实墙钟；
- 剪辑省略的移动/等待/失败成本为零；
- 视频作者做过的任务应该恢复到我们的路线；
- 视频先后顺序不同就意味着我们的路线错误；
- 旧版本/当前时光服机制完全一致。

## 3. P1：建立可查询的视频参考索引

产物：

```text
data/video-route/master-events.json
data/video-route/episode-boundaries.json
docs/archive/analysis/video-route-master-audit.md
```

目的不是制作一条“联盟最终路线”，而是让后续每张地图能快速查询视频证据。

处理：

1. 合并全部`episode-N-events.json`；
2. 统一`action`类别、置信度、时间格式和任务字段，同时保留原始action/state，禁止丢失严格证据边界；
3. 保存`episode`、集内秒数、全系列累计时间；
4. 区分接取、目标完成、最终交付、放弃、活动状态、跨剪辑唯一链闭环和未确认状态；
5. 兼容第1—3集早期JSON结构，把`completed_quest_details`/`acceptance_events`规范化为同一查询层，但明确标注为synthetic-normalized，不改写原检查点；
6. 保存原检查点路径、输入文件SHA256和集末未闭环任务状态。

验收：

- 53/53输入都可解析并进入边界表；
- 每个标准化事件都能追溯到单集JSON；
- 同一任务链阶段不会因为同名而合并；
- `objective_complete_not_turnin`/`reward_window_seen_not_final_proven`不会误算成`complete`；
- 推定等级与明确等级分开；
- 不把整理结果写进玩家执行稿。

## 4. P2：跨集连续性与缺口索引

产物：

```text
data/video-route/cross-episode-gaps.json
docs/archive/analysis/video-route-cross-episode-audit.md
```

检查：

- 上一集结束活动任务与后续集首次完成/链转移是否能闭环；
- 任务完成但没有此前接取事件；
- 接取/活动后直到系列结束都没有最终完成证据；
- 同一任务重复接取/重复完成候选；
- 视频标题等级与直接等级证据冲突；
- 同名多阶段任务是否被错误折叠。

缺口只分为：

- `resolved_unique_transition`：可由明确前后状态/唯一链确定；
- `action_exists_order_unknown`：可确定动作发生但顺序/时间未知；
- `unresolved`：无法唯一确定。

第三类不得为了生成完整路线强行补齐。P2的意义是给后续路线审计提供可信事件边界，不是追求一条无缺口的视频时间线。

## 5. P3：按地图生成视频参考块

产物：

```text
data/video-route/map-reference-blocks.json
docs/archive/analysis/video-route-map-reference-audit.md
```

只按后续审计需要组织：

- 任务中心批量接取/交付；
- 同怪、同物品来源、同小区域目标；
- 飞行、船、炉石、传送和长途移动；
- 副本、精英、组队和借助大号等特殊块；
- 剪辑时间未知块。

每块可保存视频画面时间区间，但只作为“顺序/邻接证据”。不能把视频长度直接转成我们的五开预计时间。

## 6. P4：逐地图对本项目路线做视频反向审查

这是POST阶段的核心交付，不是建立联盟路线。

对每张存在视频覆盖、且本项目已经有正式/候选路线的地图：

1. 读取本项目当前任务池、正式路线、已明确排除项和阵营边界；
2. 从视频序列中过滤联盟专属、副本/团队、互斥冲突和本项目已明确排除任务；
3. 对双方共同保留任务比较最终交付顺序、关键邻接和同片区组合；
4. 任何逆序只生成“人工复查信号”，不得自动改线；
5. 对视频独有任务逐项分类：阵营/地图外、已明确排除、任务池存在但路线未纳入、疑似真正遗漏、无法映射；
6. 只有真实地理、前置、交通、Hub成本或任务遗漏证据证明我们的路线有问题，才进入路线修订SOP；
7. 没有发现问题的地图直接记录`pass_whole_map_video_reverse_review`，不为“整理完整”继续制造文档。

诺森德北风/龙骨/灰熊/祖达克已经按这套规则完成整图视频反审，现有结果继续复用，不重复做无意义劳动；只在P1/P2发现新的有效视频事实会改变旧审计结论时才重开。

## 7. P5：发现问题后才进入路线纠错

只有P4产生真实可行动问题时才读取对应路线规则与SOP：

- 漏任务：回Questie/任务知识层核验，确认可接、阵营、前置、奖励、五开机制和实际路线成本；
- 顺序问题：比较当前顺序与视频提示顺序的真实移动/Hub/交通成本，不能机械追视频；
- 交通问题：核验当时飞行点、炉石、船/飞艇/传送状态；
- 五开机制冲突：用户实测与observations优先于视频；
- 任务取舍：仍按本项目金币/真实墙钟目标和当前阶段策略判断，不因视频作者做/不做而改变。

若确需改路线：

1. 只修改受影响地图/步骤；
2. 同步重算受影响步骤和整图预计时间；
3. 执行前置、任务日志25格、飞行状态、特殊机制和玩家可执行性审查；
4. 最后单独做“攻略第一目标”复审，内部视频审计理由不得进入玩家可见action/note/summary。

## 8. P6：阶段性输出

本阶段真正有价值的输出只有三类：

1. **可查询视频参考索引**：后续规划某张地图时可以直接取用；
2. **地图反向审计结论**：PASS / 真实漏项 / 顺序需复查 / 已修正；
3. **对我们正式路线的实际修正**：只在视频发现并经本项目事实验证后产生。

不再把“联盟路线骨架”“联盟→部落全面映射”“35—55视频优化器”当独立交付目标。历史35—55候选/重叠数据可以在对应地图审计时作为输入，但不因为POST阶段启动就整体重跑。

## 9. 后续实跑闭环

视频反审和路线纠错仍不是终点。玩家实跑时继续记录：

- 最低/最高角色经验；
- 实际分钟；
- 五号同步情况；
- 个人掉落额外击杀；
- 死亡、跑尸、跟随卡点；
- 接不到、交不了、位面异常；
- 与视频参考和路线预计的偏差。

用户当前实跑事实优先于视频和静态数据库。稳定后再冻结路线段。
