# 任务机制分类与核验规则

用途：这是项目中**“任务机制包括哪些维度、怎么确认、哪些事实不能互相推断”**的唯一规则owner。用户要求查任务机制、补攻略事实、确认五开共享/拾取/交互、洞穴楼层、事件/载具/Boss时读本文件。

具体任务核验结果一律写入Task Card；本文件不保存某个任务当前事实，不决定路线删留，也不定义Route Atlas颜色/备注格式。

## 1. 输出目标

一次任务机制核验的最终产物不是一段玩家文案，而是Task Card中的结构化事实：

- objective真实类型与数量；
- 触发/任务物/掉落/交互方式；
- 五开每个阶段的共享/个人机制；
- 地形/入口/楼层；
- 事件/护送/载具/Boss关键机制；
- 刷新/等待/失败条件；
- 证据、置信度；
- 尚未闭合的具体open question；
- 完整任务攻略事实。

玩家最终看到多少，由`route-atlas-task-presentation.md`决定。

## 2. 每个任务必须核验的机制维度

普通任务可以核验后全部为“无特殊机制”，但不能因为任务名看起来普通就跳过分类。

至少检查：

1. **目标类型**：kill / loot / interact / use_item / escort / event / talk / explore / vehicle等；
2. **目标数量**：数据库计数是否真实，对多阶段目标分别记录；
3. **目标可见性**：普通敌对、黄色非主动、潜行/隐形、召唤后出现、阶段刷新等；
4. **任务物**：获取来源、对什么使用、尸体/活体/固定物、使用是否逐号；
5. **掉落**：来源怪、参考掉率、单尸件数、拾取规则；
6. **固定物**：是否消失/刷新、一次点击是否多人同步；
7. **触发任务**：怪物掉落起始物、固定物、对话、事件、右键/自动接取；
8. **脚本事件**：波次、防守、召唤、等待、离开条件；
9. **护送/跟随**：启动条件、失败条件、是否可一次同步五号；
10. **载具**：谁进入、谁操作、进度如何结算；
11. **Boss/精英**：真正会影响成功率/墙钟的技能、打断/走位/阶段；
12. **地形**：洞穴入口、楼层、悬崖、水下、桥、建筑内部和真实可达路径；
13. **刷新/等待**：命名怪、固定物、事件重置及竞争；
14. **五开阶段机制**：每个objective/stage分别确认，而不是给整任务贴一个模糊标签。

## 3. 目标类型不能从数据库字段直接翻译成玩家动作

Questie/数据库的objective类型、坐标和目标实体只是证据，不等于完整机制。

尤其以下情况必须额外核验：

- event/rescue；
- 潜行/隐形NPC；
- 黄色非主动目标；
- 对话后变敌对；
- 需要任务物才能显形/触发；
- 同一平面坐标跨楼层；
- 目标在洞穴/建筑内部但数据库只给外部坐标；
- 数据库数量与任务追踪器/实服不一致。

不能把`event`自动写成“杀掉”，也不能把坐标相同理解为同一层可达。

## 4. Fivebox结构化机制定义

五开事实按目标/阶段记录。以下是机制**类型定义**，不是某任务的默认结论。

### `shared_kill`

同一击杀事件可为附近/符合条件的队伍成员同步推进击杀目标。

它**不能推出**：

- 尸体任务物也共享；
- 后续固定物也共享；
- 任务物使用也共享；
- 整个任务最终只需主控操作。

### `shared_progress`

某一动作/摧毁/释放/脚本结果给符合条件的队员同步计数。

必须记录共享的是哪个stage，不能覆盖任务其它阶段。

### `personal_progress`

每个角色有独立进度，必须分别达到条件。

### `ffa_loot_pool`

普通自由拾取任务物：尸体/掉落池中的物品被一个角色拾取后即被消费；五号总需求按实际物品数量累计。

这类机制下：

- 不默认同尸五号分别检查；
- 单尸可掉多件时按实际件数推进；
- 具体任务必须有证据确认属于该类型。

### `same_corpse_multi_character_loot`

同一尸体/掉落事件可以让多个角色分别取得各自任务物。

这属于任务级例外/特定机制，不能从FFA或`shared_kill`推断。

### `personal_drop`

任务物/进度由角色独立判定或独立生成。需要记录是否每角色都必须触发/击杀/拾取。

### `party_loot`

任务物遵循队伍分配/Party Loot语义。必须与普通FFA和个人独立掉落分开。

### `per_character_interaction`

固定物/NPC/任务对象需要五号分别点击/交互。

需要记录：

- 一个对象能否连续给五号点击；
- 点击后是否消失；
- 刷新时间；
- 是否需要切号定位。

### `shared_interaction`

一人交互可同步附近符合条件队员的对应进度。

### `per_character_item_use`

每个角色分别使用任务物/技能才能推进自己的目标。

### `shared_event`

一次事件/护送/脚本完成可以同步符合条件的队员。

仍要记录：

- 是否五号都必须先接任务；
- 距离/生存/阶段条件；
- 事件前置收集是否另有个人机制。

### `escort_party_shared`

已确认的某个护送任务可在普通五人小队中一次启动、多人同步完成。任务卡仍要明确记录该任务属于此类型；不能仅看到`escort`就自动赋值。

### `unknown`

当前没有足够证据时，fivebox玩家状态必须为`pending/待实测`。`verification.open_questions`用于记录具体怎么验证，建议存在但不是待实测标签的真源。

## 5. 复杂任务必须按阶段拆解

禁止只保存：

`fivebox = mixed`

而丢失细节。

应记录类似：

- `stage 1: personal_progress`；
- `stage 2: shared_interaction`；
- `stage 3: shared_event`。

这样Timing、Presentation和实跑验证可以分别消费真实阶段事实。

## 6. 掉落与任务起始物

### 普通任务物

至少记录：

- 来源怪/对象；
- `required_count`；
- 数据库参考掉率；
- 当前服务器实测样本；
- 单尸件数；
- Fivebox loot类型；
- 高密度来源区/洞穴等任务固有事实。

公开资料与实测冲突时保留证据冲突，但当前有效字段按项目证据优先级决定。

### 掉落物触发任务

必须把“任务如何被触发”和“接取后的任务目标”拆开：

- source entity；
- trigger item；
- 右键/自动接取；
- 出现条件；
- 接取后的objectives。

不能只写“自然触发/有就接”。

如果来源受稀有/事件/阶段/时间等限制，Task Card完整guide必须说明出现条件和可观察信号。

## 7. 固定物与交互

固定物任务至少确认：

- 真实对象与位置；
- 每个对象是否可多人连续交互；
- 是否点击后消失；
- 刷新时间；
- 是否竞争；
- 是否一个动作共享进度；
- 是否需要任务物；
- 多层/洞穴环境。

“固定拾取”不等于“必然个人”，“个人”也不等于“五倍完整任务耗时”；Timing根据真实操作数/刷新周期计算。

## 8. 事件、召唤、护送、载具

### 事件/召唤

记录：

- 如何启动；
- 波次/阶段；
- 重置/失败条件；
- 关键等待；
- Fivebox进度结算阶段。

### 护送

记录：

- 谁启动；
- 五号是否都需接好；
- 路线/伏击；
- NPC死亡/脱战/距离等失败条件；
- Fivebox共享类型。

“护送”只是objective类型，不能自动决定是否值得做，也不能自动决定共享。

### 载具

记录：

- 进入方式；
- 控制角色；
- 技能/目标；
- 其他角色是否需要分别进入；
- 进度共享/距离；
- 退出/失败/重试。

## 9. Boss / 精英攻略事实

Task Card可以保存详细Boss机制，但只记录真实可复用执行事实：

- 致命/高伤技能；
- 可打断技能；
- 必须移动/一直跑/停手等机制；
- 召唤/阶段；
- 五开只有主控输出时的真实风险；
- 失败后重试方式。

职业/Profile特定打法必须标适用范围，不能把圣骑专属打法写成任务的通用事实。

是否最终显示给玩家由Task Presentation判断：普通战斗细节若不影响执行不进入HUD。

## 10. 地形与真实可达性

必须区分：

- 目标坐标；
- 真正入口；
- 楼层/垂直关系；
- 山路/桥/洞穴路径；
- 水下深度/上岸点；
- 跟随号是否能通过。

只知道“在洞里”但内部路线未知时，保存`内部路径unknown`，不得根据平面坐标编造。

首次实跑确认更安全/更直接路径后，更新Task Card当前地形事实和证据。

## 11. 机制事实核验来源

核验时按需使用：

1. 用户当前服务器实测；
2. 当前Questie/客户端可见状态；
3. 已确认Task Card/observations证据；
4. Questie/本地数据库；
5. 可靠WotLK/Classic公开资料；
6. 历史路线只用于发现需要核验的问题，不能覆盖当前事实。

完整跨项目证据优先级只在`docs/rules/README.md`定义一次；本文件不维护第二套排序。

## 12. 禁止推断清单

至少禁止：

- `shared_kill → shared_loot`；
- `shared_event → 所有前置阶段共享`；
- `任务完成 → 共享机制已验证`；
- `同名/同类型任务 → 相同机制`；
- `Questie objective type → 玩家真实动作`；
- `平面坐标 → 真实可达路径/楼层`；
- `旧页面写了某机制 → 当前事实仍成立`；
- `一个角色成功 → 五号同步`；
- `护送/载具/固定物`类型本身 → 自动共享/自动个人。

## 13. unknown与现场验证

无法从资料确认、且只能由五开现场证明的事实写入Task Card：

`verification.open_questions`

问题必须可观测，例如：

- “主控炸第一座塔后，其余四号任务计数是否+1？”
- “同一尸体角色2是否仍能看到任务物？”

不能写笼统“共享待测”。

若未知会影响路线合法性，Route Profile必须进入对应验证/阻断流程；若不影响合法性，可以带`pending/待实测`状态继续首跑，Timing按未知边界处理。

## 14. 核验完成后的写回

确认新任务事实时：

1. 更新Task Card当前结构化事实与fivebox状态；
2. 写证据/日期/适用范围；
3. 关闭对应open question；
4. 通过task_id找到引用该任务的Profile，并从当前真源重新生成派生结果；
5. Route Profile本身不复制新事实；
6. fivebox标签由新状态直接生成；人工推荐备注只有用户/规则明确改变时才修改，不能因标签变化自动生成长备注。

迁移期如果旧`fivebox-task-types.json`仍是现役消费者所需兼容输入，可以同步生成/写兼容层；它不能继续作为独立权威真源。
