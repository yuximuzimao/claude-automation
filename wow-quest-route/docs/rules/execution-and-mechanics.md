# 任务机制核验规则

用途：这是项目中**任务攻略事实怎么核验、什么不能靠推断补出来、五开总体状态怎么判定**的唯一规则owner。具体某个任务的结果写进Task Card，本文件不保存任务事实、不决定路线删留，也不定义玩家页面样式。

## 1. 核验目标

一次任务核验最终只需要得到三类东西：

1. **完整攻略事实**：这个任务实际怎么接、怎么做、怎么交，以及会影响执行的任务物、掉落、NPC/入口/楼层、Boss、事件、护送、载具、刷新、失败条件和五开细节。统一写入Task Card `guide`。
2. **五开总体状态**：写入`fivebox.status`，只使用`shared / not_shared / sequential_loot / special / pending`五类。
3. **证据**：实服、Questie、本地数据库或其它可靠来源写入`evidence`。

不要为了“结构化得更细”把同一任务知识再拆成objectives/mechanics/fivebox stages。当前没有一套覆盖所有魔兽任务且无争议的任务机制分类；攻略事实保持完整比强行分类更重要。

## 2. 攻略事实应覆盖什么

不同任务情况差异很大，不要求每张卡机械填写一份固定分类表。核验时只需要确认**实际执行需要知道的事实没有遗漏**。

常见内容包括：

- Questie已有的任务目标和数量；
- 接取/交付NPC或触发物；
- 目标怪、任务物、掉落来源和使用方式；
- 洞穴入口、楼层、悬崖、水下、桥、建筑内部等真实可达信息；
- 固定物是否消失/刷新、是否需要逐号交互；
- 召唤、脚本事件、波次、防守、护送、载具；
- Boss/精英真正影响成功率的技能和失败条件；
- 特殊刷新、等待、竞争、任务起始物；
- 五开执行时共享、个人、依次拾取、距离/交互条件等细节。

这些内容统一进入`guide`。以后如果某个稳定机器消费者确实需要一种新结构化字段，再以真实需求扩schema；不能为了“以后也许会用”提前建立完整任务类型体系。

## 3. Questie / 数据库不是完整攻略

Questie中的目标类型、数量、实体和坐标是重要基础事实，但不能自动等价为完整执行方法。

尤其以下情况要结合实服/可靠证据补充：

- event/rescue类目标；
- 黄色、潜行、隐形或对话后变敌对的NPC；
- 必须用任务物才能显形/触发；
- 洞穴/建筑内部与平面坐标不一致；
- 任务起始物由怪物/固定物掉落；
- 数据库数量、掉落方式与当前服务器实际不一致；
- 护送、载具、脚本事件的真实完成条件。

数据库没有写到，不等于任务没有特殊机制；但也不能根据任务名或相似任务自行补造。

## 4. Fivebox总体分类

### `shared` / 共享

整体可以按共享任务执行。普通执行中不需要额外理解一个关键个人阶段才能避免做错。

### `not_shared` / 不共享

总体按个人任务处理；五号需要分别完成关键进度。

### `sequential_loot` / 依次拾取

同一尸体、同一掉落事件或同一来源可以让多个角色依次取得各自任务物。这种情况在实际路线中足够常见，独立成类，不归入普通“不共享”。

### `special` / 特殊

简单的“共享/不共享”不足以正确执行。典型情况包括：

- 击杀共享，但关键任务物个人；
- 一部分个人、一部分共享；
- 距离足够近才共享；
- 某个交互后队伍同步；
- 其它有明确条件或混合行为的任务。

`special`只是总体标签。具体条件全部写在`guide`，不继续拆fivebox stage。

### `pending` / 待实测

现有证据无法确认五开总体状态。

不需要再建`verification.open_questions`来表达“五开未知”。实跑确认后直接更新`fivebox.status`，并把新确认的事实写入guide/evidence。需要下一组角色专门验证的事项可以留在CURRENT/TODO/实跑计划，不作为Task Card另一套问题管理系统。

## 5. 不能互相推断的事实

以下推断一律禁止：

- 击杀共享 ≠ 任务物共享；
- 一次事件共享 ≠ 前置收集共享；
- 同尸多人可取 ≠ 普通自由拾取；
- “我这次逐号做完了” ≠ 已证明不共享；
- 任务完成 ≠ 所有机制已经验证；
- 同类任务的机制 ≠ 当前任务机制；
- Questie平面坐标 ≠ 已确认真实入口/楼层；
- 旧页面出现“共享”字样 ≠ 可以忽略同一句备注中的个人条件。

遇到混合情况，不要为了得到纯`shared/not_shared`而丢细节；用`special`，事实写guide。

## 6. 掉落与任务起始物

核验掉落任务时，按真实执行需要记录：

- 什么怪/对象掉；
- 需要多少；
- 是否必掉或随机；
- 一具尸体可出几份；
- 五号如何拾取；
- 是否存在明显刷新/竞争/高密度来源区。

掉落物触发任务需要在guide说清：什么东西触发、从哪里来、如何接取，以及接取后怎么做。不能只写“自然触发/有就接”，如果这会让以后无法恢复执行方式。

## 7. 固定物、事件、护送、载具、Boss

这些都属于攻略事实，不需要额外建立机制子对象。

只记录会改变执行的内容，例如：

- 固定物是否点击后消失、五号能否连续点、刷新多久；
- 事件如何启动、什么时候算完成、失败后怎么重来；
- 护送谁启动、五号是否一次同步、NPC死亡/距离条件；
- 载具由谁操作、其它号是否必须进入、共享条件；
- Boss必须打断/移动/持续跑/停手的关键机制。

普通战斗细节如果不影响正确执行，没有必要为了“攻略完整”堆无用信息。

## 8. 地形与位置

任务自身稳定的空间事实进入guide，例如：

- 洞穴真正入口；
- 二楼/地下层；
- 水下深度与上岸点；
- 山路、桥、悬崖、建筑内部；
- 跟随号容易卡住的位置。

某条Route Profile特有的“从西边先绕到这里，再回Hub”不是任务事实，属于路线动作/顺序。

## 9. 证据优先级与纠错

核验时优先使用：

1. 用户当前服务器实测；
2. 当前Questie/客户端可见事实；
3. 已确认Task Card/observations；
4. Questie/本地数据库；
5. 可靠公开资料；
6. 旧路线/旧备注作为待核对历史证据。

当前服务器实测能直接推翻旧推测，但只修改实测真正证明的字段。

纠错时：

- 当前有效guide/status改成新事实；
- 证据记录新来源；
- 旧错误值不继续占当前字段；
- 如果只是执行方式不同但不能证明机制，保持`pending`。

## 10. 与玩家备注、Timing和Route Profile的边界

### 玩家备注

Task Card guide可以很详细；玩家页面备注是否需要显示由Task Presentation决定。当前迁移阶段先无损搬运旧正式页面备注，后续再逐条精简。

### Timing

Timing不解析guide来猜公式。Task Card只通过`timing_rule_ref`选择Timing owner中的计算规则；真实墙钟样本属于Timing Observations。

### Route Profile

Route Profile只保存task_id和路线原子：接/做/交、地点、NPC、交通、条件、顺序、stepGroups。任务机制和攻略不复制到Profile。

## 11. 最小验收

核验一个任务后至少检查：

- task_id正确；
- Questie基础事实没有被旧页面文本覆盖；
- 会影响执行的攻略事实没有因为“无法分类”被丢掉；
- fivebox.status只使用五个固定分类；
- 混合/条件任务使用`special`并在guide写清条件；
- 未确认机制使用`pending`，没有擅自猜结论；
- guide里没有路线特有的步骤/删留决定；
- evidence能追溯关键实测事实。
