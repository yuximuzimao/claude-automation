# 玩家执行文案与任务机制规则

用途：写玩家攻略、补任务备注、处理洞穴/楼层/任务道具/触发物/五开共享机制时读取。任务取舍和经验预算见 `leveling-and-selection.md`。

## 1. 玩家执行稿的目标

执行稿必须让玩家边玩边看时直接知道：

- 下一步往哪里走；
- 到那里完成哪些任务；
- 有什么特殊机制；
- 什么时候离开；
- 回哪个NPC交什么；
- 下一片区域从哪里接上。

如果信息齐全但仍要求玩家自己重新组织任务顺序，视为未完成。

### 1.1 第一目标原则：所有玩家可见文案先回答“现在要做什么”

Route Atlas及其它执行稿中的所有玩家可见字段，都必须先服务正在游戏中的玩家，而不是服务路线设计者、审计者或开发者。

字段职责固定如下：

- **步骤/动作摘要**：动作区只写玩家此刻执行的“任务动作骨架”，例如`地点 → NPC → 交/接《任务》`或`地点 ↳ 做《任务》`。**普通任务目标数量、击杀/拾取对象、任务物怎么用、洞穴入口、楼层、水下位置、召唤/触发方式、失败条件等一律不写进动作区**；这些都属于任务备注。动作区的职责是让玩家一眼知道“现在做哪条任务/跟谁交接”，不是重复任务追踪器，也不是承载攻略细节。系统交通（飞行点、系统鸟、炉石、传送器、任务脚本运输）仍作为真实动作单独写明。禁止用动作区解释数据来源、任务为什么被保留、为什么这样排序、为什么合并、候选覆盖、Questie缺陷、人工锚点、测试状态或构建逻辑。
- **任务备注**：只写已经足够可靠、能直接帮助完成当前任务的攻略信息，包括特殊机制、任务物用法、召唤/事件、洞穴/楼层/水下入口、失败条件、等待策略，以及已经确认且会改变现场操作的五开机制。**凡“任务追踪器告诉你做什么，但没有告诉你怎么正确做到/去哪里做到”的信息，优先写进备注**。例如洞穴任务应在备注里写清可靠入口坐标/地标；多层建筑写明目标层级；任务物任务写明对什么目标使用。备注必须按任务归属明确分隔：单任务信息以`《任务名》`作为独立标识后再写攻略，不能把多个任务的说明一句接一句混在同一段让玩家自行判断归属。若该任务已经确认五开状态，则`共享：`或`不共享：`作为**任务状态前缀**直接放在该任务备注正文最前面，不另起独立说明行；普通共享只显示状态，不重复解释同步逻辑，只有特殊共享方式确实改变操作时才在前缀后补最短说明。只有真正同时约束整个步骤的地形/楼层/共同机制才允许作为步骤级备注；“按当前路线走即可”“不用中途折返”这类跟着流程自然不会犯的废话不得进入备注。任何不改变玩家当前操作的设计解释都不得进入备注。
- **五开待实测标记**：凡共享进度、同尸体拾取、固定物点击、任务物使用、载具/脚本事件等机制当前不能由资料可靠证明、需要用户五开实跑确认时，必须进入独立 `fivebox_check` 字段，不与动作摘要或普通任务备注混写。标记必须直接写清“这一步请观察什么、比较哪几个角色的什么进度”；不能只写“共享未知/待实测”。用户确认后，结论写入 observations；若结论会改变以后玩家操作，再转成普通攻略备注，并移除待实测标记。
- **步骤组标题/摘要**：标题描述这一段玩家要做的任务块；摘要概括这一段实际执行内容。不得把“为什么这样排”“防止后期折返”“保证链不断”“覆盖了哪些候选”等内部理由当成玩家摘要。
- **玩家标题不得使用“第几次/第几轮/回收/收尾”这类过程编号词**：它们只描述路线作者的组织方式，不能帮助现场执行。标题优先只写真实地点、层级、NPC或明确目标，例如`龙眠地面层·奥拉斯塔萨`、`怨毒镇·高级执行官`。真正表示空间路线循环、且玩家确实需要依赖空间循环理解方向时，`第一圈/第二圈`可以保留；否则不要为了记录访问次数而编号。
- **交接行与做任务行必须有明显视觉层级**：同一NPC/地点的交接可在一行内用`→`表示顺序，例如`斯古莉 → 交《A》 → 接《B》`。随后单独执行任务时另起一行，并使用独立的视觉引导符与上一行区分；当前固定写法为`↳ 做《任务名》`。**`↳ 做`这一行只表示“现在执行这条任务”，默认到任务名结束，不在后面追加“杀什么/捡几个/怎么用任务物/从哪个洞口进/上几层/如何触发”等攻略说明。** 这些内容如有必要全部进入该任务的备注。
- **内部审计/设计理由**：Questie字段缺失、人工事实修正、候选差集、可达性闭包、互斥判断依据、局部优化理由、覆盖率、测试结果等，只进入analysis、审计文档或结构化内部字段，不进入玩家动作/摘要/备注。

判定标准：**删掉一句话后，如果玩家仍然同样知道该去哪里、怎么完成任务、何时离开且不会更容易失败，这句话默认不属于玩家执行稿，应移到内部审计。**

## 2. 任务名、地点和动作写法

- 玩家可见执行稿中的任务引用必须写完整任务名称，任务名永远是主标识，禁止纯ID串、裸ID和“交所有已完成任务”。普通正文/任务备注默认使用`《任务名称》`；Route Atlas紧凑流程明细允许去掉`《》`，但必须用固定任务名视觉样式保持边界清晰。Route Atlas等紧凑执行页**不要求每次重复显示ID**；若任何玩家可见位置确实显示任务ID，则必须与完整任务名绑定，绝不能用ID代替任务名。结构化数据、任务卡和内部审计仍应保留ID用于精确定位。
- 地点块标题固定为 `地点名称（坐标）`。坐标必须紧跟地点/目标名，不裸写坐标。
- 野外正文使用有方向感的自然语言：从哪里出发、往哪边、到什么地标、沿路合并哪些任务、何时离开。
- **凡前后动作发生转场，尤其是为了交/接任务而换地点，必须把交接地点直接写出来**：跨Hub/跨任务区时至少明确目标地点/NPC；同一区域内只要NPC位置发生变化，也应写真实地点/NPC，不能只写“回去交”“去交《任务名》”要求玩家自己查交接点。普通自主移动（步行、地面坐骑、角色自己的飞行坐骑、借用/临时飞行坐骑等）由地图点位与连线表达，**不在玩家动作层重复写“飞往/骑往/返回”**，避免让交通能力看起来像额外任务动作。只有开飞行点、乘系统鸟、炉石、传送器或任务脚本运输这类需要明确触发的系统动作，才在动作层单独写交通方式和目的地。普通“做《任务名》”的目标位置若Questie已经能直接指向且没有洞穴、楼层、悬崖、水下、入口等隐藏地形问题，可以只写任务名，不强行重复目标地点。
- **玩家HUD必须用视觉样式表达语义，不能让地点、任务名、动作和警告全部落成同一层级正文**。当前Route Atlas紧凑流程固定为：地点使用浅蓝色普通文字；NPC使用偏白、稍粗的普通文字，与地点颜色区分，二者都不加下划线/边框/底色，也不附加点击定位等交互；`交/接/做`三个动作词本身保持普通文字；流程任务名去掉`《》`并加下划线，按动作着色——交任务绿色、接任务黄色、做任务蓝色，多任务之间用`、`分隔；任务备注里的任务名暂时继续保留`《任务名》`。备注中`顶层/一层/地下`以及`不要杀死/不要跳下/先停手`等必须注意的信息使用普通红色文字，不做胶囊、边框或大色块。整体优先克制，避免把所有语义都做成标签造成新的视觉噪音。
- **正式发布的新地图/新步骤必须直接采用上述HUD语义格式。** 这是最终执行页格式要求，不等于规定所有路线设计都必须采用“逐段修旧稿”的工作方式。已有路线如果进行批量迁移/重构，按迁移流程先保证事实与玩家文案正确再套最终语义格式；新地图仍按路线设计SOP完成事实、顺序与机制审计，并从第一版正式玩家稿直接使用本节格式。
- **无行动价值的常驻说明应删除**：颜色图例、路线级交通概述、已经形成固定认知的“五开待实测”说明、提醒“任务备注本来就要看”、以及“跟着当前路线就不会折返”之类信息，不占据HUD或地图底部空间。交通、共享/个人机制等若真正改变现场操作，必须放在实际步骤动作或对应任务备注。若某块区域没有真实需要玩家当前阅读的动态信息，允许完全留空。
- 只有两类位置用结构化逐项清单：营地出发前的接取；返回营地时的交付/新接/保留/放弃。
- 不把攻略写成几十步数据库流水账，也不连续堆“完成：/操作：/条件完成：”字段。
- 一段路线按完整可执行任务块理解，不按一次往返或一两个任务机械拆段。
- 当用户要求按“轮”规划时，一轮以主要执行任务的地图切换为边界；主城、飞艇、船或纯交通地图若只承担交通/少量交付，不机械拆成独立轮次，交付并入相邻主地图轮。
- 每个任务块的**内部估时**必须能拆出跑路、战斗/交互、拾取/共享机制等主要成本来源，并遵守`timing-and-benchmarking.md`；玩家执行页默认只展示该逻辑步骤的预计总时间与合理区间，不要求把所有成本分解塞进HUD。时间预测基于正常刷新、无竞争和当前已知最佳执行条件，不得伪装成精确实跑值。

## 3. 每个任务必须做“人类可执行性/隐藏机制审计”

所有纳入执行路线的任务都要逐任务检查，而不是只抽查“特殊任务”。至少核对：

- 平面坐标是否受高低层、悬崖、水下、洞穴入口、桥梁或建筑内部影响；
- 是否必须主动使用任务道具；
- 是否先拿钥匙、掉落物、任务起始物；
- 是否要召唤目标、对尸体/固定物交互、开笼、拧阀门等；
- 是否存在脚本飞行/传送、护送/跟随、事件波次、巡逻、稀有或阶段刷新；
- Questie给出的NPC/目标坐标是否等于玩家实际能到达/交互的位置。

普通直观任务审计后可以没有备注；凡“只看任务名+Questie坐标仍可能找不到或不会做”，必须写执行备注。

Route Atlas中：有有效执行备注的逻辑步骤显示“有备注”；没有备注表示**已审计且无需额外说明**，不是没检查。

## 4. 怪物掉落物触发任务是强制说明项

凡任务由怪物掉落物品后自动/右键触发，玩家可见攻略必须明确写：

`打什么怪 → 怪在哪里/主要刷点 → 掉什么任务起始物 → 拾取后如何接取任务`

Route Atlas动作层统一把这类行为写成`接《任务名》`，因为击杀来源怪、拾取起始物属于“如何接到任务”的机制，不应伪装成`做《任务名》`。来源怪、主要位置、掉落的任务起始物、右键/自动接取方式全部写入该任务自己的备注；动作正文不展开刷怪机制。任务接取后若另有真实执行目标，再在后续节点单独写`做《任务名》`。

禁止只写“自然触发”“顺路掉落”“有就接”“机会任务”。

若来源怪受特殊条件限制，还必须写：

- 事件波次/稀有/精英/巡逻/召唤/阶段/前置/时间天气场景等出现条件；
- 玩家现场如何判断当前能做；
- 路线是否等待；
- 若不等待，下一自然检查点是什么，或明确只检查一次。

同一触发物有多个来源时，至少写当前路线采用的主要来源和位置；若来源差异改变路线或掉率风险，要说明取舍。

## 5. 五开共享机制必须逐任务确认

不能从“击杀共享”推断其它动作共享。至少区分：

- 共享击杀；
- 普通FFA多数量任务物；
- 同尸体五号可分别拾取；
- 每角色独立掉落；
- Party Loot；
- 固定物个人拾取；
- 固定物/释放/摧毁进度全队共享；
- 每号分别使用技能/任务物；
- 护送：用户已确认普通五人小队中所有护送都可以五号一起跑；五号接好任务后只执行一次护送即可共同完成，不需要逐号重复。护送是否值得做只比较脚本相对正常移动新增的墙钟、停顿/战斗/失败风险与任务收益，不能再乘五倍执行成本。

除上述已确认的护送通则外，其它机制未实测只能标 expected / unknown，不得升级成 confirmed。用户现场确认后写入 `data/observations/fivebox-task-types.json`。

离开任务区的完成条件按真实机制：个人任务以最低进度号完成为准；共享任务主控完成后仍要核对全队任务状态。

对“建议多人/5人”的户外精英、竞技场或连续挑战任务，不能把队伍人数直接等同为有效战斗人数。当实际执行模式主要只有主控承担输出时，发布前应按主控真实战斗能力评估；如果首个遭遇可低成本重试且能代表后续压力，可把第一场同时设为**战斗能力门槛 + 五开共享门槛**：先按正常实跑方式打一场，明显打不过或失败重跑成本高就停止后续并保留回访；能稳定完成后再验证其它角色是否同步。首场通过不能自动证明后续所有特殊Boss都共享，但可以作为是否继续整条链的现场放行条件。

## 6. 洞穴、多层、水下与不可直达地形

- Questie平面坐标不能证明目标在洞外/入口层/地表。
- 只知道“目标在洞里”但内部路线未验证时，宁可写“需进洞，内部路径待实跑”，不能根据坐标编造楼层或深度。
- 有可靠入口时，备注入口坐标/地标、上楼/下楼/潜水/绕山方式和跟随号风险。
- **多层建筑的接任务/交任务点必须在玩家主动作或标题中直接写明层级**，例如`地面层 / 中层（第二层） / 顶层 / 地下 / 地下二层`；不能只在备注里说“按交通换层”，也不能让玩家靠NPC名字记忆楼层。同一平面坐标跨层重复时尤其强制。若层级事实尚未可靠验证，写“层级待实跑确认”而不是猜。
- 对水下、悬崖顶、洞穴上方等目标，必须写清垂直关系，避免玩家站在同一X/Y附近仍找不到。
- 地形已实跑证明有更安全或更密集的路线时，以实跑路径覆盖静态散点。

## 7. 任务中心首次接触与交付后二次扫描

第一次站到NPC前：

1. 检查该NPC当前全部可接任务；
2. 后续确定会做且日志有空间的，当场接走；
3. 不允许因为文档章节还没写到而留到第二次回来。

每次交任务后：

1. 不离开NPC；
2. 再扫描刚解锁的后续；
3. 连续对话/交接推进到当前能推进的最远节点；
4. 前置未满足、等级门槛、互斥、日志压力或明确排除才允许不接，并写原因。

去任何洞穴、城堡、矿区、海岸、营地等远端点前，再做一次“同目的地任务聚合检查”。

## 8. 任务日志容量

任务日志上限按25个计算。

- 默认至少预留5格给当前区域后续、物品触发和临时必接任务。
- ≤18格：可提前接未来1—3个区域确定必经、低额外负担的任务。
- 19—21格：只提前接确定必经且高价值任务。
- ≥22格：停止远期接取，优先交付或清理低价值候选。

跨区任务明确标记“必接 / 可提前接 / 不要占格”，不能因为现在能接就全拿。

## 9. 飞行点和交通写法

- 路线所处阶段的移动能力与技能策略必须从`CURRENT`/RouteState读取，不在永久规则里硬编码某张地图、某个借用坐骑或某个当前技能选择。任务基础卡必须区分“玩家只需要具备到达目标的移动能力”与“任务接取/推进本身硬性检查某技能或法术”：前者可以由任何当前合法移动手段满足；后者只有真实Availability条件满足才可执行。Questie明确`requiredSpell`时直接按硬门槛处理；Questie漏记但已有可靠实测/公开资料确认的隐藏门槛也要人工补入。若硬门槛任务是某后续的唯一可达前置，所有因此不可达的后续链都要递归退出当前执行池，但仍保留在知识层。
- 当前执行角色的已开飞行点以 `docs/verified-routes/FLIGHT-POINTS.md` 为准；未记录的点按未开启处理，具体节点列表不复制进永久规则。
- **系统飞行的目的地必须在该时点已经发现/开启。** 未开启的飞行点可以作为系统路线的中间经过节点，但不能被选择为落地点；路线设计不能因为地图连接表显示 A↔B 就假定 B 可直接飞。每条系统鸟动作都必须能从此前步骤或入口状态证明目的地已开。
- 第一次自然经过新飞行点时五号分别开启；不默认专门预跑整图开点。
- 首次开点要写新手可执行指引：从入口/落点怎么走、飞行管理员在哪一侧/哪一层/靠近什么地标。
- 已验证旧点只需写“从A飞B”和落点大致位置，不重复新手级寻找过程。
- **每个任务/任务块的交通判断都使用该时点已经开启的飞行点状态。** 不能拿整图最终状态倒推，也不能只在开点瞬间检查一次。新点开启后，尚未执行的后续跨片区步骤全部重新检查直飞、最近飞行点＋骑马、炉石组合和其它系统交通；存在更短飞法时必须改掉旧骑马/旧中转。
- 玩家稿不需要把全部飞行状态逐条展示出来，但内部路线状态必须能回答“做到这一任务时已经开了哪些点、这一段为什么不用飞”。若存在已开飞行点而仍选择骑马，必须有真实更优理由（例如飞行管理员本身绕远、落点离目标更远、沿路有生产性任务），不能只是旧路线遗留。
- 炉石、飞艇、船、传送门和远端任务后的回程都是路线步骤，不能省略成“常识”。

## 10. 当前执行稿只保留会发生的动作

- 当前日志没有、此前也没安排接取的任务，不写“如果有就交”。
- 已完成且后续不会再影响现场决策的任务从当前执行稿删除；历史原因留在NEAT/错题本。
- 条件任务只有真实条件成立才进入线性执行步骤；条件必定为假时不能留死节点。
- 可选任务必须明确可选条件和回访点，禁止模糊“以后顺路做”。

## 11. 发布前玩家视角复走

发布复审固定分两阶段，顺序不能倒置：

1. **先修改成稿**：先按当前已知问题完成一版正式玩家稿，清掉已知内部说明、补齐已知机制/地形/任务物信息；此阶段不做“第一次看攻略”的全面复审。
2. **再冷启动复审**：从最终玩家可见数据导出只含标题、步骤摘要、动作、普通备注和`fivebox_check`的纯玩家视图；复审时不得读取Builder、foundation、插入审计、路线排序理由等形成过程，也不得用这些资料替页面脑补。只有当玩家视图本身出现“不知道怎么做/不敢确认”的任务时，才针对该任务单独查资料并修正。

冷启动复审必须从玩家起点复走。至少检查：

- 是否一眼看出下一步方向；
- 是否需要回忆前文才能知道交什么；
- 是否存在纯ID或裸坐标；
- 是否把楼层/洞穴/水下问题误压成平面点；
- 返回任务中心时接交是否完整；
- 是否一句话塞了太多条件；
- 是否有内部设计解释污染玩家备注；
- 路线先后是否符合真实地形而非坐标表。

任一不通过，不得标成当前执行入口。
