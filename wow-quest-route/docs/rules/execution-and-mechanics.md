# 玩家执行文案与任务机制规则

用途：写玩家攻略、补任务备注、处理洞穴/楼层/任务道具/触发物/五开共享机制时读取。任务取舍和经验预算见 `leveling-and-selection.md`。

## 1. 玩家执行稿的目标

执行稿必须让玩家边玩边看时直接知道：

- 下一步往哪里走；
- 到那里完成哪些任务；
- 有什么特殊机制；
- 什么时候离开；
- 回哪个NPC交什么；
- 下一片区域从哪里接上。

如果信息齐全但仍要求玩家自己重新组织任务顺序，视为未完成。

## 2. 任务名、地点和动作写法

- 每次任务引用固定写 `《任务完整名称》（ID）`；任务名是主标识，ID只辅助定位。禁止纯ID串、裸ID和“交所有已完成任务”。
- 地点块标题固定为 `地点名称（坐标）`。坐标必须紧跟地点/目标名，不裸写坐标。
- 野外正文使用有方向感的自然语言：从哪里出发、往哪边、到什么地标、沿路合并哪些任务、何时离开。
- 只有两类位置用结构化逐项清单：营地出发前的接取；返回营地时的交付/新接/保留/放弃。
- 不把攻略写成几十步数据库流水账，也不连续堆“完成：/操作：/条件完成：”字段。
- 一段路线按完整可执行任务块理解，不按一次往返或一两个任务机械拆段。

## 3. 每个任务必须做“人类可执行性/隐藏机制审计”

所有纳入执行路线的任务都要逐任务检查，而不是只抽查“特殊任务”。至少核对：

- 平面坐标是否受高低层、悬崖、水下、洞穴入口、桥梁或建筑内部影响；
- 是否必须主动使用任务道具；
- 是否先拿钥匙、掉落物、任务起始物；
- 是否要召唤目标、对尸体/固定物交互、开笼、拧阀门等；
- 是否存在脚本飞行/传送、护送/跟随、事件波次、巡逻、稀有或阶段刷新；
- Questie给出的NPC/目标坐标是否等于玩家实际能到达/交互的位置。

普通直观任务审计后可以没有备注；凡“只看任务名+Questie坐标仍可能找不到或不会做”，必须写执行备注。

Route Atlas中：有有效执行备注的逻辑步骤显示“有备注”；没有备注表示**已审计且无需额外说明**，不是没检查。

## 4. 怪物掉落物触发任务是强制说明项

凡任务由怪物掉落物品后自动/右键触发，玩家可见攻略必须明确写：

`打什么怪 → 怪在哪里/主要刷点 → 掉什么触发物 → 拾取后触发什么任务`

禁止只写“自然触发”“顺路掉落”“有就接”“机会任务”。

若来源怪受特殊条件限制，还必须写：

- 事件波次/稀有/精英/巡逻/召唤/阶段/前置/时间天气场景等出现条件；
- 玩家现场如何判断当前能做；
- 路线是否等待；
- 若不等待，下一自然检查点是什么，或明确只检查一次。

同一触发物有多个来源时，至少写当前路线采用的主要来源和位置；若来源差异改变路线或掉率风险，要说明取舍。

## 5. 五开共享机制必须逐任务确认

不能从“击杀共享”推断其它动作共享。至少区分：

- 共享击杀；
- 普通FFA多数量任务物；
- 同尸体五号可分别拾取；
- 每角色独立掉落；
- Party Loot；
- 固定物个人拾取；
- 固定物/释放/摧毁进度全队共享；
- 每号分别使用技能/任务物；
- 护送是否一次共享接取和完成。

未实测只能标 expected / unknown，不得升级成 confirmed。用户现场确认后写入 `data/observations/fivebox-task-types.json`。

离开任务区的完成条件按真实机制：个人任务以最低进度号完成为准；共享任务主控完成后仍要核对全队任务状态。

## 6. 洞穴、多层、水下与不可直达地形

- Questie平面坐标不能证明目标在洞外/入口层/地表。
- 只知道“目标在洞里”但内部路线未验证时，宁可写“需进洞，内部路径待实跑”，不能根据坐标编造楼层或深度。
- 有可靠入口时，备注入口坐标/地标、上楼/下楼/潜水/绕山方式和跟随号风险。
- 对水下、悬崖顶、洞穴上方等目标，必须写清垂直关系，避免玩家站在同一X/Y附近仍找不到。
- 地形已实跑证明有更安全或更密集的路线时，以实跑路径覆盖静态散点。

## 7. 任务中心首次接触与交付后二次扫描

第一次站到NPC前：

1. 检查该NPC当前全部可接任务；
2. 后续确定会做且日志有空间的，当场接走；
3. 不允许因为文档章节还没写到而留到第二次回来。

每次交任务后：

1. 不离开NPC；
2. 再扫描刚解锁的后续；
3. 连续对话/交接推进到当前能推进的最远节点；
4. 前置未满足、等级门槛、互斥、日志压力或明确排除才允许不接，并写原因。

去任何洞穴、城堡、矿区、海岸、营地等远端点前，再做一次“同目的地任务聚合检查”。

## 8. 任务日志容量

任务日志上限按25个计算。

- 默认至少预留5格给当前区域后续、物品触发和临时必接任务。
- ≤18格：可提前接未来1—3个区域确定必经、低额外负担的任务。
- 19—21格：只提前接确定必经且高价值任务。
- ≥22格：停止远期接取，优先交付或清理低价值候选。

跨区任务明确标记“必接 / 可提前接 / 不要占格”，不能因为现在能接就全拿。

## 9. 飞行点和交通写法

- 当前首组已开飞行点以 `docs/verified-routes/FLIGHT-POINTS.md` 为准，未记录视为未开启。
- 第一次自然经过新飞行点时五号分别开启；不默认专门预跑整图开点。
- 首次开点要写新手可执行指引：从入口/落点怎么走、飞行管理员在哪一侧/哪一层/靠近什么地标。
- 已验证旧点只需写“从A飞B”和落点大致位置，不重复新手级寻找过程。
- 新点开启后重新检查直飞关系，禁止继续沿用旧中转假设。
- 炉石、飞艇、船、传送门和远端任务后的回程都是路线步骤，不能省略成“常识”。

## 10. 当前执行稿只保留会发生的动作

- 当前日志没有、此前也没安排接取的任务，不写“如果有就交”。
- 已完成且后续不会再影响现场决策的任务从当前执行稿删除；历史原因留在NEAT/错题本。
- 条件任务只有真实条件成立才进入线性执行步骤；条件必定为假时不能留死节点。
- 可选任务必须明确可选条件和回访点，禁止模糊“以后顺路做”。

## 11. 发布前玩家视角复走

成稿后脱离原编排思路，从玩家起点冷启动复走。至少检查：

- 是否一眼看出下一步方向；
- 是否需要回忆前文才能知道交什么；
- 是否存在纯ID或裸坐标；
- 是否把楼层/洞穴/水下问题误压成平面点；
- 返回任务中心时接交是否完整；
- 是否一句话塞了太多条件；
- 是否有内部设计解释污染玩家备注；
- 路线先后是否符合真实地形而非坐标表。

任一不通过，不得标成当前执行入口。
