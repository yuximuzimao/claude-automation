# 魔兽任务路线永久规则索引

用途：这是本项目永久规则的唯一总入口。不要一次性读取全部规则；先判断当前任务属于哪一类，再只加载对应子文档。

当前状态、等级、任务进度和本批次局部路线不写在这里，统一读 `docs/verified-routes/CURRENT.md`。日期化 NEAT、一次性 analysis、旧候选路线统一在 `docs/archive/` 保存形成过程，不承担永久规则入口，也不属于日常默认加载范围。

## 项目唯一目标

**本项目的唯一第一目标是打金：用尽可能少的真实墙钟，获得尽可能高、可持续、可重复的净金币产出。** 升级、任务路线、任务剔除、装备选择、路线动画、任务卡、视频拆解、自动化和页面设计都只是实现这个目标的工具，本身没有独立优先级。

固定判断口径：

- 首要比较指标是**同一种打金方式自身的长期可重复净金币 / 玩家真实墙钟**，不是单独的升级速度、经验/小时、任务完成数或单次任务金币。
- 当前任务路线本身就是一种独立打金方式：一组号从开始跑任务，到该任务路线定义的结束点，统计这套任务体系自身的总墙钟与总金币。练级阶段的任务金币/装备变现、80级后做一次性任务得到的XP折金，都属于这套任务打金方式自己的收益。
- 团本打金、日常打金等其它方式以后分别建立自己的金币/墙钟模型；它们可以在实际经营中组合，但**不得拿另一种打金方式的G/小时作为单个任务删留的机会成本**，除非用户明确要求做跨方式时间分配优化。
- 练级经验的经济价值只在这套任务打金路径内部体现：它决定什么时候能接后续任务、什么时候能获得80级XP折金以及整套任务路线何时完成；不得把经验时间价值偷换成“更早去做别的打金方式”。
- 脑力占用、切号复杂度、随机长尾、失败重跑、路线记忆负担和不可稳定复现都会降低真实金币效率：能折算到墙钟/失败成本的直接计入；难以可靠量化但明显影响长期复用的，作为硬约束或同收益方案的优先级判据。
- “最低脑力可重复”和“高复用性”不是第二目标，而是保证高金币/小时能够长期兑现的执行条件。纸面更快但需要持续判断、频繁救火或高度依赖临场记忆的方案，不视为真正高效。
- 任何阶段性策略——例如“某阶段全清”“只冲等级”“追某个外部速度基准”“整类删某类任务”——都只能作为候选实现方式。若与上述唯一目标冲突，立即失效，不得反过来约束项目。

## 所有工作都必须遵守的最小规则

1. 当前现场真值优先级：用户当前实测 > 最新 Questie/实跑状态 > observations/verified route > Questie 数据库 > 公共资料 > 旧路线假设。
2. 五开等级、经验和离图预算以五个角色中最低号为基准；任何“共享”都不能从击杀自动外推到拾取、点击、技能或任务物。
3. Questie 坐标是定位证据，不是道路导航。洞穴、楼层、悬崖、水下、桥梁、入口和跟随可达性必须单独审计。
4. 不按“护送/掉落/收集/低等级”等标签整类保留或删除；按真实剩余墙钟、重叠、掉率、地形、后续链和五开机制逐任务判断。
5. 自动候选、区域分类、当前任务日志都只负责召回，不能证明任务覆盖完整。
6. 玩家执行稿的第一目标是“给正在游戏中的玩家直接使用”，必须比玩家自己整理任务更省脑：一眼知道下一步去哪、做什么、什么时候离开、回哪里交。任何内部审计、数据缺陷说明、候选覆盖、路线设计理由、实现细节或“为什么这样排”的文字都不得占用玩家可见的动作/步骤摘要/任务备注；这些内容只能留在analysis、审计文档或内部字段。
7. 从零复用主路线和当前角色执行路线必须分离；当前角色做完任务只裁当前执行动作，不删除下一批仍需的任务知识。
8. Route Atlas 只维护一个正式 HTML：`data/routes/route-atlas-workbench.html`。地图、角色状态、版本变化都不能制造新的独立 HTML。
9. 用户实跑确认的新机制先修执行稿，再写 observations；跨地图长期有效的结论再提升为永久规则。
10. 历史经验、错误案例和一次性讨论不重复塞回永久规则；已稳定内容进入对应规则文件，临时发现只放 `tasks/lessons.md`。
11. 每一版可执行路线都必须同时给出按玩家逻辑步骤/自然任务块拆分的预计时间和整段/整图总时间；预测与实跑成对保存，禁止用某次XP/h或步骤比例线性外推不同任务块。具体算法统一读`timing-and-benchmarking.md`。
12. 户外主线默认不混入副本/团队副本；`is_dungeon`/raid任务只有在当前目标明确开启专项副本路线时才进入该专项scope。具体本批次是否开启副本属于CURRENT/路线scope，不在永久规则里硬编码。

## 永久规则准入、归属与一致性门禁

永久规则不是“遇到一次问题就加一句提醒”的收件箱。任何内容进入或继续留在`docs/rules/`，必须同时满足：

1. **跨地图/跨批次仍成立**：换角色、换地图、换当前阶段后方法仍有效；否则属于CURRENT、任务卡、observations、ERROR-BOOK或archive。
2. **描述方法或产品契约，不描述单次事实**：具体任务ID、某次实跑、某个步骤、某个阶段交通策略、外部基准数字默认不能充当永久规则正文。
3. **单一权威归属**：同一规范只允许一个子规则文件保存完整定义；其它文档只能摘要并链接，不得复制出第二套可独立演化的正文。
4. **不与项目第一目标冲突**：任务选择、估时、路线优化最终服从任务打金周期的净金币/真实墙钟与稳定复用性；经验、任务数、步骤数、历史P级、外部速度基准都只能是状态变量或辅助指标。
5. **规则与实现一致**：若代码、构建器、测试或正式数据仍违反已写明规则，视为实现缺陷，不能以“文档已经写了”判定规则落地完成。

权威边界固定为：`CURRENT`负责当前状态和阶段策略；`docs/rules/`负责长期方法/产品契约；task-library/observations负责单任务与本服事实；`ROUTE-DESIGN-PROCESS`只负责流程顺序和门禁编排；`ERROR-BOOK`保存失败案例与复查证据；archive保存历史形成过程。SOP、错题本和历史案例都不得反向成为第二套永久规则。

当两处规范看似冲突时，不按“文件更新得更晚”或“写得更具体”机械覆盖：先按上述职责确定唯一owner，把正确规则保留在owner中，再删除/改成引用其它重复正文。当前用户指令可以改变本轮策略并写入CURRENT；只有确认其方法跨批次成立时才提升到永久规则。

**触发式一致性检查：**本轮只要新增、修改或提升了一条永久规则/长期机制，在本轮收尾前必须检查受影响规则邻域，而不是只检查新加的那一句。至少核对：`是否真的永久 → 是否放对文件 → 是否与相关规则重复/冲突 → 是否夹带当前状态/单任务案例/阶段数字 → 是否仍符合项目第一目标 → 实现/测试是否同步`。只有规则架构发生较大变化、规则文件明显膨胀或用户明确要求时才做全量规则审计；普通局部修订不强制每次全文读取全部规则。

## 权威边界

- `docs/verified-routes/CURRENT.md`：当前角色状态与唯一恢复点。
- `docs/rules/*.md`：跨地图、跨批次长期规则。
- `docs/verified-routes/ROUTE-DESIGN-PROCESS.md`：完整路线设计 SOP，只在真正设计/修订路线时加载。
- `docs/verified-routes/ERROR-BOOK.md`：历史错误与发布前对抗复查，只在生成/修订/审计时加载。
- `docs/task-library/`：单任务可复用事实。
- `data/observations/`：当前服务器五开机制与阻断实测。
- `docs/archive/`：历史考古区；NEAT、旧候选路线、一次性analysis和视频历史都在这里，默认不参与日常加载。

新代码、文档和NEAT一律从本索引路由永久规则，不再维护其它永久规则总入口。
