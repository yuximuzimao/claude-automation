# 路线估时与实跑基准规则

用途：任何新路线、路线重排、实跑复盘和同路线效率比较时读取。任务取舍规则见`leveling-and-selection.md`，五开机制见`execution-and-mechanics.md`。

## 1. 每一版可执行路线都必须带时间预算

- 发布/交付路线时，必须同时给出**每个玩家逻辑步骤或自然任务块的预计时间**与**整段/整图总时间**；不能只给总时间。
- 时间默认表示正常刷新、无竞争、无明显操作失误、按当前已知最佳执行方式跑的`clean baseline`。实跑中的迷路、找楼层、机制学习、漏任务、死亡、断跟随等单独记录为异常/学习成本，不能永久写进任务固有耗时。
- 若路线只改局部窗口，至少重算受影响步骤以及该窗口后的总剩余时间；交通状态、任务机制或五开共享结论变化时必须触发重算。
- Route Atlas的步骤数据应保存中心估时和合理区间；前端至少能让玩家看到当前步骤预计时间和当前地图总预计时间。
- Route Atlas结构固定保存：地图级`hearthChain`（按实际改绑顺序）、地图级`timing.centerMinutes/rangeMinutes/actualRuns`，以及每个`stepGroup.timing.centerMinutes/rangeMinutes/includeInTotal`。条件兜底步骤可以`includeInTotal=false`，但仍必须有自己的预计时间。
- `actualRuns`只能收可靠实跑窗口，并必须带清晰scope/label；整图未完整按当前版本跑过时，不得用局部记录冒充整图实测。无可靠实测就保存空数组，前端不显示任何“实测：暂无”占位。
- 用户现场如果只能记住大致开始/结束时间，也先记录为`approximate`精度的实测窗口；宁可保留“约X分钟”的真实粗粒度数据，也不要因为缺秒级时间戳而丢失整段效率样本。后续有Journey或更精确记录时再收窄，不把粗略值伪装成精确值。
- 长期总目标基准独立于分地图预测，并统一保存在`data/observations/route-timing-runs.json`的`long_term_targets`中；永久规则正文不硬编码某一阶段的具体目标数字或路线特征猜测。外部老手基准只用于衡量整体优化空间，不直接覆盖当前各地图的component-wall-clock预测；任何关于老手任务选择方式的推测都必须在观测数据里明确标成推测，不能倒推成全局硬规则。
- 右上角和HUD的固定展示职责见`route-atlas-ui-and-assets.md`：地图级直接显示炉石链+预计总时间+可靠实测，不加“炉石与时间”之类小标题；HUD第二行显示当前逻辑步骤预计时间。时间字段生成后不得继续让旧坐标提示占据该位置。

## 2. 固定分解模型

沿用项目既有墙钟模型：

`T_total = T_move + T_objective_service + T_accept_turnin + T_wait + T_special`

其中：

- `T_move`：骑马/步行/游泳、系统飞行、炉石、船/飞艇、任务脚本移动和必要绕路；系统飞行必须用**任务发生时已经开启**的飞行网络。
- `T_objective_service`：规定击杀、掉落、固定物、任务物使用、探索、对话事件等真正完成目标的时间。
- `T_accept_turnin`：五号接取/交付与同Hub切号操作；同一NPC/同一Hub批量任务共享基础操作成本，不能给每条任务重复收完整Hub成本。
- `T_wait`：命名怪刷新、固定物刷新、事件波次和掉落方差产生的必要等待；没有证据时给区间，不伪造精确值。
- `T_special`：护送、防守、载具、脚本飞行、洞穴/楼层、逐号定位、断跟随重组等不可归入普通杀怪/跑路的固定成本。

不得用“任务数×平均分钟”“本次XP/h×剩余经验”或“已跑步骤比例×剩余步骤数”代替以上分解。

### 2.1 玩家动作与估时任务必须做语义对账

- Route Atlas生成估时时，凡玩家动作明确表达“执行/完成某任务”的任务名，都必须进入对应步骤的`objectiveTasks`；尤其`做《任务》`这类显式语句不得因为解析顺序、标题剥离或token匹配而漏掉`T_objective_service`。
- 发布前必须对当前正式地图做一次“玩家动作中的显式执行任务 ↔ 估时器识别任务”差集检查；显式`做《...》`存在任何漏识别，直接判估时门禁失败。
- `沿路/自然经过/顺手`取得的背景任务不能机械按完整独立任务服务时间重复收费；若与前台任务共享同一批怪、拾取、移动或等待，只计真实新增边际成本。这样既防止漏算，也防止把同一次战斗/移动重复计两遍。
- 修改动作解析规则后必须重算所有使用同一估时器的正式地图，并让回归测试覆盖至少当前所有正式Route Atlas地图；旧结果不得继续作为当前真值。

## 3. 当前已校准参数

这些是模型参数，不是游戏常数；新实测可覆盖：

- 普通任务怪：当前圣骑五开基线`15秒/只`，除非该怪/精英/载具已有单独实测。
- 个人尸体拾取：沿用旧模型`9秒/具`作为五开操作基线，再叠加需要的击杀数与掉率方差。
- 固定物逐角色交互：`7秒/角色/次`。
- 接交Hub：沿用旧模型`0.65分钟基础 + 0.16分钟×本次任务条数`；多任务同NPC/同Hub应合并计费。
- 普通命名怪若无可靠刷新信息：默认额外等待中心值`2分钟`，但高密度常驻/现场确认无需等则删除该等待。
- 普通脚本/事件在无更具体资料时可先用`3分钟`占位，发布前尽量换成任务实际机制。
- 地面纯骑乘：100%坐骑基础14 yd/s；当前骑乘光环+20%后按`16.8 yd/s`计算。只修正纯移动时间，不乘到战斗、拾取、护送、脚本或交互上。
- 地图坐标距离必须使用该地图真实宽高换算，并加入实际道路/地形系数；洞穴、水下、悬崖不能按平面直线直接计时。

## 4. 五开成本必须按真实机制计算

- 共享击杀：只计主控完成目标所需战斗，不乘五。
- 个人掉落：按五号最终全部完成的最慢角色建模；用掉率/刷新密度估计共享击杀次数，再加入逐尸拾取操作。不得机械把所需数量乘五，也不得假定一次掉落自动共享。
- 固定物个人拾取/点击：按五号总操作数和刷新周期计算。
- 已实测共享的任务物/事件：按主控一次操作计算；已实测个人的任务明确按五号分别完成。
- 护送/载具/脚本若五号是否共享未知，中心估时必须标记不确定来源，并给共享/个人两端区间；实测后立刻收窄。

## 5. 预测与实跑必须成对保存

统一记录到`data/observations/route-timing-runs.json`：

- 路线/地图与步骤范围；
- 预测中心值、上下界及模型版本；
- 实际开始/结束墙钟；
- 实际时间；
- 已知失误、学习、死亡、断跟随、等待、竞争等异常；
- 如果能定位，保存每个大任务块实际耗时。

比较同一路线批次时至少输出：

`时间差 = 实际墙钟 - 该版本clean baseline`

并把差值继续拆成：路线本身可优化、执行熟练度/失误、随机刷新/掉率、服务器竞争。不能把一次带失误的实跑时间直接拿来线性外推后续不同任务块。

## 6. 时间不是最终目标，必须进入经济比较

所有时间预算最终都服务于项目唯一目标：**这一种任务打金方式自身的长期可重复净金币 / 玩家真实墙钟**。因此“更快”只代表降低了分母，不自动代表方案更优；“多做任务拿更多金币”只代表增加了分子，也不自动代表方案更优。

当前任务打金周期的统计边界固定为：**一整组号从开始执行任务路线，到该任务路线定义的结束点为止**。周期可以跨越80级：练级阶段任务奖励和装备变现、80级后继续完成一次性任务产生的XP折金，全部归入同一个任务打金周期。团本、日常和其它独立打金方式的时间/金币不混入本周期。

每次比较两个正式候选路线/任务包，至少同时给出：

- 当前阶段新增/损失的直接金币、装备/物品变现；
- 任务经验改变导致后续任务可接等级、80级时点和XP折金时点怎样变化；
- 若任务计划80级后再清，记录80级XP折金及重新回图/重新定位成本；
- 任务链、交通和后续一次性任务可达性的变化；
- clean墙钟及方差来源；
- 脑力/操作复杂度对实际复用的影响；
- 最终对**整组任务周期总金币、总墙钟、金币/小时**的影响。

不得使用团本、日常或其它打金方式的G/小时做“节省这5分钟就能去别处赚更多”的机会成本推导。只有用户明确要求比较三种打金方式如何分配总游戏时间时，才在更上层做跨方式组合分析；那也不能反向污染各方式自身的内部统计口径。

老手“68→80最快约14小时”只作为升级速度参照：它能证明任务路线在纯墙钟维度还有多少优化空间，但不能单独决定任务删留。

## 7. 副本边界

当前五开户外升级主线**不打副本/团队副本**。所有`is_dungeon=true`或raid任务默认从Route Atlas升级主线排除，保留在任务知识层即可；只有用户明确要求开启副本专项路线时才单独建模，且不得悄悄混回户外清图总时间。
