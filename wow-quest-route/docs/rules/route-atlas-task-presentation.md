# Route Atlas 任务呈现规则

用途：这是 Route Atlas 中 **Task Card → 玩家任务标签与备注** 的唯一规则 owner。它只决定“任务卡里的哪些信息以什么最小形式显示”，不决定路线顺序、动作、页面容器或任务事实。

路线动作见 `route-atlas-route-display.md`；任务机制核验见 `execution-and-mechanics.md`；页面工程见 `route-atlas-ui-and-assets.md`。

## 1. 三层必须独立

同一任务允许同时存在三种表达，它们职责不同，不得互相替代：

1. **事实/攻略层**：Task Card 的基础字段 / guide / evidence，完整保存任务真实知识；任务目标、机制、位置等不再拆成多套结构。
2. **五开状态/标签层**：Task Card 的粗粒度 fivebox 状态，决定玩家看到的状态标签。
3. **人工推荐备注层**：Task Card 的 presentation note override，保存当前正式页面备注或后续用户明确确认后的备注结果；可以明确为空。

标签是标签，备注是备注。程序不得因为“共享”就自动生成一段共享备注，也不得通过备注文本反推共享状态。

以《阻断援军》为例：

- 事实层可完整保存“符文石个人、炸门共享、五号符文石完成后再走、主控炸门即可”；
- 标签层可为“共享”；
- 用户已明确认为额外备注无价值，因此人工推荐备注层应明确为空。

## 2. 五开状态标签

玩家前端当前基础状态只从 Task Card 的结构化 fivebox 状态读取：

- `共享`
- `不共享`
- `依次拾取`
- `特殊`
- `待实测`
- `无需标签`（机器状态为`not_applicable`，玩家端不显示任何标签）

复杂/条件型任务统一用`特殊`标签；具体怎么特殊只保存在Task Card `guide`中，标签本身不继续细分。

规则：

- 有可靠结果就写对应状态；
- 没有可靠结果就写 `待实测`；
- mixed/条件型结果写`特殊`，细节读取guide；
- `not_applicable`表示任务本身没有需要玩家关注的五开机制，前端不显示标签；
- Builder/Publisher 不得通过“已实测”“确认……”等自然语言前缀判断状态；
- 标签直接附着在每一次玩家可见的任务名之前，例如 `【共享】《任务名》`、`【待实测】《任务名》`；底层状态仍为`fivebox.status=pending`，只缩短玩家可见文案；不得为了显示标签在备注区额外复制一条同名任务；
- 同一任务在接/做/交多个动作中重复出现时，每个可见任务名都可以带同一状态标签；备注仍按“同一步同一任务至多一条”去重。

## 3. 人工推荐备注层

备注只回答：

> 当前路线动作 + 正常插件仍不足以让我正确、快速执行时，还缺哪一条最短必要信息？

用户明确纠正后的结果直接保存为 Task Card 的 presentation note override。它可以：

- 保存一句固定备注；
- 明确保存空字符串，表示“已经人工判断无需备注”；
- 带 scope，只有确实存在 Profile / 版本差异时才缩小范围。

明确为空与“尚未迁移/尚未判断”必须能区分。

### 旧备注迁移与现役投影清洗

旧正式页面备注已按task_id无损保存在`presentation.note_override`，原始迁移文本继续保留作证据；玩家页不再原样直出这层历史包装。Task Presentation投影必须确定性去掉：

- 当前任务自己的重复完整任务名（玩家容器已经显示`《任务名》：`）；
- `【需要单独修正优化】`等迁移标记；
- `首组/第二组实跑确认、已实测、已验证、经审计`等形成过程前缀；
- 已由fivebox标签完整表达、且没有额外执行信息的纯“共享/不共享/依次拾取”句子。

清洗只改变玩家Presentation，不反写Task Card事实/evidence，也不得从自由文本推导fivebox或其它机器事实。清洗后为空即不显示备注。

## 4. 备注允许内容

典型允许内容：

- 任务触发物从哪里/如何获得，若不写会导致玩家不知道为什么任务会出现；
- 必须对特定目标使用任务物；
- 召唤、载具、特殊事件的关键触发方式；
- 洞穴入口、楼层、水下/悬崖等插件不足以说明的空间事实；
- 会导致明显失败/返工的关键 Boss 机制；
- 必须等待或明确不补刷等真正影响执行的任务机制。

例如 `when.kind=has_item` 的机会任务在路线动作中仍只显示 `接《任务》`；`has_item` 继续作为Route Replay的机器执行条件存在，不能删掉。玩家需要知道的“触发物由什么怪/哪里掉落、自然掉落即可、不专门补刷”等写入该任务的 Task Card 事实/人工推荐备注，而不是把“若持有……”条件句塞进路线动作文本。

## 5. 备注禁止内容

- `已实测 / 已验证 / 经审计`等证据过程；
- 共享标签的同义长句；
- 当前步骤已经表达的先后顺序；
- 普通任务目标数量/普通怪位置，若插件已足够；
- 路线设计理由；
- 历史为什么这样改；
- 通过自由文本再次定义任务机制。

同一任务同一步最多一条有效备注。备注显示位置固定为任务的`objective/做`步骤；普通NPC接取与交付步骤不显示任务备注。唯一例外是任务物品触发接取（`accept + when.kind=has_item`）：因为玩家需要在接取当下知道触发物来源/处理方式，该任务允许在接取步骤显示备注。

## 6. 事实完整不等于前端完整搬运

Task Card 可以保存非常详细的 guide。Presentation 不摘要整份 guide，也不把“内部知道多少”展示给玩家。

固定判断：

> 删除这条玩家备注后，仅凭当前路线动作和正常插件，是否仍同样快、同样不容易做错？

- 是：备注应为空；
- 否：只保留改变操作的最短信息。

## 7. 用户纠正优先

用户对实际 Questie / 现场界面“这条有用/没用”的明确反馈，是备注层最高优先级决策。

- 任务特例 → 写 Task Card presentation note override；
- 整类规律 → 修改本规则，不给几十张卡重复写同一句；
- 用户固定备注只控制展示，不修改 facts/fivebox 真值。

## 8. 与 Route Display 合并

最终前端单向生成：

1. Route Profile 提供地点/NPC/接做交/交通/步骤；
2. Task Card 提供任务名、fivebox 标签状态、事实和人工推荐备注；
3. Route Display 生成动作中文；
4. Task Presentation 附着标签与备注；
5. UI 层只负责容器和视觉。

Task Presentation 不得插入/重排路线动作；Route Display 不得自行猜任务机制或备注。

## 9. 可机械验证的不变量

- 标签只读结构化 fivebox 状态；
- `特殊`只表示需要读取guide了解混合/条件机制，不继续拆stage；
- `待实测`只由fivebox.status表达；
- `not_applicable`不生成玩家标签；
- 标签与备注独立；
- 人工推荐备注允许明确为空；
- 空备注不能被统一模板重新填成长句；
- 程序不解析 guide/备注推断机器事实；
- 玩家文本不含证据过程词，也不在备注正文重复当前任务自己的完整任务名；
- 普通任务备注只出现在`做/objective`步骤；仅`accept + when.has_item`允许在接取步骤显示备注；
- 同一任务同一步至多一条备注；
- 旧页面备注完成归属审计前不得宣称迁移完成。

人工冷读仍负责判断“这条备注实际有没有用”，自动测试不能代替。

## 10. 正式Task Presentation操作

- 单任务Presentation投影可用`python3 scripts/build_task_presentation.py <task_id>`检查；该入口只输出投影，不直接写路线。
- Task Card的fivebox或presentation变化后，实际玩家产物刷新由受影响Profile的Route Display操作完成。
- Presentation脚本不得修改Task Card事实、Profile动作或通过自由文本推导机器状态。
