# Route Atlas 前端、逻辑步骤与地图资源规则

用途：修改 Route Atlas HTML、步骤/HUD/动画、地图底图、中文标签和离线复制结构时读取。路线状态和插入算法见 `route-atlas-optimization.md`；步骤/整图时间字段的生成、实跑scope和长期基准规则见 `timing-and-benchmarking.md`。

## 1. 唯一通用工作台

- Route Atlas正式运行时永远只保留 `data/routes/route-atlas-workbench.html` 一份HTML。
- 所有地图通过顶部地图选择器切换，不创建 `<zone>-preview.html`、`<zone>-current.html`、`<zone>-authoritative.html` 等分支。
- 版本历史只保存Markdown审计/NEAT；结构化层只保存当前有效路线。
- 当前地图路线统一在 `data/route-atlas/workbench-routes.json`，由 `scripts/build_route_atlas_workbench.py` 嵌入HTML。
- 目标游戏电脑运行时只依赖 `route-atlas-workbench.html + maps/`，不读取JSON、Python、manifest或网络资源。
- “预览”也使用正式工作台，不另做简化模板。是否冻结只体现在状态文字和审计文档。

## 2. 页面布局与视窗

已验收布局固定为：

`标题/状态 → 控制条 → 全宽地图 + 左上HUD → 图例 → 步骤列表 → 页脚`

- 地图默认全图。
- 切步骤、上一/下一段、播放、切地图不得自动放大。
- 只有用户主动勾选“跟随当前段”才允许自动裁剪；取消后回全图。
- 地图左上HUD固定宽度、内容高度自适应且可收起。
- HUD统一承载：当前逻辑步骤编号（`步骤 X/总数`）、**本段预计时间及合理区间**、当前逻辑步骤内**全部停靠点的完整动作**、再下一站，以及本停靠点内所有真正有执行帮助的任务备注；本步无有效备注时不显示备注区。步骤编号必须直接显示在HUD标题中，避免玩家收起下方总步骤列表后只能靠内容回忆当前做到哪一步。多停靠点步骤不得只显示`stepGroup summary`或最后一个点位动作；接取、交付、任务链后续、楼层/建筑位置等只要存在于本段动作，就必须直接出现在HUD当前动作区。HUD内容超过地图卡可视高度时，HUD正文自身使用纵向滚动，不允许继续向下撑出地图区域后被外层裁掉。
- HUD标题下的第二行位置固定为`本段预计：约X（下界—上界）`；条件兜底步骤追加`条件触发时`。这里**禁止再显示**“本段 起点→终点 (x,y)”或单独坐标提示，因为地图本身已经承担位置指向，这一行专门服务执行时间预期。
- 不重复展示同一当前步骤信息；当前动作、下一站和备注集中到HUD，普通几何坐标不再占用HUD固定信息位。
- 右上角状态卡**不显示任何小标题**，直接从第一行开始显示：`炉石：地点-地点-地点`（按真实改绑顺序；未换绑只写一个地点）、第二行`预计总时间：中心值（合理区间）`，以及存在可靠记录时的后续`实测范围：实际墙钟`。没有可靠实测就**完全不显示实测行**，不得用跨暂停/跨版本Journey跨度凑数。
- 禁止重新加入“炉石与时间”“当前状态”等小标题；右上角也不再用于“本图执行规则”“页面标记说明”“机会任务原则”等泛化提示。若这些内容仍对执行有用，应放到对应任务备注/图例/步骤，否则删除。这样四张图和后续新图始终保持同一视觉职责。
- 当前执行页默认不展示角色经验对比；标题/状态区只保留上述炉石与时间状态，除非用户明确要求扩展。

## 3. 几何停靠点不等于玩家步骤

数据层可以保存多个几何点以保持真实线路，但玩家步骤必须按自然任务块合并。所有进入正式Route Atlas的地图都必须显式维护`stepGroups`；禁止依赖“没有stepGroups时自动把每个几何点当一步”的旧回退逻辑，否则上一段/下一段会退化成点位导航而不是任务块导航。

同一个连续任务块、局部扫图、NPC批量交接或无需决策的连贯路径，应合成一个逻辑步骤。若一个步骤同时包含多轮Hub交接与多轮外出执行，或展开后出现六七个以上停靠点/动作行，应优先在Hub交接完成或新一轮外出开始处拆段；批量交接本身可以独立成一步，避免把交接、执行、再交接压成一整屏。

以下都按逻辑步骤工作：

- 步骤列表；下方“全部路线”固定只显示步骤编号、标题与`有备注 / 五开待实测`等标签，作为导航目录使用，不重复展示动作或备注明细；
- HUD；
- 上一段/下一段；
- “播放当前段”；
- 当前步骤高亮。

动画在一个逻辑步骤内依次走完该组几何线。禁止为了给每条线编号而把自然行动拆碎。

## 4. 停靠点动作语义

- 当前地图点表示“本段最终要到达的目标点”。
- HUD动作描述“到这个点后做什么”。
- 连线只回答“从上一个停靠点怎样到这里”。
- 原地接取、交付、脚本、对话等没有开放世界位移的动作仍归当前停靠点。

不能把起点动作错误挂在前往下一个目标的长连线上。

## 5. 备注与玩家可见文本

Route Atlas的第一产品目标是**让玩家边玩边看就能直接执行**。因此所有可见字段必须按职责写，不能把内部分析混进攻略。

- `point title`：只表示玩家识别得到的地点/NPC/目标，不写“人工锚点”“异常修正”“候选节点”等内部词。
- `point action / HUD动作`：只写到达后实际做什么，必须出现明确玩家动作；不能被“为什么走这里/为什么保留这条任务/为什么不折返/数据哪里缺了”等设计解释取代。同一NPC/地点交接用`→`表达动作顺序；同一动作连续处理多个任务时允许紧凑写成`交《A》、《B》`或`接《C》、《D》`，动作词覆盖这一组连续任务；一旦动作从交变接、从接变做，必须重新写动作词。禁止`交并接《B》`、`批量交`等含糊缩写。
- `point note / 任务备注`：只写已经足够可靠、能直接帮助完成当前任务的机制、操作、条件、等待/不等待和地形；已经实测确认且会改变操作的五开结论也可进入这里。
- `point fivebox_check / 五开待实测`：只承载当前必须由用户五开实跑确认的机制问题，和普通备注完全分开。步骤列表必须有独立醒目标记，HUD必须用独立分隔区显示，并明确写出要观察的角色/计数/拾取/点击/载具或事件结果；禁止只显示“未知”。确认后该标记应被删除并按结果更新 observations/普通备注。
- `stepGroup title / summary`：只概括这一组玩家实际要执行的任务块与动作；不得写“保证任务链不断”“按前置逐轮打开”“避免后期折返”“Questie缺失所以……”等设计/审计结论。
- “为什么这样排、为什么合并、为什么裁掉”、Questie/数据库缺陷、人工锚点依据、候选覆盖、可达性审计、测试结果和构建理由一律属于路线设计审计，不进入玩家动作、步骤摘要或任务备注。
- 若某条数据修正确实影响玩家执行，例如“NPC实际在二楼而Questie点在一楼”，玩家可见文本只写**玩家需要知道的正确做法**（如“上二楼找NPC”）；“Questie数据错了/我们人工修正了”仍留内部审计。
- 所有执行路线任务都必须完成逐任务人类可执行性审计；有特殊做法才产生备注。
- 有有效备注的逻辑步骤标题显示“有备注”，HUD显示具体 `备注：...`；无备注不显示空区域。
- 玩家可见标题/HUD/步骤/备注/图例/页脚禁止出现内部 `A1234 / C1234 / T1234`、裸任务ID或“用编号代替任务名”。
- 发布前扫描全部用户可见路线字符串；发现内部动作记号或裸ID即验收失败。
- 发布前还必须单独做一次“攻略第一目标复审”：逐条阅读 `point title/action/note` 与 `stepGroup title/summary`。任何一句不能直接帮助玩家导航、执行、避免失败或判断离开条件的内容，都必须删除或迁移到审计文档；这一项与JSON/JS/测试等技术门禁分开判定。

### 5.1 新路线固定使用第45步语义HUD标准

龙骨荒野第45步确认的视觉不是历史样板，而是**所有新Route Atlas路线的正式发布标准**。旧地图可以在专项优化中逐步迁移；任何新地图/新路线从第一版正式玩家稿开始就必须使用，不允许先发布旧纯文本HUD再“以后统一美化”。旧地图重构时必须以**重构当下的最终总规则**为准，而不是只复刻第45步当时的历史状态；此后新增或修正的地点/NPC、五开标记、备注密度、颜色语义等细节，都必须在逐段重构时一并落实。

固定语义如下：

- 地点：浅蓝色普通字，不加粗、不加下划线/边框/底色；地点行只承担导航/空间切换，不得把NPC名塞进地点标题后又在动作行重复一次；
- NPC：偏白、稍粗普通字，与地点明确区分。进入一个新Hub、洞穴、建筑、楼层或明显子区域时，可先单独显示一次地点行；同一空间内连续与NPC交互时，动作行直接以NPC名开头，不重复`地点·NPC`。只有空间发生变化、入口/楼层会影响寻找时才再次显示地点；
- 若纯执行目标本身是地点/固定物，则写成`地点 ↳ 做 任务`；若纯执行目标本身是NPC，则写成`NPC ↳ 做 任务`，必须使用NPC语义样式，不能借“点位标题”把NPC错误渲染成地点；
- `交 / 接 / 做`：普通正文样式，不做胶囊或标签；
- 流程任务名：去掉`《》`，保留下划线；交=绿色、接=黄色、做=蓝色；同一动作多个任务用`、`；
- 从交接进入执行任务时另起一行，使用`↳ 做`形成层级；同一NPC连续`交 → 接 → ↳做`时保持同一NPC语境，不重复姓名；
- 备注任务名：继续保留`《任务名》`，按任务独立分块；
- 五开机制关键词统一：已确认可同步推进时必须以`共享：`开头，只给`共享：`关键词使用浅绿色；已确认不能同步推进时必须以`不共享：`开头，只给`不共享：`关键词使用暖橙色；尚未确认继续使用黄色`五开待实测：`。不要再混用“进度五号共享”“五号分别做”“个人完成”等无统一前缀的写法；前缀后只保留真正影响操作的最短说明，避免重复写“共享：……共享”。
- `顶层 / 一层 / 地下 / 不要杀死 / 不要跳下 / 先停手`及同类真正会改变操作的危险/短时限词：普通红色文字，不加粗、不做胶囊/边框/大色块；
- 地点/NPC不增加点击定位、脉冲、闪烁等交互；该方案已明确放弃；
- 无行动价值的图例、常驻解释区保持为空。

数据发布契约固定为`uiStandard: "semantic-hud-v45"`。新路线的每个`stepGroup`必须有非空`actionHtml`；有真实备注时提供`noteHtml`，无备注时允许为空。`scripts/build_route_atlas_workbench.py`必须把旧路线白名单之外的任何新route key当成v45路线：缺`uiStandard`、缺`actionHtml`、流程任务名仍带`《》`、或语义HUD遗漏plaintext动作中的任务名时，直接拒绝构建HTML，禁止静默回退旧纯文本HUD。

## 6. 当前稳定控制行为

- 播放控制至少区分“当前段”和“剩余路线”。
- 点击上一段/下一段后自动播放一次所选当前段。
- 当前步骤可在步骤列表直接点击跳转。
- 多任务步骤可按需要切换任务知识卡，但执行备注优先汇总到HUD，不重复占用知识卡。
- 玩家可见任务知识卡只展示当前执行有帮助的稳定信息，例如任务特殊机制、地形、任务物、掉落/刷新、失败风险和必要时间提示；`typed relations`、Target Cluster / Spatial Instance、numeric features、路线编排理由等内部知识仍保留在后台事实/审计层，不因前端隐藏而删除，也不得为了“可审计”直接暴露给玩家。
- Questie已经直接显示的普通等级、经验、基础坐标和基础目标默认不占前端卡片版面，但后台事实层必须继续保留，不能因为前端隐藏而删字段。
- `MANUAL_SPATIAL_REVIEW`任务必须展示可用目标点/区域边界、宏观进入方向和“局部刷法待现场决定”，不得为了动画好看伪造局部最优折线。

## 7. 地图底图原则

- 清晰度优先，但必须保持现有0–100坐标几何一致。
- 替换底图前先做边界、比例和锚点配准；未通过不能切换。
- 不为了内嵌中文地名退回低分辨率图。
- 高清英文底图没有中文时，用独立HTML/SVG小标签叠加，不把中文烘焙进底图，也不把标签当坐标真值。
- 中文标签低干扰、可开关；视窗裁剪时同步当前viewBox。
- 无可靠zhCN区域数据时允许只用高清英文底图，禁止机器直译冒充客户端真值。

可靠标签生成：

- `data/routes/maps/labels-zhcn.json`
- `scripts/build_route_map_labels.py`
- `lib/route_map_assets.py`

## 8. 地图资源池与离线复制契约

- HTML固定在 `data/routes/`。
- 地图统一在同级 `data/routes/maps/`。
- HTML只允许通过 `maps/<实际文件名>` 引用底图。
- 浏览器运行时不得依赖 `../route-atlas/`、Python、manifest、网络请求或项目其它目录。
- 中文标签等运行时数据必须构建时内嵌进HTML。
- 玩家复制到游戏电脑时只需复制HTML和整个同级`maps/`目录。

地图资源池应提前缓存任务宇宙覆盖地图，而不是每做一张攻略临时下载。

文件稳定命名：`<zone_id>-<slug>.<ext>`。

`manifest.json`记录来源、缺失、回退和HD元数据；生成期默认优先经过验收的 `hd_file`，只有manifest明确回退时才用普通底图。

相关生成器：

- `scripts/download_route_map_assets.py`
- `scripts/build_hd_route_maps.py`
- `lib/route_map_assets.py`

## 9. 冻结视觉参数

除非用户明确要求修改视觉系统：

- 普通路线线宽 `1.25`
- 当前段线宽 `3.0`
- 炉石普通 `1.8`
- 当前炉石 `3.4`
- 箭头 marker `5×5`
- `markerUnits="strokeWidth"`
- `vector-effect="non-scaling-stroke"`

不得因新地图无理由漂移。

## 10. 发布门禁

修改工作台后至少验证：

1. 路线JSON可解析；
2. stepGroups覆盖有效几何范围且无重复/遗漏；
3. HTML重新构建成功；
4. JS语法检查通过；
5. 用户可见文本无内部ID泄漏；
6. 当前地图底图路径使用 `maps/` 相对路径；
7. 默认全图、不自动zoom；
8. “有备注”只在有效执行备注存在时出现；
9. 被废弃的单地图HTML没有重新产生；
10. 相关自动测试通过；
11. 每张图都有非空`hearthChain`、地图级`timing`，每个`stepGroup`都有`timing.centerMinutes + rangeMinutes`；右上角不得存在`badgeTitle`/可见小标题，必须直接显示炉石与总时间；HUD第二行必须实际渲染`本段预计`而不是坐标；
12. 无可靠实测的地图不得出现“实测”占位文本；有实测时必须标清实测覆盖范围，不能让局部实测看起来像整图总耗时；
13. **攻略第一目标复审单独PASS**：人工逐条阅读所有玩家可见 `point title/action/note` 与 `stepGroup title/summary`，确认没有内部审计/设计说明占据玩家攻略位置；这一项不能由自动测试通过代替；
14. **所有新路线必须声明`uiStandard: "semantic-hud-v45"`，且每个`stepGroup.actionHtml`非空**；构建器不得允许新route key回退到旧纯文本HUD；
15. v45样式语义必须符合5.1：地点浅蓝且只承担空间导航、NPC偏白稍粗且不得与地点标题重复、交绿/接黄/做蓝任务名去`《》`并下划线、`↳ 做`保留层级、备注按任务分块、`共享：`浅绿/`不共享：`暖橙/`五开待实测：`黄色且仅关键词着色、危险/楼层普通红字；
16. 新路线最终HTML必须实际出现其semantic HUD内容，并通过“plaintext动作任务名未在actionHtml丢失”的构建校验。
