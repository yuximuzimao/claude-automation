# Route Atlas 数据、状态与路线优化规则

用途：修改 `workbench-routes.json`、做当前路线裁剪、任务簇插入、路线状态机、炉石重算、精确优化器或全图几何审计时读取。任何路线顺序、交通、步骤或任务块变化都必须同时按 `timing-and-benchmarking.md` 重算受影响时间；HTML视觉和地图资源见 `route-atlas-ui-and-assets.md`。

## 1. 数据分层

长期分层固定为：

`Questie Raw（不可改写） → Questie Effective/派生事实 → 单任务知识节点 + typed relations + numeric features → 路线版本/路线节点 → HTML执行工作台`

- Questie Raw保存插件原始事实，实跑观察不得覆盖。
- 单任务知识节点保存与某条具体路线无关的可复用知识。
- **任务卡/单任务知识节点只能保存基础事实和属性**：奖励、目标类型、任务链、预计服务时间、五开机制、地形/操作、来源与置信度等；不得写“跳过/保留/剔除/P级”等面向某一目标的行为判断。相同任务在不同目标（升级、金币、声望、成就）下可能产生不同决策，基础数据必须保持中立。
- 路线节点保存这版路线的合并、位置、边际移动/服务成本等版本特定信息。
- P1—P4、A/B/C、候选/采用/否决等属于**优化决策层**，必须与任务卡基础数据分文件/分锁保存；决策层可以锁定，但不得回写污染任务事实。
- **Active retention override 是删除硬门禁。** 某任务/任务包一旦进入对应地图的`*-retention-overrides.json`，任何后续P级批量剔除、路线裁剪或自动优化都必须先读取该override；除非用户明确要求重审/删除该保护项，否则不得把受保护任务放入formal removal集合。临时保留默认可保留原P标签；但如果用户明确把某任务定义为“结构上不属于可剔除候选”，override可设置`priority_behavior=exclude_from_priority_candidates`，此时该任务继续留在当前可用任务池和正式路线，但退出P1—P4候选排名。发布审计必须检查“formal removal ∩ protected quest IDs = ∅”。
- RouteState必须显式维护动态交通状态，至少包括`opened_flight_points`、当前炉石绑定点/冷却、可用脚本交通与已验证直飞关系。每执行一个接取/交付/开点/转场动作后都要向后重放该状态；飞行点一旦新开启，后续尚未执行节点不能继续使用开点前的交通假设。
- HTML是执行前端，不是事实数据库。

任务知识可关联：typed facts/relations、numeric features、稳定标签、Target Cluster、Spatial Instance、五开机制、地形、特殊操作、掉落/等待风险、可交易/可购买三态、source/confidence和实跑纠错。

对任务/声望所需材料，一旦实跑确认“可交易”，就自动进入“拍卖行预购候选”层：后续完整批次规划时优先检查是否值得一次性按五号总需求备货，以替代现场刷取/拾取；但“可交易”不等于“当前服务器拍卖行稳定有货且价格合理”，未实测供给和价格前不得把预购写成硬前提。已实测可购买时，再把任务卡/准备清单明确标成可预购。

稳定标签家族至少包括 `scope:*`、`objective:*`、`chain:*`、`trip:*`、`terrain:*`、`route:*`；机器关系至少支持 `precedes`、`same_accept_npc`、`same_turnin_npc`、`same_direct/resolved_creature`、`same_direct/resolved_object`、`same_required_item`、`spatial_overlap`、`same_chain`、`same_excursion_block`。标签用于解释，不能替代底层事实和成本计算。

掉落物必须保存真实五开拾取机制；同一次掉落事件如果同尸体五号都能分别拿任务物，期望击杀次数不能机械乘五。

### 视频拆解只允许两种用途

视频中的任务选择和升级流程**不是本项目路线的上位真值**。本项目自己的任务属性、剔除决策和路线优化结果优先；已被本项目指定排除的任务，在比较视频顺序时先从视频序列中删除，再比较剩余任务。

视频拆解只允许用于：

1. **路线顺序对照**：比较双方共同保留任务的相对顺序，判断我们是否一致或更优。例如本项目保留顺序为`任务4→任务1→任务2`，视频为`任务4→任务3→任务1→任务2`且任务3已被本项目排除，则过滤任务3后视为同一顺序；若视频为`任务2→任务3→任务4→任务1`，过滤任务3后得到`任务2→任务4→任务1`，再与我们的`任务4→任务1→任务2`比较真实路线成本。
2. **遗漏审计**：检查视频是否出现了我们没有纳入、且又不属于指定剔除范围的任务；发现后回到Questie/任务事实层核对是否确实遗漏。

只要当前地图存在已经完成拆解的视频证据，**正式路线冻结前必须执行一次整图视频反向审查**：先过滤阵营/副本/互斥/已明确排除项，再对共同保留任务比较相对顺序和邻接关系，并对视频独有任务做遗漏分类。视频参考库被基础层读取、或插入过程中零散看过视频，都不能替代这项最终整图门禁。若视频系列只覆盖到某个等级/阶段，则在其实际覆盖范围内尽量用完现有证据，不等待并不存在的后续素材。

除此之外不得用视频强迫本项目保留某任务、恢复已剔除任务、复制视频路线，或因为视频先后顺序不同就直接覆盖我们的优化结果。

## 2. 从零主路线和当前执行路线

Route Atlas永久区分：

- 从零复用主路线：下一批完整地图路线。
- 当前执行路线：按当前角色状态裁剪。

当前任务完成只裁当前执行动作；任务知识、从零路线和历史不删除。裁剪后必须重算受影响窗口的前置、Hub、条件分支、炉石和路线几何。

## 3. Target Cluster / Spatial Instance / Background Layer

- 完全相同真实目标实体优先形成Target Cluster。
- **Target Cluster在正式逐簇插入前必须先形成整图初始空间序列**：结合地图入口/预期出口、真实地形、道路/桥梁/洞穴/楼层、任务中心与已知交通网络，把任务簇按“下一簇真实移动成本”排成连续骨架。这里的簇序列就是整图路线的初始骨架，不再额外维护一个与任务簇分离的“宏观大块路线层”。
- 初始簇序列允许存在暂时较长的连接边；后续任务/后续链解锁后，若新任务簇位于两簇之间或能把长边切成更短的生产性路径，应自然插入并重算受影响窗口。不能为了保持原大块边界而拒绝这种插入。
- **后发现任务链只能回插，禁止尾部补做。** 无论任务链是在候选召回、依赖审计、视频反查还是覆盖差集中多晚才被发现，都必须回到该链第一个真实可接/解锁节点，按后续每一环的自然Hub、地理落点和交通状态拆段插入现有路线；插入后重放受影响后缀并整体顺延步骤编号。只有任务依赖本身就要求该链在地图末段才出现，或成本比较证明末段就是最优合法位置时，才允许位于末尾。不得因为“路线已经写到后面了”把整条链追加成补漏尾巴。
- 跨地图桥接任务同样属于该链的硬闭包。地图foundation/覆盖审计不能只检查本地图assigned任务；若本地图任务的唯一前置/直接后续跨到其它地图，该桥接任务必须进入当前链闭包或被显式解释，禁止出现“本地图ID已100%覆盖但真实链少一环”的假PASS。
- Questie刷新点/平均坐标不等于一次真实可服务区域。
- 道路、桥、洞穴、楼层和实跑可达性决定Spatial Instance。
- 广域累计、沿途杀怪、背景拾取和低掉率自然触发可进入Background Layer。
- Background Layer不能反过来拖着主体路线绕路；预计自然覆盖不足时必须转成显式服务段。

## 4. 路线构建固定采用“候选 → 硬门禁 → 成本比较”

基础流程：

1. 建Questie/人工事实层；
2. 形成Target Cluster；
3. 建Prerequisite / Availability Network；
4. 人工解析Spatial Instance；
5. 分离Background Layer；
6. 用当前真实玩家状态建立RouteState；
7. 对待插入任务/任务簇只枚举受影响窗口内候选位置；
8. 每个候选逐项通过Hard Validator；任一失败即淘汰；
9. 只有全部通过的候选才比较成本；
10. 插入后重放受影响窗口状态；
11. 已验收前缀默认冻结，只有状态连续性被破坏时向后扩大窗口；
12. 不同Target Cluster不能在逐簇插入时临时随意选顺序：先按整图入口/出口、Spatial Instance和真实移动成本形成初始簇序列；随后只有前置/Availability/新解锁任务/交通状态或真实成本证据才打开受影响窗口重排。最终所谓“整图路线优化”即这条任务簇序列在持续插入和局部重算后收敛，不另设独立的大块排序层。

## 5. Hard Validator

候选至少独立检查：

1. `player_state`：当前等级/经验/位置/任务状态和动作一致。
2. `quest_prerequisite`：preQuestGroup / preQuestSingle / parent / chain满足。
3. `availability`：等级、声望、职业、种族、技能/法术等满足。
4. `objective_ready`：C前任务已接且目标未完成；T前目标已完成。
5. `xp_deadline`：仅对未满级、经验仍影响路线收益的阶段启用；计划交付时不越完整经验截止。满级清理路线不以该门禁强行调序。
6. `transport`：按该任务时点的RouteState检查炉石绑定/冷却、`opened_flight_points`、直飞关系和其它交通动作；不仅验证当前写法“能不能走”，还必须检查是否已经存在明显更短的系统飞行/飞行＋短骑方案。新开点后旧交通边必须重新判定，不能仅因原方案仍可用就PASS。
7. `branch_state`：条件/声望/机会任务裁成真实分支。
8. `fivebox_mechanic`：服务时间与真实共享/个人机制一致。
9. `spatial_service`：至少能定位正确宏观Spatial Instance；局部几何未知可标 `MANUAL_SPATIAL_REVIEW`，不能伪造局部最优。
10. `background_capacity`：主体路线预计覆盖量足够才可背景化。
11. `no_dead_step`：不能生成已完成、条件必假或已被前面覆盖的空步骤。
12. `trigger_source_documented`：怪物掉落物触发任务必须完整说明来源怪、刷点、触发物、任务和特殊出现/等待策略。
13. `player_visible_copy`：凡本次插入会生成或修改玩家可见的point title/action/note、stepGroup title/summary，必须符合“攻略第一目标”：动作字段是真实玩家动作；备注只含执行攻略；步骤摘要只概括实际任务块。Questie缺陷、人工锚点、候选覆盖、可达性/排序理由、测试与构建解释不得进入这些字段。
14. `state_continuity`：插入后向后重放冻结后缀；后续动作一旦失效就扩大受影响窗口，而不是强接旧状态。

返回值：`PASS / FAIL(reason) / UNKNOWN(reason)`。

UNKNOWN不能统一放行：

- 可查资料的事实先查并重新判定；
- 只能由五开客户端证明的机制向用户确认；
- 宏观区域已知、局部刷法未知转 `MANUAL_SPATIAL_REVIEW`；
- 会影响路线合法性/宏观排序且无法消解的UNKNOWN不能发布为已验证路线。

FAIL只否决“任务Q放在位置P”，不永久删除任务Q。

## 6. 可行候选之间的成本顺序

只有全部Hard Validator通过后比较：

`added_wall_clock → extra_travel → service_time → forced_wait → backtrack → xp_deadline_slack → future_route_regret → hearth_opportunity → stable_id`

禁止用加权总分把硬约束失败抵消掉。

`future_route_regret`必须考虑当前地图终点到下一地图入口/首个任务中心/跨图breadcrumb的真实成本。当前已READY的交付任务应向后寻找自然Hub的零/最小增量交付点，不因为历史版本写在“最终收尾”就固定拖到最后。

## 7. 插入验收轨迹

每个最终采用的插入至少保留：

- 枚举过的候选位置；
- 被淘汰候选失败在哪个Validator；
- PASS候选主要成本；
- 最终选择理由；
- 受影响窗口是否扩大。

这样实跑出错时能判断是事实层、Validator、实现还是成本排序问题，而不是重新依赖模型回忆。

## 8. 声望不足任务库

因 `requiredMinRep` 暂时不可接的任务不删除，按 `(faction_id, required_value, stable_id)` 进入待解锁库。

RouteState声望变化时：

1. 记录 `rep_before → rep_after`；
2. 先检查是否将越过 `requiredMaxRep`；
3. 应用声望变化；
4. 只激活当前最低刚达到门槛的任务；
5. 同门槛也一个一个重新插入并重放状态；
6. 当前门槛处理完再看更高门槛；
7. 新插入若继续改声望立即递归触发。

首跑前若缺少的只是“真实跑到某节点时的累计声望”而不是任务数据库本身，则待解锁库只用于作者侧校准，不直接暴露成玩家侧分支。先按空间位置把任务固定到一个唯一节点并按可接处理；实跑证明不可接后，再将该任务移动到第一个真实可接节点并重新固化。除明确的跨地图等级切换条件外，最终路线必须收敛成单一路径。

Repeatable真值读取Questie compact quest DB字段24 `specialFlags` 的bit 1，并在RouteState中维护 `turnin_count`，避免把重复任务误记成一次性completed。默认的一次性任务路线只执行当前scope明确要求的首轮，不自动生成第二轮重复候选；只有当前目标本身要求声望、物品、日常循环或重复任务是其它可执行任务的硬前置时，才把后续轮次显式加入对应专项scope。

## 9. 当前路线裁剪恢复流程

根据最新历程裁路线：

1. 标记 completed / active / unseen / conditional；
2. 移除completed执行动作；
3. 检查active是否仍需C/T、unseen后续能否正常解锁；
4. 局部重新排序，不机械连接旧顺序；
5. 检查关键接取是否曾被已完成任务遮住；
6. 重算起点、Hub、炉石、条件分支；
7. 整张恢复完成后再做动态图全局审查；
8. 当前裁剪不覆盖从零主路线。

## 10. 炉石和交通是可重算资源

- 炉石不是固定“一图一次”，可以0次/1次/多次；不为等冷却停工。
- 计入真实施法/交互时间，不能当0秒瞬移。
- 比较的是完整未来墙钟，不只是“现在回Hub快不快”。若自然骑回能顺路完成后续生产性动作，要与“现在炉石 + 以后再出门”比较。
- 水域、游泳、绕岸、不可骑乘地形不能按陆地坐骑直线速度折算；用户实跑耗时优先覆盖平面模型。
- 旧版本炉石点没有锁定权。新增任务影响炉石附近时，只打开受影响簇+炉石+局部后缀重新比较。
- 新地图默认沿主体路线自然经过时开飞行点/绑定炉石；只有专门预跑的额外成本能被后续明确节省覆盖时才提前初始化。
- **飞行点是会扩张的动态网络，不是一次性开点记录。** 每个路线节点都要继承当时已经开启的飞行点集合；凡下一节点/下一任务块存在明显跨片区移动，必须用“当时”的网络重新比较：直飞、飞到最近点＋骑马、炉石＋后续飞行、其它系统交通、纯骑马。已经能直飞或能显著缩短陆路时，禁止因为旧稿原本写了骑马/中转就继续沿用。
- 飞行网络审计按**任务发生时点**做，不能拿整张地图最终已开齐的飞行点反推前半段，也不能只在第一次开点时检查一次。每次新增飞行点后，对尚未执行的后缀交通边统一重算；没有任务/交付价值的中间Hub不得作为惯性中转。

总成本结构：

`T_total = T_travel + T_objective_service + T_accept_turnin + T_forced_wait + T_other_known_cost`

移动速度加成只作用于真实纯移动段，不能乘到战斗、拾取、交互、护送、脚本飞行、炉石和等待。

## 11. 未满级路线的满经验截止是硬审计

当角色尚未满级、任务经验仍会改变后续可接性或任务打金周期时，每个一次性任务物化 `last_full_xp_level = quest_level + 5`。

每个T(Q)至少计算/保存：预计交付前等级经验、该等级奖励、交付后等级经验和last_full_xp_level。

- 最低号下界账证明经验够；
- 最高/最快号上界账证明不会把低级任务交进衰减。

任一计划交付出现 `predicted_level_before_turnin > last_full_xp_level`，路线必须调整。先打开最小局部窗口，优先同图Hub交付，不先全图洗牌。角色已经满级时，任务经验按对应满级收益模型计入经济账，不再为了“完整经验截止”改变路线顺序。

## 12. 精确优化器定位

PC-SP、DP/labeling、MILP、Branch-and-Cut、CP-SAT、flexible service location、shared-service/covering等模型只用于：

- 理论母模型；
- 局部插入成本估计；
- 顺序枚举；
- 异常检测；
- 与人工路线对照。

模型不能直接替代玩家路线。只有边界、地形、服务位置和状态约束足够准确且求解器证明optimal，才可称“理论全局最优”。

## 13. 动态整图审查时机

- 先完成整图任务插入或当前状态恢复；
- 再播放全图动态路线；
- 检查大范围反向折返、异常跨图、炉石落点、阶段切换和终点方向；
- 异常只回到对应局部修正。

不得每插一个任务就做一次全图动态图审查。

## 14. 大规模路线迁移/批量重构后的双重终审

当一次改动跨越多张地图、批量改写玩家文案/步骤结构或迁移底层数据模型时，逐段局部PASS不能替代整批终审。全部受影响路线按当前最终规则迁移完成后，依次执行：

1. **改前对比审查。** 把最终新版与改动前的正式执行稿/权威快照对齐，至少比较任务集合、接/做/交动作、先后顺序、条件分支、交通动作、真实几何停靠点、任务备注/五开机制、估时和地图出口。每一个“新版没有了/位置变了/动作类型变了/备注被删改”的差异都必须分类为：已验证纠错、按最终规则主动简化、路线优化后的有意重排，或疑似回归。目标不是恢复旧版，而是利用旧版检查大规模改写有没有误删、漏接、漏交、丢失攻略信息或改变原本正确的路线事实；疑似回归必须修正后重新比较。
2. **用户视角冷读审查。** 在完成改前对比并修正差异后，不依赖作者过程记忆，只从最终玩家执行入口按实际使用顺序从头复走全部受影响路线。检查仅凭地图线、步骤标题、动作和备注能否判断“去哪里、找谁、接/做/交什么、特殊任务怎么做、何时用炉石/系统鸟/传送、条件不满足怎么办”；同时检查地点/NPC/任务语义、共享状态、楼层/洞穴入口、掉落触发方式、换行密度、遮挡和作者过程词是否仍会造成误解。

两道终审固定按“改前对比 → 用户冷读”的顺序执行。自动化player-text、flight、objective、handoff和回归测试只能提供辅助证据，不能替代这两次人工终审。两道终审都PASS前，不得把该批量迁移/重构标记为完成。
