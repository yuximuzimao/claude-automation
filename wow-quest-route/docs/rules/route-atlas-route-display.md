# Route Atlas 路线展示规则

用途：这是Route Atlas中**Route Profile → 玩家路线动作/步骤/HUD结构**的唯一规则owner。它负责地点、NPC、接/做/交、交通动作、步骤标题/摘要、步骤分段和这些元素的语义样式；不负责任务机制备注内容，也不负责地图底图/控件/线宽等页面工程。

任务机制标签/备注/角标见`route-atlas-task-presentation.md`；页面/地图工程见`route-atlas-ui-and-assets.md`；路线如何排序见`route-atlas-optimization.md`。

## 1. 第一目标

路线展示只解决一件事：

**玩家看当前步骤时，不需要重新组织路线，就能立刻知道现在去哪、找谁、接/做/交什么，以及下一动作是什么。**

路线步骤本身就是路线上下文。能够通过正确步骤顺序直接表达的信息，不再额外写成备注解释。

禁止在路线动作/标题/摘要中加入：

- 为什么这样排序、为什么不折返；
- 候选覆盖、Questie缺陷、审计结论、测试结果；
- “已验证/已实测”等形成过程；
- “继续下一段/按顺序做/保证任务链不断”等没有新增行动信息的作者话语。

## 2. 地点与NPC

### 地点

地点只承担空间导航：

- 进入新Hub、洞穴、建筑、楼层、明显子区域或交通节点时显示；
- 同一空间内连续与NPC交互时不重复地点；
- 地点不是自由文本备注区。

### NPC

NPC承担“找谁交互”的语义：

- 纯NPC交互显示NPC；
- NPC不得伪装成地点；
- 同一NPC连续交接只显示一次NPC，再串联动作。

### 隐藏空间信息

洞穴入口、楼层、悬崖、水下等如果属于某个任务本身的隐藏执行事实，存Task Card并由Task Presentation决定是否显示为任务备注；如果它是整个步骤/Hub的真实空间层级，则可直接进入地点层级。

## 3. 结构化动作到中文的固定转换

Route Display只负责把Route Profile中的**原子语义**转换成玩家中文，不从旧中文句子反解析业务。

每个动作至少由以下维度决定：

- 信息主体类别：task / npc / location / transport；
- 主体稳定ID或原子名称；
- 行为类别：accept / objective / turnin / taxi / quest_transport / bind_hearth / use_hearth / open_flight_point / interact 等；
- 必要参与者：npc/location/from/to/target；
- 当前step中的动作顺序。

典型固定转换：

- task + accept + npc → `NPC → 接《任务名》`；
- task + turnin + npc → `NPC → 交《任务名》`；
- task + objective → `↳ 做《任务名》`；
- taxi + from/to → `系统飞行：起点 → 终点`；
- quest transport + npc/target + objective task → 组合为“NPC → 乘任务飞行”与对应`做《任务》`动作；
- open_flight_point + location → `开飞行点：地点`；
- bind/use hearth + location → 对应炉石动作。

同一NPC连续交/接可以在生成阶段合并成一句，但合并只是渲染优化；底层动作仍保持独立原子，不能反过来把完整中文句保存为路线真源。

路径、NPC、任务、交通是不同语义。迁移器若无法确定某段旧中文属于哪一种，不得靠位置猜测；应保留为待迁问题或显式映射。

动作区禁止塞入任务机制攻略、共享说明、Boss技巧、掉率或证据文字。它们如果确实需要玩家看到，由Task Presentation从Task Card投影。

普通步行/骑马/自主飞行只在不写就会产生路线歧义时表达为路线移动；不得为了把每一段几何移动都文字化而污染动作区。

## 4. 任务名与动作视觉语义

当前正式语义：

- `交`任务：绿色任务名；
- `接`任务：黄色任务名；
- `做`任务：蓝色任务名；
- 同一动作多个任务用`、`；
- 流程任务名保留下划线语义；玩家可见任务名至少必须完整，不能用裸ID代替任务名；
- 地点：低强调普通字；
- NPC：比地点略高强调，但不能抢过任务动作。

具体CSS色值/字体尺寸由`route-atlas-ui-and-assets.md`维护；本文件只拥有“什么语义对应什么视觉层级/颜色角色”。

## 5. 玩家步骤（stepGroups）

几何点不等于玩家步骤。Route Profile必须显式维护玩家逻辑步骤，不能依赖`point = step`回退。

分段优先按**自然执行边界**：

- 一个Hub的一轮接取/交付闭合；
- 一次自然外出任务块；
- 一个连续任务链阶段；
- 一次明确交通转场；
- 批量交接可单独成一步。

不允许为了减少按钮数量，把多轮Hub交接和多轮外出压成一个长步骤。

### 阅读负担

历史实跑表明“约10行”可作为发现明显过长步骤的**人工报警信号**，但它不是机械生成规则：

- 明显超过约10行时必须人工确认是否存在自然拆点；
- 如果任务链/事件本身必须连续，不能为了满足数字硬拆；
- 很短的相邻步骤如果属于同一自然任务块且合并更易读，可以合并；
- 不设置“10—15行必须合并”之类反向硬阈值。

最终判断是：玩家每完成一个自然行动块后再看下一步，而不是一段需要反复上下查找多次才能执行。

## 6. 步骤标题与摘要

### 标题

标题描述真实地点、任务块或明确目标。

禁止把作者整理过程当标题，例如：

- “第几次回收”；
- “补漏”；
- “重新整理”；
- “保证不断链”。

只有“第一圈/第二圈”等确实是玩家执行上的真实空间循环时才使用。

### 摘要

摘要只在动作列表本身无法快速概括本段时使用。

- 动作已经足够清楚时允许为空；
- 不承担唯一任务信息；
- 不能用“交任务/推进后续”代替具体动作；
- 不写设计理由。

## 7. 路线级状态字段展示

Route Profile/模型可以提供炉石链、当前步骤时间、地图总时间等派生数据；前端只展示当前可信值。

- HUD当前步骤位置显示本段预计时间；
- 页面状态区显示炉石链、预计总时间；
- 可靠实跑存在时才显示实跑范围，没有数据时不显示“暂无”；
- 字段位置/容器由UI规则负责，数值由Timing/Route生成，本文只规定其路线语义。

## 8. 与Task Presentation的合并顺序

最终HUD不是从旧HTML复制，而是：

1. Route Profile产生本步骤的地点/NPC/动作/步骤结构；
2. 对步骤涉及的任务按稳定ID读取Task Card；
3. Task Presentation生成共享标签、任务备注、危险词/角标；
4. 将任务级信息附着到对应任务动作，不改变Route Profile顺序；
5. UI层负责渲染。

Task Presentation不得插入新的接/做/交顺序；Route Display不得自行重写任务机制事实。

## 9. 可机械验证的不变量

至少可自动检查：

- 每个正式Route Profile有显式stepGroups；
- stepGroups连续覆盖结构化路线动作，无缺口/重叠；
- Profile中的任务动作只用稳定`task_id`关联Task Card，不以中文任务名作为主键；
- 玩家最终任务引用不出现裸ID，显示名必须由当前Task Card解析；
- 动作`kind`只使用Route Profile定义的闭合集合；
- HUD动作没有把Task Presentation文本误塞进行为原子；
- 最终生成结果没有回退到旧plaintext-only HUD。

“是否太长/是否真的省脑”仍需最终HTML人工冷读，不能只靠行数测试。
